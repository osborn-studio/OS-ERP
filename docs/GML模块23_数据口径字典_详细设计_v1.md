## 一、这个模块要解决的是什么问题

不是「做一个指标看板」。要解决的是一个**更基础、也更难堪**的问题：

> 同一个「销售额」，看板按一个状态集算、报表按另一个状态集算、AI 问答又按第三种 ——
> 三个页面的数字互相对不上，而**没有任何一处说得清到底谁对**。

这个问题的形态很特殊：它不会报错、不会崩溃，只会让人**停止相信数字**。一旦业务方发现两个页面的「库存金额」差了几十万，接下来所有讨论都会退化成「你这个数不对」，而查不下去 —— 因为没人拿得出「这个数是怎么来的」。

所以本模块的目标不是「多一个页面」，而是**给每一个数字配一份可执行的说明**：说明与算法写在同一个地方，页面上的数字就是按这份说明现算出来的。

### 1.1 为什么口径不能只写在文档里

| 方案 | 结果 |
|---|---|
| 口径写在 Word / 注释里，SQL 散在各页 | **必然分家** —— 改了 SQL 忘了改文档，或反过来。分家是口径漂移的唯一起因 |
| 口径与人各写一半（前端算一半、后端算一半） | 前后端两个实现，注册数、缓存策略、时区任一不同就会飘 |
| 口径进表，但表是**手工维护**的 | 表与代码两处可写 = 两处必然不一致；而且没人知道该改哪边 |
| **口径与算法写在代码同一处，表是投影** | 本模块采用。改算法就必然同时改口径（它们在同一个对象里），表由启动时幂等同步 |

## 二、核心设计判断：定义与计算必须写在同一处

这是本模块唯一不容商议的设计边界。

每条指标是一个对象，`formula`（给人看的文字口径）与 `compute`（真正跑的 SQL）**挨在一起**：

    指标 = {
      key, name, module, category, unit,
      formula,      ① 怎么算（能照着复现）
      exclusions,   ② 不算什么（排除项比包含项更容易出错）
      source,       ③ 取自哪些表
      note,         ④ 什么时候会踩坑 / 为什么这么定
      compute(db, p) 真正执行的查询
    }

两点直接后果：

1. **改算法不可能只改一半**。因为口径字符串与 SQL 在同一个对象里，改 SQL 时视野内就有口径文字；这个物理上的邻近性，比任何流程规范都可靠。
2. **表里的定义不可能比代码新**。`metric_defs` 表由 `syncMetricDefs()` 从代码投影而来，只读不写人手。表存在的理由只有三个：能被 SQL 直查（报表要 join 定义）、能被 AI 读懂（否则 AI 会以为「销售额」就是 SUM 全部订单）、能靠 `updated_at` 回答「这条口径哪天动过」。

### 2.1 第四条为什么必须有：`note`

前三条（怎么算 / 不算什么 / 取自哪）任何一本数据治理手册都会写。第四条 `note` 是这份字典**真正的价值所在**，因为它记录的是**踩过的坑**：

- `turnover_days` —— 「按**数量**算而不是按金额：演示数据里同一 SKU 的单价跨度大，按金额算会被高价品带偏」
- `expiring_qty` —— 「已过期的批次故意**计入**：剔除会把最该处理的货从预警里藏起来」
- `below_safe` —— 「按 SKU 跨仓汇总后再比，不是逐仓比：逐仓比会把『A 仓缺但 B 仓有』也算成缺货」
- `unpaid` —— 「『超过已收』时不取 GREATEST(0, …)，宁可让它显示负数 —— 负数能暴露录入错误，抹平了就只能靠人去猜」
- `closed_order_ratio` —— 「**不等于** status=closed 的占比：订单可以被提前关闭（剩余不再要了），那时四段并未走完」

这些句子无法从表结构里推导出来，只能从「曾经算错过一次」里来。

### 3.1 刻意保留的「成对」指标

`purchase_amount`（含草稿）与 `purchase_amount_effective`（排除草稿）**故意都留着**，只差一个 `draft`。理由：单看一个数无法回答「草稿占了多少采购意图」，成对出现才能把这件事量化。

同理 `stock_qty` 与 `available_qty` 成对 —— 两者的差就是被订单占用的量。

### 3.2 指标之间可以互相引用

`avg_order_value`（客单价）= `sales_amount` / `sales_order_count`，实现上直接调用两者的 `compute`，而不是重写一遍 SQL：

    compute: (db) => {
      const a = METRIC_BY_KEY.sales_amount.compute(db)
      const n = METRIC_BY_KEY.sales_order_count.compute(db)
      return n > 0 ? round2(a / n) : 0
    }

这样做的意义不只是省代码 —— **它保证了分子分母的口径永远一致**。如果重写 SQL，某天有人把销售额的排除状态从 `(draft, cancelled)` 改成 `(draft, cancelled, returned)` 而漏改了客单价的分子，客单价就会系统性偏高，而且看不出来。引用同一份 `compute` 在结构上排除了这种可能。

**分母为 0 时返回 0，不返回 null**：界面上 null 会显示成空白，看不出是「0」还是「没算」。

## 四、接口设计

挂载点 `/api/metrics`。四个端点，读者不同，所以拆开：

| 端点 | 说明 | 主要读者 |
|---|---|---|
| `GET /` | 字典（按模块分组 + 当前值），定义与数字同框 | 字典页 |
| `GET /defs` | **只有定义**，没有值也没有 `compute` | 文档生成 / AI / 外部系统 |
| `GET /values` | **只有值**，可批量取（`keys=a,b,c`） | 看板 / 报表 |
| `GET /catalog` | 口径 + 当前值平铺 | 关键指标卡片 |
| `GET /stale` | 一致性自检，并摊开「表里缺的 / 表里多的」 | 治理 |
| `POST /sync` | 按代码重新投影（幂等） | 管理员 |

`/defs` 与 `/values` 拆开的理由：**它们的读者不同**。读口径的人（写文档、训 AI、对外解释）不需要数字；读数字的人（看板）不需要口径。合成一个接口，两边都得过滤掉一半字段，反而更贵。

### 4.1 一条刻意的约束：值一律现算，不进缓存

口径字典全部的价值就是「你看到的数 = 按上面写的口径算出来的数」。中间加一层缓存，字典页上的口径与数字就可能不在同一时刻 —— 那正好把这个模块废掉。指标都是单表 `SUM` / `COUNT`，千条级演示数据下现算的开销可以忽略。

### 4.2 算不出来时返回 `{ error }`，不返回 0

    { keys: { sales_amount: 5022468.16, stock_qty: { error: "no such table: inventory_stocks" } } }

**0 会被当成「真的是 0」**，那是比报错更坏的谎言 —— 报错会有人来修，0 不会。前端把这种值显示成「算不出」而不是 `0`。

## 五、治理：一致性自检与漂移检测

### 5.1 指纹机制

`syncMetricDefs()` 在写完表之后，把全部定义（去掉 `compute`）经 `stableStringify`（**键排序**，避免字段顺序变化造成假差异）+ sha256 写入 `schema_def_fingerprints` 表。`metricDefsStale()` 用同一算法重算指纹并比对。

比较时只比去注释头的正文，避免版本号变化造成误判。

### 5.2 只增不减会让字典越读越糊涂

同步时除 UPSERT 外，还会 `DELETE FROM metric_defs WHERE key NOT IN (代码里的 keys)`。指标从代码里删掉后，如果表里还留着，字典页与 SQL 直查就会各说各话 —— 而且看不出谁是对的。测试 T3 专门往表里塞一条「幽灵指标」，验证同步会把它清掉。

### 5.3 权限：查看与重投影分开授权

| 权限点 | 授权角色 | 理由 |
|---|---|---|
| `system:metrics:view` | 9 个角色（admin 到 viewer） | 口径是解释工具，越多人看得懂越好 |
| `system:metrics:sync` | **仅 admin** | 重投影是「以代码覆盖表」的写动作。放开给所有能看的角色，任何人在任何时刻都能改掉别人正在查的定义 |

与通知中心「能看渠道配置 ≠ 能推送全公司」是同一个取舍。

## 六、本次实现中被口径字典「照出来」的真实缺陷

这是本模块最值得一提的结果：**它上线后立刻暴露了一处既有缺陷**。

### 6.1 现象

`closed_order_ratio`（四段闭环率）在三个库上**都恒等于 0**。看起来像「真的一张都没关完」。

### 6.2 排查链

    恒为 0
      → 查四段关闭标记分布：到货关闭 38 张、付款关闭 5 张，但「入库关闭」0 张、「开票关闭」0 张
      → 入库关闭 = 收货单全部 status='closed'；但 38 张收货单全部停在 'received'（从未走 inspect / close）
      → 开票关闭 = invoice_amount ≥ total_amount；但 47 张订单的 invoice_amount 全是 0
      → 而 purchase_invoices 表里明明有 7 张发票
      → 查关联：purchase_invoice_items.order_item_id 全为 NULL

**根因 1（真正的缺陷）**：`refreshOrderStats` 是通过明细行的 `order_item_id` 关联到订单的，而 seed 造发票时只带 `sku_id / qty / price / tax_rate`，**没带 `order_item_id`** —— 发票本身一切正常，但它挂不上订单，于是订单上的「已开票金额」永远是 0、「开票关闭」永远不成立，而界面上完全看不出哪里错了。

值得注意的是：**路由 `/invoices-available-lines` 早就返回了 `order_item_id`**，也就是说从界面上手工开票是能挂上订单的。只有 seed 漏了。seed 的注释还写着「与路由 `/invoices-available-lines` 同一口径」——注释说了，代码没做。

**根因 2（第二个缺陷，由第一个缺陷的修复暴露出来）**：`procure-seed` 第 0 步会清空发票 / 结算 / 付款三张上游表，但**没有重置由它们推导出来的三个金额快照与两个关闭标记**。而关闭标记是「只进不退」的（migration 011 的明确口径），于是「close_invoice=1 但已开票金额=0」这种自相矛盾会被**永久保留**，而且每跑一次 seed 就更脏一层。

**根因 3**：订单状态机里 `close`（received → closed）这条边**从未被调用过**，收货单的 `inspect` / `close` 也从没被调用 —— 状态机是「有定义、无流转」的死定义，与 GR 当初「直接以 status='received' 插库」是同一类问题。

### 6.3 修复

| # | 修复 | 位置 |
|---|---|---|
| 1 | seed 造发票明细时补上 `order_item_id`，与路由同一口径 | `server/db/procure-seed.js` |
| 2 | `createInvoice` 在调用方没传 `orderId` 时**从明细行反推**表头订单；一票多单时表头留空（写哪一张都是错的） | `server/lib/purchase.js` |
| 3 | 新增 `invoiceOrderIds(db, invoiceId)`：同时取表头与明细行的关联（只看表头会漏单）；发票创建与每次状态流转后，对**全部**涉及订单重算已开票金额与关闭标记 | `server/lib/purchase.js` |
| 4 | 第 0 步清空上游后，**一并把派生的金额快照与关闭标记归零**（推导依据没了，派生字段必须跟着归零；到货 / 入库两段不动，因为它们的依据没被清） | `server/db/procure-seed.js` |
| 5 | 新增 seed 第 8 步「走完最后一段」：挑「到货已关 + 付款已关」的订单，**补齐开票缺口**（按「已收数 − 已开票数」算，缺多少补多少，不超额）、把收货单走 `received → inspected → closed`、四段齐了才用内核的 `close` 动作关单 | `server/db/procure-seed.js` |
| 6 | 回归断言 T13 锁住：开票明细必须带订单行关联、无「已提交却没挂订单行」的发票、至少一张订单四段全关、**没有「标记说关过了、金额说没关」的自相矛盾订单** | `scripts/test-purchase.mjs` |

### 6.4 结果

| 库 | 四段闭环率 | 到货 / 入库 / 开票 / 付款（关闭张数） |
|---|---|---|
| 美妆 | 4.26% | 38 / 5 / 8 / 5 |
| 餐饮 | 7.14% | 33 / 6 / 6 / 7 |
| 服装 | 4.76% | 33 / 6 / 6 / 6 |

指标从「恒为 0」变成「有真实含义的比率」；同时 `status='closed'` 的订单第一次与四段关闭标记自洽。

**这件事本身就是本模块最好的说明**：如果这四个关闭标记只是躺在数据库里、没有一个人算，`close_invoice` 恒为 0 可以再躺一年。是「必须给出一个数」这个动作，把它逼了出来。

## 七、指标口径速查（节选）

### 销售

| 指标 | 口径 | 不含 |
|---|---|---|
| 销售额 | `SUM(sales_orders.receivable_amount)` | 排除 `draft / cancelled` |
| 客单价 | 销售额 ÷ 销售订单数 | 分子分母同状态集 |
| 退货率 | 退货金额 ÷ 销售额 × 100 | 退货取 `status<>cancelled` |
| 未回款 | `SUM(receivable_amount - paid_amount)` | 负数（超收）原样保留 |

### 存货

| 指标 | 口径 | 不含 |
|---|---|---|
| 库存数量 | `SUM(inventory_stocks.qty_on_hand)` | 不含在途、不含占用 |
| 可用量 | `SUM(qty_on_hand - qty_reserved)` | 不含在途、不含冻结（本系统未启用冻结） |
| 库存金额 | `SUM(inventory_stocks.cost_amount)` | 成本口径，非售价；不现乘 `cost_price` |
| 库存周转天数 | 当前库存数量 ÷ (近 N 天出库量 ÷ N)，N 默认 30 | 出库取 `direction='out'` 流水 |
| 低于安全库存 SKU 数 | `COUNT(SKU WHERE 跨仓合计 < safe_stock)` | 安全库存为 0/空的 SKU 不参与 |
| 临期数量 | `SUM(qty_on_hand) WHERE expire_date <= today + N`，N 默认 90 | 无到期日不计；**已过期计入** |

### 采购 / 订货 / 门店 / 经销商 / 审批

| 指标 | 口径 | 关键排除项 |
|---|---|---|
| 采购金额 | `SUM(purchase_orders.total_amount)` | 排除 `cancelled`；**草稿计入** |
| 采购金额（已生效） | 同上 | 排除 `draft / cancelled` |
| 应付未结 | `SUM(settle_amount - paid_amount)` | 排除 `voided` |
| 四段闭环率 | 四段全关闭订单数 ÷ 非取消订单数 × 100 | 与 `status=closed` 占比**不是一回事** |
| 订货金额 | `SUM(oc_orders.total_amount)` | 排除 `cancelled`；门店与经销商不拆 |
| 订货满足率 | 已完成订货单数 ÷ 非取消订货单数 × 100 | 在途算「未满足」（刻意的） |
| 门店零售额 | `SUM(pos_orders.pay_amount)` | 用**实收**不用吊牌额（折扣与抹零发生在收银台） |
| 信用占用率 | `SUM(credit_used) ÷ SUM(credit_limit) × 100` | 未授信（额度=0）不参与分母 |
| 超授信经销商数 | `COUNT(credit_used > credit_limit)` | 仅统计授信额度 > 0 |
| 待审批单数 | `COUNT(approval_instances WHERE status='pending')` | 不含通过 / 驳回 / 撤回 |

## 八、AI 接入：把口径交给 AI

`server/routes/ai.js` 里的 `GET /api/ai/metrics` 原先硬编码了 10 条口径（且与代码实际算法不一致 —— 例如写着「库存金额 = `SUM(qty_on_hand * cost_price)`」，而真实口径是用表上的 `cost_amount` 列）。本次改为直接复用 `metricDefinitions()`，不再维护第二份。

一条**安全约束**：`/api/ai/metrics` 在 `server/index.js` 里被放行**免登录**（AI / 外部系统要能直接读口径）。因此该端点**只回定义、不回值** —— 否则等于把全部经营数字开成公开接口。

| 模块 04 单据内核 | 本模块**不改**内核。`closed_order_ratio` 读的是内核推导出的关闭标记；第 8 步关单走内核的 `close` 动作而非直接 UPDATE 状态 |
| 模块 22 通用审批流 | 复用其「审批与单据状态解耦」的产物：`approval_pending` 指标直接数 `approval_instances`，不重算闸门 |
| 模块 24 待办推送 | 二者都在「系统管理」下，但**职责不同**：待办推送解决「有事要通知你」，口径字典解决「数字怎么算出来的」 |
| 经营看板 | 看板理论上可以直接消费 `/api/metrics/values` 批量取数。**尚未切换** —— 看板当前的独立算法保留不动，避免一次性改动面过大；后续可逐项迁移并用 `stale` 自检守住 |
