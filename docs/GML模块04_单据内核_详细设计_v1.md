## 一、为什么必须先做这个模块

框架文档 P0 清单里，单据内核排第 2 位，理由是一句大白话：

> **状态不是功能，状态是骨架。骨架不定，后面每加一种单据就要重犯一次同样的毛病。**

改造前的真实状况（不是设计想象，是对 46 张表实测出来的）：

| 问题 | 实测证据 | 直接后果 |
|---|---|---|
| 状态值是**散落的字符串** | 46 张业务表里共出现 **53 种**「(单据类型, 状态)」组合，取值为裸字符串 | 同一种取值在不同单据里语义不同，无法跨单据统一查询或统计 |
| 流转靠**硬编码 if** | `purchase.js` 里写着 `{ submit:['draft','submitted'], approve:['submitted','approved'] … }`，每个路由各写一遍 | 非法流转只能靠每处自己拦，漏一处就写坏数据，且不报错 |
| **无流转留痕** | 单据表只有一个 `status` 字段，没有「谁、何时、从哪到哪、什么动作」 | 单据走过哪些环节事后查不到；全链路联查无从谈起 |
| **无业务流** | 跨单据的主链路（订单→到货→入库）只存在于人的脑子里 | 单据之间的推进无法驱动、无法校验、无法可视化 |

一个典型故障：某单据的流转分支只写了 `draft→submitted`，但操作员从「已审批」点提交时，因为该分支不存在，代码走的是兜底的 `UPDATE status`，状态被改成非法值——**系统不报错，界面照常显示，直到下游取数时才发现这张单状态是废的**。

所以本模块的目标不是「做一个状态管理页面」，而是把**合法状态**与**合法流转**从代码里搬进数据表，让它们成为可查询、可校验、可自检的对象。

## 二、核心设计判断：定义即数据

这是本模块唯一重要的设计决策。

```
以前：状态与流转 = 代码里的 if 分支        → 改一次要动代码、要回归、要发版
现在：状态与流转 = 数据表里的行            → 改一次是改数据，重跑迁移即生效
```

具体落到六张表：

| 表 | 存什么 | 行数（每库） |
|---|---|---|
| `doc_types` | 单据类型注册表：22 种单据的类型、所属模块、业务表名、单号前缀、有无行表 | 22 |
| `doc_states` | 状态定义：每个类型的合法状态清单，带 `kind` 与是否初始/终态 | 100 |
| `doc_actions` | 流转边：`[动作码, 动作名, 起始态, 目标态, 权限点, 是否高危]` | 106 |
| `biz_flows` | 业务流定义：跨单据的串联（6 条主链路） | 6 |
| `biz_flow_steps` | 业务流节点 | 32 |
| `doc_events` | **流转留痕**：谁、何时、把哪张单从什么状态推到什么状态 | 运行时累积 |

**关键判断：内核只做「定义与留痕」，不强制改写既有业务表。**

- 状态值仍然落在各业务表原有的 `status` 字段上（**零数据迁移风险**）
- 内核不接管业务表的写入，只提供统一流转入口
- 未迁移的老代码仍可直接 `UPDATE status`，内核不报错

这条「不强制」是有意的：一次性改造 8 个路由的状态流转，风险远大于收益。内核先立住，各路由按模块节奏逐个迁。

## 三、状态模型

### 3.1 四种状态价值（kind）

状态不能只是一串字符串，必须能回答「这个状态意味着业务走到哪了」。因此每个状态带一个 `kind`：

| kind | 含义 | 数量 | 举例 |
|---|---|---|---|
| `draft` | 未生效，可自由修改 | 20 | 采购订单草稿、门店日结待上传 |
| `active` | 流转中，已产生业务影响 | 34 | 已提交、已审批、已发货 |
| `done` | 已完成 | 26 | 已关闭、已结清、已核销 |
| `void` | 已作废/已取消/已驳回 | 20 | 已取消、已退款、已驳回 |

`kind` 的价值在于**界面与权限都能按它决策**：`draft` 才允许改行、`void` 一律只读、`done` 与 `active` 的按钮清单不同。不需要每个页面自己判断「草稿能不能改」。

### 3.2 22 种单据类型

按模块分组（全部来自实测注册，非设计臆想）：

| 模块 | 单据类型 |
|---|---|
| purchase 采购 | PO 采购订单 · GR 采购到货单 · PRT 采购退货单 |
| sales 销售 | SO 销售订单 · DL 销售发货单 · SR 销售退货单 |
| inventory 库存 | TF 库存调拨单 · CK 库存盘点单 · AS 组装拆卸单 |
| requisition 要货 | YQ 门店要货单 · SH 门店发货单 |
| produce 生产 | MO 生产订单 |
| outsource 委外 | WW 委外订单 · WM 委外发料单 · WR 委外收货单 |
| oms 商城 | OM 商城订单 |
| pos 门店 | PS 门店零售单 · PSF 收银交班单 · RC 门店日结单 |
| dealer 渠道 | DR 经销商要货单 · DS 经销商对账单 · RB 经销商返利单 |

**单号前缀按代码实际对齐**，这是实测纠正出来的一处坑：注册表里的前缀一度写成「设计上应该叫什么」，结果与库中既有单号对不上。修正为：

```
GR→PR   TF→TR   CK→SC   YQ→SQ   SH→FH
WM→WWF  WR→WWS  DL→SD   SR→SRT  PS→POS  OM→H5
```

其中 `OM` 的特殊之处：商城订单的单号字段不叫 `doc_no`，叫 `platform_order_no`（平台单号是外部给定的）。因此 `doc_types` 增加 `doc_no_field` 列做逐类型声明，而不是全局假设。

### 3.3 状态机实例（采购订单）

```
初始状态：draft
[1] draft     草稿    ：提交→已提交，取消→已取消
[2] submitted 已提交  ：审批→已审批，收货→已收货，部分收货→已提交，取消→已取消
[3] approved  已审批  ：收货→已收货，部分收货→已审批，取消→已取消
[4] received  已收货  ：关闭→已关闭
[5] closed    已关闭  ：终态
[6] cancelled 已取消  ：终态
```

三个设计细节值得单独说明：

1. **同一动作可以有多个起始态。** `取消` 可以从 draft / submitted / approved 三个状态发起，因此拆成三条边。表结构 `UNIQUE(doc_type, action, from_state)` 正是为此设计。
2. **可以有自环边。** `部分收货` 是 `approved→approved`，业务上「收了一部分但订单还没收完」。自环是合法边，不是数据错误。
3. **`received` 未标终态。** 虽然名字像终点，但它有出边（关闭），按不变量必须是 `active`/非终态。

## 四、统一流转入口

### 4.1 三件事，一个事务

所有状态变更走 `applyTransition()`，它做三件事：

```
① 校验这条边是否存在        → 不存在直接拒绝，并返回「当前可执行的动作」清单
② 更新业务表的状态字段      → 附带调用方要一并更新的其它列（白名单校验）
③ 写一条 doc_events 留痕    → 谁、何时、从哪到哪、什么动作、来源
```

三件事在**同一个事务**里，要么全成要么全不成。这就消灭了「状态改了但没留痕」和「留痕了但状态没改」两种撕裂状态。

失败时的报错对操作员友好，而不是抛一个英文异常：

```
状态「已审批」不支持动作「提交」，当前可执行：收货 / 部分收货 / 取消
状态「已关闭」已是终态，不能继续流转
```

### 4.2 为什么错误要带 httpStatus

`DocFlowError` 同时给出 `status` 与 `httpStatus`。原因是全局错误中间件读的是 `err.status`——如果只给 `httpStatus`，抛出后会返回 **500（服务器错误）**，而这类问题本质是 **409（状态冲突）**。

这个细节有现实后果：**500 会被监控当成故障报警，409 是正常的业务拒绝**。一个「终态不能继续流转」的正常业务提示被报成服务器故障，会持续污染告警。

### 4.3 三种调用形态，适配不同迁移阶段

| 函数 | 场景 |
|---|---|
| `applyTransition(p)` | 完整形态：显式传 db / docType / id / action / actor / set / payload |
| `tryTransition(p)` | 非抛错版：返回 `{ ok, data \| error }`，适合在既有路由里平滑接入而不改变错误处理风格 |
| `advanceStatus(db, req, {...})` | 路由里最常用：自动从 `req.user` 取操作人，失败即抛（全局中间件转 409/404） |

`advanceStatus` 是实际接入时的主力，8 个路由模块的状态流转全部改走它，原有的硬编码 flow 映射表**整块删除**。

### 4.4 乐观并发

`applyTransition` 支持 `expectFrom`：调用方声明「我认为这张单现在是 X 状态」，实际不符则拒绝。这是**乐观并发控制**，用于防止两个操作员同时打开同一张单、各自点按钮导致的互相覆盖。

## 五、业务流：跨单据的串联

单张单据的状态机解决「这张单怎么走」，但业务是**单据之间**的推进。因此引入 `biz_flows` + `biz_flow_steps`，先落 6 条主链路定义：

| 业务流 | 链路 | 步骤数 |
|---|---|---|
| `FLOW_PURCHASE` 采购主流程 | 采购订单创建 → 订单审批 → 到货收货 → 库存过账 → 采购结算 | 5 |
| `FLOW_SALES` 销售主流程 | 销售订单创建 → 信用校验 → 订单确认 → 发货出库 → 订单完成 → 售后退货 | 6 |
| `FLOW_STORE_REQ` 门店要货流程 | 门店要货单 → 总部受理 → 分配库存或转采购 → 门店发货 → 门店收货 | 5 |
| `FLOW_DEALER_ORDER` 经销商订货流程 | 渠道提交要货 → 按渠道取价与信用校验 → 订货审批 → 转销售订单 → 发货 → 对账 | 6 |
| `FLOW_POS` 门店零售流程 | 开班 → 扫码收银 → 交班 → 日结交款 → 上传总部 | 5 |
| `FLOW_PRODUCE` 生产与委外流程 | 生产/委外订单 → 订单审批 → 领料/发料 → 完工入库 → 质量检验 | 5 |

每个节点带：`node_type`（start/approve/handoff/branch…）、`node_name`、`doc_type`（该节点发生在哪类单据上）、`perm_code`（该节点需要的权限点）、`is_required`（是否必经）。

**业务流的作用不是「跑流程引擎」，而是「给单据之间的推进一个可校验的路由表」**：模块 07/08/12A 实施时，单据联动按这张表驱动，而不是又写一套 if。

## 六、不变量与自检自愈

内核的四条不变量写进了迁移的 `verify()`，每次启动迁移都会检查，违反即自动重跑修复：

| # | 不变量 | 为什么它是真的不变量 |
|---|---|---|
| 一 | **终态不能有出边** | 「终态」的定义就是不能再流转。若被标为终态却还有出边，界面会把按钮全禁掉——功能凭空消失 |
| 二 | **每条边的起止状态都必须已定义** | 否则流转到一半发现目标状态不存在，状态变成孤儿值 |
| 三 | **每个单据类型恰有一个初始状态** | 零个 → 建不出单；两个 → 新建时不知道落哪个 |
| 四 | **定义指纹一致** | 见下 |

### 6.1 第四条不变量背后的真实教训

前三条都是结构不变量，第四条不是——它是被一次真实故障逼出来的。

**问题形态**：有一类迁移不建表、只灌「定义」（状态机、事务字典、库存参数、编码规则）。改这类定义时**不违反任何结构不变量**，于是迁移运行器的结构自检**发现不了**，库里一直是旧定义。

**症状**：代码里加了流转边，库里没有 → 界面上的按钮就是不出现。**而且不报错**，只是「功能莫名少一个」。

**解法**（`_helpers.cjs`）：迁移把定义序列化成 JSON、排序键、算 sha256 存进 `schema_def_fingerprints`；自检时重新计算比对，不一致就重跑该迁移（`up` 全部幂等）。

```js
// 稳定序列化：对象键排序，保证同样内容永远算出同一个指纹
function stableStringify(v) { … }
function defFingerprint(data) { return sha256(stableStringify(data)).slice(0, 32) }
```

已接入指纹的迁移：`003_inv_dict`（库存事务字典 + 参数）、`008_doc_kernel`（本模块）、`009_docno_rules`（编码规则默认模式）。

**实测**：跑 `node scripts/migrate.mjs` 会看到

```
[migrate] heal 003_inv_dict   库存事务类型字典（结构缺失，已重跑修复）
[migrate] heal 008_doc_kernel 单据内核（结构缺失，已重跑修复）
[migrate] heal 009_docno_rules 编码规则（结构缺失，已重跑修复）
```

第二次运行即不再 heal，说明定义与库已一致。

## 七、接口清单

`server/routes/docflow.js`，全部挂 `/api/docflow`：

| 接口 | 说明 |
|---|---|
| `GET /overview` | 内核总览：类型数、状态数、边数、各状态真实分布 |
| `GET /types` | 单据类型列表（可按 module 过滤） |
| `GET /types/:code/machine` | **完整状态机**：状态清单 + 按起始态归集的边，前端可直接画流转图 |
| `GET /types/:code/lifecycle` | 生命周期文字说明（即上文 3.3 那种格式） |
| `GET /actions?doc_type=&state=` | 某状态下可执行的动作，可传已持权限集合过滤 `permitted` |
| `POST /transition` | 执行流转（走 `applyTransition`） |
| `GET /history/:docType/:id` | 单据一生：按时间正序列出全部流转 |
| `GET /trace?doc_no=` | **全链路联查**：给定任意单号，串起它所在业务流上所有单据的流转 |
| `GET /events` | 流转日志（分页 + 过滤） |
| `GET /flows` · `GET /flows/:code` | 业务流与节点 |
| `GET /no-rules` · `POST /no-preview` · `POST /no-issue` | 编码规则相关（模块 06，见对应设计稿） |

`traceByDocNo()` 的实现有个务实的取舍：主查 `doc_no` 精确匹配，再补一遍 `payload_json LIKE %doc_no%`（因为单据联动时会把上游单号写进 payload）。最后按事件 id 归并去重。这不是图数据库式的真正血缘追踪，但**对「订单→入库→出库→发票」这类线性链路已经够用**，且零额外存储成本。

## 九、迁移过程中的真 bug（记录在案）

本模块实施中，四个缺陷是**测试逼出来的，不是review看出来的**：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | `applied.join is not a function` | `runMigrations` 返回 `{applied, healed}` 而非数组 | 改 `const migResult = runMigrations(db)` |
| 2 | 状态机定义语义错 | `SO.completed` / `YQ.received` / `RC.uploaded` 被标为终态，但实际有出边 | 改为非终态，**并把该不变量写进 `verify()`** —— 让这类错永远能被自检抓到 |
| 3 | `applyTransition is not defined`（调拨出库 500） | 批量替换脚本的替换顺序写错，`applyTransition` 调用早于 import 合并 | 手工补 import |
| 4 | `{YYYYMMDD}` 被原样输出到单号里 | 编码解析器只认拆开的日期段 `{YYYY}{MM}{DD}`，不认复合写法 | 见模块 06 设计稿第 3.2 节 |

第 2 条最值得记录：**它不是「代码错了」，而是「数据错了」**。代码逻辑完全正确，错的是定义表里的 `is_final` 标志。这类错误只有靠不变量自检才能发现——这直接催生了第 6.1 节的指纹机制。
