# GML 模块 13：质量检验独立成单 — 详细设计（v1）

> 版本：v1（2026-10-15）
> 依赖：模块 04 单据内核、模块 06 编码规则、模块 07 采购到货（存量质检 INS）、模块 03 库存引擎、模块 02 生产订单
> 迁移：`022_quality_inspection.cjs`（三库已执行，伴随 `008_doc_kernel.cjs` 扩表）
> 契约：OpenAPI 1.11.0 · `/api/qc` 共 20 条路径（22 个端点，`/requests` 与 `/handlings` 各支持 GET + POST）
> 截图：`docs/shots/qc-01` ~ `qc-07`

## 0. 一句话定位

模块 07 已经有质检单（`purchase_inspections`，INS），但它是**绑死在到货单上**的：
一张到货单一条记录、只认采购这一个入口、抽样与检验写在同一个动作里。
到了「生产完工要检验」「在库复检」就无处安放 —— 只能复制一套，而复制出来的第二套迟早与第一套口径分叉。

本模块把质检从「采购的附属动作」提升为**独立的三段链**：

```
报检 QCR            检验 QCI              不良品处理 DH
谁来检、按什么方案 → 判的结果是什么    →  不合格的怎么办
（仓库/生产发起）    （质检岗执行）        （品质/生产决策，有库存后果）
```

三段分开不是形式主义，是三条硬理由：

| 理由 | 说明 |
| --- | --- |
| 责任人与时间不同 | 仓管报检、质检员判定、品质主管决定处置。合成一张单就只能共用一个状态，谁卡住了都看不出来 |
| 处置是多维决策 | 一次检验里不同 SKU 的处置可以不同（一部分退货、一部分让步），一张单只能有一个状态 |
| 抽样是行业惯例 | 判断不该建立在「全检」的假设上。抽样方案（n/Ac/Re）必须落库，否则「为什么判合格」半年后没人说得清 |

## 1. 三条硬口径

这三条是全部设计的出发点，其它都是推论。

**① 判定由数字推导，不由人选。** 实测不良数 ≤ Ac 判合格，> Ac 判不合格。
界面上**没有**「判合格 / 判不合格」的下拉框 —— 让人手选结论，就会出现
「不良 5 个却点了合格」而系统毫无察觉，这是质检最怕的失效。

**② 抽样量 ≤ 报检数量、不良数 ≤ 抽样量。** 不成立说明有人填反了，写库前拦住，且拦在事务里。

**③ 处置必须有后果，否则它只是一张纸。**

| 处置 | 库存后果 | 落库凭证 |
| --- | --- | --- |
| 让步接收 `concession` | 不动库存（货留下，记录「明知不合格仍收下」的风险决策） | 必须填理由 |
| 退货 `return` | **出库**：采购来源生成采购退货单（PRT，内部已出库）；其它来源走质检退料出库（QC_RET_OUT） | `out_doc_no` |
| 报废 `scrap` | **出库**：报废出库（SCRAP_OUT） | `out_doc_no` |
| 返工 `rework` | 不动库存（货回到产线，返工后可再报检） | 留执行留痕 |

## 2. 数据模型（迁移 022）

### 2.1 四张表

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `qc_requests` | QCR 报检单头 | `doc_no` / `source_type` / `source_id` / `source_doc_no` / `warehouse_id` / `supplier_id` / `request_date` / `aql` / `inspect_level` / `total_qty` / `total_sample_qty` / `inspection_id` / `status` |
| `qc_request_items` | 报检行（**抽样方案与检验结果挂在同一行**） | `line_no` / `sku_id` / `batch_no` / `qty`（批量）/ `sample_qty`（n）/ `ac` / `re` / `defect_qty` / `result` / `defect_code` |
| `qc_inspections` | QCI 检验单头（与报检单一对一） | `request_id` / `inspect_date` / `aql` / `sample_qty` / `defect_qty` / `defect_rate` / `result` / `disposition` / `handling_count` / `status` |
| `qc_defect_handlings` | DH 不良品处理单 | `inspection_id` / `sku_id` / `batch_no` / `qty` / `mode` / `reason` / `stock_direction` / `out_doc_type` / `out_doc_id` / `out_doc_no` / `status` |

**为什么抽样方案与检验结果在同一张行表上，而不是另开 `qc_inspection_items`：**
报检行与检验行**天然一一对应**（同一行货，先填「报检多少、抽多少」，后填「不良多少、判什么」）。
另开一张表会引入一个只在中间态存在的 join，而两张表的口径还得人工同步。
靠 `result='pending'` 区分「事实字段已写、判断字段没写」。

**为什么 `disposition` 是落库字段而不是纯派生：**
一次检验可能有多张处置单（不同 SKU 不同方式），此时记为 `mixed`。
它是「这批货最后怎么处理了」的唯一落点；处置单可以被再开，结论一旦下了就该冻住。

### 2.2 视图 `v_qc_pending_source`（待检来源）

把「谁在等检」下沉到库里，`union` 采购到货（`status='received'`）与生产完工（`status='completed'`），
并**同时排除**两类已被认领的来源：

- 已有未作废 QCR 的（`q.status <> 'cancelled'`）；
- 已有模块 07 质检单（`purchase_inspections`，状态不在 `cancelled/draft`）的到货单。

> 判据写在视图里而不是 JS 里，是因为「排除已报检」这条规则一旦要在每个调用点各写一遍，
> 只要有人漏一处，同一批货就会被检两次。有且只有一处定义。

### 2.3 索引 / 权限 / 编码规则 / 库存事务字典

- 索引：`idx_qcr_status`、`idx_qcr_source`、`idx_qcri_request`、`idx_qcri_sku`、
  `uq_qci_request`（**唯一**，保证报检单 ↔ 检验单一对一）、`idx_qci_status`、`idx_qci_result`、
  `idx_qcdh_inspection`、`idx_qcdh_status`、`idx_qcdh_sku`
- 权限点 3 个：`quality.qc.view`（查询，`menu`）、`quality.request.create`（提交报检）、
  `quality.handle.approve`（不良品处理批准）
- 角色授予：admin 全部 / boss 只读 / warehouse 查看 + 报检 / viewer 只读
- 编码规则：`QCR` / `QCI` / `DH`，`{PREFIX}{YYYYMMDD}{SEQ:4}`，按日重置
- 库存事务类型字典：新增 `QC_RET_OUT`（质检退料出库，`out` / `quality`）。
  **为什么不复用 SCRAP_OUT**：质检退料与报废是两种业务，混在一起统计时分不开

> `verify()` 会同时自检四张表、视图、关键索引、`inv_txn_types` 里的 `QC_RET_OUT`、
> 三个权限点、以及定义指纹。视图必须一起查 —— 整库重建会先 DROP 所有视图，
> 只查表存在会把「视图凭空消失」误判成「已迁移」，而依赖它的查询要到运行时才炸。

## 3. 单据内核与状态机

内核注册三个类型（`doc_types` 34 → **37** 种），业务流 8 → **9** 条（新增 `FLOW_QUALITY`）。

| 类型 | 表 | 状态 | 动作 |
| --- | --- | --- | --- |
| `QCR` 报检单 | `qc_requests` | `draft` 草稿 → `submitted` 已报检 → `closed` 已关闭 / `cancelled` 已取消 | `submit`（draft→submitted）、`close`（submitted→closed，危险）、`cancel`（draft→cancelled，危险） |
| `QCI` 检验单 | `qc_inspections` | `draft` 待检 → `inspected` 已检 → `closed` 已关闭 / `cancelled` 已取消 | `inspect`（draft→inspected）、`close`（inspected→closed）、`cancel`（draft→cancelled） |
| `DH` 不良品处理单 | `qc_defect_handlings` | `draft` 待处理 → `confirmed` 已执行（**终态**）/ `cancelled` 已取消 | `confirm`（draft→confirmed，`is_danger=1`）、`cancel`（draft→cancelled） |

两处刻意的状态设计：

- **`inspected` 不标终态**：结论下了之后还要处置，处置完才归档。若标终态，处置单就没有可以挂靠的开单状态。
- **`confirmed` 标终态**：它是**有库存后果**的动作（货真的出库了 / 真的生成退货单了）。
  已执行不能再撤销 —— 冲正只能再开一张反向单，这与成本调整单是同一套哲学。

`FLOW_QUALITY` 五步（报检 → 抽样 → 检验判定 → 不良品分流 → 关闭）写在 `biz_flow_steps` 里，
界面的「流程」视图与文档共用这一份定义。

## 4. 核心流程

### 4.1 抽样方案（`samplingPlan`）

AQL 2.5 · 一般检验水平 II 的**通行单次抽样数字**（按批量区间取 n / Ac / Re）。

| 批量 | 8 | 9–15 | 26–50 | 281–500 | 501–1200 | 3201–10000 | ≥ 500001 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 方案 | A | B | D | H | J | L | Q |
| n | 2 | 3 | 8 | 50 | 80 | 200 | 1250 |
| Ac/Re | 0/1 | 0/1 | 0/1 | 3/4 | 5/6 | 10/11 | 21/22 |

三条规则写死在函数里，避免不同人算出来不一样：

1. **样本量不超过批量**（小批量的货不可能抽得比它自己还多）→ 全检；
2. **样本量向下取整**（件数只能是整数），且至少 1；
3. **加严 / 放宽只调 Ac，不调 n** —— 调 n 会让「同一批货」在两次检验里用不同样本量，复现不了；
   调 Ac 是标准里也在做的事。加严 `Ac − 1`、放宽 `Ac + 1`（**加严时下限为 0**）。

> 一处**刻意的简化**，写清楚比含糊过去好：本实现不含宽严转换的完整规则，
> `inspect_level` 只做一档线性调整。目的是让「方案可追溯、可复现」，
> 而不是宣称符合某版国标的全部条款。真要对接客户的抽样标准，改 `SAMPLE_TABLE` 一处即可。

### 4.2 报检（`createRequest` / `submitRequest`）

- 来源三选一：`purchase_receipt`（须 `received`）/ `production_order`（须 `completed`）/ `inventory`（在库复检，必须自带明细与仓库）。
- 建单时**就把抽样方案算好写进行里**，不是检验时现算 —— 现算意味着同一批货今天算和明天算可能不一样（参数被改了），判过的案子就再也复现不了。
- **幂等与防重**：同一来源已有未作废报检单时拒绝，并报出那张单的单号（`QC2_DUPLICATE`，409），让人去改那张而不是再开一张。
- 行级 override：允许只报检其中一部分行 / 部分数量（`items` 按 `source_item_id` 或 `sku_id + batch_no` 匹配）。
- 提交报检时**同时生成一对一的检验单草稿** —— 「待检」这个工作台由检验单承载，唯一索引 `uq_qci_request` 兜底防重。

### 4.3 检验（`submitInspection`）

写库前逐行强校验，全部在同一个事务里，任一条不成立整批回滚：

- 不良数 ≥ 0；不良数 ≤ 抽样量（`QC2_DEFECT_OVER_SAMPLE`）；抽样量 ≤ 报检数量（`QC2_SAMPLE_OVER_QTY`）；
- 判定 = `defect_qty <= ac ? qualified : unqualified`；
- 头汇总（总数量 / 抽样量 / 不良数 / 不良率）与行合计一致；
- `result` 全合格 → 直接关报检单；有不合格 → 等处置。

**没有「跳过检验直接判合格」的入口。** 结论必须由数字推出来。

### 4.4 不良品处理（`createHandling` / `confirmHandling`）

建单前置校验四条：① 检验结论必须是不合格（合格品没有「不良品处理」可言）；
② 让步接收必须有理由；③ 处理数量不得超过该行**剩余可处置量**（否则同一批不良品会被退两次货）；
④ 必须有仓库（没有仓库就不可能产生库存后果）。

执行（`confirmHandling`）是**本模块唯一产生库存后果的动作**，四路分流见 §1 表。

- `scrap` → `applyStockOut({ docType: 'SCRAP_OUT' })`，`out_doc_no = 处理单号`；
- `return` + 采购来源 → `createPurchaseReturn`（内部**已经出库**），`out_doc_type = 'PRT'`；
- `return` + 其它来源 → `applyStockOut({ docType: 'QC_RET_OUT' })`；
- `concession` / `rework` → 不动库存。

**实现要点（本轮踩过）**：状态由内核 `applyTransition` 推进，
`out_doc_*` / `approved_by*` / `approved_at` 通过 `set` 一并交给内核写。
**不能先 `UPDATE status` 再走内核** —— 内核会读到「已是终态」而拒绝流转，报出一个与真实原因无关的错。

### 4.5 链的收口（`closeRequestIfDone`，本轮修正过判据）

关闭报检单需要**同时**满足：

1. 检验结论已下（QCI 不是 `draft`）；
2. 没有未执行的处置草稿；
3. **每一行不合格都处置满了**：该行非作废处置单的 `SUM(qty)` ≥ 报检数量。

第 3 条是本轮最重要的修正。原实现写的是「每行不合格**有没有**处置单」
（`NOT EXISTS`），于是报检 700 件、先做 300 件让步、再撤销一张误开的草稿 —— 报检单**当场关闭**，
剩下 400 件不合格品再也没人管，而且**不报错**。
判据已改为数量覆盖，并新增第 10 类审计 `shortHandle` 让它可以被一条命令查出来。

报检单关闭时，检验单跟着归档（同样走内核，不手写 `status` 与留痕）。

## 6. 演示数据（`qc-seed.js`，三库同构）

六条故事，每条都能回答界面上的一个问题：

| # | 故事 | 回答的问题 |
| --- | --- | --- |
| ① | 采购到货 → 全合格（不良数取**恰好等于 Ac**） | 判定边界长什么样；全合格会自动关单 |
| ② | 采购到货 → 同一行拆「退货 + 让步」，其余不合格行全部让步 | 混合处置（`mixed`）与「处置满才关单」 |
| ③ | 采购到货 → 报废（出库）+ **一条未执行的返工草稿** | 中间态：为什么单子还开着 |
| ④ | 生产完工 → 返工（不动库存） | 生产来源的质检 —— 模块 07 完全没有的能力 |
| ⑤ | 在库复检 → 已报检、**未出结论** | 「待检」工作台有内容 |
| ⑥ | 加严检验**草稿**（未提交） | 「提交报检」这个动作有东西可演 |

三库实测一致：**报检 6（已关闭 3 / 已报检 2 / 草稿 1）｜检验 5（合格 1 / 不合格 4）｜处置 6**，
四种处置方式各至少一张。

> 造数据的两个原则（都是前几批踩出来的）：
> **① 不良数用算法定死方向**（`defectsFor`），不让结论看运气；
> **② 不依赖「来源单至少有三行」这类假设** —— 那样会时有时无。
> 需要「未执行的处置」这种中间态时，挂到「同一行还有剩余可处置量」上，三库必有一条。

| 2 在库复检（合格） | 建单/提交/检验；**不良数恰好 = Ac → 判合格**；全部合格自动关报检单与检验单；合格单不能建处置单 |
| 3 采购到货（不合格） | **不良数 = Ac + 1 → 判不合格**；四种拦截（超量 / 让步缺理由 / 不认识的处置方式 / SKU 不在明细）且被拒后零落库；四路分流各走一遍并核对**库存真的扣了没有**、PRT / SCRAP_OUT 流水是否留下、让步与返工是否**真的没动库存**；`disposition = mixed`；撤销草稿；已执行不可撤销 |
| 4 生产完工 | 把草稿生产订单按**内核**推到完工（用完还原，不直接改 status）；未完工不能报检；加严 Ac 比正常低 1；未出结论不能建处置单 |
| 5 非采购来源退货 | 走 `QC_RET_OUT` 而非 PRT，且真的扣库存 |
| 6 数字校验 | 不良 > 抽样被拒且**事务已回滚**（检验单仍是待检、行仍未判定）；不良为负被拒；已取消的检验单不能再提交结论；**已报检的报检单不能取消**（只能关闭）；草稿取消后同一来源可以重新报检 |

**自洽审计十查**（`auditQc`）：

| 检查 | 判据 |
| --- | --- |
| `badLineQty` | 行内数量关系成立（抽样 ≤ 报检、不良 ≤ 抽样、不良 ≥ 0、Ac < Re） |
| `badVerdict` | **判定与数字一致**（判合格就不能有不良 > Ac，反之亦然） |

| `closedWithDraft` | 已关闭的报检单上还有未执行的处置草稿 |
| `shortHandle` | 已关闭的报检单里有不合格行**没处置满**（本轮新增） |

**可重复跑的机制（本模块独有）**：这是全项目里唯一**真的会扣库存**的服务层测试。
只删单据不还原库存，第二轮就会因为「库存不足」而失败，或者更糟 —— 悄悄把演示库越扣越少。
所以测试用**快照回滚**：开跑前把 `inventory_stocks` 全表拍一张快照，跑完按 id 逐行还原；
同时按单据号 / 单据 id 精确删掉本轮产生的 `inventory_transactions` 与 `stock_cost_ledger`。
这不是「绕过业务」—— 流水本来就不该留下，因为业务单据本身被删了。

## 10. 已知边界与下一步

1. **不含宽严转换的完整规则**：`inspect_level` 只做一档线性调整（Ac ±1，n 不变）。
   对接客户抽样标准时改 `SAMPLE_TABLE` 一处即可，口径已经收在 `samplingPlan` 一个函数里。
2. **检验项是「不良数 + 缺陷类型」，没有多个检验项**：真实质检常常要逐项打分（外观 / 尺寸 / 性能各一项）。
   当前用「不良数 vs Ac」的单次抽样模型覆盖大多数场景；要做多检验项，应新增 `qc_inspection_metrics` 行表，
   判定规则改为「所有检验项都合格才合格」，此时 `qc_request_items.result` 要变成派生字段。
3. **返工后不自动再报检**：返工执行完只是不动库存 + 留痕，需要人工再开一张报检单。
   可做成「返工执行后生成一张待报检提示」。
4. **让步 / 返工不联动后续计价**：让步接收的货仍按原价入账；若客户要求「让步品降级计价」，
   需要与模块 09 的成本调整单打通（生成一张 CA）。
5. **不合格品的隔离库存未落地**：当前退货 / 报废直接从原库位出库，没有「先移到待处理区」这一步。
   若客户要求实物隔离，可在 `warehouses` 下加虚拟库位并在执行时做「转库 + 出库」两步。
6. **红冲 / 反向处置**：已执行的处置单（`confirmed` 是终态）不能撤销，只能再开一张反向单。
   反向单的审批可挂在模块 22 审批流上。
