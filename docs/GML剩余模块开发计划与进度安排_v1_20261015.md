## 二、开发原则（本轮不变）

1. **数据库先行，一批一迁移。** 每个批次先落一个编号迁移（`020` → `035`），再写服务层、路由、前端。表结构定不下来不动代码。
2. **迁移必须幂等 + 带 verify。** 参照 `019_ar_receipt.cjs` 的写法：`up(db)` 可重复执行，`verify(db)` 逐表逐列自检（含 `hasColumn` 补列检查），让运行器能在结构脱节时自动重跑修复。
3. **单据即数据。** 新单据类型一律注册进 `008_doc_kernel.cjs`（`DOC_TYPES` / `doc_states` / `doc_actions` / `biz_flows`），流转只走 `applyTransition`，不在路由里散写状态字符串。
4. **错误码两段式。** 顶层 `code` 为数字（0 成功 / 1 失败），业务错误码放 `detail.code`。
5. **测试串行。** 三个库写同一份 SQLite 文件，并行跑会 WAL 竞争，所有测试脚本必须逐个执行。
6. **品牌脱敏铁律。** 一切真实客户名与品牌名不出现在界面、seed 数据、文档、截图、注释中；演示数据一律自造（美妆版 / 餐饮版 / 服饰版三条行业线）。
7. **双格式交付。** 每份设计稿产出 MD 原稿（`gml/docs/`）+ Word 副本（`~/工作文档/` 顶层 `00_` 前缀），Word 内不用围栏代码块，改 4 空格缩进。
8. **「今天」只有一个出处。** 所有**业务日**一律走 `server/lib/dates.js` 的 `localDate()` / `addDays()`，
   禁止再用 `new Date().toISOString().slice(0,10)` —— 那是 **UTC 日期**，东八区在**本地 00:00–08:00**
   之间比本地日期早一天。同一份数据里只要存在两个「今天」，账龄、账期、单号日期段、日结业务日
   就会各算一遍且**全部不报错**（批次 F 全量回归实测：逐笔逾期合计与汇总逾期差 82.32 元，
   差的就是那张"本地今天到期"的应收单）。这条与「灌数时钟只有一个出口」（`db/seed-clock.js`）
   是同一条规则的两个面：**凡是"从全局量派生出来、又参与比较"的值，先问它有几个出处。**

9. **同一份判据只有一个实现（第 1 批修复立此条）。** 数据范围的定义只有 `scopePairs()`（列表
   `scopeFilter` / 详情 `assertCanRead` 都由它派生）；金额与数量的定义只有 `numField()`
   （`numAmount` / `numQty`，建单与改单、销售与采购共用）；工具与资源的可用性只有
   `checkToolAccess()`（`tools/call` 与 `resources/read` 共用）。**"列表挡得住、详情挡不住"
   不是概率问题，是必然** —— 只要同一份规则有两个实现，就一定会只改一处。
   配套两条：**读接口与写接口一样需要功能权限门**（"能看"的门最容易被忘）；
   **"另一个入口"必须复用同一个判定函数，而不是复制同一段判定**（复制那一刻是对的，
   之后任何修改都只改一处）。

## 七、风险与已知限制

| 风险 | 影响 | 应对 |
|---|---|---|
| SQLite 单写者模型 | 多终端并发写会 `SQLITE_BUSY` | 已验证 `busy_timeout=5000` 生效；所有写操作走事务；避免长事务持锁 |
| 迁移补列未纳入 verify | 整库重建后列消失 | 新迁移统一把补列纳入 `verify`（`hasColumn` 自检），沿用 019 的做法 |
| 内核定义重名 | 静默覆盖，单据类型串码 | 新增类型前全库检索短码；注册后跑 `inspect-doc-kernel.mjs` 核对数量 |
| seed 清表清单漏表 | 残留数据触发幂等跳过，只有一个库造出数据 | 新表一律同步进 `server/db/seed.js` 清表清单 |
| 促销叠加无上限 | 出现负价单 | 促销引擎内置最低价地板（成本价或指定折扣下限），命中即截断 |
| 发票与出库口径不一致 | 应收重复或漏记 | 口径在 `settings.ar_source_of_truth` 显式落库，二选一且有唯一约束兜底 |

**批次 A 实做要点（与原计划的差异）**

1. 原计划只打算加派生视图与索引，实做时发现「逐笔账龄 / 预收 / 订货并入」三件事都需要在库里落口径，于是把三张视图一并做成了对外可用的能力（各配 1~2 个端点 + 前端页签），而不是只做底层。
2. 原计划把「OC 应收并入」列在 `routes` 层，实做时下沉到 `lib/order-center.js` 的 `transitionOrder(action='receive')` —— 并入应收必须与状态流转在**同一个事务**里，放在路由层会出现"状态变了、应收没生成"的中间态。

4. 计划外新增两个运维脚本（备份 / 重置）—— 起因是清库时踩到"视图引用已删表"的坑，需要一个能把文件系统状态也一起复位的入口。

**批次 B 实做要点（与原计划的差异）**

1. 原计划把发票挂在 `/api/sales` 前缀下与销售订单共存，实做时改为**独立前缀 `/api/invoices`** —— 「票」与「货」的授权粒度不同（`sales.invoice.*` vs `sales.*`），独立前缀才能分别授权，也让契约文档的标签更干净。
2. 原计划只做「开票 → 关联应收」，实做时把**应收来源口径做成了落库开关**（`settings.ar_source_of_truth`：`SO` 关联订单既有应收 / `SI` 开票时才建应收）。两个口径都是真实业务（月结 vs 现结），写死一个就会挡住另一个。

5. 计划外把「待开票队列」默认收窄为**排除已开完票的发货单** —— 队列语义是"还有活要干"，已开完的留在里面只会让人以为漏开了。


**批次 C 实做要点（与原计划的差异）**

1. 原计划的三张表（报检 / 检验 / 不良品处理）**全部落地**，但计划外的第四张表成了关键：
   `qc_request_items` 把「抽样方案」与「检验结果」放在**同一行**上（靠 `result='pending'` 区分
   事实字段与判断字段）。原计划隐含「检验项另开一张表」，实做时判断那样会引入一个只在中间态
   存在的 join，而两张表的口径还得人工同步 —— 报检行与检验行本来是天然一一对应的。
2. 待检来源下沉为**视图** `v_qc_pending_source`，而不是在服务层拼 `union`。
   理由：`union` 写在 JS 里意味着「排除已报检 / 排除已有模块 07 质检单」这两条判据要在每个调用点各写一遍，
   只要漏一处，同一批货就会被检两次。
3. 原计划只要求「四路分流可执行」，实做时把**库存后果做成了可断言的**：
   退货走 PRT 或 `QC_RET_OUT`、报废走 `SCRAP_OUT`、让步与返工必须原地不动库存，
   测试逐项核对库存行数量与流水是否留下。
4. 计划外发现并修复一个**静默失效**：`closeRequestIfDone` 的关单判据写成了
   「每行不合格有没有处置单」而不是「处置完了没有」，导致不合格品只处置一部分时报检单会被关掉、
   剩下的货没人管且不报错。判据改为数量覆盖，并新增第 10 类审计 `shortHandle` 把它变成可查的不变量。
5. 计划外把「处置数量不能超过剩余可处置量」的边界补全 —— 原来只挡了「超过报检数量」，
   现在逐行按 `(报检数量 − 已处置数量)` 校验，并按 SKU × 批次汇总。
6. 测试脚本引入**库存快照回滚**（本模块是全项目唯一真的扣库存的服务层）：
   开跑前拍 `inventory_stocks` 全表，跑完逐行还原 + 按单据号删掉本轮流水，
   使测试真正可重复跑，而不是「第一轮绿、第二轮因库存不足而红」。

**批次 C 收尾：把「整库重建」做成真正可复现（与原计划的差异）**

原计划的收尾只是「跑一遍全量回归 + 提交」。实做时全量回归**连续 6 轮时好时坏**：
失败点在 `test-costing` / `test-purchase` / `test-quote-credit` 之间游走，
而且**把那个测试单独跑必然通过**。顺着这条线挖下去，一共修了 7 个缺陷
（`bugcheck-log.md` 缺陷十一 ~ 十七），核心结论是：

> **「整库重建」的语义是「可复现」，不是「清掉看得见的表」。**
> 凡是能被 `ORDER BY` 影响、或作为对外标识的派生状态，漏一个，重建就退化成
> 「看起来一样、其实不一样」；而这类问题只会在**连着跑**的时候现形。

1. **取号计数器没进重建清单**（缺陷十一）—— 业务表全清了，`doc_no_counters` 却按上一代末号继续发号，
   同一批演示数据两次重建后**单号不同**，凡按单号排序取样的断言就换了人。
2. **灌数时钟是散装的**（缺陷十二）—— 每个日期工具各自 `new Date()`，
   库存流水的 `biz_time` 更远一层来自 `stock.js`。新增 `db/seed-clock.js` 收敛成**一个**时刻，
   `boot.js` 在 `finally` 里交还真实时间（放 `finally` 是必须的，否则异常时会留下「运行时时间不往前走」）。
   库存引擎那一层**不改依赖方向**（db → lib 单向），改为 `stock.js` 暴露 `setStockNowProvider()`。
3. **批次主档跨重建累积**（缺陷十三）—— `inventory_batches` 从来不清，实测攒到 **21,865 行**；
   且 `ON CONFLICT` 只更效期不更 `status`/`qc_status`，一个批次被某代判为不可用就**永远回不来**，
   拣选凭空少批次 → 库存行数在 779 / 780 之间来回跳。
4. **两处绕过确定性随机的写法**（缺陷十四）—— `ORDER BY RANDOM()`（SQLite 自带随机）
   与**没有 `ORDER BY` 的 `LIMIT 1`**（取哪行取决于物理页布局）。
5. **卫星 seed 只 `DELETE` 不重置自增序列**（缺陷十五）—— `sqlite_sequence` 只在 `DROP TABLE` 时清，
   `oc_*` / `purchase_*` 的 id 逐轮增长，而 id 会被抄进 `ar_documents.subject_id`、
   `doc_events.doc_id`、`purchase_order_items.remark`。新增 `db/seq.js` 统一处理。
6. **内核与审批定义表被迁移逐代重灌**（缺陷十六）—— `resetDatabase()` 只 DROP 业务表，
   随后 `initSchema()` 又跑一遍迁移：`doc_events` 刚被删，008 的结构自检判「脱节」→ 自愈重跑
   （实测每次重建固定 **15 个迁移**走自愈）。而 008 的 `up()` 是「DELETE + INSERT」的定义同步写法，
   表不 DROP 则序列不归零，`doc_states.id` 每重建一次长一整代。
   修法是把这些**定义表也加进重建清单**；顺带修掉「审批实例从不清理却按 id 指向 oc_orders」的存量隐患。
7. **测试把发票来源的明细当成入库单去联订单**（缺陷十七）—— 确定性做好后
   `test-purchase/food` 从「偶尔挂」变成 **100% 稳定挂**，一次定位：
   测试的联表缺 `si.source_type='receipt'`，发票 id 撞上同号入库单 id，
   凭空联出一批不在单上的订单并报成产品缺陷（产品侧 `ordersOfSettlement` 本来就带了该条件）。

**验证口径**（收尾新增，作为后续批次的固定门槛）：

- 三库各自 `reseed-all --force` 连跑两次，**忽略审计时间戳做全列比对，业务值 0 处差异**；
- 需要逐字节一致时（如 CI 比对）用 `GML_SEED_NOW=YYYY-MM-DDTHH:mm:ss` 固定灌数起点；
- 全量回归**连跑 3 轮**，不接受「重跑一次就过了」——把单跑必过、连跑游走的失败
  一律按确定性问题处理，先修成可复现再排查。

### 批次 D 实做要点（与原计划的差异）

1. **`WR`（报工单）撞码 —— 计划里的风险真的发生了。**
   原计划写「内核注册 MR（领料单）、WR（报工单）」，但 `WR` 早已被**「委外收货单」**占用。
   按原计划注册会**静默覆盖**，两个业务共用一个类型码。结合第三轮口径 G4 已定案
   **「生产不报工」**，最终**不注册独立报工类型**：`work_reports` 定位为**完工汇报明细** ——
   有单号、可追溯，但不推进状态、不进审批，作为「完工入库」的输入与凭证。
   内核类型 37 → **38**（只新增 MR 一个）。
   > 教训：新增类型之前必须**全库检索短码**。这条本来写在风险表里，这次是靠手工比对才发现的。

2. **`FLOW_PRODUCE` 由 5 步改 7 步，三处修正。**
   ① 新增 `bom` 节点（BOM 展开是生产相对于委外的独有前置，委外可只带供货目录，故不强制）；
   ② **领料与发料拆成两个节点** —— 原来两步共用 `'WM'`，导致**自制生产的领料在流程图上被画成「委外发料」**；
   ③ 质检节点由 `WR`（委外收货单）改为 `QCR`（报检单，模块 13）—— WR 是委外到货，与「生产完工后检验」不是一件事。

3. **展开口径比原计划多两条。**
   原计划只写「按 `用量 × (1 + 损耗率) × 生产数量` 汇总，替代料按替代组优先级取」。
   实做时补了两条：① 引入 **`base_qty` 基准批量**（`qty` 是「产出 base_qty 件的用量」而不是「每件用量」，
   否则整数场景会算出「每件 0.333 个」这种没法发料的结果）；② **替代料取舍必须可解释** ——
   同组内取「库存够的优先、其次优先级高」，并且**未选主料时一并返回原因与候选表**。
   按插入顺序取替代料在演示时看着对、在生产时不可解释。

4. **多做了「开工」这个前置动作。** `startOrder` 把订单推进到 `in_progress`，
   并规定**领料与完工入库都要求订单已开工**。理由：未开工就能领料 ⇒ 料挂在库外而单据上看不出异常；
   未开工就能完工入库 ⇒ 库里凭空多出一批货而没有对应的料出库，成本全落到「无材料成本」上。

5. **多做了七项自洽审计（`auditMfg`）**，其中第 ② 项「状态说已出库、流水里找不到」
   是本模块最严重的失效形态 —— 它不报错，只是账在悄悄错。

6. **修掉一个跨模块的真缺陷：成本层的数量精度低于库存层。**
   成本模块（模块 09）此前把所有**数量**都按 2 位小数收敛，而库存里的数量是 4 位小数
   （BOM 展开 / 领料 kg / 完工入库）。批次 D 是第一次往库存写入大量非整数数量，
   于是 `later.qty` 被砍掉末两位后与原始流水净额差 0.0038，
   **「残差恒为 0」这条唯一的账实自证手段在三库同时失效**。
   修法：`threeLayers` / `closePeriod` 快照 / 暂估在库量 / `recompute` 的**数量**统一 `round4`，
   **金额仍保持 `round2`（分）**。修完补了「三库 × 21 个期间逐月残差全为 0」的独立自检。

7. **`test-docflow` 的内核类型数断言写死 37** —— 新增 MR 后立刻挂掉。
   已更新为 38，并把「**为什么没有 WR**」写进断言文案（避免下一个人又去加一遍）。

8. **测试的审计故障注入原本是假绿。** `test-mfg` 的审计用例原本 `SET doc_no='__BROKEN__'`，
   而审计按 `doc_id` 找流水 ⇒ 断言**永远为绿**，等于这项检查不存在。改为 `SET doc_id = -1`。
   > 教训（已进框架文档）：凡「注入故障后必须变红」的用例，都要先确认「红」是由注入引起的。

9. **修掉一个 seed 缺陷：BOM 原料窗口不回绕。**
   `makeBom` 的 `slice(offset, offset+4)` 在排到后面时会只剩 1 种原料 ⇒ 静默返回 `null`
   ⇒ 该在制订单的成品变成「草稿样本」，而某些模式又把它全领满 ⇒ **全库再无「有待领量」的样本**，
   截图脚本的「按 BOM 自动装填」只能拍到兜底提示。
   修法：环形取窗 + `offset: i * 3`（让母件分散到原料池的不同位置）+ 失败记入 `out.bom_misses` 告警。

### 批次 E 实做要点（与原计划的差异）

原计划一行：`024 · 1 张新表 · 交班 → 缴款 → 长短款 → 日结上传`。实做比它多三块内容，
并有一处**有意删除**。

1. **新表从 1 张变 3 张，但真正的变化是「订单归属」这一列。**
   计划里只想到"把钱记下来"，实做时发现更根本的问题是**这段钱该算在谁头上**。
   `pos_orders` 原来没有任何字段指向班次，于是"这个班次的应收"只能用
   「同门店 + 同营业日 + 同收银员」去捞订单 —— 门店一天两班时两个班次会捞到**同一批订单**，
   现金应收直接翻倍，**并且不报任何错**。加 `pos_orders.shift_id` 之后，
   归属从一个"现算的口径"变成"一个确定的引用"。

2. **长短款口径被拆成三条**（详见设计稿 §1）：方向不给人选、必须按支付方式拆、
   备用金不参与。第二条是本轮最容易被忽略的：把现金差额与移动支付差额合成一个数，
   会让"店长去盘问收银员"和"总部查支付回调"两件完全不同的事挤在同一个数字里。

3. **加了两道计划里没有的门禁。**
   ① **超阈值差异门店不能自结**（`settings.pos_variance_limit`，默认 500）——
   超过就强制挂账交总部，校验在服务端；② **日结有未核款班次一票否决** ——
   未核款的班次没有实点现金，它的钱在账上没有位置，允许日结只会让当天的现金汇总
   天然不等于各段之和，而这种不等不报错、只表现为"对不上的那部分"。

4. **有意删除了 `PSF` 的 `close` 动作。**
   旧的"直接关班"等于绕过核款 —— 只要有一个入口能绕过，长短款就会有一半的单子
   不产生差异，而报表上看不出少了什么。现在唯一路径是 `declare → approve`。
   > 这类删除必须**同时把"它已不存在"写成断言**（`test-docflow` 已加），
   > 否则下次有人看到"不支持该动作"会当成漏注册，顺手加回来，而所有测试都不会变红。

5. **`up` 里补了一段历史班次单号回填，并同步推进了取号计数器。**
   回填很容易被当成"纯数据订正"，但它对 `doc_no_counters` 是一次外部写入；
   漏了不报错，只会让新号比旧号小，然后按单号取样的断言开始随机失败。

6. **`pos-seed.js` 整段替换了 `seed.js` 里的旧裸 INSERT 段。**
   旧段造出来的 5 个班次没有单号、没有支付方式明细、订单不带 `shift_id`，
   演示不了本模块任何一条口径。更麻烦的是它**抢在新 seed 之前跑**，
   把新 seed 的幂等检查架空（"已有班次"直接跳过）—— 表现为"新 seed 写了但不生效"。

7. **演示数据补了一组「未过账」的门店盘点单。**
   原样本每店只有一张"已过账"的盘点单，于是界面上「保存实盘数 / 过账调整库存」
   两个入口**永远处于隐藏态**：演示和截图看到的都是一个只能看的盘点页，
   与"这张单还没做完"长得一模一样，看不出到底是没做还是做完了。
   现在每店两张（已过账 + 只录了一行）。

8. **短款金额改成比例扣减 + 下限保护。** 演示数据原来写死"短款 6.5 / 12 元"，
   餐饮与服装线客单价小，减完变成负现金，**在美妆库上完全看不出来**，
   整库重建到第二个行业才炸 `COUNTED_NEGATIVE`。

9. **前端把「日结上传」并进了「交班核款」页签，而不是新增一个页签。**
   核款是日结的前提，分在两页会让"为什么日结按钮是灰的"变成要翻页才能回答的问题。
   老链接 `?tab=close` 保留重定向。底栏 8 个页签在手机宽度下放不下，改为**横向可滚**，
   而不是缩成谁也点不准的间隙。

10. **踩到契约检查的一个工具假设**：漂移检查脚本按 `?` 切查询串，
    所以请求路径的模板串里**不能写可选链**（`${a?.b}` 会被当成查询参数切掉），
    表现为"前端调用未登记在 OpenAPI"的假报警。改法是先把值落到局部变量。

11. **修掉一个测试残渣缺陷（本轮唯一一个"看着像产品 bug、其实是测试 bug"的失败）**：
    `test-pos2` 拿 `remark` 当清理锚点，而取消缴款会把 `remark` 覆盖成取消原因，
    于是残渣留在演示库里，把 `verify-seed` 的「缴款单金额 = 明细合计」搞成**永久失败**。
    修法：标记拼在原因前面 + 清理改前缀匹配；同时该条自检排除已取消的单子
    （取消 = 删明细 + 退班次金额，本来就该是"头上有金额、明细为空"）。
