## 一、缺陷的形状：**同一件事，两个入口，两种后果**

MCP 的工具**不是"薄封装"**，而是对同一批业务**又实现了一遍** ——
而且实现得更少。三处最典型的：

| 工具 | 原来的实现 | 少掉的后果 |
|---|---|---|
| `sales.cancel_order` | 一行 `UPDATE sales_orders SET status='cancelled'` | 库存占用没释放（那批货永远卖不出去）、授信没还（额度只减不增）、内核无留痕 |
| `approval.approve` | 一行 `UPDATE approval_instances SET status='approved', finished_at=…` | ① `finished_at` **列根本不存在**（干净库必报错）；② 不写 `approval_records`、不判"该不该你批"、不进级、**审批通过后不执行业务流转** |
| `pricing.update_price` | 直接 `UPDATE` 价格列 | 不留痕 —— 界面「价格变更历史」里看不到 Agent 改过价，而调价是 danger 级操作，事后追责只有这一条线索 |

**共同点**：走这些入口，接口 200、单子看起来也变了，但**账没跟着变**：
占用挂着、额度不减、审批记录空白、价格变更无痕。
它们不会报错，只会让"数据看起来对了、实际没动"。

## 二、MCP 复用领域服务的调用点清单（验收侧点名要求）

### 2.1 本批改掉的三处（从"平行实现"改为"调领域服务"）

|---|---|---|---|---|
| `sales.cancel_order` | `cancelOrder()` | **新增** `server/lib/sales-order.js` | 一行裸 `UPDATE` | 释放预留（`releaseForDoc`，按明细、不重拣）+ 内核流转（`advanceStatus`）+ 释放授信（`credit.js release`）+ 清 `credit_hold` |

改为调 `cancelOrder()` —— **入口可以有两个，实现只能有一份**。

### 2.3 仍是"读型直查"、**有意保留**的部分

列表与汇总类工具（`inventory.list_*` / `purchase.list_orders` / `sales.list_orders` /
`report.*` / `order.trace_document`）走的是**只读查询**，且已统一施加组织范围过滤。
它们**不需要**经过领域服务 —— 领域服务里没有"另一份列表实现"，
而这些查询本身就是"把库里的数如实读出来"。
判断标准：**这个工具有没有"写"或"改变状态"的语义**？有就必须走领域服务。

## 三、"Agent 凭什么代替人签字"

`approval.approve` 的描述写的是"**等同于代表人签字**"。而 `decideApproval()` 要求
`actor.id` 是一个**真实用户**（`canApproveStep` 拿它去查 `users` 表，落 `approval_records.approver_id`）。

所以必须先回答这个设计问题，否则修法只能是"绕过审批引擎自己改状态"——也就是原来那个错。

**答案：它不代替，它转呈。**

MCP 的 danger 工具本来就必须经人工二次确认。那就把**"点确认的那个人"**作为签字人：

1. 迁移 `029` 给 `mcp_confirmations` 加 `confirmed_by_id`（原来只有 `confirmed_by` 名字字符串，
   名字不能查权限、也不能落 `approver_id`）；
2. `POST /mcp/confirmations/:token/approve` 写入 `confirmed_by_id = req.user.uid`；
3. `tools/call` 执行时把 `ctx.confirmedBy = { id, name }` 交给工具；
4. `approval.approve` 用它当 actor；**没有确认人就直接 403 `APPROVAL_ACTOR_REQUIRED`** ——
   宁可拒绝，也不允许"没有签字人"的审批。

这与第 1 批的**禁止自批**是同一件事的两面：
那一条保证"确认人不是申请人"，这一条保证"**审批的签字人就是确认人**"。

顺带解决了一个可验证性问题：`approval_records.approver_id` 从此有值，
审批流里能查出"这一级是谁签的字"。

## 四、顺带修掉的一个真实陷阱（写这类代码时必踩）

在 `mcp/tools.js` 里用 HTTP 层的金额校验器时：

```js
const chk = numAmount(args[k], k)   // → { ok, value } 或 { ok:false, message }
params.push(chk)                    // ✗ 错：把"校验结果对象"当数字传给了 SQL
```

better-sqlite3 会把它当成**命名参数集合**，报
`Too few parameter values were provided` ——
**完全看不出"其实是金额校验没过"**。

已收口成一个口子 `mustNum(chk)`：要么取值、要么抛带业务码的 400。
教训：**校验器返回"结果对象"时，必须在同一个地方把它解包**，
否则"校验失败"会以另一种完全无关的错误形态出现。

### 5.1 "变红过"的证据

把 `server/mcp/tools.js` 换回修复前那一版再跑 G16 → **9 条变红**：

```
✗ 库存占用被释放           → 残留 1
✗ 授信占用标志被清零        → credit_hold=123.45
✗ 走了内核流转（doc_events） 
✗ 调价写入价格变更留痕
✗ 留痕标注了来源与操作人
✗ MCP 审批通过 → 成功       → {"error":"SQLITE_ERROR","message":"no such column: finished_at"}
✗ 写入了审批记录
✗ 审批记录的签字人 = 确认人   → approver_id=undefined
✗ 按级次进级               → current_step 仍是 1
（9 条红 / 通过 272）
```

其中 `no such column: finished_at` 正是验收侧 §13.2 那条 **A19 后半**的原文复现。

### 5.2 用例自己踩到的一个坑（已修）

16a 第一版造的占用用的是"任意一个有库存的 SKU"，而取消时是按**订单明细逐行**释放的
（`releaseForDoc` 按 SKU 匹配）⇒ 释放不掉，断言红。
已改为**必须选订单行里真的有的 SKU** ——
这条正好说明"释放"是按明细走的，不是"把这单名下的都清了"。

|---|---|
| `sales.cancel_order` | 现在会释放库存占用与授信（此前只改状态）—— 是**修复**，但会让"以前能作废、作废后占用仍挂着"的历史数据出现差异（不回补） |
