## 一、一句话

**`settings` 从模块 20 起就在长，而写它的那条代码什么都不做** ——
不改值校验、不留痕、没有界面、也不在接口文档里。这一批把它变成一个有定义、有约束、
**可重放**的配置系统。

```text
改前：INSERT INTO settings (key,value,updated_at) VALUES (?,?,...)
        ON CONFLICT(key) DO UPDATE SET value=excluded.value, ...
      （任何字符串都能当 key；改完没有任何痕迹；前端没有页面；端点不在契约里）

改后：writeSetting(db, { key, value, reason, actor })
      ├─ 键未登记        → 400 SETTING_UNKNOWN
      ├─ 值不满足值域    → 400 SETTING_VALUE_INVALID
      ├─ 危险项没写理由  → 400 SETTING_REASON_REQUIRED
      └─ 同事务写一条只追加的 setting_audit_log
     读取：readSetting(db, key) —— 转型 + 值域回落，唯一读取点
```

## 二、摸底查出的四个真实缺口（这一批真正的起点）

本来以为工作量是"加一张日志表"。读完全部读取点之后发现**不是** ——
只加日志表是没用的，一天之后它就会退化成"只有界面点过的那些键才有历史"的表。

### 缺口 ①：三个"幽灵配置"

| 键 | 读取点 | 默认值 | 库里有没有 |
|---|---|---|---|
| `credit.overdue_block_days` | `lib/credit.js` | 30 | ❌ |
| `quote.approval_amount` | `lib/quote.js` | 200000 | ❌ |
| `quote.valid_days` | `lib/quote.js` | 30 | ❌ |

三库的 `settings` 表各 **13** 个键，全是不带点的下划线命名 ——
这三个带点号的键**一个都不在库里**，从来没人给它们落过位。
它们走的是各模块自己的 `setting(db, key, fallback)`，**读不到就永远用 fallback**。

于是功能**看起来可配、实际不可配**：把 `quote.valid_days` 改成 7 天，
不报错、不警告、**什么都不会发生**。而"报价有效期"是硬约束（过期不能转单，
`QUOTE_EXPIRED`），"我明明配过"于是会变成一个查不出来的争议。

### 缺口 ②：同一个键，四处各写一遍默认值

| 文件 | 私有函数 | 对"读到了但值不合法"的处理 |
|---|---|---|
| `lib/credit.js` | `setting(db,key,fallback)` | 连数值都不转，原样返回字符串 |
| `lib/quote.js` | `setting(db,key,fallback)` | 要求 `Number.isFinite(v) && v > 0` |
| `lib/member.js` | `settingNum(db,key,def)` | 不要求；在**另一个函数**里单独兜"配成 0 会除零" |
| `lib/pos2.js` | 内联 try/catch | 要求 `n >= 0` |

再加上 `closing.js` / `annual.js` / `report.js` / `accounting.js` / `invoice.js` /
`order-center.js` 六个模块**各写一句 SQL** 直读 —— 同一个键被**七套规则**解释。
这就是"同一份判据有两个实现"的老账，平时不响，只在两类时刻现形：
**值域收紧时**（改了一处，另一处还按老口径放行）与**值非法时**
（一处抛出、一处静默回落、一处把字符串当数字算成 `NaN`，三种行为都"看起来正常"）。

### 缺口 ③：`settings` 是一个没有约束的口袋，而且前端根本没有设置页

- `PUT /api/meta/settings` 是裸 upsert，**任何字符串都能当 key 写进去**；
- 这组端点存在了很久，但**前端没有任何页面调用**（全项目 grep 只命中一处无关解构）
  —— 配置只能靠**直连数据库**或**裸调 API** 改；
- 它**从未登记进契约**（`openapi.js` 里只有 `/meta/health` 与 `/meta/dict`）。

合起来是一个"能改会计政策、但不留痕、没有界面、也不在接口文档里"的口子。

### 缺口 ④：一个"登记了但没人读"的配置

`ar_prepay_auto`（预收是否自动抵新应收）只在迁移 020 与 `docs/` 的表格里出现过，
代码里**没有读取点**。它被登记进 `SETTING_RULES` 并标 `wired: false`，
让"登记了但还没接上"在界面上看得出来 ——
与 `lib/period-audit.js` 的 `meta()` 给动作标 `implemented` 同一条理由。

## 三、五条口径

### 口径 1：配置的「定义」只有一个出处

`SETTING_RULES`（`server/lib/settings.js`）声明**全部 16 个键**的：

| 字段 | 含义 |
|---|---|
| `group` | 界面分组（分组清单也在同一文件，界面不自己分类） |
| `label` | 中文名 |
| `type` | `text` / `subject` / `enum` / `int` / `number` / `bool` —— **决定值的形态与校验规则** |
| `default` | 库里缺这个键时读出什么，也是 `reset` 的目标值 |
| `is_danger` | 改动是否必须写理由 |
| `enum` / `min` / `max` / `gt` | 值域 |
| `wired` | 当前代码里**有读取点**吗 |
| `impact` | 一句话说明"改了会发生什么"（直接给界面显示） |

**未登记的键在读写两侧都拒绝**（`SETTING_UNKNOWN`）。这比"允许写任意键"更严，
换来一条可验证的不变量：**库里的键集合 == 登记表里的键集合**。

16 个键按域分成 7 组：

| 组 | 键 |
|---|---|
| 会计政策 | `closing_profit_subject` · `annual_retained_subject` · `voucher_default_tax_rate` |
| 应收口径 | `ar_source_of_truth` · `ar_oc_enabled` · `ar_prepay_auto`（登记待接） |
| 促销与会员 | `promo_points_per_yuan` · `promo_points_per_yuan_deduct` · `promo_points_deduct_max` · `member_upgrade_auto` |
| 门店 | `pos_variance_limit` |
| 销售报价 | `quote.approval_amount` · `quote.valid_days` |
| 信用控制 | `credit.overdue_block_days` |
| 运维 | `backup_dir` · `backup_keep` |

**危险配置 6 个**（改动必须写理由）：期末结转目标科目 · 年结留存科目 · 默认税率 ·
应收生成口径 · 订货单收货并入应收 · 交班长短款容忍阈值。

### 口径 2：读取点唯一

```js
readSetting(db, key)   // 转型（bool→boolean / int→number）+ 值域校验 + 非法值时**回落默认值**
```

读路径**不抛错**（一个配错的键不该让整个模块在运行时炸），
但"库里现在这个值不合法"这件事由探针 `SETTING_VALUE_INVALID` 报出来。

### 口径 3：写入点唯一，且与改值同事务

```js
writeSetting(db, { key, value, reason, actor })  // 唯一的配置写入点
resetSetting(db, { key, reason, actor })         // 恢复默认值
logSettingChange(db, {...})                      // 唯一的 INSERT（日志），三条当场断言
```

`logSettingChange` 的三条当场断言（不是文档里的建议）：

1. **必须在事务里** → `AUDIT_OUTSIDE_TX`
2. **动作名必须认识** → `SETTING_AUDIT_UNKNOWN_ACTION`
3. **危险项必须写理由**（`baseline` 除外 —— 它不是谁的动作）→ `SETTING_REASON_REQUIRED`

**值没变时返回 `changed: false` 且不写日志** —— "点了一次保存但没改"不是一次变更，
写进历史只会让日志变成一串重复值。这不是错误（界面上"确认当前值"是正常操作），
但它必须如实回答。

### 口径 4：变更可重放

`settings` 表的行是**现状指针**，`setting_audit_log` 是**历史事实**（只追加）。
两者的关系是一条不变量：

```text
从空状态开始，按 id 顺序应用每一条日志，得到的必须是今天库里的样子。
```

两条路径的**出处不同**（现状来自各处的 upsert，历史来自唯一写入点），
所以它抓得到"改了没记""记了没改"。

盲区要划清：它抓不到"既没改也没记" —— 而那种情况在配置上**不存在**
（配置没有"状态"，只有值），所以不需要像期间那样再补一条"凭证表"式的第三路径。

三种动作的效果都是"把 key 设成 `value_after`"，但语义必须分开：

| 动作 | 回答的问题 |
|---|---|
| `baseline` | "这个键在我们开始记日志之前是什么"（**不是任何人的动作**，`actor_source='system'`） |
| `set` | "谁把它改成了什么" |
| `reset` | "谁把它恢复成了默认值"（与"手工填了一个恰好等于默认值的值"是两件事） |

### 口径 5：初始化入口是运行时的 `ensureSettings`，不是迁移

迁移 038 **只建表**，不碰 `settings`。原因：

- 期间的状态是被**动作**驱动的（关账/结转/年结），迁移只能"按现状补记"，所以 037 在迁移里回填基线；
- **配置没有驱动者** —— 一个库建起来的那一刻，配置就该是完整的。

把初始化写成运行时的一个入口，好处是**升级路径与重建路径走同一条代码**：

| 路径 | 过程 |
|---|---|
| 升级既有库 | 迁移建表 → 服务启动 `ensureSettings` → 补齐缺失键 + 补基线 |
| 整库重建 | `resetDatabase()` 把 `settings` 与 `setting_audit_log` 一起清掉（两者都在 `seed.js` 的 `TABLES` 里）→ `ensureSettings` 重新补齐 |

两条路径的产物完全一致，这正是 `docs/evidence/` 里那两个指纹要证明的事。

**另一个好处**：迁移里**不需要写一份键清单**。迁移是 CommonJS、定义表是 ESM，
在迁移里再抄一份 `[key, default]` 数组就是**第二份定义**。

## 四、数据结构：`setting_audit_log`

```text
CREATE TABLE IF NOT EXISTS setting_audit_log (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  key           TEXT NOT NULL,               -- 配置键（不做外键：历史必须留下）
  action        TEXT NOT NULL,               -- baseline / set / reset
  action_label  TEXT NOT NULL,               -- 动作的中文名（当时的措辞，落库即冻结）
  group_key     TEXT NOT NULL,               -- 分组（当时的，用于按域筛选历史）
  value_before  TEXT,                        -- 改动前（字符串，与 settings.value 同形）
  value_after   TEXT,                        -- 改动后
  is_danger     INTEGER NOT NULL DEFAULT 0,  -- 当时是否为危险配置
  reason        TEXT,                        -- 危险配置必填
  actor_id      INTEGER,
  actor_name    TEXT,
  actor_source  TEXT NOT NULL DEFAULT 'web', -- web / mcp / script / system / migration
  detail        TEXT,                        -- JSON 快照（人读与排障；判据不读它）
  created_at    TEXT NOT NULL DEFAULT (datetime('now','localtime'))
)
```

三个索引：`(key, id)` 按配置查历史 · `(created_at)` 按时间查 · `(action, is_danger)` 查"哪些会计政策被改过、理由写了没"。

**为什么 `action_label` / `group_key` / `is_danger` 要冗余落库**：
日志是不可变事实，它的措辞与分类不该随后续代码改名而变 ——
改名之后，去年那条日志会突然换一个说法。而"这次改动当时该不该写理由"是**历史问题**，
不能拿今天的 `is_danger` 去重判。

**为什么不加权限点**：`GET/PUT /settings` 本来就限 `admin`，日志给的是同一个信息集合的**历史**，
不是新的信息类别。凭空多一个"配置审计查看权限"只会让权限表越来越长而没人维护
（与批次 Q 不给期间日志加权限点、批次 N 不给报表导出加权限点同源）。

## 六、探针七条（`auditSettingTrail`）

**全库扫描**，不是"只查界面上正在看的那几条"。

| # | code | 查什么 |
|---|---|---|
| ① | `SETTING_AUDIT_UNKNOWN_ACTION` | 日志里有代码不认识的动作 |
| ② | `SETTING_AUDIT_REASON_REQUIRED` | 危险配置的变更没写理由 |
| ③ | `SETTING_KEY_UNKNOWN` | **库里有未登记的键**（"口袋"的反向） |
| ④ | `SETTING_AUDIT_ORPHAN` | 日志里有已不在登记表里的键 |
| ⑤ | `SETTING_KEY_MISSING` | **登记了但库里没有的键**（幽灵配置的方向） |
| ⑥ | `SETTING_VALUE_INVALID` | 现状值不满足值域（有人直接改库，或值域在本批收紧了） |
| ⑦ | `SETTING_AUDIT_DESYNC` | 重放 ≠ 现状 |

③⑤ 两个方向都查，才叫"库里的键集合 == 登记表里的键集合"。

探针接在 **`auditReport` 第 ⑪ 条**上，于是**关账前置会检查它** ——
配置被绕过写入点改掉，会让结转走到别处去，这与"账没留痕"是同一类问题。

**这一条不做初始化**（不调 `ensureSettings`）：`auditReport` 是只读自证，
在"检查"里写库会让"没配齐"这件事被检查本身掩盖掉。

## 九、边界（如实记）

- **保留原名不改**：`credit.overdue_block_days` / `quote.approval_amount` / `quote.valid_days`
  带点号，与其余键的下划线风格不一致。改名会**改变行为**（如果谁的库里手工插过那个键，
  改名之后它就失效了）—— 命名不统一是**如实记的代价**，不在这批消化；
- **`ar_prepay_auto` 登记但无读取点**（`wired: false`）：界面会显示"登记待接：当前代码无读取点"，
  改动暂不生效。这是**有意**的（让"没接上"看得出来，而不是让那个键继续躺在迁移里）；
- **只追加，没有删除与归档**：日志没有 UPDATE / DELETE 路径，也没有"导出/归档"入口
  （口径未定：给谁、按什么粒度、保留多久）；
- **`detail` 是 JSON 文本、不做 schema 校验**：它只服务人读与排障，**任何判据都不读它**；
- **`created_at` 精度只到秒**，顺序的唯一真值是 `id`（与期间日志同一条）；
- **`vite build` 在沙箱内跑会失败**（读不到 `public/enter.html`）：环境限制，不是代码问题，
  单独以非沙箱模式跑通过；
- **`test-guards` 的断言数是数据驱动的**（近十处"按库内数据行循环"）：
  本批基线 368/368/369 是"干净重建后"的口径，**跨批比数字必须同时说明库状态**；
- **未做**：配置的"按域授权"（谁能改会计政策、谁只能改促销参数）—— 现在一律限 `admin`；
  配置变更的**审批流**（改会计政策要不要走审批）—— 现在只要求写理由；
  配置的**生效时间**（预约生效 / 定时切换）—— 现在改完立即生效。
