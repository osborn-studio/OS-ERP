## 三、阻断缺陷清单

### D1 🔴 销售退货：超退无上限、成本取客户端价、应收不闭环

**实测（`audit-erp-results.json` 第 5 条）**

| 观察项 | 实测值 |
|---|---|
| 已发数量 | **94** |
| 本次退货数量 | **189**（= 94×2+1） |
| HTTP 语义 | **200 / code 0 / success true** |
| 入库 `unit_cost` | **9999**（直接取请求体 `price`） |
| 原 SO 应收 `amount` | 退货前 **13355.52** → 退货后 **13355.52**（**未变**） |
| `allocated_amount` | 前 0 → 后 0 |

**根因（`server/routes/sales.js:599-656`）**

1. **无来源行、无累计退量上限**：`POST /returns` 只把 `order_id` 存进表头（`:622`），**明细不绑 `sales_order_items`**，
   也不查「该订单行已发多少 / 已退多少」，`qty <= 0` 之外无任何校验（`:629`）。
2. **退货入库成本直接取客户端 `price`**：`unitCost: price`（`:641`），其中 `price = Number(it.price || 0)`（`:630`）。
   ⇒ 调用方传 `price=9999` 即把 9999 写进库存成本层，**污染后续出库成本与三层残差**。
3. **应收完全未动**：函数体内**没有任何 `ar_documents` / 退款/红字应收的逻辑**，`advanceStatus(action:'return')`（`:649`）只推单据状态。

**修复要求**
- 退货明细必须**绑来源行**（`sales_order_items.id`），入库前校验 `Σ本次退量 + Σ历史已退量 ≤ shipped_qty`；
  无来源行的"无单退货"必须走独立单据类型且**不得**参与来源追溯（显式标注）。
- 退货入库 `unit_cost` 必须**追溯来源出库成本**（取该订单行对应出库批次的成本口径），**不得采信客户端传值**。
- 退货必须产生**应收后果**：按退货金额生成红字应收 / 冲减原应收（走既有 `ar_documents` + 核销口径），
  退款走 `收款单/付款单` 反向流程，全程留痕；不得只改状态。

**回归要求**：三库 × {超退必拒 · 多次部分退货累计不超发 · 退货成本 ≠ 客户端价 · 退货后应收金额按退货额变动 · 幂等重放不重复冲减}。

### D2 🔴 越权读：门店详情越权 + 经销商可读全部采购单

**实测（`audit-erp-results.json` 第 1、2 条）**

| 用例 | 结果 |
|---|---|
| 门店 1 账号 GET 门店 4 的销售订单详情 | **200**，返回 `store_id = 4` |
| dealer 账号 GET 采购订单列表 | **200**，`total = 41`（全部采购单） |

**根因**

- 销售订单**列表**有数据范围（`so` 维度走 `scopeFilter`，`server/middleware/auth.js:67-72` 已支持 store / dealer 两个分支），
  但**详情接口手写判断且只判 dealer**：`server/routes/sales.js:141` 仅
  `if (req.user.role === 'dealer' && ...)` ⇒ **store 分支缺失**。
- 采购订单列表与详情**既无功能权限门、也无数据范围**：`server/routes/purchase.js:57`（列表）与 `:93`（详情）
  都只有 `requireAuth`，没有 `requireRole` / `requirePerm`，也没有 `scopeFilter`。

**修复要求**
- 详情接口与列表接口的**授权判据必须同源**：详情不得手写第二套判断。建议抽 `assertCanReadOrder(req, order)`，
  与 `scopeFilter` 共用同一份规则（含 store、dealer 两分支），避免"列表挡得住、详情挡不住"。
- **列表 / 详情 / 导出三条路径必须一致**（导出最易漏，需一并覆盖）。
- 采购域补功能权限门 + 数据范围；对 dealer / store 这类外部主体，采购单应默认**不可见**（除非显式授予）。

**回归要求**：三库 × {跨门店详情 403 · 跨经销商详情 403 · dealer 列表为 0 或仅授权范围 · 导出同样受限}。
**建议做法**：用"遍历全部角色 × 全部读接口"的矩阵式用例，而不是逐个接口手写 —— 本次两条都是"漏了一个分支/一个接口"。

### D3 🔴 负价：销售与采购均接受 `price = -5`，产生负金额单据

**实测（`audit-erp-results.json` 第 3、4 条）**

| 用例 | 结果 |
|---|---|
| `POST /purchase/orders`，`price = -5` | **200**，`total_amount = -5` |
| `POST /sales/orders`，`price = -5` | **200**，`receivable_amount = -5` |

**根因**

- 采购：`server/routes/purchase.js:122` 只校验 `!(Number(it.qty) > 0)`，**对 `price` 无任何下界校验**；
  `:145` `const price = Number(it.price || 0)` 直接入库（`:141` / `:186` 两处写入路径同病）。
- 销售：创建订单同样无价格下界校验（`price` 直接进 `receivable_amount`）。

**修复要求**
- 金额类入参统一**下界校验**（`price >= 0`，`qty > 0`），并拒绝 `NaN` / 非有限数 / 超精度值。
- 建议把校验收敛到**一处共享校验器**（数量 4 位小数、金额 2 位小数、非负），
  在 `routes` 与 MCP 工具两条入口共用 —— 否则又是一个"漏一个入口"。
- 单据落库前加**总额非负**断言（负数单据应仅允许由红冲等特定单据类型产生，且类型受限）。

**回归要求**：三库 × {负价拒 · 零价按业务规则处理并留痕 · `NaN`/`Infinity`/字符串数字拒 · 金额精度 2 位 · 数量精度 4 位}。

| 4d | 令牌白名单含 `master.search_products`、黑名单含 `inventory.stock_alert` | `tools/call` 被拒 ✓，但 **`resources/read gml://inventory/alert` 照样返回数据** |

| 4b | `server/mcp/server.js:322` | 只比对 `conf.tool_name !== tool.name`，**不比对 `conf.args_json` 与本次 `args`，也不比对 `conf.token_id` 与调用方令牌** |

| 4d | `server/mcp/server.js:171-190` | `resources/read` **完全不走工具白/黑名单**，直接 `TOOL_MAP.get(toolName).handler(...)`；且 `gml://meta/params` 连映射表都不经（`:178`）直读 `inv_params` |

**修复要求**
- **4a**：审批接口必须过权限门（建议加独立权限点，且**不得**用 `viewer` 可持有的角色）；并禁止**申请人本人**批准自己的确认单。
- **4b**：确认单必须绑定**三元组**（`tool_name` + `args` 指纹 + `token_id`），任一不符即拒；执行时用**确认单里存的参数**，而非本次请求的参数。
- **4c**：置 `used` 必须用**实际命中的那个 `confirmToken` 变量**（`args.confirm_token || req.headers['x-confirm-token']`），
  并加**原子条件更新**（`UPDATE ... SET status='used' WHERE confirm_token=? AND status='confirmed'`，按 `changes` 判定），
  防止并发双花。
- **4d**：`resources/read` 必须**复用 `tools/call` 的同一套白/黑名单与 scope 判定**；资源到工具的映射要走同一个过滤函数。
- **4e**：幂等唯一键应为 **`(token_id, tool_name, idempotency_key)` 三元组**，
  **`args_hash` 不进唯一键，而是作为一列同存、执行前比对**。判定规则：
  - 同键 **且** `args_hash` 相同 ⇒ 正常幂等命中，返回首次结果；
  - 同键 **但** `args_hash` 不同 ⇒ **409 冲突，拒绝执行，也不得返回旧结果**；
  - 唯一键里带 `token_id` ⇒ 另一令牌同 key 不再互相命中（现状 4e 就是因为查询只用 `idempotency_key`）。

  > ⚠️ **为什么不能把 `args_hash` 放进唯一键**（本条为 v1.1 订正）：
  > 一旦 `args_hash` 成为唯一键的一部分，"换个载荷"就变成了**一个全新的键** ⇒ 约束不再拦它 ⇒
  > 等于**允许换载荷再执行一次**，幂等键从"防重放"退化成"防完全相同"。
  > 正确语义是：**键标识"这一次意图"，指纹用于校验"意图有没有被换掉"** —— 键相同就必须是同一件事，换了就是冲突。

**回归要求**：三库 × {viewer 批准 403 · 申请人自批 403 · 改参/换令牌执行 409 · header 重放第二次拒 · 并发双花仅一次生效 · resources 与 tools 判定一致 · 幂等跨令牌/跨载荷不命中}。

**根因**

| # | 文件:行 | 问题 |
|---|---|---|
| 5a | `server/mcp/tools.js:260 / 285 / 547 / 582` 等 | 写接口一律 `ownerOrgId: args.owner_org_id ?? ctx.orgId ?? null` —— **显式传值即采信**，不校验其是否落在令牌的组织范围内。`orgFilter()` **只用于读接口**（`:102 / :187 / :315 / :339 / :480`），写接口没有对应的范围校验 |
| 5b | `server/mcp/tools.js:757` | `UPDATE sales_orders SET status='cancelled' ...` —— **裸 SQL**，不经 `advanceStatus` / 单据内核，不判当前状态是否允许作废（连"已发货"也放行） |
| 5c | `server/mcp/tools.js:781` | `UPDATE approval_instances SET status='approved' ...` —— **裸 SQL**，不经 `server/lib/approval.js`，绕过审批人校验、层级推进、留痕（**B 静态定位**） |

**修复要求（这条最重要：不要另起简化业务逻辑）**
- **MCP 工具必须复用领域服务**：作废走 `advanceStatus` / 单据内核的状态机；审批走 `lib/approval.js` 的审批服务；
  库存出入库继续走 `applyStockIn/Out`（这条本来就对，应作为范式）。
  **MCP 只是"另一个入口"，不是"另一套业务逻辑"。**
- **写路径必须与读路径用同一份组织范围校验**：把 `orgFilter` 的思路反向做成 `assertOrgInScope(ctx, ownerOrgId)`，
