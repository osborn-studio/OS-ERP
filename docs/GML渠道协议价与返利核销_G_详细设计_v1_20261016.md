## 一、一句话

渠道管理此前的形态是「**配置齐全，账上无后果**」：

| 已有 | 缺什么 |
|---|---|
| `rebate_policies` 六种返点政策 + `dealer_rebates` 逐期核算 | `paid` 只是一个状态字 —— **它不改任何应收**，把返利标成"已发放"之后账上分毫未动 |
| 四维价格组（渠道 × 门店类型 × 经销商等级 × 区域） | 表达的是"**这一类**客户的价"，表达不了"**这一家**谈下来的价" |
| `routes/dealers.js` 里的一份返点算法 | 新增的批量计提没有 HTTP 请求可依附 ⇒ 必然复制第二份，出现"试算说 12000、计提算成 11800" |

本批补齐两件事：**协议价接进取价链**、**返利核销产生真实账务后果**；并把返利算法收成唯一实现。

## 二、协议价：为什么必须独立成表

### 2.1 它和「价格组」不是一回事

| 维度 | 价格组 `price_groups` | 协议价 `price_agreements` |
|---|---|---|
| 主体 | `dealer_level`（金牌 / 银牌这一档） | `dealer_id`（**具体某一家**） |
| 目标 | 逐 SKU 维护在 `price_group_items` | `sku` / `category` / `all` |
| 时间 | `effect_from` / `effect_to` | **合同周期** + **起订量** `min_qty` |
| 形态 | 只存单价 | 单价 **或** 折扣（万分比 `discount_bp`） |
| 裁决 | 匹配维度多者优先 → `priority` | `priority` → `id` |

硬要用 `dealer_level` 表达"某一家"，等于**把合同的私有性降级成群组规则**：
一旦某家要单独议价，就得给它造一个等级，而等级是**共享维度** —— 会影响所有同档客户，且没人会发现。

### 2.2 在取价链上的位置（顺序本身就是一个口径）

```
促销价  >  协议价  >  会员价  >  价格组价  >  标准零售价
```

- 放在**促销价之后**：促销是"这一档期全渠道投放的价"，时间性意图更强；
- 放在**会员价之前**：**合同 > 通用权益** —— 会员价是"注册即得"的公开权益，
  协议价是逐字谈出来的，同一件货上后者必须赢。

这个顺序**只在 `lib/pricing.js` 里实现一次**；`lib/agreement.js` 只回答"命中哪一条协议"，
不参与"它排第几"。基准价由调用方给（一般是标准零售价），协议层**不自己查价** ——
否则它就成了第二处取价。

> 开关方式：探测 `sqlite_master` 里 `price_agreements` **表是否存在**，
> 不存在就**静默跳过**这一段。取价引擎是全系统最热的调用点之一，
> 任何一个"新表还没建"都不该让它整体不可用。

### 2.3 命中判定四项全中

| 项 | 判据 |
|---|---|
| 主体 | `dealer_id` 相等（**不是等级**） |
| 目标 | `sku` 命中 SKU / `category` 命中该 SKU 所属品类（**品类回溯**）/ `all` 通吃 |
| 周期 | `effect_from <= day <= effect_to`（空 = 不限） |
| 起订量 | `qty >= min_qty` |

四条都不命中就继续往下走取价链，**不报错**；但下面两种情况**必须报错**：

| 情况 | 报错 | 为什么不静默处理 |
|---|---|---|
| 折扣型协议**没有基准价** | `AGREEMENT_BASE_PRICE_REQUIRED` | 静默跳过会让"这份协议明明在有效期内却不生效"，且不留任何痕迹 |
| 折算价**低于最低限价** `price_min` | `AGREEMENT_BELOW_FLOOR` | 静默抬到限价会让"谈的 88 折"变成"实际 6 折"，**双方都不知道** |

### 2.4 返回可解释的裁决

命中后返回 `rule:'agreement'` + `agreementId/Code/Name` + `basePrice` + 轨迹字符串
（`协议价「华东区金标客户·定点协议价」命中（指定 SKU）`），界面的「取价解释」面板直接展示
`explainPrice()` 的 `trace` 串联，能逐环回答"为什么是这个价"。

## 三、返利核销：三条硬口径

### 3.1 核销才有后果，`paid` 的语义被重定义为「已核销」

| 状态 | 含义 | 能否被计提覆盖 |
|---|---|---|
| `pending` | 已核算、未确认 | **能**（重算只更新它） |
| `confirmed` | 已确认入账 | 不能 |
| `paid` | **已核销**（必须挂核销单 `settlement_id`） | 不能 |

- 计提 `accrueRebates` **只更新 `pending`**，遇到非 `pending` 一律跳过并**如实报出**
  （`skipped: [{ reason: 'locked:confirmed' }]`）—— "为什么这次计提没动它"要答得上；
- `confirmRebate` **不做跳级**：非 `pending` 调用报 `REBATE_NOT_PENDING`；
- **存量语义迁移**：旧库里 `paid AND settlement_id IS NULL` 的行是"人工打了已发放的标记但账没动"，
  在迁移 `031` 里**降级为 `confirmed`**（并把这个回填写进 def 指纹，见 §4.3）。

### 3.2 核销 = 一个事务里的四件事

```
settleRebates(dealerId, period, idempotencyKey?)
  ① 汇总该期 confirmed 的返利 —— 一笔都没有就**报错**（NO_CONFIRMED_REBATE，不生成空单）
  ② 冲应收：调 ar.offsetAr（**冲减应收的唯一实现**）
  ③ 写核销单 rebate_settlements + 明细 rebate_settlement_items
  ④ 回写每笔返利：status='paid' + settlement_id + ar_offset_amount + settled_at
```

三条不可让步的口径：

1. **只减少 `ar_documents.amount`，不生成负数应收** —— 与销售退货 D1 完全一致；
2. **冲不下的部分如实登记 `unoffset_amount`**，不静默吞掉；
3. **明细的冲减按各笔返利占比分摊，末行兜底消尾差** —— 账龄与客户汇总都按合计比，
   不能留一个"合计对不上"的差额。

### 3.3 幂等：`idempotency_key` 非空唯一

首次核销就带键，同键重放**返回首次那张单、不再冲一次应收**；
唯一索引 `idx_rebate_settlement_idem`（部分唯一，`WHERE idempotency_key IS NOT NULL`）兜住并发。

> 测试用例上的坑：**只在重放时带键是测不出幂等的** —— 那时找不到键就会被当成新的一次核销，
> 而返利已经不是 `confirmed` 了，于是报 `NO_CONFIRMED_REBATE`，看起来像"幂等做错了"，
> 其实是用例自己没给键。

### 3.4 冲减应收的唯一实现

`lib/ar.js` 的 `offsetAr(db, { arId?, subjectType?, subjectId?, amount, reason })` 是本项目
**唯一**的应收冲减实现，三个调用方共用：

| 调用方 | 用法 |
|---|---|
| 销售退货（D1，`lib/returns.js`） | 显式给 `arId`（退的是**那张单**的应收） |
| 返利核销（G，`lib/rebate.js`） | 只给主体 —— 返利不属于任何一张具体订单，是**对这个客户的债权**，按 `COALESCE(due_date, biz_date), id` 分摊 |
| 采购付款 / 其它 | 同上两式 |

`lib/returns.js` 里原本那份私有实现**已删除**，改为调用它。

## 四、迁移 `031` 清单

### 4.1 新表

| 表 | 关键列 |
|---|---|
| `price_agreements` | `code`(UNIQUE) / `dealer_id` / `target_type` / `target_id` / `price_type` / `price` / `discount_bp` / `min_qty` / `effect_from` / `effect_to` / `priority` / `status` |
| `rebate_settlements` | `doc_no` / `dealer_id` / `period` / `rebate_count` / `total_amount` / `ar_offset_amount` / `unoffset_amount` / `status` / `idempotency_key` |
| `rebate_settlement_items` | `settlement_id` / `rebate_id` / `policy_id` / `amount` / `ar_offset_amount` |

### 4.2 加列（每一列都在回答一个此前答不出的问题）

| 列 | 回答的问题 |
|---|---|
| `dealer_rebates.settlement_id` | 这笔返利被哪张核销单冲掉了（可反查） |
| `dealer_rebates.ar_offset_amount` | 其中**真正冲了应收**多少（"核销有后果"的证据） |
| `dealer_rebates.settled_at` | 什么时候冲的 |
| `dealer_rebates.commission_basis` | 计返基数的**口径说明**（快照，政策后来改了也不影响历史） |

5 个索引，含部分唯一 `idx_rebate_settlement_idem`。

### 4.3 存量回填与 def 指纹

```sql
UPDATE dealer_rebates SET status='confirmed' WHERE status='paid' AND settlement_id IS NULL;
```

这条回填**必须写进迁移的 def 指纹**（`backfills: ['downgrade_legacy_paid_rebate']`）：

> 迁移框架是按"定义指纹变了才重跑"来执行的。只改 `up()` 里的语句、
> 不动指纹，**已经执行过 031 的库不会重跑** —— 而三库里已经有一种被迁移过了，
> 于是"修好的库"和"没修的库"会长期并存，且看起来都通过。

`verify()` 断言三条不变量：协议 `target_type/target_id` 自洽、已核销必挂真实核销单、def 指纹一致。

## 五、接口、界面与演示数据

### 5.1 接口（独立前缀 `/api/dms`）

票（协议）与货（返利）的授权粒度不同，因此**独立于 `/api/dealers/*`**：
`/api/dms/meta`、`/api/dms/agreements`（CRUD + `status` + `explain`）、`/api/dms/policies`、
`/api/dms/rebates`、`/api/dms/rebates/plan`、`/api/dms/rebates/accrue`、
`/api/dms/rebates/:id/confirm`、`/api/dms/rebates/settle`、`/api/dms/settlements`、
`/api/dms/settlements/:id`、`/api/dms/rebate-audit`。写权限 `['sales','finance','admin']`。

老端点 `/api/dealers/*` 保留，但**计算全部改为调用 `lib/rebate.js`**（唯一实现）。

### 5.2 界面 `/dms/channel`（渠道中心）

三个页签：

1. **协议价档案** —— 列表 + 建档/改价/停用，附**取价解释面板**（调 `/explain` 把 `trace` 逐环展示）；
2. **返利计提与核销** —— 试算明细（"为什么是这个数"）、计提、逐笔确认、按期间核销；
3. **核销单** —— 单头 + 明细展开（逐笔返利冲了多少应收）。

### 5.3 演示数据 `db/dms-seed.js`

与界面点击**完全同一条代码路径**（`A.createAgreement` / `RB.accrueRebates` / `RB.settleRebates`），
不手工 INSERT（手工 INSERT 最容易漏派生列）。协议价一律**从 `product_skus.price_retail` 读出来再乘比例**
—— 写死"300 元"到餐饮库是荒谬的价，到服饰库又小到看不出折扣。

覆盖的形态：

| 类别 | 样本 |
|---|---|
| 协议价 | 定点 SKU 固定价 · 品类折扣（88 折）· 起订 5 件 · 与"全部商品"并存按 `priority` 裁决 · 一条**已过期** |
| 返利 | 命中的政策 · **命中但金额为 0**（阶梯没够到）· 三期计提 → 确认 → 核销 |
| 核销 | 挑一家**有未核销应收**的经销商，保证出现 `unoffset_amount`（"冲不下"也要有样本） |
