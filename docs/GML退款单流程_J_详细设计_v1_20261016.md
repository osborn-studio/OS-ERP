# GML 退款单流程（批次 J · 范围裁剪补做 · 第 1 项）详细设计

> 版本 v1 · 2026-10-16 · 批次 I 第 14 批 · 迁移 `033_refund`
> 上游依据：`docs/GML销售退货闭环_D1_详细设计_v1_20261016.md` 的「本次未做」段
> 结论：**销售退货登记的「待退款」第一次能被兑现成一次真实出账，且"还能退多少"只有一个判据。**

---

## 一、一句话

批次 D1 把销售退货闭环做到了这一步：退货额冲减原应收，**冲不下的部分如实登记为
`sales_returns.refund_due`（待退款额）**。

那句"如实登记"只解决了一半问题 —— 它答出了"该退客户多少钱"，
**但没有任何东西能把这件事变成一次真实的出账**：

| 之前有什么 | 缺什么 |
|---|---|
| `refund_due` 是一个数字，界面看得到 | **全仓搜不到一张"退款单"的表，也搜不到任何一处真正把钱退出去的代码** |
| 退货单有状态、有明细、有留痕 | 退款**没有单据、没有状态、没有审批** —— "这笔退了吗"答不出来 |
| 业务域都在往账上落后果 | 退款**没有账务后果** —— 钱出去了，账上什么都没发生 |

于是那个数字**永远停在界面上**：既不能被核销，也不能被审计。
这是本项目反复出现的那类形态的又一次 ——
**一个数字被记录下来了，但没有任何单据 / 状态 / 账务后果与之对应**。

本批落的是一条完整闭环：

```
已收款订单 → 退货（应收已收清 ⇒ 冲不动 ⇒ 登记 refund_due）
           → 登记退款单（草稿，钱不动）
           → 确认退款（出账，终态）
           → 生成记账凭证（借 2203 预收账款 / 贷 1002 银行存款）
```

## 二、四条硬口径

### 2.1 退款上限 = 待退款额 − **已确认**退款额（按退货单累计）

判据只写在 `server/lib/refund.js` 的 `planRefund()` 一张函数里，三处共用：
① 登记时的入参校验；② 确认时的**重验**；③ 界面上的"可退余额"列。
三处各写一遍，就会出现"界面说还能退 100、提交说超了"这类**没有赢家**的争论。

**只算 `confirmed` 的退款单**：草稿是"打算退"，不该占用额度 ——
否则两张草稿各占满额度，"先建单、后作废"就成了一条永远退不出去的路。

```js
const already = refundedOf(db, rid, { excludeRefundId })   // 只统计 status='confirmed'
const available = money(due - already)
if (used + amt - available > EPS) throw new RefundError('REFUND_OVER_DUE', ...)
```

### 2.2 客户必须一致 —— 一张退款单不能同时退给两个客户

```js
if (customer.type !== cust.type || Number(customer.id) !== Number(cust.id)) {
  throw new RefundError('REFUND_CUSTOMER_MISMATCH', ...)
}
```

把两个客户的退货单混在一张退款单里，等于**把 A 的待退款付给了 B**，
而两边各自的账都是对的 —— 这类错不会以任何形式报警，只会在某次对账时冒出来。

客户由**退货单自己**推导（`customerOfReturn`），不是调用方传的：
渠道优先看经销商，其次看门店，都没有就是散客（walkin）。

### 2.3 只有 `confirmed` 才真的出账，且**确认前重验一次**

`draft` 是"打算退"，不是"退过了"。
**建单时合法 ≠ 确认时合法**：两张草稿可以各自合法地答应退同一笔额度，
真正冲突的是**确认的那一刻**（与 A07 收款单同源）。

与付款单那个坑（"重验把自己判死"）的差别在于：
这里**只统计 `confirmed`**，而本单在重验时仍处 `draft`、本就不计入已退额 ——
所以不需要像付款单那样把自己加回来。**这条口径天然免掉了"看见自己"的问题**，
但两句话都要有测试守着，否则"改成就地累加"时会静默重复出账。

### 2.4 幂等键非空唯一 —— 动钱的动作最怕重放

`idx_refunds_idem`（部分唯一索引）；同键重复提交**返回首次那张单**，不重复登记。
并发撞上唯一键时回查那张单并如实返回 ——
"重放返回同一张"是**承诺**，不是尽力而为。

## 三、数据模型

### 3.1 `refunds`（退款单）

| 列 | 说明 |
|---|---|
| `doc_no` | `RFD + 年月日 + 序号` |
| `source_type` / `source_id` | 来源（当前为 `sales_return`，指向退货单） |
| `customer_type` / `customer_id` / `customer_name` | 往来对象（**由退货单推导**） |
| `refund_date` / `method` / `bank_account` / `serial_no` | 退款日期、方式、账户、流水号 |
| `amount` | 本次退款额 = 明细合计（`verify()` 断言头行一致） |
| `status` | `draft` / `confirmed` / `voided` |
| `idempotency_key` | 非空唯一 |
| `void_reason` | 作废理由（作废必填，`verify()` 断言非空） |
| `confirmed_by` / `confirmed_by_name` / `confirmed_at` | **谁放的这笔钱**（已退款必填） |

### 3.2 `refund_items`（分摊明细）

`refund_id` + `return_id` + `return_doc_no` + `amount`，唯一键 `(refund_id, return_id)`。

**为什么必须有明细**：一个客户可能同时有多张退货单各自产生待退款额，
**一次性退给他**是常见业务。只记一个总额的话：

- 退款上限判据无法**按退货单累计**（只能看到一个总额）；
- 对账时无法说明"这张退货单的钱退了没有"。

唯一键排除"同一张退货单在同一次退款里被分摊两次" ——
那会让金额校验里的 `used` 累计出现歧义（两条各不超、合起来超）。

### 3.3 单据内核：**RFD = 第 40 种单据类型**

```
draft（已登记，钱没动） → confirmed（已退款） → voided（已作废）
```

- `confirm`（`draft → confirmed`）：权限 `finance.refund.approve`，**高危**（出账）；
- `void`（`draft → voided`）：权限 `finance.refund.edit`，非高危；
- `void`（`confirmed → voided`）：权限 `finance.refund.approve`，**高危**（会让已出的钱从账上消失）。

**登记与出账分权**：能录一张退款单的人，不该同时能把钱放出去。

> `confirmed` **刻意不登记为终态** —— 与本项目"终态不能有出边"的内核规则一致
> （`test-docflow` 有一条断言专门守这个）。一笔钱退错了必须能纠正，
> 能做的只有"作废后重退"，与凭证 `posted` 可作废同构。
> 这条在实现时是**先写错再被内核规则打回来**的：初版把 `confirmed` 标成 `is_final=1`
> 同时又留了出边，`test-docflow` 的「终态无出边」当场变红。

## 四、账务后果

`lib/accounting.js` 注册业务场景 `refund`：

```js
refund: {
  label: '销售退款', doc_type: 'RFD', source_type: 'refunds',
  okStatuses: ['confirmed'],        // draft 是"打算退"，不是"退过了"
  facts(db, row) { return { total_amount: money2(row.amount), customer_name: ... } }
}
```

模板 `TPL_REFUND`：

```
借 2203 预收账款（带客户辅助核算）    total_amount
贷 1002 银行存款                      total_amount
```

**为什么借"预收账款"而不是"应收账款"**：
`refund_due` 是**已收款退货**里"应收冲不下的那一部分"，其经济实质就是
**我们多收了客户的钱**（预收负债）；退款就是清偿这笔负债。
挂应收会让"退货冲减应收"与"退款"同时反向操作同一个科目，
账上看起来像什么都没发生 —— 而事实上钱确实出去了。

**含税拆分**：退款与收付款一样**不拆税**（`['receipt','payment','refund']` 走例外分支）。
它们的金额是"资金的进出"，本身不是价税合计；退货那一步已按含税口径冲过应收，
这里再拆一次会重复。

## 五、前端 `/finance/refunds`（退款管理）

两个页签，各回答一个具体问题：

1. **退款单** —— 「这笔钱出去了没有？」
   状态三态（已登记 / 已退款 / 已作废）；**登记与出账是两个按钮**；
   作废（尤其作废已退款）弹窗提示"会让一笔已出的钱从账上消失"，必须写理由；
   展开行显示每条明细的「本次退款 / 该单待退款 / 当前可退余额」三列。
2. **可退清单** —— 「还能退多少？」
   待退款额 − 已确认退款额，与后端 `planRefund()` **同一个口径**；
   底部写清"草稿不占用额度"的理由。

登记弹窗里，前端**自己先拦一道**（超了就指出是哪一张、差多少），
后端仍独立校验 —— 前端拦是为了体验，不是为了让后端省事。

**刻意没有"编辑已登记退款单"的入口**：改金额等于换一笔出账，
正确做法是作废后重开（作废要写理由，留痕）。

## 六、演示数据（`server/db/refund-seed.js`）

要造的是一条完整闭环，**全程走服务函数**（`createSalesReturn` / `createRefund` /
`confirmRefund` / `voidRefund`），与界面点击完全同一条代码路径。

**为什么必须先"收清货款"才能退**：

```
货没付款 → 退货冲减应收，refund_due = 0（不需要退钱，把账冲掉就行）
钱已经收了 → 应收已结清、冲不动 → 退多少就是多少待退
```

所以演示要覆盖"已退款"，就**必须先有一笔真实的收款**（走 `createReceipt + confirmReceipt`，
不是手工改 `allocated_amount` —— 手工改出来的"已收"没有核销明细，
"这笔钱抵了哪一笔"就答不出来，而退款的前提恰恰是"这笔钱确实收过"）。

**三种形态都要有**：已退款（confirmed）/ 已登记未退款（draft）/ 已作废（voided）。
只造 confirmed 的话，"草稿不占用额度"与"作废必须写理由"这两条口径
在演示与截图里根本看不到 —— 而它们恰恰是最容易被后来者改坏的规则。

候选订单的两个刻意排除：

- **逾期单不挑** —— `ar-seed` 刻意造了逾期样本，把它们收掉会让"账龄"演示消失；
- **已退过的单不挑** —— `seed.js` 已造 18 张退货单，再退一次会让
  "已退量 ≤ 已发量"那条上限判据失去样本（都贴到上限，看起来像判据没生效）。

排序按"未结余额升序"：优先挑**已经收清**的单，这样不必额外改动应收演示数据。

## 八、边界（本批未做）

- **反核销**：退款出账后没有"冲减流水"可反冲，纠正只能"作废 + 重退"（本批已提供）；
  真正意义上的"反核销"（把已出的钱按原路收回并自动对账）属独立课题。
- **跨期合并退款**：当前按退货单分摊，不支持"按客户一次性汇总结转"；
- **退款审批流**：当前是"登记 / 确认"两态 + 权限分离，未接通用审批模板；
- **预收款退款**（客户多付了钱、要求退回）：本批只做"退货产生的待退款"这一种来源；
- **退款到第三方账户 / 分批到账**：`bank_account` 只存一个字符串，未做账户主数据校验。

## 九、与其它域的关系（一致性检查表）

| 关注点 | 本项目既有口径 | 本批如何对齐 |
|---|---|---|
| 同一份判据不允许有两个实现 | 数据范围只有 `scopePairs()`；算钱只有 `checkout.quote`；**冲减应收只有 `ar.offsetAr`** | 退款上限只有 `planRefund()`；前端展示与后端校验同源 |
| 状态字不能当"事情做了"的证据 | 模块 13 处置必须落库存；批次 G `paid` 重定义为「已核销」 | `draft` 明确"钱没动"，`confirmed` 必须有确认人 + 账务后果 |
| 值域是引擎的责任 | A17b：出入库数量符号闸门 | `planRefund` 拦非正数、非正数明细拒绝 |
| 重验必须能看见自己 | 收尾批次：付款单 `selfPaymentId` | 确认前重验**排除本单**；因只算 `confirmed`，天然免掉"加回自己" |
| 末行兜底 | 优惠分摊 / 核销冲减分摊 / 成本三层 / 税额拆分 | 退款明细**不按比例分摊**（金额由用户填），故不涉及；但头行一致由 `verify()` 守住 |
| 派生状态必须能重建 | `verify-reseed` 两次重建逐项一致 | `refund_items` / `refunds` 已进 `seed.js` 清理清单 |
