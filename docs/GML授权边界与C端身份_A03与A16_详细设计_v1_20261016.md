## 二、A03：写路径的组织越界

### 2.1 原形

```js
// server/mcp/tools.js
function orgFilter(ctx, alias, column = 'org_id') { /* 只被列表查询用 */ }

// inventory.stock_in
handler({ db, args, ctx }) {
  const r = applyStockIn(db, { ..., ownerOrgId: args.owner_org_id ?? ctx.orgId ?? null })
}
```

`ctx.scope` 由 `buildContext()` 从令牌绑定的组织子树算出 —— **这个范围只影响"看得到哪些行"**。
写工具的货主来自**调用方传参**，显式传一个不在范围内的组织时直接采信。

**验收侧独立动态复现**：令牌 org=5（path `/1/2/5/`）调 `inventory.stock_in` 传 `owner_org_id=3`
（`/1/2/3/`，不在其子树内）→ **成功**，库内该批次 `owner_org_id=3`、`qty_on_hand=1`。

**后果**：一个只能看 5 号组织的 Agent，可以往 3 号组织的货主名下入库 ——
这批货在 5 号的报表里**永远看不到**（读有过滤），却真实存在于 3 号的库存里。
对账时是"凭空多出来的一批货"。

### 2.2 修复：一处判据，两处使用

```js
/** 目标组织是否落在本令牌的组织范围内（未绑组织的令牌 = 全局，放行） */
function assertOrgInScope(ctx, orgId, label = '货主组织') {
  // ... 不在范围内 → throw { code: 'ORG_OUT_OF_SCOPE', status: 403 }
}

/** 仓库本身 + 它的货主都必须在范围内；返回解析出的货主组织 */
function assertWarehouseInScope(ctx, db, warehouseId, label = '仓库') {
  // wh.org_id 在范围内 && resolveOwnerOrg(wh) 在范围内
}
```

**为什么把"仓库"也一起校验**：`inventory.adjust`、`inventory.transfer` 根本没有 `owner_org_id` 参数，
货主是**从仓库推导**出来的。只查 `owner_org_id` 的话，这两个工具就是敞开的门。

接入点（全部写 + 高危工具）：

| 工具 | 校验 |
|---|---|
| `inventory.stock_in` | 仓库（含货主）+ 显式 `owner_org_id` |
| `inventory.stock_out` | 同上 |
| `inventory.transfer` | **调出仓 + 调入仓**（两个仓 = 两个可能越界的入口） |
| `inventory.ownership_transfer` | 两个仓 + **两个显式货主**（最容易越界的工具） |
| `inventory.adjust`（danger） | 仓库（没有 `owner_org_id` 参数，货主由仓库推导） |
| `inventory.get_cost` / `pick_suggestion`（读） | 显式 `owner_org_id` 与仓库 |

**读路径也一并校验**：`inventory.get_cost` 传 `owner_org_id=别的组织` 同样能读到别人的结存。
写读用**同一个函数**，不另开一套。

### 2.3 A03 增量：列表与汇总 handler 不接收 `ctx`

`purchase.list_orders` / `sales.list_orders` / `order.trace_document` / `report.sales_summary`
四个 handler 的签名里**没有 `ctx`** —— 令牌绑了组织也照样看全量。

修复的关键不是"给每个 handler 补一个 if"，而是先回答：**单据表的组织归属是什么？**

```
purchase_orders    → warehouse_id / target_store_id
sales_orders       → store_id / dealer_id / warehouse_id
stock_transfers    → from_warehouse_id / to_warehouse_id
production_orders  → warehouse_id
outsourcing_orders → warehouse_id / material_warehouse_id
```

**这些表都没有 `org_id` 列** —— 它们靠业务主体归属，而主体各自挂在某个组织下。
所以先做一次映射，再过滤：

```js
/** 组织范围 → 各业务主体的可见 id 集（单一定义处）。null = 不受限 */
function scopeEntityIds(ctx, db) {
  // 令牌未绑组织 → null（全局）
  // 否则：storeIds / dealerIds / warehouseIds 分别 = 各自 org_id 落在范围内的 id
}

/** 把「任一归属列落在可见主体集内」写成 SQL 条件；一个主体集都算不出来 → AND 1=0 */
function entityScopeClause(e, { stores = [], dealers = [], warehouses = [] } = {})
```

**为什么用映射而不是给单据表加 `org_id`**：单据的归属本来就是"属于哪个门店/经销商/仓库"，
`org_id` 是一个**推导值**。加一列等于把推导值落库，将来主体换组织时两处会不一致 ——
这正是"同一份判据不允许有两个实现"要避免的东西。

**为什么算不出主体集时是 `AND 1=0` 而不是放行**：fail-closed。
查不到主体 = 这个令牌在本库里没有任何业务归属 = 它不该看到任何单据。
（分行业裁剪时某些表不存在，也会走到这个分支。）

### 2.4 单条追溯：越界单据当作"不存在"

`order.trace_document` 按单号探 5 张表。加了范围后，越界单据**不返回 403，直接当作没找到**：

```js
if (row && entityRowVisible(e, row, owns[t] || {})) hits.push(...)
```

**报 403 等于确认"这张单存在，只是不是你的"** —— 单号是连续可猜的，
403 会变成一个"存在性探测器"。这是与第 1 批 `assertCanRead` 同一条口径
（那处判 403 是因为调用方已经通过列表知道了这一行的存在；这里是"按号盲查"，必须 404）。

### 2.5 顺带修掉的 A19 一半：`report.sales_summary` 用的是**不存在的列**

```sql
-- 原：SUM(so.total_amount)  —— sales_orders 没有这一列（只有 goods_amount / receivable_amount）
-- 现：SUM(so.goods_amount) AS amount, SUM(so.receivable_amount) AS receivable_amount
```

干净库上原来这个工具**必然抛 `no such column`**。
挑 `goods_amount` 作为"销售额"是因为它才是货值口径（`receivable_amount` 含运费与整单折扣），
两个口径都返回，避免下游猜。

> **A19 的另一半（`approval.approve` 用 `approval_instances.finished_at` + 裸 `UPDATE`）
> 本批未修**，按验收侧的分批归入 **D5**。理由：它的正确修法是"改调 `lib/approval.js` 的
> `decideApproval`"，而 `canApproveStep` 要求 `actor.id` 是一个**真实用户** ——
> 于是必须同时回答"Agent 凭什么代表人签字"。这不是补一个 if，要单独设计（见 §五）。

## 三、A16：C 端身份不能是手机号

### 3.1 原形

整个 `/api/mall` 免 token，"手机号即会员（一账通主键）"：

```js
// POST /api/mall/orders
const { phone = '' } = req.body || {}
if (!/^1\d{10}$/.test(phone)) return fail(res, '请先登录（手机号）')

// GET /api/mall/orders/:id
const o = db.prepare('SELECT o.* ... WHERE o.id=?').get(Number(req.params.id))
if (!o) return fail(res, '订单不存在', 404)     // ← 没有任何身份判定
return ok(res, { order: o, items })              // ← 返回完整详情（含收货人 / 电话 / 地址）
```

**验收侧独立动态复现**：
- 未登录 `POST /api/mall/orders` 传一个合成手机号 → **200**，单就成了；
- 另一个手机号的**未登录** `GET /api/mall/orders/:id?phone=…` → **200**，拿到完整详情。

**为什么这条比看起来严重**：手机号不是秘密。它印在快递面单、写在名片、出现在群里。
把它当身份，等于**任何人只要知道你的手机号，就能看你的全部订单（收货人、详细地址、消费金额），
还能以你的名义下单**。而"校验了格式 `^1\d{10}$`"看起来像是做了校验 —— 那是格式校验，不是身份校验。

### 3.2 修复：C 端自己的会话

```js
const MALL_AUD = 'gml-mall'

function signMallToken(customer) {
  return jwt.sign({ cid, phone, role: 'mall' }, JWT_SECRET,
                  { expiresIn: '30d', audience: MALL_AUD })
}

/** C 端会话门：身份只认会话，不认请求里的 phone */
function requireMall(req, res, next) {
  // 从 x-mall-token（或 Authorization）取，校验 audience 与 role==='mall'
  // → req.mall = { id, phone }
}
```

规则：

| 端点 | 变化 |
|---|---|
| `POST /login` | 校验验证码后**签发 C 端令牌**（原来只回手机号） |
| `GET/POST /cart`、`/cart/update`、`/cart/clear` | `requireMall`；身份取 `req.mall.phone`，**请求里的 `phone` 一律忽略** |
| `POST /orders` | `requireMall`；下单手机号取会话 |
| `GET /orders` | `requireMall`；只列自己的 |
| `GET /orders/:id` | `requireMall` + **归属判定**，越界 → **404** |
| `GET /member` | `requireMall` |
| `GET /home`、`/products`、`/products/:skuId` | **仍然公开**（目录是公开信息，不能误伤） |

**为什么越界返回 404 而不是 403**：与 §2.4 同理 —— 403 等于确认"这张单存在"。
订单号是自增的，403 会把接口变成"订单号探测器"。

### 3.3 与后台凭据的隔离

同一签名密钥、**不同 audience 与 role**，互不通用：

- 内部 JWT 调 C 端接口 → 401（`role !== 'mall'`，且 audience 不符）；
- C 端令牌调后台接口 → 后台只认 `role`，不会把 C 端令牌当管理员。

**为什么不干脆复用后台 JWT**：那是"给前台发一个能当后台用的凭据"。
两边的权限量级完全不同 —— 前台只要"看自己的单"，后台能看全公司的账。

前端（`src/api/client.ts`）对应改动：
- 新增 `gml_mall_token`（与 `gml_token` **分开存、分开送**）；
- 只对 `/mall/**` 请求附带 `x-mall-token`（后台请求不该看到前台凭据）；
- C 端 401 **只清 C 端令牌，不跳后台登录页**（原来会把逛商城的用户踢到后台登录）。
