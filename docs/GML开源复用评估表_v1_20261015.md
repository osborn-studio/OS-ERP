## 二、按模块组的复用矩阵

### 2.1 权限与行级数据规则（P0）—— casbin，**最高性价比**

| 可抄 | 位置 | 说明 |
|---|---|---|
| `rbac_with_domains` | `examples/rbac_with_domains_model.conf` | `r = sub, dom, obj, act`，`dom` 直接映射**组织/仓库**，正是多行业多库的隔离正解 |
| 域继承 | `rbac_with_hierarchical_domains_model.conf` | `g2` + `regexMatch(r.act, p.act)`，支持总部>大区>仓的层级与动作正则 |
| **行级规则（关键）** | `abac_rule_model.conf`：`m = eval(p.sub_rule) && …` | 策略里存**表达式**、对请求对象属性求值 —— 这就是「某人只能看某仓库某类单据」的机制 |
| 功能权限 + 行级 + 显式拒绝 | `multiple_policy_definitions_model.conf` | `p`(RBAC) 与 `p2`(ABAC, 带 `eft:deny`) 共存，一套覆盖四维 |
| 审计留痕 | `coreEnforcer.ts:710` `enforceEx` | 返回命中的规则原文，可直接落审计日志 |
| 高并发 | `util/builtinOperators.ts:342` `generateGFunction` 带 memoize | 鉴权热路径靠它扛 |

**落地**：写一套 SQLite 适配器（实现 `persist/adapter.ts` 的 Adapter 接口），把 `p/p2/g/g2` 落到 4 张表。
**两个坑**：① 列表中**不要逐行 `enforce()`**，要用 `keyGet2/globMatch` 把规则反向编译成 SQL `WHERE` 片段（否则列表页必炸）；② `SyncedEnforcer` 的锁是进程内的，PM2 cluster 下失效；③ **字段级脱敏 casbin 完全不支持**，必须在响应序列化层另做。

### 2.2 促销引擎与价格本（P1 商城）—— medusa，**可直接抄领域模型**

| 可抄 | 位置 | 说明 |
|---|---|---|
| 促销主模型 | `modules/promotion/src/models/promotion.ts` | `code`/`is_automatic`/`type`/`status`/`limit`+`used`（总用量限制）/ `is_tax_inclusive` |
| **动作** | `application-method.ts` | `type`=fixed\|percentage；`target_type`=order\|items\|shipping；**`allocation`=each\|across\|once**（分摊） |
| **条件（数据驱动）** | `promotion-rule.ts` + `promotion-rule-value.ts` | `attribute` + `operator` + `values[]` 三段式，加新条件不改代码 |
| 预算与每人限用 | `campaign-budget.ts` + `campaign-budget-usage.ts` | 按 `attribute_value`（customer_id/email）独立计数 |
| **计算范式（必抄）** | `services/promotion-module.ts` `computeActions()` L697-995 | ① 先下发 `REMOVE_*_ADJUSTMENT` **全量重算、不做增量叠加**（幂等的关键）；② 比较器 `sortByBuyGetType`（buyget 先于 standard，再按力度降序）；③ `methodIdPromoValueMap` 累加已用金额防超额叠加 |
| 券核销并发（必抄） | `registerUsage()` L305 | 按 id **排序后**加锁再重读（不排序会死锁）；SQLite 下退化为 `UPDATE … WHERE used < limit` 判 `changes` |
| 赠品贪心 | `utils/compute-actions/buy-get.ts` L160-183 | 预留 buy 侧数量时**优先占用不能作为赠品的行**，否则「买2送1」会抢走赠品自身 |
| 价格本与调价 | `modules/pricing/src/models/price-list.ts` | `status` 草稿/生效、`type` SALE/OVERRIDE、`starts_at`/`ends_at`；`price-rule.ts` 有 **`priority`** 字段 |

**必须补的三列**：medusa 的 promotion **没有** `priority` / `stack_group` / `is_exclusive`（全仓搜 `exclusiv|stackable` 零命中）—— GML 的「含叠加规则与优先级」需求必须自己加，并在比较器里前置 `priority` 降序。

### 2.3 业财一体 / 应收应付（P2 与 P1）—— medici，**抄记账内核**

| 可抄 | 位置 | 说明 |
|---|---|---|
| 凭证结构 | `src/models/journal.ts`、`transaction.ts` | `journal`(本) + `entry`(行)；**借贷用两个非负数列表达**（`credit`/`debit`），金额恒正、方向由方法决定 |
| 冗余下沉 | README 254 行 | `book/memo/datetime/voided` 冗余到 entry，避免查明细 join |
| 业务维度挂载 | `meta` 自由 JSON | 承载 clientId / docId —— 这是复式账能当应收应付用的关键 |
| 科目层级 | `parseAccountField.ts` | `account_path.0/1/2` 前缀匹配 |
| **平衡校验** | `src/Entry.ts` `commit()` | `Σ(credit-debit)===0` 否则 throw；GML 用整数分后可精确相等 |
| **红冲不作废** | `Book.void()` + `addReversedTransactions.ts` | 原凭证置 `voided`，**另写借贷反向新凭证**，原字段复制进 `meta` |

**medici 没有、必须自研**：① **账龄** —— 应收要按**单据维度**（`ar_bill(due_date, amount, writeoff)` + `ar_settle` FIFO 冲销）分桶，不能用「科目余额按日期区间」；② **期间关闭与结转**；③ 存货成本。
**不要抄**：余额快照机制（依赖 Mongo TTL 索引，删 entry 需手动清快照，单文件库收益为负）、ObjectId 当游标（改 `seq INTEGER`）、`Medici_Lock` 集合（SQLite 单写者下多余）。

### 2.4 订货中心（模块 12A）与 DMS —— bagisto-b2b，**只抄表结构与状态机**

可 1:1 汉化落地的五组表：`b2b_customer_companies` / `b2b_company_roles` / `b2b_company_invitations` / `b2b_customer_requisition_lists`(常购清单) / `b2b_customer_quotes`(RFQ，头+行+消息+报价+附件)。

**信用账本抄 `Helpers/CreditManager.php` 的「余额 + 流水 + after 快照」三件套**：
- `available = credit_limit − outstanding_balance`（可为负＝超额/预收）
- `apply($credit, $operation, $amount, $direction, …)`：`direction=+1` 增加欠款、`-1` 还款/退款
- 每条流水记 `outstanding_balance_after / available_credit_after / credit_limit_after` 三快照 + `actor_type/actor_id`
- **GML 增项**：`payment_term_days` 与 `aging_bucket`（bagisto 没有）

**明确缺失（必须自研）**：返利、账期、经销商 DMS、对账单 —— grep `rebate|payment_term` 零命中。
**不要抄**：PHP/Eloquent/Blade 层；「每个 catalog 背后藏一个隐藏 customer_group」这层妥协（GML 直接建 `company_tier_price(company_id, product_id, min_qty, price)`）；`setPrices()` 的全删重写（会静默抹价，改 upsert）；`product_price_indices` 异步索引表（GML 实时算价即可）。

### 2.5 售后与退款、库存地点 —— medusa order / inventory

- **售后骨架（值得整体照抄结构后重写）**：`modules/order/src/models/` 的 `return` / `return-item` / `claim` / `claim-item` / `exchange` / `order-change` / `order-change-action` / `transaction`。「订单 → 退货/换货/索赔 → 变更动作 → 事务」的分离，是**门店退货 + 商城售后最好的骨架**；`credit-line.ts`（贷项行）比直接改订单金额更利于长短款追溯。
- **权限**：`modules/rbac/src/models/` 角色-策略多对多 + `rbac-role-parent`（角色继承），映射 店员/店长/总部 三级。
- **三段式库存**：`inventory-level.ts` 的 `stocked_quantity` / `reserved_quantity` / `incoming_quantity` + **计算列 `available_quantity`**；占用单独 `reservation-item.ts`。可直接迁移。
- **订单路由**：medusa 只做到「过滤出可用地点后取 `location_ids[0]`」，**不支持跨地点拆单/部分分配**。GML 需自写：优先级地点链 → 逐地点扣减 → 生成多个 reservation → 不足转调拨或预售。只抄它三级降级的思路。

### 2.6 幂等、重试、补偿、定时（P0）—— bullmq，**抄语义不抄实现**

规格书（v6.3.15）：`deduplication:{id,ttl,extend,replace,keepLastIfActive}`（去重，`keepLastIfActive` 保证至多 1 active + 1 waiting）；`attempts`；`backoff:{type:'exponential',delay,jitter}` 公式 `round(2^(n-1)*delay)`；`UnrecoverableError`（立即放弃）；`DelayedError`（再延时）；`queue.upsertJobScheduler(id, repeatOpts, template)`（已取代旧 `repeat`）；`FlowProducer` + `failParentOnFailure`（**现成的事务补偿骨架**）。

⚠️ **bullmq 没有 SQLite 后端**（`DatabaseType = redis|valkey|dragonfly`），与「单文件 SQLite」部署形态冲突。二选一：
- (a) 可引入 Redis → 直接用官方版；
- (b) 坚持纯 SQLite → **自研 `jobs` 表**（`id, queue, payload, status, attempts, available_at, dedup_key UNIQUE, last_error`），用「UPDATE … RETURNING」原子抢占 + 定时器做 ack/stale 回收，**把上表的退避公式与 dedup 语义当设计规格移植过去**。

### 2.7 POS 交班 / 缴款 / 长短款（P1）—— **两个仓库都没有，必须自研**

`posopen-www` 的 `CashierScreen.tsx` 是 `Array.from({length:12})` 生成的假数据，全仓 grep `shift|cashup|session|offline|queue` 零命中，README 是愿景文档。**只能把 MVP Functional Scope 一节当功能清单用。**

建议自建模型（GML 侧草案，非抄自参考库）：
- `pos_shift`：store/device/opened_by/closed_by/**opening_float(备用金)**/declared_cash/**expected_cash(系统应收)**/**counted_cash(实点)**/**variance = counted − expected**/variance_note/approved_by
- `pos_shift_payment`：shift_id/method/system_amount/declared_amount/diff —— **长短款必须按支付方式拆分**，否则无法区分现金短款与移动支付漏单
- `pos_cash_drop`（缴款）：shift_id/amount/handed_by/**received_by(店长)**/dropped_at/reference_no
- `pos_daily_close`（日结）：store/business_date/shift_ids/totals_json/**upload_status(pending|uploaded|conflict)**/hq_batch_id
- 离线：本地库存商品快照+挂单 → `outbox` 表（幂等键 `client_order_id`）→ 恢复后批量上传 → 服务端按幂等键 upsert → 冲突进人工核

## 四、已知的坏榜样（抄了就出事）

1. `available = on_hand − reserved` **只在 INSERT 时算一次、UPDATE 时漏更新** → 可用量永久失配。正解：SQLite **STORED 生成列**。
2. **无事务的多语句写**（取单号→插单→写日志三步裸 await）→ 中断即脏数据。
3. **check-then-act 超收校验**（先读额度再 `$inc`）→ 并发双双通过突破上限。正解：条件 UPDATE 判 `changes`。
4. **单号前端生成 + 后端事后自增** → 并发必重号。正解：`counters(type, ym, seq)` 表 + 事务内 `UPDATE … RETURNING` + 唯一键。
5. **删除即反向回滚而非留负向凭证** → 审计链断裂。
6. **状态跃迁无校验表**（draft 可直跳 refunded）→ 应有 `doc_transition(from, to)` 表在应用层校验。
7. **金额用浮点**：`currency.js` / `BigNumber` / `MEDUSA_EPSILON` 都是历史包袱。GML 一律 **INTEGER 分**存储。
8. **审计日志硬编码 `user_id = 1`** → 所有改单记到同一账号。

## 五、建议的取用顺序（对齐 GML 优先级）

1. **促销引擎**（P1 商城最缺）← medusa，工作量中等、收益最高，且 `computeActions` 是纯函数可直接迁为纯 JS。
2. **行级数据规则**（P0 权限纵深）← casbin，把模块 05 的四维补成「功能 + 行级 + deny」。
3. **复式记账内核**（P2 业财）← medici，为应收应付与凭证生成铺路。
4. **幂等与补偿** ← bullmq 语义，先按纯 SQLite 自研 `jobs` 表落地。
5. **售后退款骨架** ← medusa order 模块（门店退货与商城售后共用）。
6. **B2B 表结构** ← bagisto，模块 12A 已落地，可用于补齐常购清单与 RFQ。
