## 一、这一批补的是什么

从批次 L 起，会计期间有了状态与"定稿"动作；批次 M 加了期末结转与撤销结转；批次 O 加了年结、封整年与利润分配。到今天，能改变期间状态或定稿结果的动作有**八个**：

```
关账 · 反关账 · 期末结转 · 撤销期末结转 · 年度结转 · 撤销年度结转 · 利润分配 · 撤销利润分配
```

而它们留下的痕迹是**覆盖式**的 —— 期间表上只有"最后一次"：

| 列 | 含义 | 被谁覆盖 |
|---|---|---|
| `status` | 关账状态 | 关账 / 反关账 / 年结（封整年） |
| `closed_by` / `closed_by_name` / `closed_at` | 关账人与时间 | 关账；反关账时清空 |
| `reopen_reason` | 最后一次反关账的理由 | 反关账 |
| `closing_voucher_id` / `closing_by` / `closing_at` | 本期结转凭证与执行人 | 期末结转；撤销结转时清空 |
| `closing_reverse_reason` | 最后一次撤销结转的理由 | 撤销结转 |
| `annual_voucher_id` / `annual_by` / `annual_at` | 年结凭证与执行人 | 年度结转；撤销年结时清空 |
| `annual_reverse_reason` | 最后一次撤销年结的理由 | 撤销年结 |
| `dist_voucher_id` / `dist_by` / `dist_at` | 分配凭证与执行人 | 利润分配；撤销分配时清空 |
| `dist_reverse_reason` | 最后一次撤销分配的理由 | 撤销分配 |

于是下面这些**审计上必答**的问题答不出来：

1. 这一期**被反关账过几次**？每次的理由是什么？
2. 3 月关账之后又反关账、改了账、重新关账 —— 现在这个"已关账"是谁关的？
3. 期末结转被撤销过吗？撤销时账上是什么样？
4. 年结封了整年 —— 其中哪几个期间是被年结顺手封的、哪几个是各自关的？

交接文档里把它记成"反关账清 `closed_by`（审计链不完整）"。**这个措辞只说对了一半**：清空本身是对的（见第二节），缺的是"历史去哪了"。

## 二、先纠正一个口径：期间表上那些列是**指针**，不是历史

反关账时把 `closed_by` / `closed_at` 清空，看起来像"销毁证据"，其实是唯一自洽的写法：

> 一个 `status='open'` 的期间同时带着 `closed_by='张三'`，这句话本身是矛盾的 ——
> 读它的人必须先知道"这是历史还是现状"才能解释，而**列名不携带这个信息**。

所以本批**不**改成"保留旧值"，而是把两件事分开：

| | 承载什么 | 可变性 |
|---|---|---|
| **期间表**（`accounting_periods`） | **当前状态指针** | 随时被下一个动作覆盖 |
| **审计日志**（`period_audit_log`） | **历史事实** | **只追加**，没有修改与删除路径 |

这与批次 M 定下的"`closing_voucher_id` 只是指针、`vouchers` 才是事实"是同一条口径，只是这次落在**期间**上。

配套的断言（写进 `verify-seed` 第 23 节）：

```
status='open' 的行不带 closed_by / closed_at
```

## 三、日志表设计

```sql
CREATE TABLE period_audit_log (
  id                   INTEGER PRIMARY KEY AUTOINCREMENT,
  period               TEXT NOT NULL,   -- 动作落在哪个期间 'YYYY-MM'
  action               TEXT NOT NULL,   -- 动作名（见 PERIOD_ACTIONS）
  action_label         TEXT NOT NULL,   -- 动作中文名（**当时**的措辞，落库即冻结）
  scope                TEXT NOT NULL,   -- period / year
  scope_key            TEXT NOT NULL,   -- period 动作 = 期间；year 动作 = 'YYYY'
  status_before        TEXT,            -- 动作前的状态（基线条目为 NULL）
  status_after         TEXT,            -- 动作后的状态（NULL = 本动作不改状态）
  closing_voucher_id   INTEGER,
  annual_voucher_id    INTEGER,
  dist_voucher_id      INTEGER,
  voucher_doc_no       TEXT,            -- 便于人读；不是真值来源
  amount               REAL,            -- 结转 / 分配金额；不涉及则为 NULL
  reason               TEXT,            -- 撤销类动作必填
  remark               TEXT,            -- 备注（关账的 remark 落在这里）
  actor_id             INTEGER,
  actor_name           TEXT,
  actor_source         TEXT NOT NULL DEFAULT 'web',   -- web / mcp / system / migration
  detail               TEXT,            -- JSON 快照（如年结"封了哪几期"）
  created_at           TEXT NOT NULL DEFAULT (datetime('now','localtime'))
)
```

### 3.1 为什么这些列非有不可

| 列 | 为什么非它不可 |
|---|---|
| `action_label` | 日志是不可变事实，措辞不该随后续代码改名而变 —— 否则去年的日志会突然换一个说法 |
| `scope` / `scope_key` | 年结会**封整年**；只按期间记，"这一期是被年结顺手封的"这件事查不出来 |
| `status_before` / `status_after` | 状态迁移的两个端点；`before` 允许为空（基线没有"之前"） |
| 三个凭证指针 | 与期间表**同名同义** —— 重放才能逐字段比对而不用做映射 |
| `amount` | 结转账 / 分配凭证的金额，人读日志时最想知道的那一个数 |
| `actor_source` | 区分"人做的"与"迁移补的基线"—— 后者不是谁的动作 |

### 3.2 索引

- `(period, id)` —— 界面展开某一期的历史
- `(scope, scope_key, id)` —— 按年查
- `(action, closing_voucher_id, annual_voucher_id, dist_voucher_id)` —— "每条派生凭证都要有来源"

### 3.3 为什么不新增权限点

能看 `/api/reports/periods` 的人**已经能看到** `closed_by_name` / `reopen_reason` / `closing_reverse_reason`。日志给的是同一个信息集合的**历史**，不是新的信息类别。凭空多一个"审计查看权限"只会让权限表越来越长而没人维护（权限通胀会让真正的授权边界被淹没）。这条理由与批次 N 不给报表导出加权限点同源。

## 四、唯一写入点与 `PERIOD_ACTIONS`

### 4.1 只有一份「动作 ↔ 效果」定义

八个动作散在三个模块（`report.js` 两个、`closing.js` 两个、`annual.js` 四个），每个动作都是"改某个字段 + 写一条日志"。**如果日志内容由各调用点自己拼，"这个动作改了什么"就有了两份定义**：一份在 `UPDATE` 语句里，一份在日志参数里。两份定义迟早只改一处，而它的表现是**日志说改 A、实际改了 B** —— 两者都"看起来正常"，只有把日志重放一遍才会现形。

所以效果只声明一次（`server/lib/period-audit.js`）：

```js
export const PERIOD_ACTIONS = {
  baseline:            { label: '基线（迁移时现状快照）', scope: 'period', effect: 'snapshot' },

  period_close:        { label: '关账',        scope: 'period', effect: { period_status: 'closed' } },
  period_reopen:       { label: '反关账',      scope: 'period', effect: { period_status: 'open' }, requires_reason: true },

  profit_carry:        { label: '期末结转',    scope: 'period', effect: { closing_voucher_id: 'voucher' } },
  carry_reverse:       { label: '撤销期末结转', scope: 'period', effect: { closing_voucher_id: null }, requires_reason: true },

  annual_carry:        { label: '年度结转',    scope: 'year',   effect: { annual_voucher_id: 'voucher', period_status: 'closed', spread_year: true } },
  annual_reverse:      { label: '撤销年度结转', scope: 'year',  effect: { annual_voucher_id: null }, requires_reason: true },

  profit_distribution: { label: '利润分配',    scope: 'year',   effect: { dist_voucher_id: 'voucher' } },
  dist_reverse:        { label: '撤销利润分配', scope: 'year',  effect: { dist_voucher_id: null }, requires_reason: true }
}
```

`effect` 的取值语义：

| 写法 | 含义 |
|---|---|
| `{ period_status: 'closed' \| 'open' }` | 把期间状态改成它 |
| `{ x_voucher_id: 'voucher' }` | 把该指针指向**本行记录的凭证** |
| `{ x_voucher_id: null }` | 把该指针**清空**（撤销类动作） |
| `spread_year: true` | 该动作对该年度**每一期**都生效（年结封整年） |
| **没有出现在 `effect` 里** | 本动作**不动它**（重放保持前值） |

**这三态（指向 / 清空 / 不动）必须能分开**，否则"撤销"与"不涉及"在日志里长得一模一样。

### 4.2 三道当场断言

`logPeriodChange` 是全项目**唯一**的写法（只有一个 `INSERT`，没有 `UPDATE`、没有 `DELETE`），并在写入时断言：

| 断言 | 错误码 | 为什么 |
|---|---|---|
| 必须在事务里（`db.inTransaction`） | `AUDIT_OUTSIDE_TX` | 否则"账改了、日志没写"或反之会真的出现 |
| 动作名必须是 `PERIOD_ACTIONS` 里的 | `UNKNOWN_ACTION` | 宁可炸，也不落一条代码事后解释不了的记录 |
| 撤销类动作必须带理由 | `AUDIT_REASON_REQUIRED` | "谁撤销的"与"为什么撤销"是同一件事的两半 |

**这条铁律写进文档没人记得，写成断言才拦得住。**

### 4.3 八个接入点（全部在产生它的那个事务内）

| 动作 | 位置 | 事务 |
|---|---|---|
| `period_close` | `report.js` → `closePeriod` | 本批**新包**的 `db.transaction` |
| `period_reopen` | `report.js` → `reopenPeriod` | 本批**新包**的 `db.transaction` |
| `profit_carry` | `closing.js` → `carryForward` | 原有事务内 |
| `carry_reverse` | `closing.js` → `reverseClosing` | 原有事务内 |
| `annual_carry` | `annual.js` → `carryForwardAnnual` | 原有事务内 |
| `annual_reverse` | `annual.js` → `reverseAnnual` | 原有事务内 |
| `profit_distribution` | `annual.js` → `distributeProfit` | 原有事务内 |
| `dist_reverse` | `annual.js` → `reverseDistribution` | 原有事务内 |

关账与反关账原本不在事务里（它们只做一次 `UPDATE`）—— 本批把它们一并包进事务，因为"写日志"必须与"改状态"同生共死。

## 五、自证：重放日志必须得到期间表的现状

### 5.1 不变量

> 从空状态开始，按 `id` 顺序应用每一条日志的效果，得到的必须是今天的样子。

### 5.2 为什么这条互证有分量（以及它的盲区）

两条路径的**出处不同**：

- **现状**一侧来自各动作里的 `UPDATE accounting_periods ...`；
- **历史**一侧来自 `logPeriodChange` 写下的行。

它们**共享**的是"动作有哪些"（`PERIOD_ACTIONS`）。所以它抓得到：

- 改了状态忘了写日志；
- 日志写了状态没改；
- 日志被挂到别的期间名下。

抓**不到**：

- `PERIOD_ACTIONS` 本身写错（例如忘了声明 `spread_year`）—— 由动作表自检 + 该年其它期间的断言补位；
- 某个动作**既没写日志也没改状态**（两条路径都看不到它）—— 由下面的字段级双向核对补位。

**判断一条互证型探针的有效范围，先问"这两条路径共享什么"**（批次 P 的教训）。

### 5.3 年维度动作的一个特例（重放时必须区分）

年结与分配的凭证指针**只写在年末那一行**（`UPDATE ... WHERE period=YYYY-12`）。重放若不区分这件事，就会把 12 月的年结指针**加到这一年的每一期上**，于是 1 月的重放结果里凭空多出一个"年结凭证"。

这会产生**假红** —— 对着正确的账报错。所以重放里有一行：

```js
if (e.scope === 'year' && p !== `${e.scope_key}-12`) continue
```

配套的断言在 `test-period-audit` 的 Q6（"1 月**不会**拿到别人的年结指针"）。**假红比漏报更消耗信任**：一旦运维见过几次"明明没问题却报红"，下一次真红时他的第一反应是"又是误报"。

## 六、字段级双向核对（补重放的盲区）

期间表上"有值就该有日志"的字段，以及哪些动作能解释它：

| 字段 | 能解释它的动作 |
|---|---|
| `closed_by` | `period_close` / `annual_carry` / `baseline` |
| `reopen_reason` | `period_reopen` / `baseline` |
| `closing_voucher_id` | `profit_carry` / `baseline` |
| `closing_reverse_reason` | `carry_reverse` / `baseline` |
| `annual_voucher_id` | `annual_carry` / `baseline` |
| `annual_reverse_reason` | `annual_reverse` / `baseline` |
| `dist_voucher_id` | `profit_distribution` / `baseline` |
| `dist_reverse_reason` | `dist_reverse` / `baseline` |

第三条路径**完全不读期间表**：`vouchers` 表里每一张 `biz_type ∈ {profit_carry, annual_carry, profit_distribution}` 的凭证，都必须能被某条日志的对应指针列认领。这是"账上有票，但没人记得谁生成的"的直接检测，也是三条路径里**来源最硬**的一条（凭证是实际发生过的事）。

## 七、六条探针

| 错误码 | 抓什么 |
|---|---|
| `PERIOD_AUDIT_DESYNC` | 重放日志 ≠ 期间表现状（逐字段） |
| `PERIOD_AUDIT_MISSING` | 期间表有留痕，却没有任何能解释它的动作日志 |
| `PERIOD_AUDIT_VOUCHER_ORPHAN` | 派生凭证在日志里找不到来源（**不读期间表**） |
| `PERIOD_AUDIT_UNKNOWN_ACTION` | 日志里出现代码不认识的动作名（有人绕过唯一写入点） |
| `PERIOD_AUDIT_REASON_REQUIRED` | 撤销 / 反关账类记录没有理由 |
| `PERIOD_AUDIT_YEAR_GAP` | 年结承诺"封整年"，但该年度仍有期间未关账 |

全部**全库扫描** —— 只在用户点开某一期时才跑的探针等于不跑（批次 N 的教训）。它们在 `auditReport` 里作为**第 ⑩ 条**，因此**关账前置会检查它**："账没留痕"与"账不平"同等对待。

## 八、基线：迁移怎么处理"已经用过的库"

迁移跑在一个**已经用过的库**上时，期间表里已经有状态（演示库升级前就有 1 个已关账期间 + 1 个已结转期间），而它们的动作发生在日志表存在之前。这里只有两个诚实的选择：

1. 让探针"从有日志的期间开始查" —— 于是恰好把**唯一需要解释的那个状态**跳过了；
2. **按现状补一条 `baseline`（基线）条目**，并且明写它"不是某个人的动作"。

选后者。它与批次 O 的一条教训同源：**"没有配置 / 没有基准"不等于"从零开始"**。基线让重放不变量**从第一个期间起**就成立，而不是从"我们开始记日志的那天"起才成立。

基线的措辞刻意写成：

```
基线：迁移 037 引入审计日志之前，这个期间的状态就已经是这样了；
本条按现状补记，**不表示任何人的动作**
```

它的 `actor_source='migration'`、`action='baseline'`、`effect='snapshot'`（整行快照）。

### 8.1 但基线**不该**出现在重建出来的库上

整库重建后，`accounting_periods` 与 `period_audit_log` 都被清空，seed 用 `closePeriod` / `carryForward` **真的**关账与结转 —— 于是日志由 seed 自己的动作写出，**没有基线**。

这是设计对的一个旁证：基线是"升级既有库"的补丁，不是常态。测试里两种情形都要走（断言不能依赖"这个库恰好有基线"）。

## 九、与整库重建的关系

`period_audit_log` **必须**进 `seed.js` 的 `TABLES`（重建清理清单），理由与 `vouchers` 同源：

> 它按 `period` 与凭证 id 记录"谁把这一期改成了什么样"，而这两样在重建后都会指向新一代 —— 一张上一代的结转凭证日志会**看起来指向一张真实存在的凭证**（id 被复用），而审计链自证会当场报 `PERIOD_AUDIT_DESYNC`。

重建后由 seed 自己的动作重新写一份，**不需要迁移再回填基线**（已验证：重建后三库 `period_close=1 / profit_carry=1`，自证全绿）。

## 十、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/reports/periods/audit` | 变更历史。筛选：`period` / `year` / `action` / `limit` |
| GET | `/api/reports/periods/audit/check` | 审计链自证（六条探针的结论） |

**`year` 筛选必须同时返回该年的年度动作与期间动作。** 只匹配 `scope_key` 的话，"2024 年做过什么"只会返回年度动作，把 11 次关账全漏掉 —— 而那 11 次关账同样是这一年的事。这是本批实现时现场修掉的一个真实缺口。

## 十一、前端

「期间与关账」页签：

- 顶部新增**审计链自证横幅**（与"报表三条恒等式"并列的第二类健康检查：那三条问"账算得对不对"，这一条问"现在这个样子能不能由来路解释"）；
- 每行新增「变更历史」按钮 —— **懒加载**展开该期的全部记录（一次列出所有期间的所有日志没有意义）；
- 历史表逐列展示：时间 / 动作 / 状态迁移 / 金额 / 操作人 / 理由。

## 十三、未关闭项 / 边界（如实记）

- **日志只按 `id` 递增排序，不提供"按时间排序"** —— `created_at` 精度只到秒，同一秒内的多条无法定序；顺序的唯一真值是 `id`。
- **`baseline` 只回填一次**：如果将来手工往 `accounting_periods` 里塞入一条历史期间（不走任何动作），探针会报 `PERIOD_AUDIT_MISSING` —— 这是**有意**的（绕过唯一写入点就该被发现），但没有"补一条基线"的运维入口。
- **`detail` 是 JSON 文本**，不做 schema 校验：它只服务人读与排障，**任何判据都不读它**（判据只读有类型的列）。
- 仍未关闭（与前批相同）：钉钉/飞书「组织同步 + 审批同步」· 真实联调 · 容器内实测 · 真机验证 ·
  现金流量项目辅助核算 · 业务码两个落点形状未统一 · 跨年度报表 · 报表导出 Excel/PDF ·
  以及验收侧仍待独立复验的第 4–20 批全部内容。
