## 一、缺陷的形状：**预留只有"数字"，没有"谁"**

`inventory_reservations` 表从 `002_stock_five_dims` 就建好了，`reserveStock` / `releaseStock`
也早就带了 `sourceDocType / sourceDocId / sourceDocNo` 三个参数 —— **但没有任何调用方传过**。

实测：三库该表**长期 0 行**。于是"预留"只剩库存行上的一个数字 `qty_reserved`：

| 想知道什么 | 能不能回答 |
|---|---|
| 这个仓这个 SKU 被占了多少 | ✅ 库存行上有数字 |
| **是替哪张单占的** | ❌ 没有任何记录 |
| 这张单占的是**哪几个批次** | ❌ 没有 |
| 发货时该扣哪些批次 | ❌ 只能"重新按当前库存再拣一次" |

最后一行就是事故的起点。发货时 `pickBatches` 按 `qty_on_hand - qty_reserved` 拣选 ——
而那批货**正被自己占着**，free = 0，于是：

```
库存 10 → SO 10 件 confirm → on_hand=10 / reserved=10（可追溯到该 SO 的 reservation 行 = 0）
→ deliver → pickBatches 拣不到任何东西 → 发出 **0 件**
```

验收侧独立复现的结果正是：`deliver = 200` 但 `deliveredQty = 0`、`shortages=[{sku, shortage:10}]`、
订单停在 `picking`、`reserved` 仍为 **10**。

**三件后果，一件都不报错**：

1. **一张 0 数量的发货单**，状态却是「已发货」——它不改变任何数字，只让订单看起来发过了；
2. **10 件预留永远挂着**（幽灵预留）——这批货再也卖不出去，账面上"有货"但拣不出来；
3. 取消时同样"重新拣一次"，拣到的很可能**不是当初那批** ——
   本单的预留没释放，**别人的预留被放掉了**。

## 二、三条规矩

```
① 占库必须登记来源      reserveForDoc()
② 发货必须消费"本单占住的那批货"   planShipment()
③ 取消必须按明细释放     releaseForDoc()
```

三者都按「来源单据」读写同一张明细表，所以判据只有一处。

### 2.1 `reserveForDoc` —— 唯一的占库入口

```js
export function reserveForDoc(db, { sourceDocType, sourceDocId, sourceDocNo, warehouseId, items })
```

拣选 → 预留 → **登记明细**。不足直接抛 `INSUFFICIENT_STOCK`（调用方在事务里，整体回滚）。

登记的三个字段就是"谁占的"：`source_doc_type` / `source_doc_id` / `source_doc_no`。
**少了它们，预留就只是一个数字** —— 这是本缺陷的全部根因。

### 2.2 `planShipment` —— 发货计划

```js
const { plan, shortage, mode } = planShipment(db, { sourceDocType, sourceDocId, warehouseId, skuId, needQty })
// mode: 'reservation'（按本单预留消费）| 'legacy'（历史单据，无明细）
```

**先消费本单据自己的预留**：

- 逐条读 `reservationsOf(...)` → 按需 `consumeStock()`（明细置 `consumed` + `qty_reserved` 递减）；
- 不够就是 **缺口**，如实报出来 → 部分发货。**不抢别人的预留。**

**为什么"不抢"是硬要求**：两个订单竞争同一批货时，A 已经占住了货，B 若能在发货时
把 A 的预留抢走，A 的发货就变成"0 数量发货单"、A 的预留永远挂着 ——
**预留的全部意义就是"这货已经有主了"**。

**顺序不能反**：必须先 `consumeStock`（减 `qty_reserved`）再 `applyStockOut`（减 `qty_on_hand`）。
因为 `applyStockOut` 的可用量判据是 `qty_on_hand - qty_reserved` ——
预留不减，出库本身就会被判"库存不足"。这正是幽灵预留的成因。

### 2.3 `releaseForDoc` —— 按明细释放

取消/作废时按明细逐条释放（`status='released'` + `qty_reserved` 递减），
**不是**"重新按当前库存再拣一次"。

### 2.4 历史单据的兼容路径

确认早于本次修复的单据**没有预留明细**（那时代码从不写这张表）。它们必须还能发出去，
所以 `legacy` 分支保留旧行为，但做了一处收窄：

```
先拣"没有任何人占用"的货（includeReserved: false）
不够的部分才动用 qty_reserved 里的货（includeReserved: true）
```

历史单据的"占用"只体现在库存行的 `qty_reserved` 上，所以它确实有权动那部分；
但**先花"无主的"**，能少动一次别人的预留。

> 同时把 `seed.js` 的线上订单转单路径**补上来源登记** ——
> 重建之后的演示数据不再产出"没有明细的占用"，`legacy` 分支只服务于真正的旧库升级。
> 实测重建后不变量成立：`SUM(qty_reserved)` **等于** active 预留明细合计（11 = 11 / 0 = 0 / 5 = 5）。

### 2.5 不许落 0 数量发货单

```js
if (qtyAll <= 0) throw Object.assign(new Error('没有任何货可发…'), { code: 'NOTHING_TO_SHIP', status: 409 })
```

一张"已发货、0 件"的单没有任何业务含义，却会让订单看起来发过了、而库存一件没动 ——
**全链路没有一处会报错**。所以把"什么都没发"明确变成一个可断言的失败，
而不是一张静悄悄的空单。

## 三、同族入口一并收口

同一个形状在三个地方各写了一遍（这正是"同一份判据多个实现"的老问题）：

| 入口 | 原写法 | 现在 |
|---|---|---|
| `routes/sales.js` 确认 | `pickBatches` + `reserveStock`（无来源） | `reserveForDoc` |
| `routes/sales.js` 发货 | 重新拣选 + `releaseStock` + `applyStockOut` | `planShipment` + `applyStockOut` |
| `routes/sales.js` 取消 | 重新拣选 + `releaseStock` | `releaseForDoc` |
| `routes/oms.js` 转单（单笔/批量） | 同上 | `reserveForDoc` |
| `routes/oms.js` 发货回传 | 同上 | `planShipment` |
| `routes/oms.js` 退款 | 同上 | `releaseForDoc` |

**改法不是"在三个地方各修一遍"**，而是把这段逻辑抽成 `lib/stock.js` 的三个函数，
让六个调用点都变成一次调用。

## 四、回归与反例（`test-guards` G11）

| 段 | 断言 |
|---|---|
| 11a 正常闭环 | 确认后**登记了可追溯的预留明细**（原来 0 行）且数量等于订单量 · 全局 `qty_reserved` 确实增加 · 发货单 `total_qty > 0`（原来 0）· 订单推进到 `shipped` · **该单的预留全部被消费**（不留幽灵）· 全局 `qty_reserved` 回到基线 |
| 11b 两单竞争同 SKU | 先到者占满可用量 → 后来的订单确认 **400 库存不足** · **先到者的预留没被抢走** · 取消后 `qty_reserved` 回到基线 |
| 11c 取消按明细释放 | 取消前有 active 明细 → 取消后该单 active 归零 → 全局回到基线 |
| 11d 无货可发 | 注入"预留被清空" → 发货 **409 `NOTHING_TO_SHIP`** · **没有落下任何 0 数量发货单** · **没有产生空出库流水** · 清场后回到基线 |

> **用例自己踩过一次**：11d 的注入只把明细 `qty` 置 0，**没有同步减掉库存行的 `qty_reserved`** ——
> 于是注入本身制造了一处"数字对不上明细"的脏数据，最后一条基线断言变红。
> 这恰好说明**预留的两半（明细 + 库存行数字）必须一起变**；用例已按此修正。
