## 零、这一批修的是什么

三条，**两条是我自己修复里留下的洞，一条是我修复时造成的误伤**：

| # | 问题 | 性质 |
|---|---|---|

第 1、2 条错在"凭据没看全"，第 3 条错在"对象看错了"。

## 一、A16 反向：C 端令牌能当后台令牌用

### 1.1 现象（验收侧 §26.1 静态定位 → §27.1 动态坐实）

商城令牌作为 `Authorization: Bearer` 访问后台入口：

| 请求 | 修复前 | 现在 |
|---|---|---|
| `GET /api/docflow/overview` | **200 且返回数据** | 401 |
| `GET /api/purchase/settlements` | **200 且返回数据** | 401 |
| 任一 `requireAuth + requireWrite` 写入口 | **可过**（`requireWrite` 只挡 `viewer`，`role:'mall'` 不在其内） | 401 |

而"后台令牌进商城"这一侧第 3 批已经拦住了（401）。**也就是说隔离只做了半边。**

### 1.2 根因

```js
// 第 3 批的 C 端签发（写了 audience）
jwt.sign({ cid, phone, role: 'mall' }, JWT_SECRET, { audience: 'gml-mall' })
// 第 3 批之后的后台验签（**没要 audience**）
req.user = jwt.verify(token, JWT_SECRET)
```

`jsonwebtoken` 的 `verify` 在**不指定 `audience` 时不校验 `aud`**。
演示环境两套凭据共用同一个签名密钥，于是商城令牌在后台是**一张完全合法的登录态**。

### 1.3 为什么危险

`role: 'mall'` 在后台的语义是"一个既不是 viewer、也不是任何受限角色的用户"，
所以它在 `requireRole`（不指定 roles 时放行）、`requireWrite`、数据范围判定里
**都走"最宽"的那一条分支**。这不是"多看到一点"，而是**前台凭据直接变成后台身份**。

### 1.4 修复：两套凭据各自要求自己的 audience

| 位置 | 改动 |
|---|---|
| `middleware/auth.js` | 新增 `export const BACK_AUD = 'gml-erp'`；`signToken` 加 `audience: BACK_AUD`；`requireAuth` 改 `jwt.verify(token, SECRET, { audience: BACK_AUD })` |
| `routes/mall.js` | 已有 `MALL_AUD = 'gml-mall'`，签发与验签两侧都用它（第 3 批已对） |
| `middleware/auth.js` | `requireWrite` 从"只挡 `viewer`"改为**后台角色白名单**（`ROLES` 里有名字且非 viewer），并补 `!req.user → 401` |

`requireWrite` 那一条是**纵深防御**：它当前没有被任何路由挂载，
但"只挡一个具体角色"的写法意味着**任何将来新增的非后台角色都自动获得写权限**——
C 端 `mall` 就是这么过的。写闸要能自己识别"这不是后台身份"，而不是指望上游一定挂过 `requireAuth`。

### 1.5 教训

> **签的时候标了身份，验的时候也必须看这个标。只在签发侧加 `audience` 等于没加。**

"双向隔离"只要有一侧不验，就还是单向的。这与第 1 批 D2（"有登录态 ≠ 有资格"）同形，
只不过这次错在**我自己的修复里**：我在写 `signMallToken` 时想到了加 `aud`，
却在改 `requireAuth` 时"没想起来它得要求这个"。**改一侧判据时，必须把对侧一起过一遍。**

## 二、C 端会话的行业由请求头决定

### 2.1 现象（验收侧 §26.2 / §27.1 观察）

C 端令牌 payload 是 `{cid, phone, role}` —— **没有 `industry`**。
而 `server/index.js` 的行业解析是「先取 `x-industry` 头，令牌里有 `industry` 才覆盖」：

```js
let industry = req.headers['x-industry'] ? normalizeIndustry(...) : DEFAULT_INDUSTRY
if (payload.industry) industry = normalizeIndustry(payload.industry)   // C 端没有这个字段
```

⇒ C 端会话的行业**完全由请求方填的头决定**：一张 cosmetic 的令牌 + `x-industry: food`
就指向 food 库。验收侧实测：cosmetic 会话调 food 的会员入口 → **200**。

### 2.2 为什么危险

**行业决定读哪个库**。行业可被请求方指定，等于"换个头就能换一个库"——
数据隔离的最后一层是空的。而且它不报错：接口一切正常，只是读到了另一个行业的数据。

### 2.3 修复

1. **`industry` 钉进令牌**：`signMallToken(customer, industry)`，签发时写死；
2. **解析时一并处理 C 端令牌**：`index.js` 的行业解析原来只看 `Authorization`，
   而 C 端令牌走 `x-mall-token` ⇒ **两条头都要解析**，否则"钉死"只对把令牌塞进 `Authorization` 的调用方成立；
3. **加一道防回归**：`requireMall` 里比对 `payload.industry === getCurrentIndustry()`，不一致即 401
   （`index.js` 已钉死，所以正常请求恒等；这条断言的作用是——将来有人把"令牌带 industry"删掉、
   行业退回由头决定时，它会立刻红）；
4. 新增 `GET /api/mall/session`（C 端会话自省，返回 `{phone, industry}`）——
   它是"行业钉死在令牌"这条口径**可断言**的落点。

### 2.4 教训

> **参与授权与数据定位的上下文（身份、组织、行业、租户）都必须"签发时确定、之后不可改"。**

判断一次请求该读哪份数据的那些字段，只要有一个能由请求方提供，隔离就只写在文档里。
另一个具体坑：**同一类凭据可能有多个承载位置**（这里 `Authorization` 与 `x-mall-token`），
"在某处做了校验"必须逐个承载位置过一遍。

## 三、A03 修偏：授权判定的"对象"看错了

### 3.1 现象（验收侧 §27.2 A 级复现）

令牌组织 **5**，目标仓 **4** 的 `org_id=6` **在子树内**，显式 `owner_org_id=6` **也在子树内**，
却返回 `ORG_OUT_OF_SCOPE`，错误信息是"仓库 #4 的**货主组织 #1** 不在范围内"。

### 3.2 根因：判定的是"仓库默认货主"，不是"这次要用的货主"

```js
// 第 3 批写的
const owner = resolveOwnerOrg(db, warehouseId, null)   // ← 仓库默认货主
assertOrgInScope(ctx, owner, ...)
// 而本次真正传给引擎的是
applyStockIn(db, { ownerOrgId: args.owner_org_id ?? ctx.orgId ?? null })   // ← 显式传的 #6
```

**判定对象与使用对象不是同一个**。于是多货主仓库（一个仓里躺着多个货主的货）里，
"范围内仓 + 范围内显式货主"这样一个**完全合法**的请求，被一个**本次根本不会被用到**的默认货主挡住。

### 3.3 为什么危险

它不产生错误数据，只**拒绝正确操作** —— 所以特别难被发现：
没有越权、没有脏数据、没有告警，只是"这个仓入不了库"。
而它正是我在第 2 批写下的教训（"收紧一条门必须先跑一遍这条门原本该放谁进来"）
**在自己身上又犯了一次**：收紧判定时只跑了"该拒的"，没跑"该放的"。

### 3.4 修复：把"本次要用的货主"作为唯一判定对象

```js
function assertWarehouseInScope(ctx, db, warehouseId, { ownerOrgId = null, label = '仓库' } = {}) {
  // 仓库不属于本范围 → 拒
  assertOrgInScope(ctx, wh.org_id, `${label} #${warehouseId} 所属组织`)
  // 判定「**本次实际要用的货主**」：显式传了就用它；都没传才是仓库默认货主
  const explicit = ownerOrgId != null
  const target = explicit ? Number(ownerOrgId) : resolveOwnerOrg(db, warehouseId, null)
  assertOrgInScope(ctx, target, ...)
  return target   // 同时把解析结果交回调用方，**判定用的值与执行用的值从此是同一个变量**
}
```

调用点按"本次用哪个货主"逐个对齐：

| 工具 | 判定对象 |
|---|---|
| `stock_in` / `stock_out` | `args.owner_org_id ?? ctx.orgId ?? null` |
| `get_cost` / `pick_suggestion` | 同上（**读路径同样不能靠传参越界**） |
| `transfer` | 两仓各自的**默认货主**（本工具不接受货主参数，用默认是正确语义，不是误伤） |
| `ownership_transfer` | 两个**显式**货主 |
| `adjust` | 默认货主（无货主参数，货主由仓库推导） |

并且在 `stock_in` / `stock_out` 里把返回值**直接当作写库用的货主**——
"判定用 A、执行用 B"这种写法本身就是缺陷的温床。

### 3.5 双对照（验收侧 §27.2 要求的判据）

同一个仓、同一张令牌，只差"传不传货主"，一放一拒：

| 场景 | 期望 | 依据 |
|---|---|---|
| 范围内仓 + **显式范围内货主** | **成功**，且货落在显式货主上 | 修复前被默认货主误拒 |
| 同一个仓 + **显式范围外货主** | 403 `ORG_OUT_OF_SCOPE`，且无落库 | 不该放的仍然不放 |

为了让对照真的能区分修复前后，用例在跑之前把该仓的**默认货主临时改成范围外组织**：
修复前它会用这个不用的货主判定 ⇒ 误拒；修复后判定对象是显式货主 ⇒ 成功。

### 3.6 教训

> **"判定谁"和"用谁"必须是同一个值。** 只要这两者能不同，就一定会在某个维度上判错。

收紧任何一条门，回归里都要有一对**正向/反向**用例：
反向证明"不该放的确实被拒"，正向证明"该放的确实放行"。
**只有反向的回归，会把"门装成了墙"当成修复成功。**

## 四、两套凭据的完整口径（本次定型）

| | 后台 | C 端（商城） |
|---|---|---|
| 签发 | `POST /api/auth/login` | `POST /api/mall/login` |
| 密钥 | 同一个 `JWT_SECRET`（演示环境） | 同一个 |
| **audience** | `gml-erp` | `gml-mall` |
| 承载位置 | `Authorization: Bearer` | `x-mall-token`（也接受 `Authorization`） |
| 验签处 | `requireAuth`（**要求 `gml-erp`**） | `requireMall`（**要求 `gml-mall`**） |
| 角色 | `admin/purchase/sales/warehouse/finance/dealer/store/viewer` | `mall` |
| 行业 | 令牌携带，**头不能覆盖** | 令牌携带，**头不能覆盖** |
| 交叉使用 | 商城令牌 → 后台：**401** | 后台令牌 → 商城：**401** |

### G13 凭据双向隔离与 C 端行业钉死

| 断言 | 说明 |
|---|---|
| C 端令牌 → `GET /api/docflow/overview` = **401** | 修复前 200 且返回数据 |
| C 端令牌 → `GET /api/purchase/settlements` = **401** | 修复前 200 且返回数据 |
| C 端令牌 → `POST /api/sales/orders`（写入口）= **401** | 修复前能过写闸 |
| **不带 audience 的旧式令牌 → 401** | 反证"校验真的在跑"，不是"恰好没命中" |
| 正常后台令牌 → 200 | 对照：不能把后台一起挡死 |
| 后台令牌 → C 端接口 = 401 | 保留既有方向 |
| C 端令牌 + 谎报 `x-industry` → 行业仍是签发时那个 | **钉死**，`x-mall-token` 与 `Authorization` 两条通道都测 |
| 谎报行业读会员 → 仍读到**本库**那一行 | 钉死的**实质后果**（探针会员只在当前库存在） |
| 用例自还原（两个库的探针会员都清除） | 测试要能重复跑 |

### G9 正向对照（A03 修偏）

| 断言 | 说明 |
|---|---|
| 范围内仓 + 显式范围内货主 → **成功** | 修复前被"本次不用的默认货主"误拒 |
| 入库落在**显式指定的货主**上 | 判定对象 = 使用对象 |
| 同一个仓 + 显式范围外货主 → 403 | 对照的另一半：不该放的仍然不放 |
| 越界那次没有落库 | 拒绝 = 什么都没发生 |
| 用例自还原（默认货主与本次库存行都已清） | 用例临时改过仓库默认货主，必须还原 |

## 七、对外行为变更（对接方须知）
