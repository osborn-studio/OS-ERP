## 一、两条独立的缺陷，都属"配了但没生效"

| # | 现象 | 为什么不报错 |
|---|---|---|
| 1 | `docker-compose.yml` 配 `JWT_SECRET`，而代码只读 `process.env.GML_JWT_SECRET` | 代码有**内置回退密钥** —— 读不到就用演示密钥，服务照常起来，只是**所有人都知道密钥是什么** |
| 2 | `requireAuth` 在 `jwt.verify` 之后**直接把 payload 当 `req.user`** | 令牌本来就"验得过"，只是里面装的是**登录那一刻的快照** |

共同形状：**配置/授权"看起来配了"，但真正起作用的是另一份东西。**

## 二、缺陷 1：改名不能只改一处

```yaml
# docker-compose.yml（原来）
JWT_SECRET: ${JWT_SECRET:-gml-demo-secret-change-me}
```
```js
// server/middleware/auth.js（原来）
export const JWT_SECRET = process.env.GML_JWT_SECRET || 'gml-supply-chain-demo-secret-2026'
```

容器里 `JWT_SECRET` 谁都不读；`GML_JWT_SECRET` 没人给 ⇒ **一直用回退密钥**。
README 里写的也是 `GML_JWT_SECRET` —— 也就是说**文档是对的、compose 是错的**，
而错的那一侧不会导致任何故障，只会让"我们换过密钥了"这句话不成立。

**修复**：两侧同时动 ——
- 代码：`process.env.GML_JWT_SECRET || process.env.JWT_SECRET || <演示回退>`（兼容旧名字，避免"改了 compose 忘了别的部署方式"）；
- compose：统一为 `GML_JWT_SECRET`（与代码、README 一致）。

> 教训：**凡"改了名字"，都要问一句：还有谁在用旧名字？**
> 而"读不到就回退"的写法会把"名字对不上"变成一条**静默成功**的路径 ——
> 这正是它比"启动报错"更危险的地方。

## 三、缺陷 2：令牌是"声明"，权限与可用性必须以库为准

原来：

```js
req.user = jwt.verify(token, JWT_SECRET)   // payload 直接当 req.user
```

于是三件事都不即时生效：

- **停用账号** → 旧令牌最长还能用 12 小时；
- **角色降级** → 旧令牌里仍是老角色，**权限跟着旧角色走**；
- **账号被删除** → 令牌照样畅通。

在权限系统里这是很重的问题：**撤了权却还能用，而且不报错** ——
管理员以为已经撤掉了（这与第 5 批"凭据双向隔离"是不同性质的一件事：
那条管"谁的令牌能进哪个入口"，这条管"撤权之后还灵不灵"）。

**修复**：每次请求回库核对一次，用库里的值覆盖 token 里的：

```js
const u = getDb().prepare(
  'SELECT id, username, name, role, is_super, status, dealer_id, store_id, org_id, data_scope FROM users WHERE id=?'
).get(p.uid)
if (!u) return fail(res, '账号不存在或已被删除，请重新登录', 401, 401)
if (String(u.status || 'active') !== 'active') return fail(res, '账号已停用，请联系管理员', 403, 403)
req.user = { ...p, uid: u.id, username: u.username, name: u.name, role: u.role,
             is_super: u.is_super, dealer_id: u.dealer_id, store_id: u.store_id,
             org_id: u.org_id, data_scope: u.data_scope }
```

> 教训：**token 是"我是谁"的声明，不是"我有什么权限"的凭证。**
> 凡是"登录时算好、之后一直用"的东西（角色、组织、门店、数据范围、租户），
> 都要问一句：**它变了以后，手上这张旧凭据还灵吗？**
> 代价是每请求一次索引查询 —— 对本地 SQLite 可以忽略，
> 换来的是"撤权即时生效"这个**能被验收的性质**。

## 四、一个必须一起改的连带影响（测试手法）

修完之后，`test-guards` 里的跨主体用例**立刻红了 6 条** ——
因为它们原来是这么造"另一个门店"的：

```js
forge({ uid: uidStore, role: 'store', store_id: otherStoreId })   // 同一个真实用户 + 改 token 内容
```

"以库为准"之后，**token 里的 `store_id` 不再生效**，那份伪造自然失效。

正确做法是**在库里造一个真实的探针用户**：

```js
makeProbeUser({ username: 'guard_store_b', role: 'store', storeId: otherStoreId })  // 不走登录，故不需要密码
```

用完删掉（`probeUserIds` 统一清理）。顺带把 `rw`（写连接）提前到用例开始前。

> 这条本身是个好信号：**修复让"伪造 token 就能换身份"的测试手法失效**，
> 说明修的确实是那个行为。反过来说，如果修完之后那些用例**照样能过**，
> 就得怀疑"是不是根本没修到"。

## 五、回归补强（没有反例的修复不算修完）

`scripts/test-guards.mjs` 新增 **G17**（8 条/库）：

| 反例 | 期望 |
|---|---|
| 基线：viewer 走写入口 | 403 |
| **把库里的角色临时改成 admin** | 同一张旧令牌**立刻获得该角色**（不是登录时的快照） |
| 改回 viewer | 同一张令牌**立刻变回 403**（**撤权即时生效**） |
| **把账号 `status` 改成 `disabled`** | 旧令牌立刻 **403「账号已停用」**（原来最长还能用 12 小时） |
| 恢复账号 | 回到基线行为（对照：不是把账号整体挡死） |
| 令牌指向**不存在的用户** | **401**（原来会当成 admin 放行） |
| 用例自还原 | 角色 / 状态 / 探针用户全部恢复 |

## 七、对外行为变更

| 变更 | 影响 |
|---|---|
| `GML_JWT_SECRET` 与 `JWT_SECRET` 都认 | 部署方两个名字都能用（推荐前者） |
| 每次请求多一次 users 查询 | 本地 SQLite 可忽略；换来的"撤权即时生效"是可验收的性质 |
| **停用账号后旧令牌立刻失效** | 这是修复；运维上"停用即踢下线"从此成立 |
| 角色变更立刻生效（升也即时、降也即时） | 同上 |
| 删号后旧令牌 401 | 原来会当成 admin 放行 |
