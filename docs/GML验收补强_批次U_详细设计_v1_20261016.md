## 一、本批起点与口径

用户口径是「**全部做，完美验收全部**，钉钉飞书与**外部接口**先不动」。

上一批（批次 T）已经把钉钉飞书里**不依赖真实租户**的那部分做完了 ——
`lib/im-sync.js` 的组织同步 / 审批同步 / 冲突判定、`/api/im/self-test` 的全链路自检
（在一个会回滚的事务里跑完，库里一行都不多）。真实租户调用声明为「未实现」并且**如实写在契约里**
（`real_call_ready: false`）。所以本批**不重开这条线**，也不去碰外部接口。

本批真正的起点不是"再补几个用例"，而是一句话：**"完整验收"由开发侧自己先做一遍**。
九条硬标准里明确要求「**逐动作**覆盖，含 `is_danger=0` 但带副作用的边」与「反例不改库」。
这两条把工作量从"写断言"变成了"造得出反例 + 证明断言真的抓得住"。

于是本批交付的是**三样东西**：一套能独立跑的验收台（可重跑、留证据、挂固定提交）、
一批**先红后证**的注入式反例、以及在做这些的过程中**真实抓到的三条缺陷**。

另外，本批还有一个**新功能**：「**现金流量项目辅助核算**」（编号 **②-2**）——
它是本批最大的一块，单独写在**第六章**。它与「③ 报表纵深之四」「④ 跨年度报表」
**不是同一条线**：②-2 已经交付；③④ 也已交付（**已实现 · 已配反例 · 独立复核进行中**，见 8.1 的修订说明）——
但**它们的作者不是本文档作者**，所以本文档**不充当它们的验收依据**。

## 三、统一业务码落点

### 3.1 问题：同一个码，因**入口不同**而落在不同字段

「业务码」是错误对象上的 `code` 字符串（`PERIOD_CLOSED` / `DOC_STATE_ILLEGAL` / `PAY_NO_SUPPLIER`…）。
它原先有**三处落点，形状互不相同**：

| 入口 | 改前形状 | 业务码在哪 |
|---|---|---|
| `lib/http.js` 的 `failFromError` | `fail(res, e.message, e.status, 1, { code: e.code, ... })` | 只在 `detail.code`，顶层**没有** `error` |
| `middleware/audit.js` 的 `errorHandler` | `{ code: err.code?1:status, success:false, message, error: err.code, detail: err.detail }` | 只在顶层 `error`，`detail` 里**不带** `code` |
| `routes/docflow.js` 的 `handleFlowError` | 两处都写 | 顶层 `error` **与** `detail.code` |

**不统一会怎样**：调用方为了读一个码得写 `b.error || b.detail?.code` 两套判断，少写一半就漏判；
而"漏判"的表现不是报错，是**错误提示退化成一句中文** —— 用户报障时无从定位。
更麻烦的是这类"形状漂移"**不会让任何测试报错**：两条入口各自都能跑通，
所以它只会一路静默地扩散。

### 3.2 收敛：唯一构造点 `bizFail`

```text
server/lib/http.js
export function bizFail(res, err)                       ← 唯一构造「带业务码的失败响应」的地方
  status = err.status || err.httpStatus || err.http || 500
  body   = { code: code ? 1 : status, success: false, message: err.message || '服务器内部错误' }
  有业务码 ⇒ body.error = code
             body.detail = { code, ...(err.detail || {}) }
  无业务码 ⇒ 不写 error；err.detail 存在时原样透传（保持旧中间件行为）
```

**为什么 `error` 与 `detail.code` 两处都写**：这两个读法各自都已有使用者
（前端历史读法 + 三套测试里的 `detail?.code || error` 兜底），删任何一处都是破坏性改动。
两处同值是最小代价的兼容，等读法统一后再收一处。

**为什么 `status` 要认三个字段名**：各领域错误类的字段名不统一 ——
`DocFlowError`/`PurchaseError` 写 `.status`+`.httpStatus`，`ImError` **只写** `.httpStatus`，
`ArError`/`InvoiceError` 额外写 `.http`。少认一个，那类错误就会被报成 500，
而 500 会把排查方向从「我的参数不对」带偏到「服务器挂了」。

这条兜底链后来抽成了**唯一出处** `statusOf(err)`（`lib/http.js:45`）：
`bizFail` 用它定**响应码**，`errorHandler` 用它决定**要不要打 `[error]` 日志**。
两处各算一遍、字段顺序还不一样时，就会出现「**日志里的码 ≠ 用户看到的码**」——
只有 `.httpStatus`/`.http` 的错误按 `err.status || 500` 会算成 500，日志记 500、响应实际 400，
于是一条参数错误在日志里被读成"服务器挂了"。

三个入口全部改成薄封装，各自只保留"这算不算业务错误"的判定：
`failFromError`（`lib/http.js:84`）、`errorHandler`（`middleware/audit.js:36`）、
`handleFlowError`（`routes/docflow.js:57`，为可测性改为 `export` —— 不导出就无法在进程内对拍三入口形状）。

### 3.3 真正的收益在"收编"：22 处形内手写

把三处收敛完，守卫第一次跑就**扫出另外 21 处**形内手写点（产出的是旧形状 ——
只写 `detail.code`、顶层没有 `error`）。随后又发现第 22 处：

- **第 22 处是 `routes/sales.js` 的 `CREDIT_BLOCKED`**，它是**多行**写法
  （`fail(res, \`信用校验未通过：…\`, 409, 1, { code: 'CREDIT_BLOCKED', detail: credit })`），
  单行 grep 漏了它。
- 它是**被升级后的守卫（Ⅱ 级 `fail()` 参数式）第一次跑就揪出来的** ——
  旧判据只认"含 `success:false` 的对象"，而这一级**不含 `success:false`**（`success` 由 `fail()` 自己写），
  所以旧判据对它**永远静默**。

**这一条最值得记的不是"22 处"，是"守卫自己漏过什么"**：

| 漏过的形态 | 为什么漏 | 现在怎么防 |
|---|---|---|
| `success: false` 的对象里**只写 `detail: { code }`**（不写 `error:`） | 第一版判据要求"`error:` 与 `detail:` **同时**出现" | 改成：只要有**业务码**（非数字字面量的 `code`，含简写）就算构造点 |
| `detail: { code: 'X' }` —— **`code` 是第一个键** | 正则要求 `code` 前面是 `{` 或 `,`，而 `{ code` 里的 `{` 已被 `\{` 吃掉，剩下前导是空格，匹配不上 | 同上（换成"业务码"判定而不是"键位"判定） |
| `success: !1`（压缩器产物） | 用 `indexOf('success: false')` 找起点，写法变体直接穿透 | 改成正则 `success\s*:\s*(?:false\|!1)` |
| `fail(res, msg, 409, 1, { code })` —— **`success` 不在字面量里** | 判据只扫"含 `success:false` 的对象"，这类对象里压根没有它（`fail()` 自己写） | 新增 **Ⅱ 级**：把 `fail()` 的实参整段取出来找业务码 |
| `const body = { code: e.code }; fail(res, m, 409, 1, body)` | Ⅰ 看不到（无 `success:false`），Ⅱ 也看不到（实参位上只有标识符） | 新增 **Ⅲ 级**：同文件数据流（收集"字面量里带业务码"的变量名，看它有没有出现在 `fail()` 实参里）；**跨文件/跨函数仍看不出来**，如实写在判据注释里 |
| 注释里写的形状说明把自己带偏 | 扫描不剥注释 | `stripComments` 先剥注释再匹配；字符串/模板字面量用**等长填充**遮住（保留换行，否则行号整体错位）—— 否则错误文案里的 `code: ` 会**误报**，而全遮又会把 `code: 'X'` 的真业务码一起遮掉 |

**⚠️ 上面这张表还漏掉了一条最重要的**：判据**自己有没有失效**这件事，最初也没人管 ——
于是"**扫不到**"与"**真干净**"在输出上长得一模一样（本次就是这样全绿的）。

**判据退化时的表现不是变红，而是变绿。** 实测两件事都成立：

- 把 **Ⅰ 判据退回历史版本**（就是当年真漏过 `detail:{code}` 首位 / 顶层 `code` 简写 /
  改名 helper / `success:!1` 的那一版）⇒ **「真实扫描」那一格仍然是绿的 —— 假绿**；
- 把**扫描器整个打瘫**（`bizCodeHits` 直接 `return []`）⇒ 同样**绿**。

所以"这次真的干净"必须与"这次根本没扫到"**在输出上可区分**。这条区分现在由
**合成违规样本 + 一条干净对照样本**的反向自检守住（9 条「自检：」断言）：
`F1` 拼失败对象 + `error:` 键 / `F2a` `detail` 里 `code` 是**第一个**键（当年穿透的就是它）/
`F2b` `code` 在展开之后 / `F3` 顶层 `code` 用**简写**（qimen.js 的真实形态）/
`F4` Ⅱ `fail()` 第 5 参放 `code`、跨 7 行 / `F5` Ⅲ 先放中间变量再传 `fail()` /
`F7` 另起一个不同名字的同类助手 / `F9` `success` 写成压缩风格 `!1`；
外加**干净样本不许被误判**（判据不能"见谁都咬"）。
而且**自检自己也有反例**：`S1` 判据退回、`S2` 扫描器打瘫 —— 各自让自检变红，
并打出一条「**⛔ 扫描器失效**」横幅。

> **配套判据：「少判一条就报」，而不是「一条都判不出才报」。**
> 判据通常是**部分**退化（换个正则、少认一个键名），而部分退化**同样产生假绿、
> 且比全瘫更危险** —— 因为它看起来还在工作。

**声明边界（漏检但不修，如实记）**：对象键被**动态拼接**时（`{ ['co'+'de']: x }`）
静态判据抓不到 —— 越加正则越容易误报，而**会被忽略的守卫等于没有**，
所以判为边界、不修。⚠️ 它**不在**上面那 9 条自检的编号里（自检里的 `F7` 是另一件事）。

判据升级这一步本身也要给证据：**拿收编前的形态跑一次，守卫必须变红**。
本轮的实测：把 `quote.js` / `sales.js` 改回旧写法 ⇒ 守卫恰好红在
`静态：server/ 下（除 server/lib/http.js）无任何形内业务码构造点` 上，
并指名 `server/routes/quote.js:44（Ⅱ fail() 参数式）`；还原后回绿。

### 3.4 声明名单：不是所有"码"都该收编

守卫有**两类**声明，**刻意分开**（混在一起会让"豁免"这个词失去意义）：

**（甲）`DECLARED_ALIEN` —— 命中判据、但刻意保留（当前 1 条）**

- `server/routes/qimen.js` 的 `json({ success: false, code, message, ...extra })` ——
  **奇门标准化协议**：承接方一律回 **HTTP 200**，成败放在响应体的 `{ success, code, message }` 里，
  `code` 是**协议错误码**（`'1001'/'1002'/'9999'`…）。它的消费者是**外部 ERP/平台**，不是本项目前端；
  改成 `bizFail` 的项目信封（顶层 `code` 数字 + `error`/`detail.code`）会**直接违反协议**。
  同文件里成功响应也是 `{ success: true, code: 0, ... }` —— 可见这是"整个网关不属于项目信封"的
  协议级决定，不是漏改。
- 定位方式：用**行内容**（`contains: 'json({ success: false, code, message, ...extra })'`）而不是行号 ——
  行号会在任何人插入一行注释时漂掉，而"漂了也红"是这条断言的义务。
  名单里的落点如果消失了（被收编成 `bizFail`），守卫也会提醒删掉这一条，
  否则它会在将来变成一张**过期通行证**，悄悄豁免掉同一位置上的新写法。

**（乙）`ENVELOPES` —— 不命中判据、但必须记账（当前 2 条）**

判据只覆盖"响应体的失败形状"。下面这些通道的码**不由响应体形状表达**，
所以判据扫不到 —— **扫不到不等于不存在**：它们是"一个业务码、多种读法"的既成事实，
必须声明出来，并且每条都断言"仍然存在"，否则文档与代码会各说各话。

| 通道 | 它是什么 | 为什么不属于项目信封 |
|---|---|---|
| **MCP `toolError`**（工具级错误） | 外层是 MCP 规范的 `result.isError`（不是 JSON-RPC error），消费者是 **Agent 宿主**，线格式由规范定 | payload 内部**沿用项目字段名** `{error, message, detail}`，所以会读 `bizFail` 的人就会读它。**已声明的差异**：它只在 `error` 一处给码、**没有 `detail.code`** —— 跨通道两种读法是既成事实，统一它**是另一件事**，本批不做"应该统一"的判断 |
| **MCP `rpcError`**（协议/传输层错误） | JSON-RPC 的 `error.code` | 它是**协议层**码，不是业务码；"与业务码归类不同"是刻意的 |

**（丙）顺带记一笔：形内手写失败形状（**无业务码**）恰好 7 处**

这是**棘轮**式断言（`HANDWRITTEN_DECLARED = 7`）：这 7 处与 `fail()` **逐字节相同**，
只是把信封抄了一遍、码用的是数字/固定的非业务码。它们**不构成**业务码构造点，
但"改信封时要记得改它们"—— 写死数量是为了让**新增**第 8 处时变红，
逼人回来判断"这是一处新的重复，还是我该收编它"。

**（丁）保留键 `code` 也进了判据**

「业务码用 `code`、非业务码另起名」这条约定原先只是注释（见 3.6 第 1 条的翻车）。
复核线在同批内补了一条静态断言把它变成可核对的：
`静态：没有把保留键 code 当 detail 键名的地方（协议号之类请改用 agreement_code 这类名字）`。

### 3.5 对外形状变更一处（需留痕）

`routes/sales.js` 的信用拦截，`detail` 由 `{ code: 'CREDIT_BLOCKED', detail: credit }`
改为 `{ code: 'CREDIT_BLOCKED', ...credit }`（`credit` 展平）。

**第 2 条的"三段式"（照 team-lead 给的标准句式，不简化成任何一头）**

> **防御性统一：两处 guard 的兜底分支形状与另外 13 处不一致，构造上会挂住请求（已用探针实测机制），当前业务路径不可达。**

1. **今天不可达**：`code: null` / `code: ''` 全仓 **0 处**，`PurchaseError` / `DocFlowError`
   构造器对 `code` 都有非空默认值 ⇒ **当前仓库里没有任何路径能触发**。
   所以它**不是**"修了一个正在发生的故障"。
2. **但后果经实测确认，而且比"报错"更坏**：在隔离副本里注入一个走**真实 `guard()`** 的探针路由，
   抛 `new PurchaseError(msg, { code: null, httpStatus: 400 })` ——
   - **buggy 版**：客户端 **5s 超时**（**一个响应都没有**），**且服务端连一条日志都没有**（静默挂住）；
   - **修复版**：**2ms** 拿到 `400 {"code":400,"success":false,"message":"…"}`。
   所以这条的红是**超时**而不是断言红 —— 断言得**带 5s 上限**才抓得到它。
3. **一处事实更正（两份复核结论冲突 → 以实测为准）**：另有复核说"13 处 `failFromError` 调用点都有 `throw e` 兜底"，
   **数错了一处，而且处数不是 13 是 15**；原先**是 13 处本来就对、2 处不对**。
   15 处：`report:37` · `refund:24` · `purchase-chain:49` · `meta:108/126` · `dms:29` · `accounting:26` ·
   `mall:437/469/552` · `promo:89` · `pos:197/230/309` · `purchase:43` —— 现在**全部**是
   `if (failFromError(res, e)) …` 带 `throw e` 兜底的形状。

**"这五处为什么会一起出现"**：它们的共同点是**在形状统一之后才看得见**——
形状互不相同时，读的人会以为"这是另一个入口的约定"；统一之后每条路径都长一个样，
于是"这一处为什么不一样"才变成问题。**统一不是终点，是把问题变得可读。**

> 另一条副产品：第 1 / 第 5 条把"`code` 是**保留键**"从口头约定变成了可核对的判据
> （见 3.4 丁）。这正好回答了"注释里的约定为什么靠不住"：它靠得住的前提是**有东西在读它**。

**⚠️ 复核线自己引入并修掉的一个问题（记在这里，因为它是本轮最容易被重复的错）**

**那条"保留键"判据的第一版只扫 `detail: {` 字面量 ⇒ 反例 C5 没有变红。**
根因：`agreement.js` 的 detail 是**位置参数**（`new AgreementError(code, msg, status, detail)`），
源码里**根本没有 `detail:` 这三个字**。改成"读每个错误类的构造器签名、按 `detail` 的参数位取实参"之后才红。

> **同一个盲区连着坑了两次**：前一次它让上一轮把第 1 条误判为"不可达"（扫描清单只看了 `detail:` 字面量），
> 这一次它让一条反例**静默地没红**。
> **教训：反例没红，先怀疑"反例没造对"，别急着宣布"没漏"。**

## 四、MCP 参数下界

### 4.1 起点：`assertPositiveQty` 一直都在，但**没被执行**

`inventory.stock_out` 传 `qty: -5`，**不报错**，返回
`{ summary: '出库 -5，涉及 0 个批次', picks: [] }` —— 一个**成功**的响应。

根因不是"少写了一个 if"：handler 在 `!args.batch_no` 时走自动拣选
（`pickBatches(..., -5)`），非正需求让它返回**空拣选**；于是下面那个
`for (const pk of picks)` 一次都不跑，最后照样 `return ok(...)`。
而 `lib/stock.js` 的 `assertPositiveQty` **一直都在**，注释还专门写了
「`applyStockOut(-5)` 在旧实现里不会报库存不足……库存反向增加 5 件」——
**它的调用点在循环里**。循环不进，判据就没被执行。

> **判据存在 ≠ 判据被执行**：一条判据只要挂在"可能一次都不跑"的分支上，它就等于不存在。
> 同一个洞在 `inventory.transfer` / `inventory.ownership_transfer` 上一样成立
> （都是"先拣选、后循环"的形状）。

### 4.2 修法：闸门**下沉**到参数校验层

放在 handler 里修是治不好的 —— 下一个 handler 还会再犯一次。
所以闸门放到 `server/mcp/validate.js`（**参数校验层**，所有工具调用的必经之处）：

- 支持 `exclusiveMinimum`（`validate.js:41-46`），与既有的 `minimum` / `maximum` **同一处**（唯一出处）；
- `S.num` / `S.int` 接受第二个参数作为**额外 JSON Schema 约束**（`tools.js:36`）；
- 声明（共 **5 处** `exclusiveMinimum: 0`）：
  `inventory.stock_in.qty`、`inventory.stock_out.qty`、`inventory.transfer.qty`、
  `inventory.ownership_transfer.qty`（`tools.js:932/978/1025/1067`）、
  `purchase.create_payment.amount`（`tools.js:1547`）；
- 另有 `unit_cost: { minimum: 0 }`（`tools.js:933`）—— 这里是**含零**的，成本可以为 0。

**`create_payment.amount` 为什么要单独列**：它的描述本来写着「> 0」，
而此前**没有任何东西在入口处兑现这句话** —— 自称的元信息必须由实算派生。

**刻意不列 `inventory.adjust.delta`**：**负数是它的合法取值**（正 = 盘盈 / 负 = 盘亏）。
一刀切会把一个正确功能改成缺陷 —— 拦"看起来像错的"，比漏拦更危险。

### 4.3 常驻守卫为什么写成"必须被拒"

`scripts/test-mcp.mjs` 的 **T9**（`section('T9 数量类参数的下界 …')`）数据驱动地断言
7 组 `(工具, 参数, 非法值)` **必须**被参数校验层拒掉
（`stock_in.qty=-5/0`、`stock_out.qty=-5/0`、`transfer.qty=-1`、`ownership_transfer.qty=0`、
`create_payment.amount=-1`）。

**判据刻意写成"必须被拒"而不是"schema 里有没有写约束"**：
后者在约束被删掉时**不会变红**（没有约束就没有断言 —— 正是那种"安静的洞"）。
反例已验：注入 E 把 `exclusiveMinimum` 去掉 ⇒ T9 的
`A17b MCP 负出库被拒` / `A17b 拒绝理由说清是数量非法` 变红。

## 五、库存参数读取口径

### 5.1 现象

`server/lib/stock.js` 的 `getInvParam`，同一个函数里两个分支**口径不一致**：

```text
scope_value 分支：  … WHERE param_key=? AND scope_value=?  ORDER BY id DESC LIMIT 1
global 分支（旧）： … WHERE param_key=? AND scope='global'                 LIMIT 1
```

### 5.2 为什么这是真缺陷（不是"风格不一致"）

SQLite 在**没有 `ORDER BY`** 时按 **rowid 升序**返回行，所以 `LIMIT 1` 拿到的是
**最早**那一行 —— 也就是说「后来补了一行新配置」是**确定性不生效**，不是"看运气"。
实测：先插 `OLD` 再插 `NEW`（两行同名 `global`），`getInvParam` 读到的是 **`OLD`**。

而"**手工补一行参数**"恰恰是现场与验收最常走的操作：例如真实场景要把"待检区隔离"打开，
就是把 `inv_params.block_pending_qc` 置 1 —— 而这个键在种子里**根本没有这一行**
（只在 `lib/stock.js` 的注释里被提过一次），所以现场只能手工补。
补完不生效、又不报错，排查时会先怀疑"闸门没实现"，而不是"我的参数没被读到"。

### 5.3 修法

`stock.js:189-191` 的 global 分支补 `ORDER BY id DESC`，与 `scope_value` 分支同口径 ——
**同一件事不能有两个写法**。注释里写清"同一键多行时以最新一行为准，理由是什么"。

### 5.4 常驻守卫为什么放在 `test-guards` 而不是验收台

`test-guards.mjs` 的 G12 组新增 **A12b**（3 条断言）：造两行同名 `global`（先 `OLD` 后 `NEW`），
断言 `getInvParam` 读到 **`NEW`**；收尾删干净并自我断言。

判据刻意是**行为断言**（读到哪个值）而不是"源码里有没有 `ORDER BY`" ——
后者在子查询被改写、或 `ORDER BY` 被挪到别处时**不会变红**。
放在 `test-guards` 而不是 `selfcheck` 的理由：它是库存引擎的读取口径不变量，
而 `test-guards` 在回归里**每轮 × 三库都跑**，覆盖比"只在验收台跑一次"广 ——
判据该放哪儿的问法是"哪种跑法会更多地碰到它"，不是"哪个文件方便"。

反例已验：去掉 `ORDER BY id DESC` ⇒ A12b 的
`同一 global 键多行时读到**最新**那一行` 变红（`实际 "OLD" / 期望 "NEW"`），还原后回绿。

## 六、现金流量项目辅助核算（②-2，本批最大的新功能）

### 6.1 起点：现金流量表原先只能"猜对手科目"

034 把三张报表做出来了，但现金流量表是**分析填列**：拿凭证里非现金那几笔的**对手科目**
去套报表行的科目区间。这在**单边凭证**上够用；到了**复合凭证**（一笔收款同时冲应收账款、
预收账款、主营业务收入、应交销项税）就只能把净额扔进兜底行
（「其他（未能归类的现金收支）」）。

于是「经营活动到底收了多少现金」这句话，答案是**推出来的**，不是**记下来的** ——
而"推出来的"与"记下来的"在报表上长得一模一样，没人分得清，也没人说得清差在哪。

本批把「现金流量项目」做成一个**跨科目的独立维度**：分录上标一个项目 code
（`voucher_entries.cash_flow_item`），归集时**优先按它走**。

### 6.2 为什么是"一张字典表 + 分录上一列"

**不是**往科目表加一个 `aux_type` 取值。理由：
`accounting_subjects.aux_type` 承载的是"**这个科目**要挂客户还是供应商"，那是挂在某个科目上的属性；
而现金流量项目是**跨科目**的 —— 同一个「销售商品、提供劳务收到的现金」
要能同时落在应收账款 / 预收账款 / 主营业务收入 / 应交增值税-销项税额上。
把它做成科目上的枚举，等于**每加一个报表项目就改一次科目表结构**，而科目表是主数据 ——
**主数据不该因为报表口径而变**。

数据结构（迁移 `041_cash_flow_item`）：

| 对象 | 内容 |
|---|---|
| 新表 `cash_flow_items` | `id` / `code`（UNIQUE，机器键）/ `name` / `category`（`operating\|investing\|financing`）/ `direction`（`in\|out\|both`）/ `is_builtin` / **`report_line_code`（项目 → 报表行的**显式**落点，可空）** / `sort_no` / `status` / `remark` / 时间戳 |
| 新列 | `voucher_entries.cash_flow_item TEXT`（可空；`addColumn` **幂等**；**存量分录一律留空、不回填**） |
| 索引 3 条 | `idx_cfi_category`（`category+sort_no`）/ `idx_cfi_status` / `idx_voucher_entry_cfitem` |
| 内置项 | **22 条：经营 10 / 投资 6 / 筹资 6**（全部行业中性，无任何真实客户名或品牌名） |
| 权限点 2 个 | `finance.cashflow.item.view`（admin/boss/finance）、`finance.cashflow.item.edit`（admin/finance） |

**`report_line_code` 为什么要显式写成一列**：项目比报表行**细**（22 个项目 → 现金流量表 10 个科目行），
所以"同 code 对应"这条路走不通。而靠**命名约定**匹配更危险：报表行可以被人在界面上改
（`finance.report.config`），改完名字之后靠约定匹配就会**静默错行** —— 而报表看起来完全正常。

**为什么不把存量凭证一次性回填**：回填只能靠"分析填列"再写回去 ——
那等于把**推测**固化成**事实**，而且之后再也分不清哪一条是推的、哪一条是记的。
（实测：新库里 `cash_flow_item IS NOT NULL` 的分录 **0 条**，与"不回填"一致。）

**迁移的幂等与自证**：def 指纹**含 items 代码清单** ⇒ 以后加项目会自动重跑 `up`；
`verify` 守 4 条不变量（取值域 / 分录标记句句有出处 / 内置项一条不少 / 指纹不脱节）。
三个**开发库已在 041**（跑 `test-guards` 这类脚本时 `bootAll` 顺带迁的）；迁移本身在临时目录验证过。
作者另在临时库上实测：22 条内置项齐、三条索引齐、`voucher_entries` 有 `cash_flow_item` 列。

### 6.3 填列口径：唯一的岔路口是 `if (tagged.length === 0)`

`lib/report.js` 的 `cashFlowBuckets()`（`:1295`）里**只有一个**地方要分叉（`:1403`）：

- **有标记**（`tagged.length > 0`）⇒ 按项目 `report_line_code` 落到对应报表行，**剩余非现金分录的净额**进兜底桶；
- **零标记** ⇒ 走的分支与**改造前逐字一致**（纯对手科目分析填列）。

**为什么要把岔路口收敛成一个**：这条新功能最大的风险是"**老账算出来变了**"。
把它做成"一条 if"，就让"没标记时结果不变"从一句承诺变成一个**可对拍**的命题（见 6.4）。

新增返回字段（让"标了多少 / 推了多少"能被看见）：
`item_buckets` / `tag_supported`（`:1451`）/ `tagged_count` / `untagged_count` /
`tagged_vouchers` / `tagged_unresolved_count`（`:1455`）。

### 6.4 「无标记时结果不变」怎么证的（三层对拍）—— 本批最该被复制的部分

一句"兼容旧口径"如果是靠**读代码**得出的，它随时会失效。所以它是**三层各自独立的证据**：

**第 1 层（独立参照实现）**：测试里**照 034 的算法独立重写了一份旧口径参照实现** ——
只共用"口径读取/解析"的纯工具，**不引用被测函数的任何内部结果**。
对每个已过账期间，逐行金额 / 合计 / `cash_in·out·net` / 凭证数 / **对手科目分桶**逐字节对拍。
并且断言「**至少一个期间分桶非空**」来**防空跑** ——
否则"两边都是 0"也会被判成"相同"，那是最典型的假绿。

**第 2 层（自造期间覆盖形态）**：造一个自造期间 **2099-07**，覆盖 **5 种凭证形态**：
现金内部划转 / 复合凭证两侧都有 / 单边流入多笔同向 / 单边流出。
再对一次，并断言**兜底行 = 300** —— 证明它**真的走了净额法**，不是空跑。

**第 3 层（等价于"041 之前的库"）**：把快照里的**字典表删掉**
（于是 `tag_supported=false`，等价于 041 之前的库），结果必须与迁移后的库**逐字节相同**；
空期间逐行全 0。

> 三层的分工：**第 1 层**证明"算法同源"，**第 2 层**证明"参照实现真的跑到了净额那一支"，
> **第 3 层**证明"没有字典表时也不会炸、也不会变形"。
> 只做第 1 层会漏"参照实现自己也是空的"；只做第 2 层会漏"老账整体变了"。

### 6.5 探针：只查不修

两个探针接进 `auditReport`（`lib/report.js:2739` / `:2752`）：

- **`CF_ITEM_UNKNOWN`** —— 分录挂了字典里**不存在**的项目；
- **`CF_ITEM_DOMAIN`** —— 字典的**取值域被写坏**（`category` / `direction` 出现非法值）。

**只查不修**：探针的职责是"如实报出来"，不是自动改数据 ——
自动修会把"谁写坏的"这条线索一起抹掉。

### 6.6 打标记的闸门：**差分驱动**（为什么这里要理由、那里不要）

`tagVoucherCashFlow()`（`lib/report.js:1173`）：

- 在**空白**分录上第一次标 ⇒ **日常动作，不要理由**；
- **清除**或**改动"已经标过"**的分录 ⇒ 必须写理由（`CF_TAG_REASON_REQUIRED`，`:1254`）——
  把一笔已经定性的钱改到别的项目上，等于**改这一期报表的一行金额**；
- **重复提交同一个值是空操作**，也不要理由。

**为什么是"差分驱动"而不是"一律要理由"**：一律要理由会把日常动作也拖慢，
而人一旦学会"随手填个理由"，那条闸门就等于不存在 ——
**闸门必须只在"有后果"的那一步亮**。

**A06 授信"占用在哪，释放就在哪"**（S15）：

> **⚠️ 跨节注：「显式核销」这个语义在种子阶段也承重。**

> 也就是说**建库时就在跑**同一段核销逻辑。这条不是常识，是本批**被反例逼出来**的：

判据 ④ 两张草稿各抵同一应收：草稿各自合法，**第二张确认**被拒 409 `AR_OVER_ALLOCATED`
且仍是 `draft`（没被偷偷确认）。

**A10 部分发票红冲不得作废整笔订单级应收**（S16）：
判据 ① 样本必须是"发票 `linked` 到**订单级** SO 应收"（`source_type='SO'`，不是发票自建的 `SI`）；
判据 ② 红冲后该应收 **`status` 不变**；判据 ③ 金额不变；判据 ④ 已核销额不变；
判据 ⑤ 红冲这件事**本身是真的**（原票置红冲 + 生成一张负数红字票指回原票）。

**A11 跨批次领料成本**（S17，走真实 HTTP）：
用一个**该仓零库存的 SKU**（保证参与拣选的只有本用例造的两批）+
MCP 入库两批（5×10 / 5×20）+ HTTP 建领料单（不指定批次）→ 审批 → 确认出库。
判据 ① 出库流水是**逐批两行**；判据 ② **行成本 == 各批次金额之和 == 150**

  而 `grep "A\|B"` 零输出。本批**因此把一处漏检当成了"干净"**，同一个坑一共踩了 3 次。
- **修法**：多分支 / 元字符一律走 ripgrep（或编辑器检索）；裸 `grep` 只用于**单一字面量**。
  与"判据退化时的表现是变绿不是变红"是**同一族**：**工具静默失败 + 人类读绿**。
- **注意它和缺陷 189 的关系**：189 是"守卫脚本自己漏过 5 种形态"，193 是"**工具**让人看不见自己漏了"。

**另两条已编号、此处只做索引**：
- **188**（`getInvParam` 的 `global` 分支缺 `ORDER BY` ⇒ 确定性读到最早一行）—— 见 5.1–5.4；

**194 · 🔴 「断言助手的参数顺序错位」第二次撞车**（测试侧 · **铁律 27 的复发**）
- **现象**：有人从 `test-xlsx.mjs` 抄 `ok(name, cond, detail)` 的写法写进 `test-export-excel.mjs`
  —— 而后者是 **`ok(cond, msg, detail)`** ⇒ **条件位收到一个非空字符串（中文串恒真）**
  ⇒ **断言永远绿**。**健康跑全绿时完全看不出来**（永远不会失败，也永远不会报"空跑"）。
- **怎么被逮住的**：**靠同一轮新加的反例** —— 注入"静默跳过一组"之后，
  **应到 / 实到总数不匹配（70 / 1）当场把它顶出来**。
  ⇒ 这是 **8.8 的「乙」（计数行）与「丙」（自报）口径的直接收益**：
  **没有总数可对，就没有第二种方式发现"少跑了一组"。**
- **全貌（实测）**：全仓 `ok()` **4 种形状并存** —— `(cond, msg, *)` 多数 ·
  `(name, cond, *)` **9 份** · `(msg, cond, *)` **1 份 = `test-im-sync.mjs`（上一次就是它）** ·
  `(cond, msg)` 两参 **6 份**；`eq()` 两种。
- **对策（两条，缺一不可）**：
  1. 该批文件里给 `ok()` 加**自保**：**"条件必须是布尔值，否则当场抛"** ——
     把"恒真的字符串条件"从**静默通过**变成**立刻炸**；
  2. 新增常驻守卫 **`scripts/check-test-helper-shape.mjs`**：**钉住每份文件的助手形状不许在没人注意时变**
     （新文件必须登记；**出现第 5 种形状直接失败**）。
- **口径（与「判据退化的表现是变绿而不是变红」同族）**：
  **"写错的断言"与"通过的断言"在输出上必须可区分** —— 参数错位两样都会产生"绿"，
  而**绿是最不需要被追究的那种输出**。

**195 · 🔴 参数闸门「认得的形状」与「生效时读取的形状」不同源**（验收工具侧 · 「丁」的扩展）
- **现象**：`--dry=1`。闸门按「取 `=` 左边那截」判白名单 ⇒ 认为它"认得 `--dry`"、**放行**；
  而**生效时真正读取的是 `argv.includes('--dry')` ⇒ false** ⇒ `DRY` 保持 false ⇒ **照常整套跑完**。
  用户以为"只验锚点、不跑"，实际得到"跑了一遍" —— **两条路都正常结束，输出还长得一样**。
- **发现方式（值得单列）**：不是读代码看出来的 —— 是**参数矩阵循环"撞到脸上"**：
  轮到 `--dry=1` 那一格，它跑了 **4 分钟、被 SIGTERM 打断**。**耗时格把它暴露了。**
- **覆盖面**：`a14-a18-reversal` / `reversal-cashflow` / `reversal-report-deepening` **三份同中**
  （`smoke-report-deepening` 本来就安全：它的白名单不含 `--dry`）；同族还有
  `--keep=1`（放行、但副本照删）与 `--help=1`（放行、但用法不打印）。
- **修法**：**参数只解析一次** —— 裸开关必须**整字相符**（`BARE_FLAGS`），
  只有 `--only` / `--jobs` 这类**带值**的才允许 `=` 形式；`DRY` / `KEEP` **从同一份解析结果读**。
- **判据（可传播）**：**闸门认得的形状，必须与生效时真正读取的形状，来自同一次解析。**
  与 **190①**（**日志里的码 / 响应里的码不同源**）**同一族**：同一个事实被两处各解析一次，
  就一定会有一天两处不一致。
- **实测**：三份的 `--dry=1` / `--keep=1` / `--nonsense` ⇒ **退出码 2**（修前 `--dry=1` 会跑完整套）。
- **附带限定（明写，不含糊）**：`--dry=1` 修前"跑完整套"是**机理级证明**
  （闸门放行 = true 且 `argv.includes('--dry')` = false），**不是现场复现** ——
  现场复现要花 4 分钟并被 SIGTERM 打断，没做。

### 8.7 批次 U 的**隔离性判据**（修掉一个假信号）

> 这一节回答的是"**这份证据到底是在哪儿跑出来的**"。它换掉了缺陷 192 那个假信号。

**产物里现在没有"自证布尔"，只有一组可观察事实** —— `isolation_facts`：

| 字段 | 它是什么 | 副本里 / 工作区里 |
|---|---|---|
| `source_root` | 被测源码的根目录（如实记录） | —— |
| `repo_root_at_runtime` | **运行时去问 git**：`git rev-parse --show-toplevel` | 副本**不在任何仓库里** ⇒ `null`；工作区里 = 仓库根 |
| `has_git_dir` | 有没有 `.git` 目录（**结构性证据**：`run-on-copy` 刻意不复制 `.git`） | 副本必为 `false` |
| `has_data_dir` | 有没有 `data/`（**结构性证据**：刻意不复制 `data/`） | 副本必为 `false` |
| `sentinel` | 由 `run-on-copy.mjs` 写进**副本**的哨兵文件（含**源仓库** HEAD sha、脏行数、复制时间） | **只有 `run-on-copy` 会写它** ⇒ "哨兵在"是"确实在副本里"**最硬的证据** |
| `harness_declared_copy` | run-on-copy 通过环境变量**声明**的 | ⚠️ **这只是声明**，单独一个字段，与上面的**实测**字段分开读 |
| `contradictions` | 几条信号**互相矛盾**时的清单（例如"有哨兵"却"有 `.git`"） | **不平均成一个 `true`**，而是在控制台**喊出来** |

另加一个与 SHA 并列的字段 —— **`commit_sha_source`**：
`env：harness 传入` / `git：实测 rev-parse` / `none`。
要点是：**「这个 SHA 是谁说的」和 SHA 本身一样重要** ——
副本里没有 `.git`，SHA 只能由 harness 传进来；把来源写出来，读者才知道该信到什么程度。

**实测对照（同一个目录，两种判据给出不同结论）**：

| 判据 | 结论 |
|---|---|
| **旧**（缺陷 192 的写法） | `true` —— "是独立副本" |
| **新**（可观察事实） | `has_git_dir: true` + `repo_root_at_runtime` = **它自己** + `sentinel: null` ⇒ **任意读者都能判定：这是工作区，不是副本** |

**这一条为什么值得单列**：旧判据**没有撒谎** —— 它只是比了一个字面量。
而"**看起来被证明了**"比"没证明"更危险，因为它让人不再去验。
同一个道理在本批出现了三次（判据退化变绿 / `grep` 静默 exit 1 / 这个假信号）——
**凡是"自证"，都要能被第三方用别的量复算出来。**

### 8.8 验收脚本的**收尾四联**（本批新定的口径）

> **为什么要有这一节**：这批新落盘的三份验收脚本（`scripts/accept/reversal-cashflow.mjs` ·
> `reversal-report-deepening.mjs` · `smoke-report-deepening.mjs`）是在**隔离副本**里跑的，
> 它们**只写 `/tmp`** —— 但"只写 /tmp"这件事**必须由脚本自己说出来**，
> 否则读者分不清"**不碰**"与"**没量**"（铁律 21：没做要可见）。

**甲 · 每组一行**（收尾必须能被逐组核对）
```
[id] ✓ 锚点唯一命中 <文件>:<行号>   <这一组拆的是哪道闸门>
     注入点：<文件>:<行号>（唯一命中） · 变红的具体断言名 · 命中期望 N/N · 还原后失败数
```
- **锚点必须唯一命中**：命中 0 次或 >1 次一律报"锚点未命中"，**不许凑合跑** ——
  行号会漂，所以定位用**行内容**，命中数由脚本自己数。
- **实测（2026-10-16 20:0x，我跑的 `--dry`）**：`reversal-cashflow` **9 / 9 组锚点就绪** ·
  `reversal-report-deepening` **9 / 9 组锚点就绪**。
  ⚠️ **这两个 9 都是"截至 20:06:03"，不是终值** —— `reversal-report-deepening` 在 **20:02:22 还是 4 组**；
  **脚本 owner 冻结组数之前，正文里任何组数一律写"截至 <时点>"**。

**乙 · 收尾计数行 + 退出码**
```
计数 通过 N / 失败 M
```
- 退出码：**全通 0 / 否则 1**（可被 CI 直接判）。
- ⚠️ **报数带口径**：这里的 N 是**这一份脚本自己的组数**，不是套件总数，也不是"断言条数"。

**丙 · 库改动自报**（**没碰也要显式打 0**）
```
本次改动数据库：工作区 0 条 / 副本内快照 N 条
```
- `scripts/accept/` 下的脚本只写 `/tmp` 副本，所以**"工作区 0 条"必须由脚本自己说出来**；
  **不打印 = 读者无法区分"没碰"与"没量"** —— 这正是本节存在的理由。
- 目前最接近丙 的是 `smoke-report-deepening.mjs` 收尾的**「工作区自证」块**：
  `本次创建的 1 份临时副本…收工时仍存在 0 份` + `未变 <5 个源文件>` +
  `git status --porcelain 与开跑前一致（开跑前 73 行 / 收工 73 行）`
  —— **是丙 的雏形，但字段名与"工作区 0 条"的口径还没统一**。

**丁 · 参数自证**（**不认识的参数：打一行用法 + 非 0 退出**）
```
未知参数：--dry
用法：node scripts/accept/smoke-report-deepening.mjs          # 无参：全跑
（本脚本没有 --dry / --only / --keep）        ← 退出码 2
```
- **为什么有丁（本批实测出来的）**：`smoke-report-deepening.mjs` **没有 flag 分支**，
  有人传 `--dry` 以为"只验锚点、不跑" —— **实际整套跑了一遍**。
  这与**缺陷一百八十六**（`qty: -5` 静默返回"成功"）是**同一族**：
  **无意义的动作被静默接受**。区别只在"用户"是谁：一个是 Agent，一个是敲命令的人。
- 判据写法与「必须被拒」同源：**不许静默忽略** —— 忽略参数的人**以为自己要的行为发生了**，
  而脚本**从没打算做那件事**；两条路都"正常结束"，输出还长得一样。

> **⚠️ 实现状态（如实记，本文档不替脚本宣布做到）**
> 截至本文档写定时：**甲 / 乙 已实装**（上面两段就是它们跑出来的原文）；
> **丙 / 丁 本批补**（`smoke-report-deepening.mjs` 的「工作区自证」块是丙 的雏形；
> 丁 目前**三份脚本都没有** —— 我是**传了 `--dry` 实测**才发现的）。

**丁 的同族症状（第二条，实测）：`--only` 写错字母 ⇒ 空跑与通过同形**

- **现象**：`--only=<id>` 里 id 写错一个字母（或大小写不同）⇒ 脚本**一组都不跑**，
  收尾照样打 **`通过 0 / 失败 0`** —— 与"真的全通过"**输出同形**，退出码也是 0。
- **判据（与"`grep` 静默 exit 1"、「判据退化变绿」同一族）**：
  **"没有匹配到任何东西"必须与"匹配到且都通过"分开。**
- **改法**：**命中 0 组 ⇒ 响亮失败 + 退出 1**；并且 id 匹配改**大小写不敏感**（写 `3A` 不该等于没写）。
- **为什么写在这里而不是 §8.6**：它不是产品缺陷，是**验收工具自己的**"无意义动作被静默接受"——
  和「丁」同一条判据：**不认识的输入要么被拒、要么被报，不许被忽略。**
