# GML 报表体系纵深之二（批次 N）详细设计

> 版本：v1 · 日期：2026-10-16 ｜ 模块 28（财务报表）的续之二 ｜ **无新迁移**
> 性质：**内部设计底稿**。相关文档：批次 L 报表体系、批次 M 期末结转与结账、批次 H 业财一体凭证。

---

## 一、这一批补的是什么

批次 L 让三张报表算得出来，批次 M 让"结账"这个词有了内容。
但报表仍然只能**一期一期地看**：

- 「这期利润 12 万」不是一个结论，「这期 12 万、上期 30 万」才是 —— 缺**跨期比较**；
- 报表只能看不能带走 —— 缺**导出**；
- 试算平衡表只给到"某科目本期借 8 万" —— 缺**下钻到凭证分录**。

三件事都有一个共同的失败方式：**同一件事出现第二个真值**。

| 功能 | 最危险的那种坏法 | 为什么危险 |
|---|---|---|
| 跨期比较 | 比较列自己算一遍，与"单独打开那一期"不是一个数 | 两个数都长得像真的，谁也不报错 |
| 报表导出 | 导出另写一条取数路径（页面是 A、文件是 B） | 用户拿着文件去开会，**会上没人能发现** |
| 逐行展开 | 展开自己拼一遍筛选条件，与汇总不是一批凭证 | 差的那几笔说不清是哪一步漏的 |

所以本批的产出**主要不是三个功能，而是四条新的自证探针**（第六节）与三处"同一个事实只有一个出处"的收敛（第七、八节）。

> 本批**无新迁移、无新权限点**：跨期比较、导出、逐行展开**全是只读**动作。
> 导出与查看能拿到的信息完全相同，凭空多一个"导出权限"只会让权限表越来越长而没人真的去维护它。

## 二、跨期比较：两列必须来自同一个计算入口

`compareReport(reportCode, period, mode)` 的实现短得几乎不像一个功能：

    当前列 = computeReport(reportCode, period)
    基期列 = computeReport(reportCode, period = 模式推导出的那一期)
    差额   = 两列相减

关键在于**它没有第三条取数路径**。比较不是一个"算法"，而是"把同一份计算跑两次再并排"。于是：

- 界面上"两列并排"与"分别打开两期"**永远是同一组数**（这是可执行断言的，见第六节）；
- 比较不需要任何新的取数逻辑，因此也不会有新的口径分叉。

### 比较模式只做两个

| 模式 | 基期 | 说明 |
|---|---|---|
| `previous`（环比） | 期间 − 1 个月 | "这期比上期怎么样" |
| `yoy`（同比） | 期间 − 12 个月 | "这期比去年同月怎么样" |

基期**只由模式决定**，两处各写一次 `-1` / `-12` 迟早就对不上，所以推导只有一处（`resolveCompareMode`）。
跨年由 `shiftPeriod` 负责：`2026-01` 的环比基期是 `2025-12`，不是 `2026-00`。

## 三、时点 vs 期间（这一节的会计判断）

三张报表并不都是同一种东西，比较的含义因此不同：

| 报表 | 口径 | 比较的是 | 于是"上期"对它意味着 |
|---|---|---|---|
| 资产负债表 | **时点**（期末余额） | 两个时点的家底 | **上期末**，而上期末**就是本期期初** |
| 利润表 / 现金流量表 | **期间**（本期发生额） | 两个期间各发生了多少 | 上一期的那一段时间 |

第二行推出一个额外的、**不依赖比较功能**的强恒等式：

> **本期的期初余额（逐科目）＝ 上一期的期末余额（逐科目）**

它是"期初滚动"这件事的自证。它值得单独守，因为**别的探针都抓不到它**：
少滚一期发生额时，那一期的 `Σsigned` 本来就是 0（凭证借贷平衡），
所以资产负债表**仍然是平的**，净利润与现金流也各算各的 —— 账面上一切正常，
只有"期初接不上"这一个证据。这条探针落在 `auditReport` 的第 ⑦ 条（见第六节）。

## 四、差额与变动率的口径

### 差额：只由两列相减

不"再算一遍"。再算一遍就有了第二个真值 —— 正常情况下两者同值，
只有在边界上（四舍五入、某一列被后处理过）才分叉，而那时两列看着都正常。

### 变动率：分母取绝对值

    变动率 = 差额 ÷ |基期| × 100%

分母取**绝对值**是刻意的：基期为负（上期亏损 100）时，"亏 100 → 亏 50"是**改善**，
变动率应为 `+50%`。直接用带符号的基期做分母会得到一个负号，
而它会让人把"好转"读成"恶化" —— 三处符号相乘，谁都算不对。

### 基期为 0：留空，不写 0、不写 ∞

基期绝对值为 0 时变动率为 `null`。**不是 0**（0 表示"没变化"，而"从无到有"恰恰是最大的变化），
**也不是 ∞**（除以 0 会写出 `Infinity` / `NaN`，而它们会被 Excel 读成一串乱码）。

## 五、可比性：没数据 ≠ 全是零

基期"没数据"是**常见事实**（上月确实没开张），不是错误。所以：

- **不拒绝比较**（"上月无发生"本身就是要看的信息）；
- **也不假装差额就是增长** —— 一个"基期 0 → 本期 8 万"的差额看起来像暴涨，
  实际是"基期没有业务"，界面必须能说出这个区别。

判据（不依赖取数口径）：

    可比 = 基期有已过账凭证  或  存在 period ≤ 基期 的期初登记

第二个条件不能省：资产负债表在"基期无凭证、但更早登记过期初"时仍有非 0 的期末余额（滚动而来）。
漏一个来源就会把"有数"说成"不可比"。

界面据此显示一条明确提示：**这一列的 0 表示"那期没有业务"，不是"那期全是零"**。

## 六、四条新的自证探针（本批真正的产出）

`auditComparison(db, {reportCode, period, mode, result})` —— **`result` 可注入**，这是刻意的：
如果它只会"自己算一遍再自己核对"，那它就永远是对的，测试也就无法证明它**真的会响**。

| 探针 | 守的口径 | 失效方式 |
|---|---|---|
| `COMPARE_BASE_PERIOD_BAD` | 基期必须由模式唯一决定 | 基期算错一个月（**看期间**） |
| `COMPARE_CURRENT_MISMATCH` | 本期列 = 单独打开本期 | 本期列被后处理过 |
| `COMPARE_BASE_MISMATCH` | 基期列 = 单独打开基期 | 基期列来自别的期间/别的路径（**看金额**） |
| `COMPARE_DIFF_MISMATCH` | 差额 = 两列相减 | 差额被"再算一遍" |
| `COMPARE_RATIO_BAD` | 变动率为空 ⟺ 基期绝对值为 0 | 把 `null` 写成 0（看起来像"没变化"） |

`auditReport` 新增第 ⑦ 条：`OPENING_NE_BASE_CLOSE`（本期期初 = 上期期末，逐科目）。

### 关于探针的两条现场教训（详见 `bugcheck-log.md` 缺陷一百四十二 / 一百四十三）

**（1）"只查我正在看的那一期"是覆盖面盲区。**
探针第一版写成"检查参数里传进来的那一期"，于是它的覆盖面 = 调用时恰好传的那个期间。
反例注入（少滚一期发生额）在 `2026-10` 上**看不出任何差异**（它前两期都没有发生额），
偏差全部落在 `2026-09` —— 只查本期的探针**一声不吭**。
修法：改成**全期间扫描**（`accounting_opening_balances` ∪ 有已过账凭证的期间），与第 ⑥ 条结转探针（本来就全表扫）对齐。

**（2）"结果自称的元信息"必须由实际算出来的东西派生。**
`base_period` 第一版取自**模式推导**，而基期**列**取自**实际计算**，两者可以分离：
"算的是 2026-08、自称的是 2026-09"没有任何人发现。
修法：`base_period` 取 `base.period`（实际算的那一期）；推导值只留给 `auditComparison` 做对照。

> 这两条放在一起才说明问题：**探针的覆盖面与探针的证据来源，都可能悄悄错位。**

## 七、导出：导出即视图

    导出 = computeReport / compareReport 的结果 → buildReportCSV（纯函数）→ text/csv

| 决定 | 理由 |
|---|---|
| `buildReportCSV` 是**纯函数**（不碰数据库） | "导出 = 视图"因此可以脱离 HTTP 与文件单独断言 —— 测试把 CSV 解析回来逐行逐列比 |
| 元信息放**末尾注释行**，不放首行 | 首行是表头；任何"首行放元信息"的做法都会让用工具读这个 CSV 的人拿到一行废数据 |
| 带 **BOM** | 不带 BOM 的 UTF-8 CSV 在 Excel 里中文全是乱码 |
| 生成时间走 `localNow()` | 本项目的日期只能从 `lib/dates.js` 派生（第（4）条铁律） |
| 文件名**双写** | `filename*=UTF-8''…` 给现代浏览器（中文名），`filename="…"` 给老浏览器兜底 |
| 格式选 **CSV** 而不是 Excel / PDF | CSV 是唯一"不需要引入第三方库"的格式；Excel 的格式细节会随版本变化，PDF 还会把"排版"变成一个新的、需要维护的正确性问题。导出的**预期用途**是"拿去再加工"，那正是 CSV 的用途 |

前端侧：`api.download` **不能复用 `request`** —— 后者对响应体做 `JSON.parse`，
CSV 会直接抛"返回数据格式异常"，于是"这个接口本来就不返回 JSON"被报成"接口坏了"。
新通道鉴权头与行业头与 `request` **同一套规则**，失败时仍试着按 JSON 解析错误体把业务原话带出来。

## 八、试算平衡表逐行展开：展开与汇总必须筛同一批凭证

`trialBalanceDetail(db, {period, from, to, subjectCode})` → 该科目在**同一筛选条件**下的全部分录明细。

三处"只有一个出处"：

| 抽出物 | 为什么 |
|---|---|
| `trialBalanceFilter()` | 汇总与明细**共用同一个 where**。各拼一遍的后果是"展开后对不上汇总"，两边都不报错 |
| `balanceOf(direction, debit, credit)` | 余额方向判定只写一处；展开行把"借 − 贷"的累计**拆回借贷两列**再进来，所以两张视图给出的方向必然一致 |
| 返回 `summary_row` | 让"对得上"**当场可见**，而不是把两个数并排摆着让人自己比 |

另外两条口径：

- 超出行数上限**如实回报** `truncated` / `total_count`，**不静默截断** ——
  一张"看着像全量、其实少了一半"的明细比报错危险得多；
- 不指定科目直接拒绝（`DETAIL_SUBJECT_REQUIRED`）：展开是**某一行的下钻**，不是"全部分录"。

## 九、范围裁剪：为什么不做「本年累计」

利润表最常用的比较形态其实是「本期 / 本年累计」。本批**刻意不做**，理由是它的代价被低估了：

- 累计列要求"发生额按**区间**聚合"，那会让 `subjectBalances` 同时承担"单期"与"区间"两套语义 ——
  而它是三张报表**唯一的取数口**。为一个多出来的比较列去动摇它，代价比收益大。
- 而且"累计"对**时点**口径的资产负债表根本没有意义（"1 月到本月的余额加起来"是一个不存在的量），
  所以它还会带出一条"这个参数只对某些报表有效"的分支 —— 参数能让人读出一个不存在的数，
  与"配置能改账"是同一类问题。

**这是范围裁剪，不是遗漏**：累计口径留给后续批次单独设计（届时应连同"区间口径对 `subjectBalances` 语义的影响"一起论证）。

## 附：本批的四条口径（可单独引用）

1. **比较的两列必须等于"单独打开那一期"** —— 比较是"同一份计算跑两次再并排"，不是第三个算法。
2. **差额只由两列相减** —— 不许有第二个真值；变动率分母取绝对值，基期 0 时留空。
3. **导出即视图** —— 导出的内容就是报表内容，且这条要写成可执行断言（把文件解析回来比）。
4. **同一个筛选条件只能有一个出处** —— 展开与汇总共用一个 `where`，与"同一份判据不允许有两个实现"同源。
