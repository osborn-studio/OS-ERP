# GML 收尾批次详细设计：三条遗留不变量 + 重建可复现性

> 版本：v1 · 2026-10-16 ｜ 范围：`A10` / `A17b` / `A18` 三条验收遗留项 + 整库重建暴露的一类 seed 缺陷
> 迁移：**无**（本批不改表结构）｜ 新增测试：`scripts/test-final.mjs`（5 节 82 条）
> 新增模块：`server/lib/catalog.js` · `server/mcp/validate.js` · `scripts/verify-reseed.mjs`

## 一、为什么是这三条，以及它们为什么"看起来都不严重"

验收侧从 20 项静态发现里归并出的三条遗留（`A10` / `A17b` / `A18`），
共同形状是**"局部看起来对，合起来是错的"**：

| 编号 | 一句话 | 为什么一直没被发现 |
|---|---|---|
| `A10` | 部分发票红冲会把**共享的**整笔 SO 应收作废 | 红冲本身成功、界面正常、那张应收也确实"应该"被处理 —— 只有**同一订单上别的票**在无声受损 |
| `A17b` | 改单只改单头不重算 · 负数量出入库反向 · MCP 只验必填 | 三处都**返回成功**、都**不留报错**，错的那个数躺在库里 |
| `A18` | 采购付款核销不校验主体 / 状态 / 金额符号 / 未付余额 | 手工核销的每一条都**长得像正常输入**，只有跨供应商时才看得出来 |

它们都属于同一类：**判据缺了一道**，而缺的这道恰好不在"常用的那条路径"上。

## 二、三条不变量

### 2.1 `A10`：一张发票 ≠ 一笔债权

**两个口径下的应收是两种东西**：

| 口径 | 应收的来源 | 发票与应收的关系 | 红冲一张票的正确后果 |
|---|---|---|---|
| `SI`（开票新建） | **发票自己**建一张 | `relation='created'` | 整张作废（那张应收就是它的） |
| `SO`（关联既有） | **销售订单**建一张 | `relation='linked'`（可被多张票共享） | **不动那张应收** —— 债权的作废属于订单的生命周期 |

**判据落点**：`redChartInvoice` 读 `invoice_ar_links.relation` 分流。
`linked` 时**连前置的"已有收款不能红冲"检查也跳过** ——
共享应收上有没有收款，与"这张票能不能换开"无关；不跳过就会出现
「订单收过一分钱，这个订单上任何一张票都再也红冲不了」。

**不变量**：`linked` 的应收，其 `amount` / `status` 不因任何单张发票的红冲而改变。

### 2.2 `A17b`：三处"形状对但数不对"

| 面 | 旧实现 | 新口径 |
|---|---|---|
| 出入库数量 | `applyStockOut(-5)` 不报库存不足（`可用 < -5` 恒假）⇒ 库存**反向加 5**、还写了一条出库流水 | **引擎入口** `assertPositiveQty`（先于成本期间闸门）非正数抛 `STOCK_BAD_QTY`；**不写任何流水** |
| 销售订单改单 | 只在传了 `items` 时 `recalcOrder` ⇒ 只改运费/整单折扣时**应收不变**，且"应收为负就拒"的闸门根本没触发 | 触发条件改为 `Array.isArray(items) \|\| headChanged`；留在事务内，抛错整笔回滚 |
| MCP 入参 | 只验 `required` ⇒ `category_id: "abc"` 走进 handler 变成静默默认值 | `server/mcp/validate.js`：required / type / enum / min / max / **未知字段**；数字允许字符串但 `"abc"`、`3.7`（integer）拒 |

**判据落点**：数量符号在 `lib/stock.js` 一处；重算条件在 `routes/sales.js` 与派生公式的入参列表对齐；
入参形状在 `mcp/validate.js` 一处（server.js 与测试共用）。

### 2.3 `A18`：付款核销的四道闸 + 一道"看得见自己"的重验

**手工核销逐条过闸**（`assertPaymentAllocations`）：

1. **主体一致** —— 给 A 供应商付款不能抵 B 的结算单；
2. **状态可核销** —— `audited` / `settled` 之外一律拒（草稿、已作废不该收到钱）；
3. **金额为正** —— 负分摊会反向增加该结算单的未付额；
4. **按结算单累计不超未付余额** —— 同一张结算单在多条明细里重复出现时也要管（"两草稿同余额"）。

再加**币种白名单**与**生效/执行付款两次时点重验**（建单时有效 ≠ 生效时还有效）。

**"重验必须能看见自己"** 是本批最值钱的一条：

```
建单(draft)   → 未付 934554.89，本单未生效 ⇒ 可用 = 934554.89  ✅
submit        → 未付 934554.89，本单刚生效但 paid_amount 尚未刷新  ✅
pay           → 未付 0          ，本单已计入 paid_amount ⇒ 拿"本单 + 本单"比 settle_amount ❌
```

修法：`selfPaymentId` —— **本单已生效的额度加回来**（`available = 未付余额 + 本单已生效额`）；
未生效（draft）时**不能**加（那等于给"超余额"开后门）。

## 三、整库重建暴露的一类 seed 缺陷（本批最大的意外收获）

### 3.1 怎么发现的

跑 `reseed-all --force` 做收口验证时**直接崩**，而且**在未改动的基线（HEAD）上同样复现**
（`git stash push -- server/` 后照样崩）—— 证明它不是本批改出来的：

```
Error: SKU#40 单价异常                     ← seedPos → createPosOrder → posQuote
AgreementError: 定价型协议必须给协议单价      ← seedDms → createAgreement
```

### 3.2 共同根因：**"挑样本"的筛选条件没排除非卖品**

| 处 | 旧筛选 | 后果 |
|---|---|---|
| `seedPos` | "该门店仓库存量最大的 8 个 SKU" | 门店仓**确实会存原料**（实测三库 16 / 130 / 15 行）；原料堆到 ≥5 件就按库存量排进候选，而原料 `price_retail = 0` ⇒ `posQuote` 以"单价异常"抛错 |
| `seedDms` | "按 id 取前 40 个 SKU" | 原料排在中后段，取到后 `round2(0 × 0.82) = 0` ⇒ `createAgreement` 拒绝 |

**为什么能沉睡这么久**：`seedPos` / `seedDms` 都是**幂等**的（库里已有数据就跳过），
正常起服务**永远跑不到**；只有整库重建才会执行 ——
而报错点离真正的原因隔着好几层调用栈。

> **这是"跳过"这种幂等策略的代价**：跳过路径不报错，只让某段代码永远不被执行过。
> 由此立一条新规矩：**幂等的 seed 也必须能被完整跑一遍 —— `reseed-all --force` 进回归。**

### 3.3 修法：可售商品的判据只在一处

`server/lib/catalog.js`：

```js
export const SELLABLE_COND = "IFNULL(p.item_type,'') <> 'material' AND s.price_retail > 0"
```

两条缺一不可：分类上排除原料（`item_type`），**事实上必须有零售价**（`price_retail > 0`）——
后者更本质，因为分类可能没人维护。`seedPos` / `seedDms` / `seedOc` 三处改为调用
`sellableSkusInWarehouse` / `sellableSkus`。

### 3.4 顺带修掉：`GROUP BY` 后按 bare column 排序 ⇒ 重建不可复现

```
... GROUP BY s.id ORDER BY st.qty_on_hand DESC    ← st.qty_on_hand 是"组内任意一行"的值
```

SQLite 允许这么写，但排序结果**不确定** ⇒ 同一份数据每次重建可能排出不同顺序 ⇒
演示样本换人、依赖样本的断言与截图随机漂移。
改为 `SELECT ... SUM(st.qty_on_hand) AS qty_on_hand ... ORDER BY qty_on_hand DESC`。

### 3.5 再顺带：`price_change_logs` 漏登记 ⇒ 每轮重建 +7 条

专门写了 `scripts/verify-reseed.mjs`（`--force` 重建两次，逐项比对业务值）之后，
它抓到的**第一个也是唯一一个**漂移项就是这张表：三库每轮各 +7 条（协议价造 7 条协议、
每建一条写一条留痕），而它**不在 `seed.js` 的清理清单里**。

同时发现 `mcp_idempotency` 也漏了 —— 它按 `idempotency_key` 缓存"首次执行结果"，
重建后自增 id 被复用 ⇒ **重放会返回上一个世界的结果**（与 `doc_events` 同一类跨代引用）。

### 3.6 防线：清单完整性守卫

光补这几张表不够 —— 下次新增表忘记登记，症状还是"很久以后才发现"。
所以：

- `seed.js` 导出 `TABLES`（清理清单）与 **`KEEP_TABLES`（有意不清的清单，41 张，分三类并写明归属）**；
- `verify-seed` **第 16 节**断言：**库里每一张表都必须落在两者之一**，且两者不重叠，
  并点名六张历史上真实踩过的"跨代必清"（`doc_events` / `doc_no_counters` /
  `inventory_batches` / `inventory_reservations` / `price_change_logs` / `mcp_idempotency`）。

### 3.7 新命令：重建可复现性验证

`scripts/verify-reseed.mjs`（已接入 `regress-all`）：

- 对每个库跑两次 `reseed-all --force`，比对**业务值指纹**：
  每张表的**行数** + 每张表里**对外标识列**（`doc_no` / `code` / `key`）的**完整有序序列**（sha1）；
- 刻意**不比对**任何时间戳列（灌数时钟冻的是逻辑起点，真实执行耗时会让墙上时间不同 —— 比它只会得到假红）。

## 四、反例与证据

**A 组**（三条缺陷，修复前）：`test-final` 首跑 **44 / 25**，25 条红逐条对应三个面。
**B/C/D 组**（重建崩溃）：分别在**基线 HEAD**、**修完 POS 之后**、**全新库**三处复现。
**修完后**：三库 `reseed-all --force` 全部成功、`test-final` 三库 **82 / 82 / 82**。

人造成反例（第 4 节）值得单说：把一个**原料**塞进门店仓、库存开到 99999，
**先证"不过滤时它确实排第一"**（先决条件），再断言可售样本里没有它 ——
这样这条断言不会退化成"永远为真"。

## 六、本轮未做（边界）

- **`mcp_call_logs` 等运行痕迹的保留策略**：本批把它们纳入清理（重建后从零开始），
  但"跨重启保留调用审计"是另一件事，未做；
- **`KEEP_TABLES` 里 B 类（satellite 自清）的归属只做了声明**：
  它们由各自的 `ownedTables` + `resetSequences` 保证，本批未逐个独立验证；
- **`posQuote` 对"不可零售的 SKU"的报错语义**：仍是"单价异常"（含糊），
  本批只从**取样侧**堵住，未改报价侧的措辞；
- **`promo-seed` / `quote-seed` 的 SKU 取样**：前者按 `status='active'` 取全部、
  后者按 `ORDER BY id LIMIT 6`，本批**未统一**到 `catalog.js`（它们当前不触发缺陷，
  属"下次动了再说"）；
- 容器内实测 · Windows / 真机 · 钉钉飞书真实联调（与前面批次相同，本机无条件）。
