## 一、这个模块是怎么被发现的

它不是设计出来的，是**沟通中被用户点出来的**：

> "我发现漏了一块，就是门店要货其实是订货，可以统一一个订货平台来弄，包括经销商，这个你可以参考下网上标准的东西，比如用友的 U 订货什么之类。"

对照原模块地图，问题很清楚：

| 同一件事 | 修正前被放在哪 | 后果 |
|---|---|---|
| 门店要货 | 挂在「门店要货 → 总部发货 → 门店收货」闭环（`server/routes/requisitions.js`） | 一套代码 |
| 经销商订货 | 模块 19「经销商 DMS：档案分级与渠道订货」 | 另一套代码 |
| 取价 / 审批 / 授信 / 对账 | 两边各写一半 | **口径分叉** |

**问题的本质不是"少一个菜单"，而是"同一件业务被拆成两条实现"**：门店要货与经销商订货都是"下级向我方订货"，差别只有四项参数——客户类型、取价维度、审批阈值、分仓候选。分两处实现，意味着将来每加一条渠道规则都要改两边，改一边漏一边。

所以本模块的目标不是"再做一个商城"，而是**把两条线收口成一张单（`oc_orders`）与一套规则（`server/lib/order-center.js`）**。

### 1.1 与原模块的关系（不是新增，是重组）

| 原编号 | 原名称 | 处置 |
|---|---|---|
| 12~14 | 线上商城（渠道商品 / 促销引擎 / 订单路由） | **保留不变** —— 它面向 C 端消费者 |
| 19 | 经销商 DMS：档案分级与渠道订货 | **拆分** —— 订货侧并入本模块，本项只留渠道档案分级 |
| 20 | 经销商 DMS：价格政策与返利对账 | **归入**本模块的渠道管理侧 |
| — | **新增 12A**：订货中心（B2B 订货平台） | **统一承载门店要货 + 经销商订货** |

现有 `requisitions.js`（门店要货）**不再单独演进**，作为历史单保留；前台入口标注「（历史单）」。

## 二、核心设计判断：订货平台 ≠ 零售商城

这是本模块唯一不容商议的边界。两者**共享商品/库存/订单内核，但不共用前台与规则**。

| 维度 | **订货平台（B2B）** | **零售商城（B2C）** |
|---|---|---|
| 定价 | **因人而异**（等级 / 区域 / 渠道 / 阶梯） | 统一定价 |
| 支付 | **账期 + 授信额度** | 在线即付 |
| 审批 | 常有（信用 / 金额 / 缺货 / 特批） | 无 |
| 对账 | **核心功能** | 无 |
| 客户 | 需审核入驻、分级分权 | 注册即用 |
| 商品可见性 | 按等级 / 区域控制 | 全公开 |
| 起订量 | 有（件数 / 金额） | 无 |

调研里最直接的"避坑指南"就是这一条：**把零售商城改成订货系统一定失败**——因为价格体系、审批流、账期、对账四件事完全不同。因此本模块**另起一套前台**，而不是给商城加开关。

## 三、多级渠道模型

### 3.1 订货方只有两种来源，但可以成树

    oc_customers
    ├─ source_type = 'store'     ← 门店（直营 / 加盟），取自 stores 档案
    └─ source_type = 'dealer'    ← 经销商，取自 dealers 档案
            └─ parent_customer_id  ──→ 经销商的下游客户（source_type = 'downstream'）

`parent_customer_id` 是本模块最关键的一个字段。参考 U 订货的公开口径——"把核心经销商建立为**客户兼商家**，经销商可自行维护自己下游渠道"——订货关系**不是单向的，而是多级的**。落到数据上是同一张客户表自关联，落到服务上是 `customerTree()`：任何一个订货方都能看到自己这一支。

演示口径只展开两级（品牌方 → 经销商 → 终端门店），但表结构支持任意层。

### 3.2 直营门店是"内部主体"，不适用对外授信（踩过的坑）

档案推导时有一个判断必须做对：

    直营门店 = 内部主体，货主归总部，走内部调拨往来 → settle_type = 'internal'
    加盟门店 = 独立主体，货权独立              → settle_type = 'credit'
    经销商   = 独立主体，按档案账期            → 'credit' 或 'prepay'

**这条曾经写错过，而且错得很典型**：初版把所有门店都按对外客户处理，直营店拿不到授信额度（`credit_limit = 0`），于是全部门店下单时被"额度已用尽"拦死，seed 只造得出 4~5 张单。

教训写在这里：**一个不存在的额度被当成 0 来校验，比不校验更糟**——它不报错，只是让整条业务线静默停摆。正确做法是"不适用"就明确不适用（`internal` 分支直接跳过授信校验），而不是补一个 0。

### 3.3 经销商档案的中文口径只翻译一次

经销商档案里的结算条件是中文描述（「月结 30 天」「现结」「预付」），订货中心需要可判定的口径。**翻译规则只此一处**，不散到各路由：

    原始值 '月结 30 天'  → settle_type='credit', credit_days=30
    原始值 '现结'/'预付'  → settle_type='prepay', credit_days=0
    无法识别            → 取档案 credit_days，缺省 30

## 四、六个硬设计点逐条落地

调研（对应 U 订货类产品的标准形态）提炼出 6 个硬设计点，逐条落到函数：

| # | 硬设计点 | 落点 |
|---|---|---|
| ① | **价格因人而异** | `quoteItems()` → 走模块 05A 的 `resolvePrice`，按客户维度取价 |
| ② | **下单前必须校验** | `checkOrder()` → 返回 `checks[]`，任一 blocking 即拒单 |
| ③ | **审批是有条件的** | `decideApproval()` → 按 `oc_approval_rules` 命中规则 |
| ④ | **对账是主功能** | `buildStatement()` / `confirmStatement()` / `settleStatement()` |
| ⑤ | **智能分仓** | `pickWarehouse()` → 按库存满足率 + 区域就近打分 |
| ⑥ | **多端多种下单方式** | `createOrder({ source })` → 支持 web / import / repeat / mcp |

### 4.1 ① 价格因人而异

同一商品，不同客户看到不同价。取价维度不新造，直接复用模块 05A 的四维价格组：

    客户等级 level      vip / gold / silver / bronze
    渠道     channel    direct / franchise / dealer / sub_dealer
    区域     region     华东 / 华南 / 华北 …
    客户类型 storeType / dealerLevel

**关键取舍**：订货中心**不自己算价**。如果它自己写一套取价逻辑，模块 05A 的"四维价格组 + 匹配度打分 + 调价留痕"立刻就变成两份实现。因此 `quoteItems()` 只做两件事——把客户档案翻译成取价维度、把结果落进订单行快照。

### 4.2 ② 下单前必须校验（三档 severity）

校验项不是一个布尔值，而是**分档的清单**，因为不同问题的处置方式完全不同：

| severity | 含义 | 处置 |
|---|---|---|
| `block` | 硬拦截 | 不允许提交 |
| `warn` | 提示但可继续 | 允许提交，界面黄标 |
| `info` | 说明性 | 仅提示 |

校验项与分档：

| 校验项 | 口径 | 默认档位 |
|---|---|---|
| `CREDIT_EXCEED` | 本单金额 + 已占用 > 授信额度 | **block**（仅账期客户） |
| `CREDIT_FROZEN` | 客户被冻结 / 未准入 | **block** |
| `MIN_QTY` / `MIN_AMOUNT` | 未达起订量 | **block** |
| `OUT_OF_STOCK` | 全行缺货 | `warn` |
| `PARTIAL_STOCK` | 部分行缺货 | `warn` |

**缺货为什么默认 warn 而不是 block**：B2B 订货里"先下单、后补货"是常态，硬拦会把大部分真实单子挡在门外（实测初版就是这样）。改为由客户档案上的 `allow_shortage` 策略决定——需要严格控货的客户可以设成硬拦。缺货本身则转成一条审批规则（见下）。

### 4.3 ③ 审批是有条件的

不是"下单即成立"，而是**按规则触发**。规则表 `oc_approval_rules` 支持三种作用域（`global` / `channel` / `customer`）与四种判定字段：

    条件字段 cond_field：amount 金额 / qty 数量 / credit_over 超授信 / short_lines 缺货行数
    比较符   cond_op  ：>  >=  <  <=  ==  !=

演示三库里预置的规则（餐饮版 5 条）：

| 规则 | 作用域 | 触发条件 | 优先级 | 审批角色 |
|---|---|---|---|---|
| `AP-CREDIT` | global | 超授信额度 | 5 | finance 财务授信特批 |
| `AP-FR-3W` | channel=franchise | 金额 > 3 万 | 8 | sales 加盟业务主管 |
| `AP-AMT-5W` | global | 金额 > 5 万 | 10 | sales 区域经理 |
| `AP-AMT-20W` | global | 金额 > 20 万 | 20 | boss 销售总监 |
| `AP-SHORT` | global | 存在缺货行 | 60 | sales 缺货交期确认 |

规则命中的多个节点**按 `seq` 串成审批链**（逐节点推进，不是一次性全过），命中结果写在 `oc_orders.approval_reason` 与 `oc_order_approvals` 上。

### 4.4 ④ 对账是主功能

B2B 里对账不是附属功能，而是**甲方最常用的一屏**。因此它不是一个报表，而是一张**带状态的单据**（`OCS` 订货对账单）：

    建单（按周期汇总订单） → 确认对账 → 结清
                            ↘ 作废

`oc_statement_items` 记录本期纳入的每一张订货单，`diff_amount` 记录差异（已付 vs 应付），差异保留人工申诉与挂账的余地。

### 4.5 ⑤ 智能分仓

按"库存满足率 + 区域就近度"打分选仓：

    得分 = 0.7 × 满足率 + 0.3 × 就近度
    就近度：同城 1.0 / 同区域 0.6 / 其他 0.2

0.7 : 0.3 的权重是有意的——**先保证发得出去，再谈远近**。反过来（就近优先）会出现"近的仓不够货、硬拆两仓发货"，履约成本反而更高。

候选仓先按客户所属组织的数据范围过滤（`customerWarehouseIds()`），再做打分，最后只有一个仓中选，`ship_warehouse_id` 与快照名一并写入订单。

### 4.6 ⑥ 多端 + 多种下单方式

`oc_orders.source` 记录下单来源：

    web    后台 / 门户下单
    import 批量导入
    repeat 历史订单复制（POST /orders/:id/repeat）
    mcp    Agent 侧下单
    seed   演示数据

来源字段不是为了统计，而是为了**审计与幂等**：批量导入与历史复制是最容易重复下单的两个入口，必须能区分出来回查。

## 五、授信单一口径：额度 = 未回款金额的上限

这是本模块**最容易写错、也最值得写下来**的一条。

### 5.1 唯一真相在台账，不在客户表

    oc_credit_ledger   ← 唯一真相。额度怎么被用掉的，必须能一笔一笔查出来
    oc_customers       ← **不缓存** credit_used

客户已用额度永远由 `SUM(oc_credit_ledger.amount)` 现算，不落冗余列。原因是冗余列与台账之间一旦不同步，就会出现"两边都对不上、还不知道哪边对"的死结。`balance_after` 只是留痕快照，不参与计算。

### 5.2 四种变动，含义各不相同

| change_type | 方向 | 触发时机 |
|---|---|---|
| `occupy` | 占用 `+` | 下单提交 |
| `release` | 释放 `−` | 取消 / 驳回 |
| `repay` | 释放 `−` | 回款（按 FIFO 摊到具体单据） |
| `adjust` | 人工调额 `±` | 老板特批调额度 |

### 5.3 收货**不**释放额度（这里曾经是真 bug）

初版在"收货"时也写了一条释放，理由是"货到了业务就闭环了"。结果是：

    收货释放一次  +  回款再释放一次  =  同一笔钱释放了两次额度

实测差异：台账余额 459k vs 订单在途占用 530k，**差 71k 就是被重复释放的那部分**。

修正后的口径一句话：**额度 = 未回款金额的上限。货发了、钱没回，额度就还在被占。**

    下单 → occupy（占用）
    收货 → 不动额度（货走了，钱没回）
    回款 → repay（释放），按 FIFO 摊到具体单据，台账与订单两侧同步减少
    取消/驳回 → release（释放）

### 5.4 回款不虚增：非账期客户不写台账

现结（`prepay`）与内部往来（`internal`）客户**本来就没有占用额度**，回款如果照样写台账，会凭空产生负余额（实测出现过 `-876.0` 这样的余额）。因此加一道守卫：

    usesCredit = (客户结算方式 === 'credit')
    只有 usesCredit 才写台账、才做 FIFO 分摊

## 六、状态机与业务流

### 6.1 订货单（`OC`）—— 10 状态 / 15 条边

    初始状态：draft 草稿
    [1] draft      草稿    ：提交→已提交，取消→已取消
    [2] submitted  已提交  ：进入审批→审批中，审核通过→已审核，驳回→已驳回，取消→已取消
    [3] approving  审批中  ：审核通过→已审核，驳回→已驳回
    [4] approved   已审核  ：智能分仓→已分仓，发货出库→已发货，取消→已取消
    [5] allocated  已分仓  ：发货出库→已发货，完成→已完成
    [6] shipped    已发货  ：确认收货→已收货
    [7] received   已收货  ：完成→已完成
    [8] completed  已完成  ：终态
    [9] rejected   已驳回  ：终态
    [10] cancelled 已取消  ：终态

三个设计细节：

1. **`received`（已收货）不是终态。** 虽然中文名像终点，但"签收"之后还要走**在线对账**，业务没有结束。按第四条第不变量（终态不能有出边），它必须是 `active`/非终态——内核自检会在启动时把这类错误抓出来。
2. **`approving` 与 `submitted` 是两条并行的入口。** 审批链逐节点推进：首次审批走 `review` 边进入 `approving`，后续节点在同状态内补留痕。这样"多级审批"与"一次审批"共用同一套边，不必为级数不同写不同状态。
3. **`submitted → approved` 是直通边，`submitted → allocated` **不是**。曾经误加过一条 `allocate` 从 `submitted` 出发的边，等于"提交即可绕过审批直接分仓"。这条边被删掉了——**状态机上的每一条边都是一次授权，多一条就多一个绕过点**。

### 6.2 订货对账单（`OCS`）—— 4 状态 / 3 条边

    初始状态：draft 草稿
    [1] draft     草稿   ：确认对账→已确认，作废→已作废
    [2] confirmed 已确认 ：结清→已结清
    [3] closed    已结清 ：终态
    [4] voided    已作废 ：终态

### 6.3 业务流 `FLOW_ORDER_CENTER`（8 环节）

| # | 类型 | 环节 | 发生单据 | 权限点 | 必经 |
|---|---|---|---|---|---|
| 1 | admit | 客户准入 | OC | `dms.dealer.approve` | 是 |
| 2 | catalog | 可见商品与按客户取价 | OC | `master.price.view` | 是 |
| 3 | check | 下单前校验（授信/账期/起订量） | OC | `order.place` | 是 |
| 4 | approve | 按规则审批 | OC | `order.confirm` | 否 |
| 5 | allocate | 智能分仓 | OC | `order.confirm` | 是 |
| 6 | ship | 发货出库 | DL | `sales.outbound` | 是 |
| 7 | receive | 客户签收 | OC | `order.view` | 是 |
| 8 | statement | 在线对账 | OCS | `order.statement.view` | 否 |

业务流的作用**不是跑流程引擎**，而是给"单据之间的推进"一张可校验的路由表——第 6 步挂的**不是 OC 而是 DL（销售发货单）**，这正是"订货单发货要落到销售出库单上"这条业务事实的落点。

## 七、数据模型

### 7.1 10 张表 + 1 个视图

| 表 | 存什么 |
|---|---|
| `oc_customers` | 订货主体（门店 / 经销商 / 下游），带准入状态、交易条件、订货策略 |
| `oc_addresses` | 收货地址（一个客户可多个） |
| `oc_orders` | 订货单头（客户快照、金额、授信占用、审批、分仓、来源） |
| `oc_order_items` | 订货单行（含取价维度快照） |
| `oc_approval_rules` | 条件审批规则（作用域 + 判定字段 + 阈值 + 角色 + 优先级） |
| `oc_order_approvals` | 审批节点记录（逐节点留痕） |
| `oc_credit_ledger` | **授信台账（唯一真相）** |
| `oc_statements` | 订货对账单头 |
| `oc_statement_items` | 对账单明细（本期纳入哪些单） |
| `oc_visibility_rules` | 商品可见性规则（按等级 / 渠道 / 客户控制） |
| `oc_orders_history`（视图） | **只读统一历史入口**：把 `store_requisitions`（旧门店要货）与 `dealer_requisitions`（旧经销商要货）并成一张表 |

### 7.2 视图为什么是视图

旧的两张要货表不能删（历史数据、旧接口还在用），但新前台需要"一个入口看全部历史单"。用视图把两表 `UNION ALL` 并起来，**不复制历史数据、不改动旧表**，是这里成本最低且无副作用的做法。

### 7.3 与内核的挂接

- **定义归 008，结构归 010。** `010_order_center.cjs` 只建表，`OC` / `OCS` 的状态与边登记在 `008_doc_kernel.cjs`。
  这条分工不是洁癖：008 有定义指纹自愈，任何"定义漂移"都会被重跑修复；如果定义写在 010 里，008 的自愈会把它当作未登记的旧定义抹掉。
- **单号走编码规则。** `nextDocNoByRule(db, { docType: 'OC' })`，规则缺失时回落到 `OC{YYYYMMDD}{SEQ:4}`。
- **权限点对齐。** 给 store / warehouse / finance 三个角色补 `order.place` / `order.view` / `order.statement.view`，避免"功能上了但没人有权限点"。

## 十、三个真 bug 与三处口径修正

实施中三个缺陷是**测试逼出来的，不是 review 看出来的**：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 三库里两个行业 `test-oc` 失败（无 downstream、授信测试挑到现结客户） | ① seed 写死了某个行业的经销商编码，别的行业建不出下游；② 测试挑"第一个客户端"测授信拦截，挑到了现结客户 | ① `downstream` 改为**数量声明式**，挂排序最前的 N 个经销商，编码由经销商自己的 `code` 派生；② 测试改为只从 `settle_type='credit'` 的客户里挑；③ 额度 0 的用例结束后**还原原值**而不是写死 100 万 |
| 2 | 授信台账 459k vs 在途占用 530k，差 71k | 收货释放 + 回款释放 = 同一笔钱释放两次额度 | 口径改为"额度 = 未回款金额的上限"，**收货不释放** |
| 3 | 中国香港 / 内部往来客户出现凭空负余额（`-876.0`） | 现结/内部客户本就没占用额度，回款却照样写台账 | 加 `usesCredit` 守卫，非账期客户不写台账 |

三处口径修正（不是 bug，是"原本想错了"）：

| # | 修正前 | 修正后 | 为什么 |
|---|---|---|---|
| 1 | 直营门店按对外客户处理，授信 0 | 直营门店为**内部主体**，不适用对外授信 | 一个不存在的额度被当成 0 校验，静默拦死整条业务线 |
| 2 | 缺货**硬拦**下单 | 由客户档案 `allow_shortage` 决定，默认 `warn`；缺货转成一条审批规则 | "先下单后补货"是 B2B 常态，硬拦挡掉大部分真实订单 |
| 3 | 存在 `submitted → allocated` 边 | **删除** | 等于"提交即可绕过审批直接分仓"，多一条边就多一个绕过点 |

## 十一、待确认（不阻塞）

1. **渠道层级深度** —— 当前演示只展开两级（品牌方 → 经销商 → 终端门店），表结构支持任意层。是否需要演示三级（总代 → 区域代 → 门店）？
2. **门店要货的审批链** —— 当前按金额分级（3 万 / 5 万 / 20 万）。是否要按品类分级（如生鲜单独一条链）？——第三轮曾提过此为待确认项。
3. **订货中心与商城共用同一套库存与商品** —— 当前实现是共用（只是可见性与价格策略不同），符合补充轮建议。是否确认？
4. **退换货** —— 订货单目前只有"取消"，没有"退货/换货"闭环。B2B 退换货涉及货权与授信回滚，建议单独一轮（模块 07 采购退货可共用一套机制）。
5. **拆单 / 改单** —— 调研里的"下单 → 审核 → 拆单/改单"目前只做了拆单来源字段（`parent_order_id`），未做拆单规则。
6. **在线支付** —— 现结客户目前只有 `prepay` 口径，未接支付渠道。属模块 24 集成。
7. **`oc_visibility_rules` 只落了两条样例** —— 美妆/服装两库为 0 条（无品牌可见性诉求）。是否需要为按品类控制可见性补规则？
