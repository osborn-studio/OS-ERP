## 一、这个模块是怎么被发现的

不是设计出来的，是**对账对不上**对出来的。

框架文档第四章 A 节把采购标为：

> 🟡 订单 / 收货 / 退货已通，**缺请购、到货单、质检、发票、结算、付款**

当时只有三张单：`purchase_orders`（采购订单）、`purchase_receipts`（收货单）、`purchase_returns`（退货单）。这意味着系统只能回答一个问题：

> 「货收到没有？」

而这只是采购的一半。真实现场要回答的是：

| 现场会问的问题 | 当时的系统能不能答 |
|---|---|
| 这批货是谁提出要买的？为什么要买？ | ❌ 没有请购单，需求无载体 |
| 供应商说货发了，但只到一半，算不算收货？ | ✅ 收货单支持部分收货 |
| 货到了，票也来了，票和货对得上吗？ | ❌ 没有发票，没有三单匹配 |
| 这个月的应付账款是多少？ | ❌ 没有结算单，应付无处落 |
| 钱付了多少？还剩多少没付？ | ❌ 没有付款单，收付款是黑洞 |
| 这张采购订单算完事了没有？ | ❌ 只有「已收货」，没有「已开票 / 已付款」 |

**问题的本质不是"少几个菜单"，而是"业务只做了一半就停了"**：采购的实质是「用一笔钱换一批货」，货的腿走完了（入库），钱的腿没走（发票 → 结算 → 付款）。只做一半的结果是：库存准确、成本失真、应付不可查。

所以本模块的目标不是"再补几张单"，而是**把采购从"收货即完成"改造成"九个环节的完整账"**。

### 1.1 与原模块的关系（不是新增，是补全）

| 原编号 | 原名称 | 处置 |
|---|---|---|
| 07 | 采购管理 | **补全为九环节** —— 本次新增请购、发票、结算、付款四类单据 |
| 07（订单侧） | 采购订单 / 收货 / 退货 | **保留既有实现**，只做口径对齐（超量控制、单号走规则、收货走内核） |
| 03 | 库存中心与成本层 | **复用** —— 收货入库、退货出库仍走同一套库存引擎，不另写一套 |

现有 `server/routes/purchase.js`（订单 / 收货 / 退货）**不重写**：新功能挂在同一路径前缀 `/api/purchase` 下、注册在其之后，未命中的请求落到新路由。既有链路的调用方（前端、测试）零改动。

## 二、核心设计判断：采购不是「一张订单」，而是「九个环节的账」

设计过程中最容易走错的一步，是把采购建模成"一张采购订单 + 一堆状态"。那条路会立刻撞墙：

- 请购是**需求**，采购订单是**承诺**，两者的行项目不是一对一（可以合单、可以拆单、可以部分转）
- 发票是**外部凭证**，数量金额由供应商决定，与订单、入库单天然存在差异（暂估差异）
- 结算是**一个期间的批量动作**，不是一张单的属性（一张结算单覆盖多张入库单/发票）
- 付款是**钱的动作**，与单据不是逐票对应（一笔付款可能核销多张结算单）

这四件事的粒度根本不同，硬塞进一张单必然产生「一张订单上有 6 个意思不清的状态字段」。

**本模块的设计判断**：

1. **四类单据各自独立、各有状态机**，通过「来源字段 + 结算明细」关联，不做单表继承；
2. 环节之间的**衔接规则**（能否转单、能否收货、能否结算）写成代码里的硬校验，而不是靠人记得点对按钮；
3. 所有「数量 / 金额」的权威值都**从明细算**，单据上的汇总字段只是快照。

## 三、九个环节逐环节落地

### 3.1 环节 1-2 · 请购（PRQ 请购单，7 状态 / 8 条边）

请购的关键设计点是**申请主体不是只有采购部**：

    申请人主体 applicant_type:  org 部门 / store 门店 / warehouse 仓库
    申请来源 source:          manual 手工 / auto 自动补货 / demand 需求驱动 / pos 门店自采
    交易类型 trade_type:      normal 普通请购 / store 门店自采 / urgent 紧急请购

现场真实情况是：门店店长发现缺货、生产计划部要备料、市场部要做新品、行政部要买工程物资 —— 这些都是采购需求，但都不是采购部提的。如果请购单只有一个 `created_by`，就无法回答「这单是谁的需求」，也就无法按部门做预算与考核。

所以申请人用 `applicant_type + applicant_id + applicant_name + department` 表达，`creator` 只表示"谁录的单"。

**状态机**：

    draft 草稿 → submitted 已提交 → approved 已审批 → converted 已转采购 → closed 已关闭
                                ↘ rejected 已驳回            ↘ cancelled 已取消

`converted` **不是终态**：请购支持**部分转单**（先转一部分给供应商 A，剩下的再转给 B），只有全部行都转完才能 `close`。这是 8 条边里唯一的判断点，测试里专门覆盖了「转 4 件 → 仍有剩余 → 补转 → 无剩余 → 再转被拒」这条路径。

### 3.2 环节 3-4 · 采购订单（PO，复用既有 + 补列）

订单侧不新增单据，只补三组列（迁移 011）：

    交易类型     trade_type                     同一张单可以有多个交易类型（用友口径）
    超量控制     over_receive_ratio             允许收货量 = 订单量 ×(1+比例)
    四段关闭     close_arrival / close_inbound / close_invoice / close_payment
    后段金额快照 invoice_amount / settle_amount / paid_amount
    转单来源     source_type / source_req_id / source_req_no / req_id

**转单时的硬校验**：供应商与入库仓必须明确（`PO_SUPPLIER_REQUIRED` / `PO_WAREHOUSE_REQUIRED`），且必须先过供货目录校验。校验不过**不出订单** —— 先建单再报错会留下一堆废单。

### 3.3 环节 5-6 · 到货与入库（GR 收货单，走内核）

收货单原有实现是**直接以 `status='received'` 插入**。这意味着 GR 虽然在单据内核里定义了状态机，却没有任何流转：

> 有状态机但没有任何流转，等于这张单没有留痕。

本次改为 `draft` 插入 + 走内核 `confirm` 边（`server/routes/purchase.js`），让收货也有「谁、何时、从哪到哪」的流转日志。

**超量控制在写库之前拦**：

    允许收货量 = 订单量 × (1 + over_receive_ratio)
    超出 → block 级拦截，在 INSERT 之前返回 409

为什么强调"写库之前"：多收的货如果已经入过库再撤销，库存流水会多出一进一出两条、成本会多算一次。**能在入口拦的，绝不放进去再回滚。**

### 3.4 环节 7 · 采购发票与三单匹配（PI 采购发票，5 状态 / 6 条边）

发票分两类，共用一个单据类型：

    invoice_type: vat_special 增值税专票 / vat_normal 普票 / fee 费用发票（运费、卸货费…）

**票号唯一性**：同一供应商下票号不能重复（`PI_DUPLICATE`）。这是财务红线 —— 一张真票只能入一次账。

**三单匹配**在 `verify`（发票校验）动作里执行，校验规则是「开票数量不得超过已入库数量」：

    over = 本票数量 + 该 SKU 已开票数量 − 该 SKU 已入库数量
    over > 0 → block，返回 INVOICE_OVER_RECEIPT，并逐行给出「本票 / 已开 / 已入库」三个数

匹配结论写进 `remark` 留痕，不做静默通过。

**状态机**：

    draft → submitted → verified 已认证 → posted 已入账
       ↘ voided（draft/submitted/verified 都可作废）

`verified → voided` 这条边是**本次补的**：认证只说明票与入库对得上，票本身开错（金额、税率、张冠李戴）在入账前必须能撤。`posted`（已入账）不给出边 —— 账已经记了，要改得走红字发票，不能一作废了事。

### 3.5 环节 8 · 三单结算（PST 采购结算单，5 状态 / 5 条边）

「三单」= 入库单 + 采购发票 + 费用发票。结算有三种模式，金额算法不同且必须显性：

| 模式 | 结算金额 | 适用场景 |
|---|---|---|
| `manual` 手工 | = 入库暂估金额 | 无票先结（月底关账时票还没到） |
| `auto` 自动 | = 已认证发票金额（无票则回落入库金额） | 常规：按票结算 |
| `fee` 费用折扣 | = 普通发票 + 费用发票 | 运费/卸货费要摊进成本 |

**暂估差异必须显性落库**：

    diff_amount = 入库金额 − (有票 ? 发票金额 : 入库金额)

差异不进任何"合计"，而是单独一列。财务要看的正是这个数（暂估与实票的差），把它混进金额里等于把问题藏起来。

**费用摊入成本**：费用发票金额按各入库行的金额占比摊到行上，算出 `final_cost`（该批次真实入库成本）：

    share      = 该行入库金额 / 入库金额合计 × 费用合计
    final_cost = (该行入库金额 + share) / 该行数量

**状态机**：

    draft → submitted → audited 已审核 → settled 已结清
       ↘ voided（draft/submitted 可作废）

### 3.6 环节 9 · 付款核销（PAY 付款单，4 状态 / 4 条边）

付款单的核心不是"记一笔支出"，而是**核销**：这笔钱抵掉了哪几张结算单的哪一部分。

    draft 草稿 → approved 已审批 → paid 已付款
       ↘ voided 已作废

创建付款单时可以指定核销明细（`allocations`），不指定则按**FIFO 自动核销**：按结算日期先老后新，把金额填到未结清的结算单上。

## 四、四个硬设计点

### 4.1 取价有链，且必须带来源

采购取价不是"读一个字段"，而是一条四档链，每档都必须带回来源标签：

| 档 | 来源 | source | 说明 |
|---|---|---|---|
| ① | 供货目录协议价 | `agreement` | 带有效期校验（valid_from / valid_to） |
| ② | 该供应商最近成交价 | `last_deal` | 收货时自动回写 `last_price` |
| ③ | 最近采购订单价 | `last_order` | 带回来源单号，可追溯 |
| ④ | 标准成本兜底 | `cost_std` | 什么都没有时的最后底线 |
| — | 手工录入 | `manual` | 传了就直通，不参与链条 |

**为什么必须带来源**：采购员看到 12.80 这个价，第一个问题一定是"这价哪来的"。没有来源标签，取价引擎就是个黑盒，谈完价之后没人敢确认系统里的价对不对。

**协议价不能被收货悄悄改掉**：收货只回写 `last_price`，不动 `price`。

> 协议价是谈出来的，不能被一次收货悄悄改掉。

### 4.2 供货目录是硬拦截（「没登记」≠「登记为不供」）

`supplier_products` 一张表承载三件事：**是否可供 / 协议价 / 最小起订量**。语义边界必须写清楚：

    is_available = 0  → 显式的「不可供」，下单/转单时 block
    is_available = 1  → 可供
    记录不存在        → 未维护目录，**不拦**

最后一行是最容易写错的地方：如果"没登记"也拦，新供应商第一次合作就永远下不了单（目录是慢慢维护起来的）。所以拦的只应是**明确的否定**。

**最小起订量（MOQ）**同理，`min_order_qty > 0` 且数量不足时 block。演示数据里每个供应商都埋了一条 `is_available=0` 的记录与一档非零 MOQ，专门用来验证这两个分支真的会被触发。

### 4.3 超量控制

见 3.3。补充一条实现细节：`checkOverReceive` 同时校验**该商品是否在本订单内**（`NOT_IN_ORDER`）—— 收货时把别的订单的货混进来，是比超量更严重的问题。

### 4.4 四段关闭只进不退

采购订单的四段关闭是**自动推导**的，且**单向**：

    close_arrival 到货关闭 = 全部行收货量 ≥ 订单量
    close_inbound 入库关闭 = 有收货单且全部已关闭
    close_invoice 开票关闭 = 已开票金额 ≥ 订单金额
    close_payment 付款关闭 = 已付金额 ≥ 结算金额

    条件满足 → 置 1；条件不再满足 → **不自动打开**

> 关闭是单向动作。一旦关了不能因为后来改了单据又自动打开 —— 那会让已经停止的业务重新流动。

测试里专门做了这件事：把某张已「到货关闭」订单的收货量清零再刷新，旗标仍然是 1。

## 五、核销单一口径：paid_amount 永远是明细算出来的

这是本模块**最容易出错、也最值得写清楚**的一处。

### 5.1 生效点 = 付款单审批通过（草稿不算已付）

付款单有四态，其中 `draft` 与 `approved` 之间正好横跨一条**核销生效线**：

| 付款单状态 | 核销明细已录 | 计入结算单已付金额 |
|---|---|---|
| `draft` 草稿 | ✅ 已录（这是"核销计划"） | ❌ **不计入** |
| `approved` 已审批 | ✅ | ✅ 计入（用友口径：付款单审核即核销） |
| `paid` 已付款 | ✅ | ✅ 计入（`paid_at` 记录实际付款时间） |
| `voided` 已作废 | ✅ 保留 | ❌ 不计入（金额自动回退） |

**为什么这样定**：录入付款单时就选好核销对象是必要的（出纳要照着单子付款），但那只是**计划**。如果草稿态就计入已付，会出现"钱还没付，结算单已经显示收齐了"—— 这在财务上是不能接受的。所以：

    settlements.paid_amount = SUM(purchase_payment_items.amount)
                              WHERE 付款单状态 IN ('approved','paid')

**永远是 SUM 算出来的，不是累加出来的**。累加（`paid_amount = paid_amount + amount`）在作废、重复提交、并发时会漂移，而且漂移之后无法自证。本模块所有涉及金额的地方都遵循同一条原则 —— 与模块 12A 订货中心的授信台账完全一致。

### 5.2 作废保护：不能让已结清的结算单失血

结算单结清是单向的（状态机里没有 `settled → audited` 的边）。如果允许随意作废付款单，就会出现：

    结算单已结清 → 付款单作废 → 已付金额掉下来 → 结算单停在「已结清」却金额不足

这是账实不符，不是显示问题。所以作废前先算一笔账：若作废后该结算单的剩余生效核销金额不足，直接拒绝：

    PAY_VOID_BREAKS_SETTLEMENT → 「结算单 X 已结清，作废本付款单会使其金额不足；请先作废该结算单」

测试里覆盖了"被拦之后结算单金额与状态都没被改动"（拒绝必须是干净的）。

### 5.3 一单一结（暂估冲回列为待确认）

**入库单与发票各自只能被一张未作废的结算单引用**。理由与上面一致：宁可少算（可以人工再结一次），绝不重复算（应付虚增，且很难发现）。

代价是：`manual` 暂估结算后，发票来了无法在同一批入库单上做"暂估冲回"。这在用友里是允许的（需要暂估标识与冲回分录），本模块选择不做 —— **列入待确认，不假装支持**。

### 5.4 「执行付款」= 核销 + 状态前进，两件事必须一起发生

本轮修掉的一个真 bug：`pay` 动作只做了核销、没有推进状态，导致付款单永远停在「已审批」，而钱已经核销掉了。

    只核销不推状态 → 付款单永远停在已审批（账实不符）
    只推状态不核销 → 结算单永远收不到钱

两者必须原子地一起发生。这是"看代码很对、跑起来不对"的典型：核销真的落库了（所以结算单显示结清），付款单状态却没动（所以列表里还写着待付款）。

## 六、状态机与业务流

### 6.1 四类新单据的定义规模

| 类型 | 名称 | 状态数 | 流转边数 |
|---|---|---|---|
| `PRQ` | 请购单 | 7 | 8 |
| `PI` | 采购发票 | 5 | 6 |
| `PST` | 采购结算单 | 5 | 5 |
| `PAY` | 付款单 | 4 | 4 |

定义全部写在**模块 04 单据内核（迁移 008）**，不写在 011。原因写在 011 的注释里：

> 定义写在 008 而不是这里，是因为 008 有定义指纹自愈，会被重跑修复；写在 011 里会被 008 的自愈当成"未登记的旧定义"抹掉。模块 12A 已踩过这条。

### 6.2 业务流 `FLOW_PURCHASE`（9 环节）

| # | 环节 | 单据 | 权限点 | 必要 |
|---|---|---|---|---|
| 1 | 请购申请 | PRQ | `purchase.req.edit` | ✔ |
| 2 | 请购审批 | PRQ | `purchase.req.approve` | ✔ |

### 7.2 迁移 012：一处补列 + 四个索引

`purchase_payments.paid_at`（实际付款时间）：`approved` 是"审批通过、核销已生效"，`paid` 是"出纳已把钱付出去"。两者金额口径相同、**时间不同** —— 财务对账要答的是"这笔钱哪天出的"，`approved_at` 答不了。

四个索引都是按查询形状建的：核销回写按 `settle_id` 查明细、应付看板按 `供应商 + 状态`、FIFO 计划按 `结算日期` 排序、结算明细反查订单。

### 7.3 一个容易踩的坑：008 先于 011 执行

模块 04 的状态机定义里引用了权限码（如 `purchase.req.edit`）。008 先跑，会把权限码以「code 当 name」的占位形式插入 `permissions` —— 结果界面上显示的是 `purchase.req.edit` 而不是「提交请购单」。

所以 011 写权限点必须用 UPSERT 纠正名称，不能用 `INSERT OR IGNORE`：

    ON CONFLICT(code) DO UPDATE SET name=..., module=..., category=...

自检 `verify()` 也同时校验 name 与 module，只校验"存在"是查不出这个问题的。

## 十、本轮修掉的 8 个真 bug 与口径修正

按发现顺序，每个都是"跑起来才露出来"的：

**① 「执行付款」只核销不推状态**
`pay` 动作直接返回 `writeOffPayment()`，从不调用状态流转 → 付款单永远停在「已审批」，而结算单已经显示结清。改为核销 + 状态前进一起做。

**② 付款单作废后已付金额不回退（幽灵核销）**
核销金额只在 `writeOffPayment` 里重算，作废走的是另一个分支 → 付款单没了，钱还算着。引入统一的 `syncSettlePaid()` 重算，任何影响生效线的状态变化都走它。

**③ 已结清结算单的付款单可被作废**
结算单结清是单向的，付款单作废会让它"停在已结清却金额不足"。加 `PAY_VOID_BREAKS_SETTLEMENT` 拦截。

**④ 路由被通配段吃掉：转单接口永远到不了**
`POST /requisitions/:id/:action` 先注册，把 `/requisitions/:id/convert` 匹配成 `action='convert'`，返回 400「请用 POST /requisitions/:id/convert」—— 而那个接口谁都到不了。调整注册顺序，并在代码里写明顺序敏感。

**⑤ 已认证但未入账的发票无法作废**
状态机缺 `verified → voided` 边，票开错了只能留着往下走。008 补这条边（`posted` 仍不给出口 —— 账已记，要走红字）。

**⑥ 同一入库单/发票可被多张结算单重复引用**
`buildSettlement` 只按状态筛，不排除已被结算引用的单据 → 应付虚增。加排除条件，明确「一单一结」。

**⑦ 收货接口不传日期就 500**
`receipt_date` 直接拿 `req.body.receipt_date` 插库，缺省即撞 NOT NULL 约束。缺一个可选字段不该是服务端错误，改为缺省取当天。

**⑧ 采购 seed 查了三个不存在的列**
`s.p_cost`（在 `products` 上）、`moq`（真实列名 `min_order_qty`）。服务启动即抛 `SqliteError`，整个采购域数据造不出来。

**⑨ 采购 seed 重置漏了"转单订单上的收货单"**
清理只删订单不删收货单 → `purchase_receipts.order_id` 外键失败；更严重的是**收货已经把货记进库存**，只删单据会让库存凭空多一批。改为先用库存引擎按批次反向出库（`PUR_IN_REV`），把现存量/批次/流水一起退回再删单据。

**⑩ 冒烟脚本的 5xx 统计被写链路的 ✗ 掩盖**
写链路的失败只计入 4xx 计数，导致收货接口 500 时总计仍显示「5xx 0」。修正统计逻辑，5xx 必须计入异常。

**⑪ 测试断言写死了单据类型数（24 → 28）**
定义规模变化后测试红灯，属于预期内的口径更新，同步改为 28 并注明构成。

## 十三、口径与边界

**这个模块管什么**

- 从「谁提出要买」到「钱付出去」的完整九环节
- 采购取价的四档链路与来源追溯
- 供应商供货目录（可供性 / 协议价 / 起订量 / 交期）
- 三单匹配（入库单 + 采购发票 + 费用发票）与暂估差异
- 应付账款的唯一真相与付款核销

**这个模块不管什么**

| 不管的事 | 归谁 |
|---|---|
| 供应商主数据、供应商分级与考核 | 模块 02 主数据 |
| 货权、批次、效期、库存成本 | 模块 03 库存中心与成本层 |
| 出入库单据的状态流转 | 模块 04 单据内核 |
| 谁能看成本、谁能审核结算 | 模块 05 组织与权限 |
| 单号生成 | 模块 06 编码规则 |
| 门店向总部要货 | 模块 12A 订货中心（`store_requisitions` / `oc_orders`） |

**最后一条要特别说明**：本模块的**请购**（`purchase_requisitions`，内部主体 → 外部供应商）与模块 12A 的**门店要货**（`store_requisitions`，门店 → 总部）名字接近、语义完全不同：

    请购：我要买 → 面向外部供应商，产生应付账款
    要货：我要领 → 面向内部仓库，产生内部往来（或转成采购订单后才有应付）

两者**不合并**。历史上 `server/routes/requisitions.js` 里存在过 `transferred 已转采购` 状态（门店要货也可转采购订单），这条路径保留但不再演进，前台标注「（历史单）」。把它们混成一张单，会让"内部往来"与"外部应付"两本账混在一起 —— 那是财务口径的灾难。
