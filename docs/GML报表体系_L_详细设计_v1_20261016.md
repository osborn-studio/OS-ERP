# GML 报表体系（批次 L · 模块 28）详细设计

> 版本：v1 ｜ 日期：2026-10-16 ｜ 迁移：**034_report** ｜ 契约：1.19.0
> 说明：文中客户与品牌一律为虚构行业名（美妆版 / 餐饮版 / 服饰版），演示数据均为虚构。

---

## 一、这一批补的是什么

批次 H 把业务事实变成了借贷平衡的凭证，批次 J 把"待退款"兑现成了真实出账。
但整条财务链上**只有一张试算平衡表**。

试算平衡表能回答的是"**总账平不平**"。它回答不了经营者真正要问的三句话：

| 问题 | 需要的东西 |
|---|---|
| 我这家公司现在有多少家底？ | **资产负债表** |
| 这段期间到底赚了多少？ | **利润表** |
| 钱是怎么来的、又花到哪去了？ | **现金流量表** |

所以本批不是"再加几个查询接口"，而是把账**读出意义**来。

## 二、四条硬口径

### ① 报表结构是会计政策，不是代码

「货币资金 = 1001 + 1002」「营业成本 = 6401」这类映射由人来定，且要能被审计、
能追溯改过什么。所以它入库（`report_defs` / `report_lines`），
与凭证模板（`voucher_templates`）同一个道理：**能改的东西不该写死在 if 里**。

`report_lines` 的四件关键配置：

| 列 | 作用 |
|---|---|
| `subject_range` | 本行认领的科目码闭区间，**可多段**（`1122~1122\|2203~2203`） |
| `sign` | 方向口径：行金额 = `sign × Σ(本行认领科目的 signed)` |
| `only_direction` | 仅现金流量表：只接流入 / 只接流出 |
| `subtotal_expr` | 小计/合计行：**只允许「行号 + 加减号」**（`1+2+3-4`） |

**为什么区间要支持多段**：现金流量表的一行常常对应**几个互不相邻的对手科目**
（"销售商品收到的现金" = 应收 1122 + 预收 2203 + 收入 6001 + 销项税 222101）。
只给一个区间的话，要么拆成几行同名（界面上重复出现，像 bug），
要么把中间的科目一起圈进来（把"预付账款"算进"销售收现"）—— 两者都是在配置里撒谎。

**为什么小计不能写表达式**：可被界面编辑的配置一旦能写表达式（`*`、`/`、括号、字段引用），
就等于**配置能改账**。这与凭证模板的 `amount_key` 只能取封闭字典是同一条铁律。
写入时即拦（`parseSubtotalExpr`），且**引用必须当场解析得开** ——
写一条指向不存在行号的小计，写入时不报错，要等到有人打开那张报表才炸，
而那时离改动已经很远，报表页只会显示"算不出来"，看不出是哪一次配置改动造成的。
被小计引用的行也**不允许删除**（删掉会让小计静默少一块，而报表仍然很好看）。

### ② 期初余额按借贷两列存，且整批覆盖

- **两列存**（`debit_amount` / `credit_amount`）而不是一个带符号的数：
  余额方向由科目自身的 `direction` 决定（负债类与资产类相反），
  用一个 signed 数存下来，读的人就得先知道"这个数是按谁的方向算的" ——
  而这正是把负债读成负数的来源。两列存法还能表达「资产科目出现贷方余额」这种异常。
- **同一科目不能两边都有数**（"借 100 贷 100"会让试算平衡看起来平，但那一行读出来是 0）。
- **整批覆盖 + 写入前对整批做平衡校验**：不平就**整批不落库**。
  逐条改的时候，人看不到"现在的合计是多少"；而一张不平的期初试算表
  会让之后**每一期的资产负债表都不平**，且差额来源从此不可考。

### ③ 期初余额要**滚动**到本期

取 `period <= P` 中**最近一次登记**的期初作为基准（记作 B），
再滚上 `[B, P)` 区间内已过账的发生额。

**为什么必须滚动**：演示库只在 2026-05 登了一次期初，出 2026-10 的报表时
如果只认当期登记，报表会变成"只有 10 月发生额"—— 资产合计与负债合计看起来都很小，
而且**恰好仍然平**（因为都从 0 起算），于是没有任何东西会告诉你这笔账漏了五个月。

没有登记过任何期初 → 全部为 0，并在接口里如实标注 `has_opening: false`。

### ④ 关账后不能再过账，但**可以**生成

`accounting_periods.status='closed'` 是"期间"这个概念唯一的落点：
没有它，9 月的报表会随着 10 月做事而改变。

- **只拦过账、不拦生成** —— 生成出来的 `draft` 不计入任何报表，
  拦它只会让"先录单、后开账"这条正常流程走不通。
- **不存在的期间视为未关账**：建库时不可能把每个期间都预先登记，
  而"没登记"与"关过账"是两件不同的事；混为一谈的后果是第一批凭证全部过不了账，
  且错误信息会说"期间已关账"（一个从没关过的期间）。
- **关账前必须**：① 三张报表自证通过；② 没有未过账的草稿凭证。
  带着一张不平的资产负债表定稿，等于把差额永久封存在这一期里；
  而关账后草稿的期间再也过不了账，只能作废重录。
- **反关账必须写理由** —— 它会让已定稿的期间重新可变，与作废已过账凭证同一个道理。

期间工具（格式 / 位移 / 状态 / 过账闸门）下沉到 `lib/period.js`：
凭证模块（`postVoucher`）与报表模块（`closePeriod`）都要用**同一个**闸门，
而如果把它写在报表模块里，凭证模块就要 import 报表模块 —— 方向是反的。依赖图是一条直线。

## 三、三条自证恒等式（报表域的核心）

三条都**不是**"再算一遍核对"，而是**数学恒等式**：

### ① 资产合计 = 负债合计 + 所有者权益合计

记 `signed(科目) = 借 − 贷`。因为每张凭证"借方合计 = 贷方合计"，
把所有已过账分录按科目汇总后 **Σ signed 恒等于 0**。于是：

```
Σ资产 = −Σ(负债 + 权益 + 损益) = 负债 + 权益 + 损益
```

⇒ **只要借贷是平的，这张表就必然平**，与科目余额的大小无关。

这条恒等式给了两件东西：

- **一个"判定没做到位"的探针**：报表不平**只可能**是两个原因 ——
  期初余额本身不平，或**报表行漏了某个科目**（那个科目的余额没被任何一行认领）。
  后者是配置错误里最隐蔽的一种（报表看起来很好看，就是差一个数）。
- **一个不依赖人工核对的验收口径**。

**未结转损益的处理**：本系统**没有做期末结转**，损益类科目期末仍有余额。
所以资产负债表把 6xxx 的余额一并计入所有者权益（`BS_UNCARRIED_PL` 行）。
不这么做，资产负债表必然差一个"本期利润"。做了期末结转之后这一行自然归零
（余额被转到 4103 本年利润），报表照样平 —— 口径是兼容的。

### ② 净利润 = Σ(损益类科目发生额，按科目方向取号)

利润表用**本期发生额**（不是期末余额）：收入行 `sign=−1`、成本费用行 `sign=+1`，
行金额 = `sign × (本期借 − 本期贷)`。

### ③ 现金流净增加额 = 现金类科目期末余额 − 期初余额

现金流量表的算法在下一节。

### 探针（`auditReport`）覆盖的七类问题

| 码 | 含义 |
|---|---|
| `SUBJECT_UNCOVERED` | 声明要穷尽覆盖的科目没人认领（**排除兜底行**，见下） |
| `LINE_RANGE_OVERLAP` | 两个科目行的区间重叠 ⇒ 该科目被算两次 |
| `FALLBACK_NONZERO` | 兜底行金额非 0 ⇒ 有科目没被任何具体行认领 |
| `BS_NOT_BALANCED` | 资产 ≠ 负债 + 权益 |
| `PL_MISMATCH` | 净利润 ≠ 损益类科目发生额合计 |
| `CF_MISMATCH` | 净增加额 ≠ 现金类科目变动 |
| `CF_NO_FALLBACK` / `OPENING_NOT_BALANCED` | 现金流缺兜底行 / 期初不平衡 |

**关于兜底行**：它接走"没有任何具体行认领的科目"，用途是**不让金额凭空消失**，
不是掩盖漏配。所以对资产负债表 / 利润表它**应当恒为 0**，一旦有金额就报 `FALLBACK_NONZERO`。
对现金流量表它**会**有金额（复合凭证的净额本来就归不到任何一行），那是预期的。

> ⚠️ **覆盖检查必须排除兜底行**：兜底行的区间是 `0000~9999`，
> 把它算进并集的话，`SUBJECT_UNCOVERED` 这条检查会**永远通过** —— 而它的全部价值就在于抓漏配。

**一张报表只能有一个兜底行**：两个兜底行不会报错，
只会让"没人认领的科目"被**任意一个**接走（谁在前谁接），
于是同一份账两次查询得到不同的报表，且没有任何东西会告诉你。
兜底行也必须**排在最后**被计算，否则它会先把科目抢走，上面的行一道也认领不到。

## 四、现金流量表：没有辅助核算，就只能"分析填列"

系统没有"现金流量项目"辅助核算，也没有做期末结转，所以现金流量表只能从凭证本身分析出来。

### 算法（`cashFlowBuckets`）

逐张已过账凭证：

- 现金类科目集合由 `report_defs.cash_subjects` 配置（默认 `1001,1002`）；
- `cashDebit` / `cashCredit` = 该凭证里现金类科目的借 / 贷合计；
  `otherDebit` / `otherCredit` = 非现金分录的借 / 贷合计；
- 不涉及现金的凭证**整体跳过**；
- **单边配对**（非现金分录方向单一、且金额正好对上现金侧）：
  非现金 `credit` 是现金的**来源**（+），非现金 `debit` 是现金的**用途**（−），
  逐条按其**对手科目**匹配报表行；
- **复合凭证**（现金与非现金在多条线上交叉）走**净额法**：
  净额 `cashDebit − cashCredit` 归到兜底行，并**如实计数**回报
  （`complex_vouchers`），不假装它被精确归了类。

### 为什么行要带 `only_direction`

同一个科目在两个方向上语义不同：贷 `222101` 是"随货款代收的销项税"（属销售收现），
借 `222101` 是"实际缴税"（属支付税费）。只靠科目区间无法区分。

因此现金流的匹配按 **(科目, 方向)** 分配到**第一个**匹配的行，
**认领键也必须带方向** —— 只按科目记认领，贷方被"销售收现"认领之后，
它的借方（缴税）那一笔会直接掉进兜底。

### 自证恒等式

凭证平衡 ⇒ `cashDebit + otherDebit = cashCredit + otherCredit`
⇒ `otherCredit − otherDebit = cashCredit − cashDebit`

左边就是填进报表的全部金额，右边就是现金类科目的净变动（期末 − 期初）。
**两种填列法都满足它** —— 净额法只是把同一笔总额放到了兜底行。
所以这条恒等式同时也是"现金期初余额登记得对不对"的探针。

## 五、口径的单一实现

| 判据 | 唯一实现 |
|---|---|
| 期间格式 / 位移 / 状态 / **过账闸门** | `lib/period.js` |
| 科目余额（期初 / 本期发生 / 期末） | `lib/report.js` 的 `subjectBalances` —— 三张报表**唯一**取数口 |
| 现金类科目集合 | `report_defs.cash_subjects`（不在两处各写一个数组） |
| 报表计算 | `computeReport` —— 三张报表只是它的薄封装（`balanceSheet` / `incomeStatement` / `cashFlow`） |
| 域自证 | `auditReport` —— 与 `verify-seed` 第 18 节**共用同一份** |
| 报表行写入 | `saveReportLine` —— 界面与 seed 都走它 |
| 报表定义装饰 | `decorateDef` —— `listReportDefs` 与 `getReportDef` 共用一份 |

**"资产负债表自己查一遍、利润表再查一遍"正是 D2 那类缺陷的原形**，
所以三张表从同一张余额表取数。

## 六、计算的两轮结构与顺序约定

`computeReport` 分两轮：

1. **先算全部 `item` 行**（含兜底行）—— 它们只依赖科目余额表与现金流桶；
2. **再按 `line_no` 升序算 `subtotal` / `total` 行** —— 它们只引用已算出的行金额。

之所以不需要拓扑排序：小计表达式只允许行号加减（无嵌套、无跨表），
所以"被引用的行"要么是 item 行（第一轮已好），要么是行号更小的 subtotal 行（第二轮已好）。
兜底行是 item 行，因此在 total 引用它时已经算完 —— 这一点靠第二轮保证，不靠行号大小。

**还有一个坑必须显式处理**：所有 item 行的金额**先初始化为 0** 再往上加。
现金流口径下"本期没有任何一笔匹配到这一行"是完全正常的（例如本期没交过税），
但如果那一行压根没被写进 `amounts`，引用它的小计会在第二轮报 `SUBTOTAL_REF_MISSING` ——
报的却是"第 2 行还没算出来"，指向一个**其实只是没有发生额**的行。

## 七、经营分析：账上 vs 业务，差异如实展示

本系统里**不是每条业务流都生成了凭证**（生成是显式动作，且演示数据刻意留了一张 draft）。
所以"应收科目余额"与"业务应收未收余额"本来就可能不相等。

把它们并列摆出来 + 说明差异，比强行让它们相等（或只显示一个）诚实得多 ——
**报表最容易骗人的方式不是算错，而是只显示一个来源**。

差额本身是「**还没记到账上的业务**」的度量，不是错误。

业务口径各自也只有一处定义：

- 发货成本取 `inventory_transactions`（出库那一刻的成本），不是"发货行金额 × 某个毛利率"；
- 应收未收取 `ar_documents` 的 `amount - allocated_amount`（核销明细的和），不是反推。

## 八、与既有链路的关系

- **不新增单据类型**（报表是只读产物，不是单据），也不改单据内核。
- 唯一碰到既有链路的是 `postVoucher`（关账拦截），见第二节 ④。
- 新增 4 个权限点，**分开授权**：

| 权限点 | 为什么单独 |
|---|---|
| `finance.report.view` | 三张主表能推出成本、毛利与负债结构 —— 连 viewer 都不给 |
| `finance.report.config` | 改报表口径能让**同一份账**得出不同的利润 —— 这是会计政策 |
| `finance.period.close` | 关账会挡住记账；反关账会让已定稿的期间重新可变 |
| `finance.opening.edit` | 改一个期初数字会同时改变之后**每一期**的资产负债表，且改完仍然"看起来平" |

## 九、本批新增的边界（未做，如实登记）

1. **期末结转与结账**：未做损益结转的自动凭证（靠 `BS_UNCARRIED_PL` 行等价处理）。
2. **报表体系只到三张主表 + 经营分析**：无所有者权益变动表、无现金流量表补充资料、
   无分部报告、无合并报表。
3. **现金流量表用"分析填列"**：没有现金流量项目辅助核算，
   复合凭证按净额归兜底行（`complex_vouchers` 如实计数）。
4. **无跨期比较与趋势**：只有单期间的报表，没有"上期 / 去年同期"对照。
5. **无报表导出**（Excel / PDF）。
6. **无严格的"关账 - 反关账"审计链**：留了 `closed_by` / `closed_at` / `reopen_reason`，
   但反关账会清掉 `closed_by`（不是追加一条历史）。
7. **PI/PST/PAY 的存量行 `org_id` 为空**（批次 K 的遗留边界，本批未涉及）。
