### 1.4 ③-b `yoy_ytd`：先手算，再比

**手算（起点月 = 1，本期 2026-07）**：本期累计窗口 = `2026-01 ~ 2026-07`；基期必须是**同一窗口整体下移 12 个月** ⇒ `2025-01 ~ 2025-07`（7 个月、同相位）。**错误形态**是 `[2025-07, 2026-07]`（13 个月、含去年全年）。

实测：
```
mode_label      = 上年同期累计（累计同比）（2025-01 ~ 2025-07）
base_period     = 2025-07
base_range      = {mode:'ytd', from:'2025-01', to:'2025-07', is_range:true, year:2025}
```
⇒ **是「整体下移 12 个月」，不是错误形态** ✓；标签自证窗口，读文件的人不必自己推。

列定义：`本期累计(2026-01~2026-07)` / `上年同期累计(2025-01~2025-07)` / `累计差额`(money) / `累计变动率%`(percent)。

**手算差额**：本期 `37304.5` − 基期 `0` = `37304.5`；实测 `diff = 37304.5` ✓（净利润 `19105.9 − 0 = 19105.9` ✓）。
**基期为 0 时**：`ratio = null`（不是 ∞ / NaN / 100%），且 `base_meta.comparable = false`、`posted_vouchers = 0` ⇒ 如实标出"基期没有业务" ✓。

**起点月 = 4 时**（临时改 settings，`try/finally` 还原）：基期 = `2025-07`，窗口 = `2025-04 ~ 2025-07` ✓（下移 12 个月后的会计年度年初）。

## 二、我推翻或怀疑什么

### 2.1 ⚠️ 「金额单元格 == 报表金额」这条断言**只在 0 上被验证过**（覆盖缺口，不是产品 bug）

`test-export-excel.mjs:97` 选期间的方式是
```js

```
`availablePeriods` 是**倒序**的 ⇒ 选中 **2026-10**。而：
- 2026-10 的**损益类分录数 = 0**（该期 4 张已过账凭证只涉及 `1002/1122/2202/2203`，全是 asset/liability）；
- ⇒ 该期利润表**六行金额全是 0**（我实测：`[0,0,0,0,0,0]`）；
- ⇒ E3 里"金额单元格是数值类型、且 == 报表金额、且与 CSV 那一格逐字相同"这三条，**每一格比的都是 `0.00` vs `0`**。

```bash
node -e 'import("./server/lib/report.js").then(R=>{const D=require("better-sqlite3");const d=new D("data/gml_cosmetic.db",{readonly:true});for(const p of["2026-05","2026-07","2026-10"])console.log(p,JSON.stringify(R.computeReport(d,{reportCode:"pl",period:p}).rows.map(x=>x.amount)))})'
```

**我补做了这条覆盖**：换 2026-07（非零）+ 在真实 result 上注入 `-1234.56 / 19105.9 / 0 / null`，用 openpyxl 读回逐格核对（见 1.2）—— **通过**。所以**产品是对的，套件这条断言是"在跑但信息量≈0"**。
**建议**：期间改成"找一张金额非零的报表"，或加一条"本次核对的数值格里至少有一个非零"的自证断言（否则永远不知道它是真核过还是核了一堆 0）。

### 2.2 ⚠️ `test-export-excel.mjs` 的"跳过"是静默的，且没有总数自证

```js
if (!fs.existsSync(file)) { console.log(`  （跳过 ${ind}：${file} 不存在）`); continue }
```
脚本末尾只打印 `通过 N / 失败 M`，**没有**"应到断言数恒定"的判据（`test-xlsx.mjs` 有：`ok('Python 断言总数恒定（27 条…）', count === 27 && lines.length === 27)`）。
⇒ 少一个库，会得到一个**更小但仍全绿**的计数（98 → 66/0；**注：`98` 同样是本节时点的数，见 1.1 的时点标注，现为 `102`**），**跳过与通过输出一样**（铁律 22）。
**建议**：把"应到的 3 个库 × 每组断言数"做成常量断言，或让缺库直接 `ok(false, …)`。

### 2.3 ⚠️ 被测代码抛出的**非预期异常**会让两套脚本整轮崩掉，丢掉后面全部断言

- B3 实测：去掉 `yoy_ytd` 的 `range` 后，`test-ytd-compare` **先打印了可读的红**（`✗ 模式自带区间 ytd：期望 "ytd"，实际 null`），随后 `RANGE_COMPARE_UNSUPPORTED` 在某个非断言的调用点抛出、未被捕获 ⇒ Node 直接退出，**没有** `通过 N / 失败 M`，**后面所有断言一条都没跑**。
- 同一件事两套脚本处置不一致：`test-xlsx.mjs` 对"解释器不可用"是 `ok('Python 解释器可执行', false, …)`（可读的红，继续跑）；`test-export-excel.mjs` 的 `readWithOpenpyxl` 是 `throw`（整轮崩）。
**建议**：统一成"捕获 → `ok(false, …)` → 继续"，或在套件最外层包一层 try/catch 打一张"未完成"的收尾表。

### 2.4 ⚠️ 硬编码的本机解释器路径（与我刚修掉的 `is_isolated_copy` 同一类：自称的元信息/环境假设）

两套脚本都写死：

### 2.5 观察（不是缺陷，但值得知道）

- `fiscalYearOf(p, undefined)` → **用默认 1 月**（不报错）；`fiscalYearOf(p, null)` → **抛错**；`fiscalYearOf(p, '4')` → **接受**。三种"没给/给空/给字符串"行为不同。读路径 `fiscalStartMonth(db)` 是容错的（非法一律回落默认），写/推路径 `fiscalYearOf` 是严格的 —— 这个不对称是否有意，建议作者确认一句。
- `MULTI_YEAR_LINE_MISSING`（某一年缺某一行的兜底抛出）**我构造不出来**（见三-1）。
- `multiYearPeriods(p, '2')` 接受字符串年数（`Number` 强转）。与上一条同源。
- 40000 字符的单元格能写能读，但模块**没有 32767 上界校验**；报表路径今天产不出这种格（见三-5）。

### 2.6 我自己的脚印 —— 而且这恰好是 R 批探针**正确地抓住了我**

我在 1.3 测"起点月 = 4"时，用 `S.writeSetting` 改成了 4，但**还原时用了裸 SQL**：
```js

```
⇒ 重放审计日志得到 `4`、现状是 `1` ⇒ 之后 **`test-cashflow-item` 报 8 条红、`test-fiscal-year` 报 2 条红**，全部是 `SETTING_AUDIT_DESYNC`（`自造期间报表自证通过 → ["SETTING_AUDIT_DESYNC"]`）。

- **这不是被复核代码的缺陷** —— 是 **R 批的 `SETTING_AUDIT_DESYNC` 探针按设计工作了**：它抓住了"有改动没留日志 / 绕过唯一写入点改配置"。抓的是**我**。
- 我按正确方式修复（**走写入点**写回），现在 `重放 == settings 现状`。**可复算的三库自证（用被复核方自己的探针，不是我写的重放代码）：**
  ```bash
  node -e 'import("./server/lib/settings.js").then(S=>{const D=require("better-sqlite3");for(const i of["cosmetic","food","apparel"]){const d=new D("data/gml_"+i+".db",{readonly:true});const r=S.auditSettingTrail(d);console.log(i,"ok="+r.ok,"problems="+JSON.stringify(r.problems),"keys="+r.keys_checked,"entries="+r.entries_checked);d.close()}})'
  # cosmetic ok=true problems=[] keys=17 entries=20
  # food     ok=true problems=[] keys=17 entries=17
  # apparel  ok=true problems=[] keys=17 entries=17
  ```
  ⇒ 三库 `SETTING_AUDIT_DESYNC` **各 0 处**（`problems` 是空数组）。
- **那 3 行审计日志是谁、为什么（逐行）** —— 它们**只追加、都带 `reason`**，保留比抹掉更诚实：
  | id | key | 动作 | 值变化 | 是谁 / 为什么 |
  |---|---|---|---|---|
  | 18 | `fiscal.start_month` | set | `1 → 4` | **我**（独立复核，2 节的"起始月=4"边界用例）用 `writeSetting` 临时改动 |
  | 19 | `fiscal.start_month` | set | `1 → 2` | **我**（还原用的中间一跳：`writeSetting` 对"值没变"会**跳过日志**，所以必须先跳到别的值才能让下一跳被记上） |
  | 20 | `fiscal.start_month` | set | `2 → 1` | **我**（把起点还原成 1 月默认值，收尾） |
  净效果：`settings` 表的值回到 `1`（与复核前一致）、行数不变（17）；`setting_audit_log` **17 → 20**（cosmetic），food/apparel 未受影响（仍 17）。**代价已知、已披露，不隐藏。**

- **顺带记下这次踩到的那个坑（留给下一个人）**：`settings.writeSetting` 对"值没变"会**直接短路、跳过留痕**：
  ```js
  // server/lib/settings.js:503（writeSetting 的事务里）
  if (before === next) return { key, value: next, changed: false, logged: false }
  ```
  后果：**想用"唯一写入点"把一个被绕过改动的值改回去，单跳是无效的** —— 那一刻"现状"已经等于目标值，`writeSetting(目标值)` 会被判成"没变"而不写日志，于是重放**仍然停在坏值**上、desync 不会消失。
  ⇒ 修复必须**两跳**（先写一个不同的值、再写回目标值），两步都会留痕 —— 这次就是先跳到 `2` 再跳回 `1`（即上面 id19 / id20 的由来）。
  ⇒ 这条短路本身没问题（"没变就别记一条噪声日志"是对的），但它正是**「重放日志 ≠ 现状」这类坑的成因之一**：一旦有人绕过写入点改过值，`writeSetting` 的"幂等短路"就再也没法把日志拉回来，**必须靠一次真实的改动去覆盖它**。

- **代价（如实报）**：cosmetic 的 `setting_audit_log` **17 → 20 行**（id18 = 我的临时改动、id19/20 = 修复，三条都带 `reason`）；`settings` 表行数不变（17）。food/apparel 的日志仍为 17 行、未受影响。
- 顺带得到一个可复用的结论：**"拿坏掉的代码跑用例"会往开发库留下副作用**（本例是我自己造成的，但它说明这类套件的自还原只在"顺利跑完"时有效）。所以"改坏 → 跑 → 还原"这套手法，跑完必须**核对库不变量**（我就靠 `auditReport` 才发现自己弄脏了）。
