# 批次 P 反例先红后证 · 反例 F：取数 SQL 漏掉 `status='posted'`

## 注入内容

文件 server/lib/report.js → movementOf()（发生额的**唯一一份 SQL**）

    -  WHERE v.status='posted' AND v.period >= ? AND v.period <= ?
    +  WHERE v.period >= ? AND v.period <= ?   /* 反例注入 F：漏掉 v.status='posted' */

含义：把**未过账**（draft）凭证也当成发生额。这是本项目最根子的一条口径
（"draft 是生成出来了但还没进账"），而它一旦被破坏，报表上不会出现任何"看起来不对"的迹象：
数字只是比应该的大了一点。

## 这组反例的真正价值：它证明了一条探针的**盲区**

`R3` 的"**累计 = 本年逐月各算一次再相加**"这一次**没有响**。

原因：那条探针的两条路径（整段一次聚合 / 逐月各算一次）
**读的是同一份取数 SQL**，所以取数条件错时它们会**同步**错，两侧仍然一致。
它抓的是"聚合逻辑错"（例如把区间首尾算错、把某个月加了两遍），
抓不到"取数条件错"。

**教训（本批最要紧的一条）："两条路径互证"只能覆盖它们**不共享**的那部分。
判断一条互证型探针的有效范围，要先问一句："这两条路径**共享**什么？"
共享得越多，它能抓的东西越少。**

## 那这一次是谁抓住的？

`auditReport` 的 `CF_MISMATCH` —— 现金流量的净增加额取自 `cashFlowBuckets`
（**自己一套实现**：逐张凭证分析现金与非现金分录），
而"复算"一侧取自 `subjectBalances`（本批被改坏的那份 SQL）。
两者的**实现不同**，所以一个坏了另一个不坏，差额当场现形：

    CF_MISMATCH  现金流量表净增加额与现金类科目变动对不上：
                 报表 -943890.95 ≠ 复算 -944982.8（差 1091.85）

这正好从反面印证了同一个道理：**探针的价值不在数量，而在它们的失效方式是否不同。**
同时它也给出一条可操作的结论 —— 本批新增的 `R8` 里那几条
"未过账凭证不进报表 / 不进累计"的断言是**必要的**：
它们不是"再测一遍同一件事"，而是**直接断言那条口径本身**（自造 draft + 手算期望），
这是"同步错"唯一防不住的失效方式。
