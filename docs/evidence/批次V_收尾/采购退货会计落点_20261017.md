## 0. 缺口到底是什么（先钉事实，再说修法）

采购侧原本**只有一条凭证路径**：`purchase_inbound` —— 到货即 `借 1405 库存商品 / 贷 2202 应付暂估`。
也就是说它是**只挂不减**的：

| 环节 | 修之前 | 后果 |
|---|---|---|
| **凭证（总账）** | 没有采购退货的业务类型 | 货退回供应商后，**暂估应付与存货双双虚高**，且**没有任何一处会报错**（凭证生成根本不知道"退货"存在） |
| **应付台账** | `/api/purchase/payables` 只汇总结算单；而结算明细的来源类型只有 `receipt / invoice / fee` | 台账上的"未付"是**含退货的虚高值**，界面上也没有任何提示 |
| 应付模块 | 库里**没有** `ap_*` / payables 表 | 所谓"应付"在本系统里 = 结算单（`settle_amount − paid_amount`），没有独立子台账 |

**实测依据（可复算）**：

```
# `createPurchaseReturn` 实际变更的表（对全部 194 张表做 sha256(JSON.stringify(SELECT *)) 前后差集）
purchase_returns · purchase_return_items · inventory_stocks · inventory_transactions ·
stock_cost_ledger · purchase_order_items · purchase_orders · doc_no_counters · doc_events
# ⇒ 里面没有任何应付/发票/结算表；`purchaseReturnSource()` 全仓无调用点
# 结算明细的来源类型实测：
SELECT source_type, count(*) FROM purchase_settlement_items GROUP BY source_type;
#   cosmetic → receipt 61 / invoice 10 / fee 2      （没有 return）
```

## 1. 修了什么 —— ① 凭证落点（本批主体）

`server/lib/accounting.js` 新增业务类型：

```
purchase_return  →  doc_type PRT · source_type purchase_returns · okStatuses ['confirmed','completed']
```

`server/db/finance-seed.js` 新增模板 `TPL_PURCHASE_RETURN`：

| seq | 摘要 | 方向 | 科目 | 取数键 | 辅助核算 |
|---|---|---|---|---|---|
| 1 | 采购退货冲回应付 {doc_no} | **debit** | **2202** 应付账款 | `total_amount` | `supplier_name` |
| 2 | 采购退货冲回库存 {doc_no} | **credit** | **1405** 库存商品 | `total_amount` | `supplier_name` |

**与 `TPL_PURCHASE_INBOUND` 严格镜像**（那条是 借1405/贷2202）—— 两侧共用同一个取数键，
所以**金额口径只有一处**，不存在"两处各算一遍迟早分叉"。

两条设计口径，都写进了代码注释：

- **只收 `confirmed` / `completed`**：与 `refund` 同源 —— **只有"货真退回去了"才能入账**。
  `draft` 是"打算退"，此时库存与成本侧**一行都没写过**（`createPurchaseReturn` 实测证明），
  给它记账等于凭空记一笔还没发生的退货。
- **同一来源只生成一张**：凭证表 `UNIQUE(biz_type, source_type, source_id)` 兜住 ⇒
  `confirmed` 时生成的凭证，到 `completed` 不会重复生成（已实测幂等）。

三库实测（`reseed-all --force` 之后）：

| 美妆连锁版 | id 7 / active | 借2202 · 贷1405 | PZ…0001 posted 1092.00 · PZ…0002 draft 1215.20 | 相等且 = 退货金额 |

## 2. 修了什么 —— ② 应付台账**披露**（刻意不并进结算口径）

`routes/purchase-chain.js` 的 `/api/purchase/payables` 增加**独立的 `returns` 块**：
按供应商聚合 `confirmed` / `completed` 的退货合计。

**为什么当时不把退货从 `settle_amount` 里减掉**（这是最容易做错的一步）：
结算单是按「入库单 / 发票**一单一结**」算出来的（`buildSettlement`），而"退货怎么抵减"是
**业务规则**，至少有三种合法答案 —— 按单抵 / 按期间抵 / 已审结算单要不要追溯；
而且退货对应的可能是**上一期**已经结算过的货（期间错配）。悄悄减掉会让"三单匹配"的结果
**从此说不清**。⇒ 第一版取"**披露**"：让"其中有多少是已退还没抵的"一眼看得见。

### 2.1 ⚠️ 2026-10-17 追加：抵减**已做成配置项**（客户口径）

客户原话：「退货是否递减这种你都可以做到供应链设置里，客户选择是，就递减，不设就不抵，
这个供应链设置可以全局覆盖。」

⇒ 把"业务规则"交给客户，而不是替客户选一种。落地三处（提交 `70c9356`）：

| 层 | 内容 |
|---|---|
| **配置** | `settings.purchase_return_offset`（分组「供应链参数」· bool · **默认 `0` = 不抵 = 上线前行为** · 危险项 · 已接线） |
| **引擎** | `buildSettlement` 只在**一处**读这个键；打开时按「同供应商 + 同期间 + `confirmed`/`completed` + 未被未作废结算单引用」取退货，`settle_amount = 应结 − 退货合计`，明细记 `source_type='return'` 的**负数行** |
| **单头** | 迁移 **048** 加 `purchase_settlements.return_amount`（`NOT NULL DEFAULT 0`，存正数）—— 抵减额必须与 `settle_amount` 并排，否则读者只能去明细里把负数行加起来倒推 |

四条写进 `impact` 的边界（都是会静默出错的地方）：
1. **关掉 ≠ 没有退货** —— 只是不抵；`/purchase/payables` 的 `returns` 块照旧披露。
2. **一单一结** —— 一张退货只被一张未作废结算单引用；关掉再打开、反复生成都不会抵两次。
3. **不追溯** —— 只对**新建**结算单生效；已审/已付的一律不动（补一笔抵减会让账上多出一笔
   "退过但没记账"的钱，而两边都不报错）。
4. **不允许抵成负数** —— `PST_RETURN_OVERFLOW`（409）**拒绝建单**，不静默截成 0：
   "退得比进的多"是一条真实的业务信号，截掉等于把它藏起来。

**⚠️ "登记了"≠"接线了" —— 唯一证明是"改配置 ⇒ 行为真的跟着变"**（见 §4.2 的反例）。

### 4.1 反例：**"平"不等于"方向对"**（本批最重要的一条方法论产出）

在影子副本里把模板两条分录的 `direction` **对调**（借1405/贷2202）—— 注意**金额键没变，
所以生成出来的凭证依然借贷平衡**：

```
注入（方向对调）  退出码 1   通过 33 / 失败 5
   ✗ ① 借方 = 2202 应付账款（冲回应付，不是又挂一笔）
   ✗ ① 贷方 = 1405 库存商品（冲回存货）
   ✗ ① 与采购入库模板严格镜像（入库 借/贷 ⇄ 退货 贷/借）
   ✗ ② 落库分录 借 2202
   ✗ ② 落库分录 贷 1405
   （平衡那两格） ✓ ② 借贷合计相等
   （平衡那两格） ✓ ② 借贷合计 = 退货金额      ← ⚠️ 方向反了，它**照样是绿的**
还原后          退出码 0   通过 38 / 失败 0     仓库文件 sha256 逐字节一致
```

**判据**：借贷平衡只证明**分录自洽**，不证明**记对了**。凡是"方向/科目有语义"的配置，
断言必须钉到**科目 + 方向**上；只断言"平"的测试在方向写反时会**替错的版本背书**。

## 6. ⚠️ 一并登记一条**我自己的方法缺陷**：`cp` 不是备份

第一次回归跑出 14 项失败（`test-annual` / `test-closing` / `test-compare` / `test-fiscal-year`
报 `ReportError: 报表「pl」不存在`）。**根因不是代码，是我准备隔离副本的方法**：

```
cp data/gml_cosmetic.db /tmp/probe-cp/          # ← 只复制主文件
  副本: report_defs=0  vouchers=1
  原库: report_defs=3  vouchers=14              # ← 数据在 -wal 里，没被复制
```

⇒ **WAL 模式下 `cp <db>` 会丢数据**。正确的做法是 **WAL 安全的备份**：
`better-sqlite3` 的 `db.backup(dst)` 或 `sqlite3.connect(...).backup(dst)`
（`regress-all` 与本批各测试脚本本来就是这么做的，**是我手工准备副本时漏了**）。
换成安全备份后**同一批代码 138/0 全绿**。

**诚实补充**：此前两次"全绿"的回归，副本曾先被 `test-gates-*` 起的服务自愈过（`bootAll` 会补齐
报表定义等），所以那些结论仍然成立；但**那次流程本身是脆的**，不该靠"恰好被自愈了"过关。
