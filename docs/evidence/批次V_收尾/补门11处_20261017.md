## 2. 统一形状（10 个路由一个模子）

```js
r.post(path, requireAuth, requireRole(同文件相邻端点的取值), wrap((req, res) => {
  const head = db.prepare('SELECT id, doc_no, status FROM <表> WHERE id=?').get(id)
  if (!head) return fail(res, '<单据>不存在', 404)
  advanceStatus(db, req, { docType: '<码>', id, action: '<动作>', remark: '…' })
  audit(req, { action: '<动作大写>', module: '<模块>', entity: '<表>', entityId: id })
  return ok(res, { id, status: '<内核返回的新状态>' })
}))
```

三条硬纪律：

1. **状态推进只走内核** `advanceStatus`（`server/lib/docflow.js`）—— **零处裸 `UPDATE … SET status=?`**。
   本项目一整族缺陷都出自裸 UPDATE（不留痕、绕过校验、内核看不见这张单）。
2. **路由里不写状态白名单**。非法来源态由内核抛 `DocFlowError`（带 `httpStatus`）⇒ 统一码。
   写第二份判据必然与内核分叉 —— 这是铁律。
3. **前端路径写死字面量**，动作段不许拼成变量（`` `/${action}` ``）。契约漂移检查靠字面量，
   拼了就只能跳过，等于没检查。

`TF.cancel` 的两条边**只写一个路由**，让 `advanceStatus` 按当前状态选边 —— 不在路由里 if/else 分派。

## 3. 补门顺带撞出的两处"新可达状态"缺口（不补就是半截活）

开了门之后，两个**此前根本造不出来**的状态变成真实可达，而它们的界面文案没跟上：

| 位置 | 缺什么 | 后果 | 处置 |
|---|---|---|---|
| `server/routes/meta.js` `transfer_status` | 缺 `submitted` | **字典是页签的唯一来源** ⇒ 已提交的调拨单**整档从页签消失**（不是显示成裸值，是页签里没有它） | 补 `submitted: '已提交'` |
| `server/routes/meta.js` `check_status` | 缺 `cancelled` | 同上：已作废的盘点单没有页签 | 补 `cancelled: '已取消'` |
| `src/pages/inventory/Assembly.tsx` 本地 `STATUS_LABEL` | 缺 `cancelled` | 会渲染成「**待过账**」——一个**看起来正常但完全错误**的词 | 补 `cancelled: '已作废'` |

> 判据：**新增一个可达状态时，必须同步它的文案出口**（字典 / 本地文案表 / Tabs 来源），
> 否则"加了一条路"会以"多了一个没名字的状态"结算。

## 6. 如实登记（不许被"已修"掩盖）

### 6.1 边权限：本轮**不补**，且这是**既有的跨域缺口**

`assertEdgePermitted` 的调用点只有 5 处 —— `routes/docflow.js`（通用流转入口）、
`routes/purchase-chain.js`、`routes/order-center.js`、`mcp/tools.js`、`lib/purchase.js:2100`。
而**所有领域专属流转端点**（`inventory.js` 的 `/transfers/:id/ship`、`purchase.js` 的
`/orders/:id/receive`、`oms.js` 的 `/orders/:id/ship`、`pos.js` 的 `/shifts/:id/approve`）
**一处都没调**。

⇒ 不是"我们这 10 个新门漏了"，而是**一整类端点都不走边权限**。只给新门补会让
**同一张单据的两条动作走两套规则**（`ship` 不校验、`cancel` 校验），比不补更坏；
全类统一补则是一次权限模型变更（牵几十个既有端点），属于客户明确"先放演示、标未来"的那一类。
**处置：登记为跨域既有缺口，等权限那一轮统一收口（一次改干净，不零敲碎打）。**

### 6.2 采购退货在会计侧**没有任何落点**（并更正一处说过头的话）

实测 `createPurchaseReturn`（=`PRT.confirm`）实际变更的表（对全部 193 张表做
`sha256(JSON.stringify(SELECT *))` 前后差集，带上游订单来源时）：

```
purchase_returns · purchase_return_items · inventory_stocks · inventory_transactions ·
stock_cost_ledger · purchase_order_items · purchase_orders · doc_no_counters · doc_events
```

**其中没有任何应付/发票/结算表**（`purchase_settlements` / `purchase_invoices` / 付款表一张没动），
本系统**也没有应付模块**（库里没有任何 `ap_*` / payables 表）；`purchaseReturnSource()` 全仓**无调用点**。

🚩 **据此更正我自己此前的一句话**：我把"采购退货单停在已确认"的后果写成"**货已经退了、应付也冲了**"——
**"应付冲了"是按业务说法推的，不是按代码报的**，作废。准确表述：
**货确实退回去了（库存与成本侧有真实出入库），但单子不闭合；采购退货在会计侧没有落点。**

→ 顺带这牵出一条**真实存在、本轮不做**的缺口：采购退货既不冲应付（没这个模块）、
也不抵减结算单、不进采购发票。补它属于**功能决策**（要引入应付/结算抵扣这一整块），
登记进「未做 · 待裁决」，**不自行扩大范围**。
