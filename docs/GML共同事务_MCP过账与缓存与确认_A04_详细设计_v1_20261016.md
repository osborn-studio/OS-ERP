## 一、缺陷的形状：**三件事各写各的，接口报错但业务已经生效**

`POST /mcp` 的 `tools/call` 里，一次写操作实际上由**三个动作**组成：

| # | 动作 | 归属 |
|---|---|---|
| ① | 业务过账（扣库存 / 写流水 / 改成本 / 记台账） | `tool.handler()` 内部（多数自带事务） |
| ② | 结果缓存写入（`mcp_idempotency`） | `tools/call` 里 handler 之后 |
| ③ | 确认单消费（`mcp_confirmations` 置 `used`） | handler **之前**（第 1 批改的原子占用） |

三件事**各写各的**。验收侧在同一脚本上复现了两条：

### finding ① 调拨循环中断

目标第二批 `INSERT` 失败：

- 总库存 **5 → 2**（本该不变，调拨是平移）
- 库存流水 **2 → 5**
- 幂等缓存 **0 行**（因为整体报错）

⇒ 第一批（调出）已落库、第二批（源出库）未回滚 —— **库存与流水对不上，接口报错但什么都没退**。

### finding ② 业务成功之后，结果缓存写失败

- 接口**报错**
- 而库存 **+1**、成本 **10**、流水**都在**、幂等缓存 **0 行**

⇒ 调用方以为没成功，**重试会再执行一次** ——
这正是幂等机制要防的事，却被幂等自身的写入失败破了。

## 二、根因：**没有共同边界**

单独看每一段都没写错：handler 内部有事务（`applyStockIn` / `applyStockOut` 各自是原子的），
确认单占用也是原子的（条件更新 + `changes` 判定）。
但"**几个原子动作连起来**"这件事**没有人负责** ——
① 与 ② 之间没有边界，② 失败带不回 ①；① 内部循环的第二步失败，也带不回第一步已经交给上层的结果。

### 一个被误导过的修法方向

验收侧原话：「只给 handler / 调拨循环加事务不够」。
因为给 handler 加事务只解决"handler 内部原子"，而 finding ② 的失败点在 handler **之外**；
给调拨循环加事务只解决"循环内原子"，而缓存与确认单在循环**之外**。

**正确的边界是"一次工具调用"**：从占用确认单开始，到结果缓存落库为止。

## 三、修复：把边界提到 `tools/call`

```js
const runInOneTx = db.transaction(() => {
  // ③ 确认消费：原子条件占用（原来是执行前单独 UPDATE + 失败后手工退回）
  if (claimedToken) {
    const claim = db.prepare("UPDATE mcp_confirmations SET status='used', … WHERE confirm_token=? AND status='confirmed'").run(…)
    if (claim.changes !== 1) throw Object.assign(new Error('确认单已被使用…'), { code: 'CONFIRM_ALREADY_USED' })
  }
  // ① 业务过账
  const out = tool.handler({ db, args: execArgs, ctx })
  // ② 结果缓存
  if (idemKey) db.prepare('INSERT OR IGNORE INTO mcp_idempotency (…) VALUES (…)').run(…)
  touchToken(db, row.id)
  return out
})
```

配套改动：

1. **确认单的占用从"执行前"挪进事务内**。原来是在执行前 `UPDATE`，失败后在 `catch` 里
   `UPDATE … SET status='confirmed'` 手工退回 —— 现在这段补丁**整体删除**：
   回滚会把确认单自然带回 `confirmed`。
2. `CONFIRM_ALREADY_USED` 从"直接返回"改为"抛错 → 由 `catch` 统一映射"，
   与其它业务错误走同一条出口（错误形状因此也统一了）。
3. `logCall` 保持在事务**外**：它是留痕，不该参与业务原子性（其内部已自带 try/catch）。

### 为什么事务能放得下

`better-sqlite3` 是**同步** API，`db.transaction(fn)` 里可以自由调用其它函数；
handler 内部自己的 `db.transaction` 会退化成 **savepoint**，嵌套不会互相干扰。
所有 MCP handler 都是同步的（这也是当初选 better-sqlite3 的收益之一）。

## 四、教训

> **"几件必须一起成败的事"必须由某一段代码负责划定边界。**
> 每个动作各自原子，不等于它们合起来原子 ——
> 而"合起来"这件事默认**没有人负责**，于是它就成了漏点。

### 4.1 "回滚的自然结果" ≠ "手工写的补丁"

第 1 批为了让"执行失败不消耗一次人工确认"，在 `catch` 里写了一段"退回 `confirmed`"。
**行为是对的，但实现方式是补丁**：只要有人以后改动了执行顺序、或者在别处 `return` 了，
这个补丁就可能不再被执行，而且**不会有人发现**（失败路径的测试本来就少）。

放进共同事务之后，同一件事变成回滚的自然结果 —— **不需要记得写，也不会因为重构而失守**。
判断标准很简单：**一个正确性依赖"某段代码记得执行"，它迟早会失守。**

### 4.2 报错必须意味着"什么都没发生"

`finding ②` 是最恶劣的一类：**接口告诉调用方失败了，而数据已经变了**。
对 Agent 而言，它一定会重试（这正是幂等存在的意义），于是"一次失败"变成"两次执行"。
通用判据：**任何返回错误的写接口，都要能断言"数据与请求前完全一致"**。
这条断言要写进回归 —— 见第五节。

## 五、回归补强（没有反例的修复不算修完）

`scripts/test-guards.mjs` 新增 **G14**（26 条/库），并把反例做成**注入式**：

| 注入 | 断言 |
|---|---|
| 在 `mcp_idempotency` 上建触发器 `RAISE(ABORT)` | 接口报错 **且** 库存不变 **且** 无流水 **且** 无缓存行 |
| 同上，故障消除后**用同一个幂等键**重试 | 成功；库存恰好 +3（不重复执行）；缓存落下；再调一次幂等命中且库存不再变 |
| 在 `inventory_transactions` 上 `WHEN NEW.doc_type='TR_IN'` 注入失败 | 调拨报错 **且** 源仓库存**没被扣** **且** 总库存不变 **且** 无部分流水 |
| 同上，故障消除后重试 | 成功；源仓恰好 −1 **且** 总库存不变 |
| 在 `WHEN NEW.doc_type='ADJ_IN'` 注入失败（高危操作） | 报错 **且** 确认单仍是 `confirmed`（可再次执行，不必重找人批） |
| 同上，故障消除后用**同一张**确认单执行 | 成功；成功后状态才变 `used` |

注入手法与验收侧一致：用同文件的**另一个连接**建触发器（DDL 对服务进程可见），用完立刻删；
每条用例都带 `finally` 还原（触发器 + 库存行 + 流水 + 批次 + 幂等缓存）。

### 5.1 "变红过"的证据

把 `server/mcp/server.js` 换回修复前那一版（`git show HEAD:…`）再跑 G14，**7 条变红**：

```
✗ A04-② 库存**没有**增加（原来业务已成功、只有缓存没写）
✗ A04-② 没有留下任何库存流水
✗ A04-② 重试后库存恰好 +3（没有重复执行）        → 实际 +6
✗ A04-② 幂等命中时库存不再变化
✗ A04-① 源仓库存**没有**被扣掉（原来第一段已落库）  → 2839 → 2838
✗ A04-① 没有留下部分流水
✗ A04-① 重试后源仓恰好 -1（没有重复扣减）        → 2839 → 2837
```

**A04-③（确认单）在旧版也是绿的** —— 因为旧版有那段"手工退回"补丁，行为一致。
这恰好说明：**行为正确不等于结构正确**；补丁能过测试，但过不了重构。

## 七、对外行为变更

| 变更 | 影响 |
|---|---|
| `tools/call` 的失败语义收紧 | 报错即"什么都没发生"（此前可能已部分落库） |
| 确认单消费与业务过账同生共死 | 执行失败时确认单回滚到 `confirmed`（行为与第 1 批一致，实现由补丁改为回滚） |
| `CONFIRM_ALREADY_USED` 的错误形状 | 与其他业务错误统一（`{ error, message, detail }`） |
| 事务范围变大 | 单次 `tools/call` 的写锁持有时间略增；同步 API 下无并发死锁风险 |
