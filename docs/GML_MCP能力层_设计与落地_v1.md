## 一、这一层要解决什么

第二轮你讲的第一句话是设计目的：

> 「是为了取代传统 ERP……我们现在开放的所有系统，都是从一开始就可以提供 MCP 的……这点你先记住。」

这句话的技术含义很具体，它不是一个"加个 AI 接口"的需求，而是**架构分层的问题**：

| | 传统 ERP 的 AI 接入 | 本系统 |
|---|---|---|
| 能力从哪来 | 在既有业务之上**外挂**一层适配器 | 业务内核**直接**暴露 |
| 能力范围 | 适配器实现了多少，AI 就能用多少 | 内核有什么，AI 就能用什么 |
| 一致性 | AI 与界面各取一套数，口径可能不一致 | 同一套引擎、同一套权限 |
| 演进 | 业务改了，适配器要跟着补 | 业务改了，能力自动跟着变 |

所以本层的实现原则是**不另写取数逻辑**：MCP 工具直接调用五维库存引擎与模块 05 的组织数据权限。这样 AI 看到的数据与人在界面上看到的永远是同一份——不会出现「AI 说还有 10 件、页面显示 0 件」。

## 二、协议实现

### 2.1 传输

- 端点：`POST /mcp`（同时挂 `/api/mcp` 供浏览器调试）
- 协议：**JSON-RPC 2.0，无状态**（对齐无状态传输形态）
- 兼容两种方法传递方式：请求体 `method` 字段，或 `Mcp-Method` 请求头
- 工具名可走 `Mcp-Name` 头或参数

### 2.2 支持的方法

| 方法 | 说明 |
|---|---|
| `initialize` | 握手，**无需凭据**（标准客户端先握手再带凭据），返回协议版本与三项能力声明 |
| `ping` | 心跳 |
| `tools/list` | 工具清单，**按 Token 权限过滤** |
| `tools/call` | 调用工具 |
| `resources/list` / `resources/read` | 4 个资源：经营 KPI、组织树、库存预警、成本参数 |
| `prompts/list` / `prompts/get` | 4 个提示模板：库存健康检查、销售复盘、补货建议、单据全链路追溯 |

### 2.3 错误分层（实测中修正的一处）

初版把工具级错误和协议级错误混用了，实测时客户端拿不到结构化失败原因。现已分层：

| 错误类型 | 走哪条路 | 例子 |
|---|---|---|
| 协议 / 鉴权 / 传输 | JSON-RPC `error` | 无 Token、Token 吊销、方法不存在 |
| 工具执行失败 | `result.isError: true` + 结构化文本 | 权限不足、缺参数、库存不足 |

区别很重要：前者表示"连不上或没资格"，客户端应重试或换凭据；后者表示"工具跑了但失败了"，客户端应把原因交给模型处理。

## 三、三级开放程度（第三轮 A1）

按"能造成多大后果"分级，而不是按"技术上能不能"分级：

### 3.1 read —— 查询类，可用即开（15 个工具）

工具清单：`master.search_products`、`master.get_product_360`、`master.list_partners`、`inventory.query_stock`、`inventory.list_batches`、`inventory.get_cost`、`inventory.pick_suggestion`、`inventory.list_transactions`、`inventory.stock_alert`、`purchase.list_orders`、`sales.list_orders`、`order.trace_document`、`report.sales_summary`、`report.dashboard_kpi`、`org.tree`

### 3.2 write —— 事务类，强制幂等键（4 个工具）

`inventory.stock_in`、`inventory.stock_out`、`inventory.transfer`、`inventory.ownership_transfer`

**为什么必须强制幂等键**：LLM 调工具存在重试语义，网络超时后客户端会重试。"再扣一次库存"是不可接受的。因此：

- 请求缺 `idempotency_key` → 直接拒绝，不执行
- 同一幂等键重复调用 → 返回**首次执行结果**并标记 `_idempotent_replay: true`，**不重复扣减**

实测验证：入库 3 件后重复同一幂等键，库存仍为 3。

### 3.3 danger —— 高危类，必须人工二次确认（4 个工具）

`inventory.adjust`（库存调整/盘盈亏）、`pricing.update_price`（调价）、`sales.cancel_order`（作废订单）、`approval.approve`（审批通过）

**执行链**：

```
Agent 调用
  ↓ 无 confirm_token
返回 confirmation_required + confirm_token（30 分钟有效）
  ↓ 人工在系统内 POST /mcp/confirmations/:token/approve（用人的 JWT）
确认单置为 confirmed
  ↓ Agent 带 confirm_token 重试
校验：状态=confirmed、未过期、工具名一致 → 执行 → 确认单置为 used
```

三个安全细节：
1. **确认必须由人做**——确认接口要人的 JWT，Agent Token 进不来。这才是"人工二次确认"。
2. **一次性**——用完置 `used`，不可重复执行。
3. **校验工具名一致**——防止「确认了调价、实际执行了作废」这类偷换。

## 四、Agent 接入凭据（第三轮 A2 / A3）

### 4.1 为什么 Token 单独建表

Agent 不是人。它有独立的生命周期（可吊销、可限速、可设有效期），而且必须能独立审计"哪一次 AI 调用改了什么"。混在用户表里做不到。

**与人的 JWT 严格分离**：人用 JWT（12 小时、跟浏览器走）；Agent 用 Token（长期、可吊销、可限速、独立审计）。混用会导致"AI 拿到了某人的全权凭据"这种无法追责的局面。

### 4.2 Token 属性

| 属性 | 说明 |
|---|---|
| `token_hash` | 只存 sha256 哈希，**明文仅签发时返回一次** |
| `org_id` | 绑定主体（A3：会话绑单一主体，跨主体签多个 Token） |
| `scopes` | read / write / danger 组合 |
| `allow_tools` / `deny_tools` | 工具白名单 / 黑名单 |
| `rate_limit` | 每小时调用上限（默认 600） |
| `expires_at` | 有效期 |
| `status` | 可吊销 |

### 4.3 数据权限复用

Token 绑定的 `org_id` 直接复用模块 05 的 `resolveOrgScope()`：

- 绑总部 → 可见总部子树全部数据
- 绑某个门店 → 只可见该门店数据
- 未绑 → 全量（仅演示用）

**不另写一套取数逻辑**——这是"AI 与界面口径一致"的技术保障。

## 五、审计

每一次工具调用都落 `mcp_call_logs`，包括：

- Token 身份、工具名、级别
- 参数、结果摘要、耗时、来源 IP
- 成功/失败、错误码、幂等键
- **被拦截的失败调用同样留痕**（谁试图做什么、被什么规则拦住）

管理接口：`GET /api/mcp/logs`（明细）、`GET /api/mcp/stats`（按级别/工具聚合）、`GET /mcp/confirmations`（待确认清单）。

## 六、实测结果

`scripts/test-mcp.mjs` —— **33 项断言全通过**：

| 分组 | 验证内容 |
|---|---|
| T1 握手 | `initialize` 无需凭据、三项能力声明 |
| T2 权限过滤 | 全权 Token 见 23 个工具，只读 Token 见 15 个，只读仅含 read 档 |
| T3 只读调用 | 库存查询、KPI 正常返回 |
| T4 越权拦截 | 只读 Token 调事务工具被拒且提示权限范围；无 Token 被拒 |
| T5 幂等 | 缺键拒绝 → 带键成功 → 重放返回首次结果 → **库存未重复扣加** |
| T6 高危确认 | 返回待确认 → 未确认被拒 → 人工确认 → 执行成功 → 确认单失效 |
| T7 资源与提示 | resources 4 项、prompts 4 项可读可用 |
| T8 审计 | 调用留痕、级别记录、失败调用留痕、幂等键记录、统计聚合 |

## 七、对外表述口径（重要）

关于"和金蝶、用友的差别"，按你的纠正，统一为：

> **不是说他们不开放 MCP，而是架构位置不同。他们的 MCP 是在既有 ERP 之上外挂的一层适配；我们的系统是从内核长出来的，能力与权限本来就是一套。**

这个说法的区别在于：前者是"接进来的"，后者是"本来就是"。这决定了 AI 能力的天花板——外挂层能覆盖多少业务，取决于适配器做了多少；内核暴露则随业务自然生长。
