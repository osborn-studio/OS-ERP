## 一、这个模块要解决的是什么问题

不是「给采购加一张质检单」。要解决的是一个**语义混装**的问题：

> 到货单上写着「已收货」，但它同时要回答两个不同的问题 ——
> 「送来了什么」（称出来的、看得见的）和「收不收」（人的判断）。
> 两个问题塞在一张单里，就必然有一个答不出来。

既有链路里，到货单的状态机本来就有 `received → inspected`。也就是说：「已质检」这个状态**一直存在**，
但**没有任何一张单承载它**。它被 `applyTransition(GR, 'inspect')` 直接推过去了 ——

- 查不到**谁**检的、**怎么**判的；
- 「这个供应商判退率多少」算不出来（数据在备注里，或在某个人脑子里）；
- 判退**没有后果** —— 状态说检过了，劣品还在正品库存里，退货单一张也不会生成。

所以本模块的目标不是「多一张单」，而是把**事实与判断分家**，并让判断**有代价**。

### 1.1 为什么判断不能写在到货单的备注里

| 方案 | 结果 |
|---|---|
| 判断写进到货单 `remark` | 台账变散文。算不出判退率、追不到原因码、无法按供应商聚合 |
| 给到货单加更多状态（如「部分合格」） | 状态机被迫承担两种语义；`received` 之后的时间差（今天到货、明天出结论）无处安放 |
| **到货单记事实，质检单记判断** | 本模块采用。两张单各自可以独立地被查询、统计、追责 |

时间错开这一点最容易被忽略：**货到是今天下午，质检可能明天才出结论**。
塞在一张单里，就必须让到货单同时承担「已到货」和「已判定」两种时间语义，而这两种时间是不同的。

## 二、核心设计判断

### 2.1 三条口径

**① 三数闭合：`合格 + 让步接收 + 判退 = 到货数`**

不闭合意味着有货既没算合格、也没算退货 —— 它**凭空消失了**，而账上不会报警。
所以这一条不是「校验」，是**写库前的前置断言**，在 `assertClosure()` 里拦住，错误码 `QC_NOT_CLOSED`。

附带一个细节：合计口径不放在明细行上「加总得到」，而是在**每一行**上都要求闭合
（`server/lib/qc.js` 的 `assertClosure(qty, q, c, r, skuId)` 逐行校验，并报出是哪一行）。
理由是：整单合计闭合不代表逐行闭合 —— 两行的差额可以互相抵消，而消失的货仍然消失了。

**② 判退必须有后果**

提交质检结论时，判退数量**自动生成采购退货单（PRT）并反向出库**。

顺序固定，不能反（`submitInspection()` 里的四步）：

    ① 用传入的行级数字覆盖草稿（并强校验三数闭合）
    ② 判退数量 → 生成采购退货单并出库
    ③ 到货单 received → inspected（走内核）
    ④ 最后一次写结论与汇总，再走内核把质检单推进到 inspected

如果顺序反过来（先改状态再判退），判退失败时会留下一张「已质检但没退货」的单 —— 劣品还在正品库里。
代码注释里把这条写成了硬约束：**先退后检**。

**③ 让步接收要留痕**

让步（收下但记录不合格）**不影响入库数量**，但它是最容易被和「合格」混起来的一项。
混起来之后索赔依据就没了。所以让步单独一列、单独统计、单独出指标（`concession_qty`），
并且必须带原因码（`defect_code`，7 档：外观不良 / 规格不符 / 包装破损 / 效期不足 / 批次错误 / 性能不达标 / 其它）。

### 2.2 结论由数字推导，不让人手选

`resultOf({ total, qualified, concession, rejected })`：

    全退      rejected >= total
    部分判退  rejected > 0
    让步接收  concession > 0
    全部合格  qualified >= total
    待质检    total <= 0

五个取值（`pending / qualified / concession / partial_rejected / rejected`）。
**人只填数字，结论由数字算出来** —— 否则会出现「结论写合格、数字里有判退」这种自相矛盾，
而这种矛盾在界面上完全看不出来（结论是一行文字，数字在明细里）。

### 2.3 「草稿」不算「检过了」

这一条是踩出来的。提交质检结论可能失败（最典型：判退要出库，而货已被下游消耗掉 → 库存不足）。
失败时事务回滚，但**建单那一步是独立事务、已经落库**，于是留下一张 `draft` 草稿。

如果「待质检」的判据写成「没有任何质检单」，这张到货单会从待质检队列里**消失** ——
既不在待办里，也不在已质检里，除非有人记得去翻质检单列表的草稿页。

所以判据是「**没有已出结论的质检单**」（`status NOT IN ('cancelled','draft')`），
并把草稿单号一起带到队列上；前端据此把按钮变成「继续填写」而不是「建单」
（新建会撞 `uq_inspection_receipt` 唯一约束，报一个与真实原因无关的错）。

配套的还有两件事：

- `inspectionOverview` 里把 `waiting_receipts` 与 `draft_ready` **分列** ——
  两者都要做，但要做的事不一样：前者去建单，后者是改数字重提交；
- 采购 seed 里判退失败时**降级为全部合格并记账**（`qc_downgraded`），不留卡住的草稿。

## 三、单据定义（内核）

### 3.1 质检单 INS

状态四值，`kind` 四值齐全（这是模块 04 的硬约束，缺一个 kind 会让「终态判定」失效）：

    状态      名称      kind      含义
    draft     待质检    draft     建单后、未出结论
    inspected 已质检    active    已出结论（有后果已发生）
    closed    已关闭    done      归档终态
    cancelled 已取消    void      作废（不进入统计）

动作三条：

    动作     名称            from → to            权限
    inspect  提交质检结论    draft → inspected    quality.inspect
    close    关闭            inspected → closed   quality.inspect
    cancel   取消            draft → cancelled    quality.inspect

### 3.2 主流程里的位置（环节数 9 → 10）

`FLOW_PURCHASE` 在 `receipt` 与 `inbound` 之间插入质检环节：

    请购 → 采购订单 → 到货单 → **质量检验（INS）** → 入库过账 → 采购发票 → 三单结算 → 付款核销

这条顺序是有承重意义的，测试里专门盯着：质检必须挂在 **INS** 上（不是挂在到货单上），
且必须排在**到货之后、过账之前**。挂错位置的后果是「先过账再质检」——
账上货已经能卖了，质检才说有一半要退。

**定义归内核，结构归各自迁移**：新增单据类型必须改 `008_doc_kernel.cjs`，
否则内核的自愈（`verify` 返回 false 即重跑 `up`）会把新增的定义抹掉。

### 3.3 权限点

本模块补齐了三个**从未被声明过**的权限点：`quality.inspect.view` / `quality.inspect` / `quality.inspect.edit`。

之所以要单独说：质检权限此前不存在，功能靠角色白名单放行，界面上看不出「谁有质检权」。
授权：`admin` / `purchase` / `warehouse` 三个角色给全三个，`boss` / `viewer` 只给 `view`。

## 四、数据模型

### 4.1 `purchase_inspections`（表头）

    doc_no / receipt_id / receipt_no   ← 单号、来源到货单（receipt_no 是**快照**，见 6.2）
    order_id / supplier_id / warehouse_id
    inspect_date / inspect_by / inspect_by_name
    result                             ← 结论（由数字推导，不是人填）
    total_qty / qualified_qty / concession_qty / rejected_qty
    return_id / return_no              ← 判退生成的退货单（回写）
    status / remark / created_by / created_by_name / created_at / updated_at

### 4.2 `purchase_inspection_items`（明细）

    inspection_id / line_no / receipt_item_id / sku_id / batch_no
    qty / qualified_qty / concession_qty / rejected_qty
    defect_code / defect_reason / remark

数量以**到货行**为来源（`receipt_item_id`），不允许质检单自己编数量 —— 这是事实来源的唯一性。

### 4.3 唯一约束 `uq_inspection_receipt`

一张到货单只能有一张质检单。作废后可以重开：`createInspection` 会把已作废的旧单**连同它的留痕一起删掉**
再建新的（旧单已作废，没有保留价值；留着会直接撞唯一约束）。

## 五、接口设计

     方法   路径                                  作用
     GET    /api/purchase/inspections/meta        结论枚举 + 不合格原因码（7 档）
     GET    /api/purchase/inspections/overview    概览（含判退率、判退金额、草稿待提交数）
     GET    /api/purchase/inspections/pending     待质检的到货单（质检岗的工作台入口）
     GET    /api/purchase/inspections/receipt/:id 装填：到货事实 + 已有草稿（前端一屏填完）
     GET    /api/purchase/inspections             质检单列表（分页 + 状态/结论/供应商/到货单筛选）
     POST   /api/purchase/inspections             从到货单开质检单（可带明细，默认全部合格）
     GET    /api/purchase/inspections/:id         详情（含明细与流转留痕）
     POST   /api/purchase/inspections/:id/submit  **提交质检结论**（唯一有后果的动作）
     POST   /api/purchase/inspections/:id/close   归档
     POST   /api/purchase/inspections/:id/cancel  作废（作废后可重开）

两处刻意的约束：

1. **静态段必须注册在 `:id` 之前**（`/pending`、`/meta`、`/overview`、`/receipt/:id` 都排在 `/inspections/:id` 前），
   否则 `pending` 会被当成 id 走详情分支，报一个莫名其妙的 404。
2. **`submit` 的 `lines[].id` 要的是质检行 id，不是到货行 id**。
   传错**不会报错**，只会静默覆盖不上 —— 结论仍然停在旧值。
   这条陷阱同时写进了 OpenAPI 的 `InspectionSubmit` schema 描述，以及 smoke 的第 5c 段断言里
   （断言「结论真的变了」，而不是只看 HTTP 200）。

## 六、本轮被质检拆分「照出来」的真实缺陷

这是这个模块最有价值的部分：**它本身是一个新功能，但它像探针一样把三处旧账照了出来。**

### 6.1 到货单直接推 `inspected`，而全库无质检单

拆分前，`procure-seed` 第 8 步直接 `applyTransition(GR, 'inspect')` 把到货单推到「已质检」。
状态改了，但**全库找不到任何质检记录** —— 典型的「状态说检过了，但查不到谁检的、怎么判的」。
修复后改为走质检单：能复用残留草稿就复用，否则建单再提交。

### 6.2 `purchase_inspections` 没进整库重建的清理清单

**这是本轮最隐蔽的一个。** 整库重建后到货单 id 被**复用**，于是上一轮的质检单看起来
仍然「指向一张存在的到货单」，不会被任何按 `receipt_id` 的孤儿检查发现。
后果：新建质检单撞 `uq_inspection_receipt`，而这个错误**只在带 try/catch 的调用处被吞掉** ——
表现是「质检功能点了没反应」，32 张到货单全停在 `received`。

修复分两层：

1. `seed.js` 的清理清单加入两张质检表；
2. `procure-seed` 的失效清理改用**快照单号**判据而不是 `receipt_id` ——
   因为 id 会被复用，单号不会。质检单落库时把到货单号存进了 `receipt_no`，对不上就说明它不是这票货。

### 6.3 静默吞异常让上面两个 bug 藏了很久

修 6.2 时意识到：真正的帮凶是「异常被吞掉，没有任何计数」。
于是加了 `qcIssues` 计数并进 summary（`qc_issues` / `qc_issue_list`）——
**任何一次灌数结束，都能一眼看到有没有没走通的地方**，不必靠人去翻日志。

### 6.4 连带查出：流转留痕积累 6 万条孤儿并已在错挂

做端到端验证时发现「刚建出来的草稿质检单上有 2 条留痕」。追下去是 `doc_events`
（跨所有单据类型的旁支表）从不清理：主表重建后 id 复用，旧留痕被新单「认领」。
三维实测：美妆库到货单留痕「看起来有效」153 条、重建后真实 26 条 —— **127 条挂到了别人身上**。

详见《GML 巡检日志》2026-10-15 条目。内核新增 `pruneOrphanEvents()`（判据取自 `doc_types.table_name`，
不写死表名清单），三库一次性清掉 59,237 条孤儿留痕，「零孤儿」已成为 `verify-seed.mjs` 的可断言不变量。

## 九、与其他模块的边界

| 模块 | 边界 |
|---|---|
| 04 单据内核 | 状态与流转的**定义**归内核（必须改 `008`）；质检单的**结构**归 `016` 迁移 |
| 03 库存中心 | 判退通过 `createPurchaseReturn` 反向出库；质检单自己不碰库存 |
| 22 通用审批流 | 审批与单据状态**解耦**；闸门挂在 `applyTransition` 上只检查不写库 |
| 23 数据口径字典 | 判退率、让步量等指标口径写在 `lib/metrics.js`，页面数字现算，不进缓存 |

### 已知边界（写清楚比含糊过去好）

既有链路的到货单在「确认收货」时就把货记进了库存（**收货即入库**），
所以本模块的判退表现为「生成退货单 + 反向出库」，而不是「入库前先扣掉判退量」。

两条路都成立，差别只在质检窗口期内**待判货物是否计入可用库存**：

- 收货即入库时，未判定的货已可被销售占用；
- 质检后入库时，它们要等判完才算数。

改成后者需要动「收货 → 库存」的整条链路（销售可用量、拣货、调拨都会受影响），
单独作为一步更安全，故本次先保证「**单据分开 + 判退有后果**」这一层。

另有一条既定边界（本轮未改）：`seed.js` 直接插库生成采购订单与到货单，不走内核，
所以这两个环节的**创建**动作没有留痕。全库 29 种单据类型中目前只有 10 种有留痕，
其余属「逐步迁移到 `applyTransition`」的待办，不是数据错误。

---

## 十、一句话总结

**到货单记事实（送来了什么），质检单记判断（收不收、收多少、为什么）。**
判断要能统计、要有后果、要与事实的时间错开 —— 这三件事只要缺一件，
质检就会退化成一张纸，而「已质检」这个状态会继续是一个没有任何单据背书的空状态。
