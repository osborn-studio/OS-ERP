## 一、这一层要解决的难点

第三轮你定的口径是：价格组按 **渠道 × 门店类型 × 经销商等级 × 区域** 四个维度分，**不设主维、自由组合**。

这条口径在数据建模上会撞到一个具体难题：**不设主维，就没法用一条固定的 WHERE 链把价格取出来。**

传统做法是设主维（比如先按渠道分，再按区域分），取值时逐层收敛，SQL 是确定的。但你明确不要主维，理由是业务上确实存在"华东金牌经销商"这种跨维度的特殊价，硬设主维会把它拆散。

所以必须换一种取值机制。

---

## 二、设计：匹配度打分 + 优先级排序

### 2.1 规则

把价格组的每个维度都看成**可选的筛选条件**：

| 情况 | 处理 |
|---|---|
| 该维度留空 | 视为"不限"，不影响匹配 |
| 该维度有值，且与本次上下文一致 | **命中 +1 分** |
| 该维度有值，但与上下文不一致 | **直接排除该价格组** |
| 价格组直接绑定了目标组织 | 额外 +1 分（强匹配） |

取值时：**得分高者优先**（越具体越优先）；**同分按人工 `priority` 字段排序**；再同按 id。

### 2.2 这套规则解决了什么

它让"细组合"与"宽组合"能共存，而且宽组合**自动成为细组合的兜底**：

```
「华东金牌经销商专价」  渠道=dealer 等级=gold 区域=华东   → 3 维，得分 3
「经销商金牌价」        渠道=dealer 等级=gold            → 2 维，得分 2
「经销商银牌价」        渠道=dealer 等级=silver          → 华东金牌来了直接排除

华东金牌下单 → 命中得分 3 的专价
华南金牌下单 → 专价排除（区域不符），回落得分 2 的通用金牌价
华东银牌下单 → 所有金牌组排除（等级不符），命中毒银牌价
```

**不需要为每个组合建一张表**，也不会出现"某个组合没配价就取不到"的空洞——宽组合天然兜底。

### 2.3 阶梯价

价格组明细带 `min_qty`，取价时取 `min_qty <= 本次数量` 中**最大**的那档。这样同一个价格组内可以表达"满 100 件再降 3 个点"。

## 三、数据模型（007 迁移）

| 表 | 用途 |
|---|---|
| `price_groups` | 价格组主表，四维标签 + `priority` + `currency` + 生效区间 |
| `price_group_items` | 明细：`sku_id` × `price` × `min_qty`（阶梯价），唯一键三元组 |
| `price_group_targets` | 价格组直绑组织（某家门店/经销商专价），与四维标签可叠加 |
| `member_prices` | 会员价：`sku_id` × `member_level` → `price` |
| `price_change_logs` | 调价留痕：改前值/改后值/原因/操作人/来源（web/mcp/import） |
| `price_rules` | 取价规则与顺序（可配） |

商品/SKU 另补 `price_min`（最低限价，防乱价）与 SKU 的 `price_cost`（参考成本）。

## 四、取价引擎

`server/lib/pricing.js`，顺序按 `price_rules.seq` 配置：

```
① 促销价     活动期特价（促销表未上线前自动跳过，但优先级位置已占住）
② 合同价     一客一价的合同约定价
③ 会员价     按会员等级
④ 价格组价   四维匹配度打分
⑤ 标准零售价 兜底
```

返回结构不止价格，还包括：

- `source` —— 这个价来自哪条规则
- `groupId` / `groupCode` / `groupName` —— 命中的价格组
- `matchedDimensions` —— 命中几个维度（可解释"为什么取这个价"）
- `ladderMinQty` —— 阶梯起订量
- `trace` —— 可读解释链

**`explainPrice()` 这条设计是刻意加的**：价格是最容易起争议的数据，界面上必须能回答"为什么给这个客户报这个价"。实测输出：

```
价格组「华东金牌经销商专价」命中（匹配 3 个维度）
```

## 五、接口

| 接口 | 说明 |
|---|---|
| `GET /api/pricing/resolve` | 取价（单 SKU） |
| `POST /api/pricing/resolve-batch` | 批量取价（避免 N 次往返） |
| `GET /api/pricing/explain` | 取价解释链 |
| `GET /api/pricing/groups` | 价格组列表（含明细数与覆盖 SKU 数） |
| `POST /api/pricing/groups` | 新建/更新价格组 |
| `GET /api/pricing/groups/:id/items` | 明细（分页 + 搜索） |
| `PUT /api/pricing/groups/:id/items` | 批量改价（**自动写留痕**） |
| `GET /api/pricing/logs` | 调价留痕 |
| `GET /api/pricing/rules` | 取价规则顺序 |

## 七、实测结果

`scripts/test-pricing.mjs` —— **30 项断言全通过**：

| 分组 | 关键验证 |
|---|---|
| T1 单维匹配 | 线上/专柜/直营/加盟 各自命中对应组，系数正确 |
| **T2 多维匹配** | **华东金牌命中 3 维专价，而非 2 维通用金牌价**；华南金牌正确回落；银牌不命中金牌专价 |
| T3 取价优先级 | 会员价优先于价格组价；无匹配回落标准零售价 |
| T4 阶梯价 | 满 100 件取更低一档，起订量正确返回 |
| T5 解释链 | 输出"价格组「华东金牌经销商专价」命中（匹配 3 个维度）" |
| T6 调价留痕 | 改前值/改后值/原因/操作人完整落库 |
| T7 边界 | 缺参抛 `BAD_ARGS`、SKU 不存在抛 `NOT_FOUND` |

服务冒烟：**2xx 102 / 5xx 0**。
