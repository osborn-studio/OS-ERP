## 一、本轮修的是什么

验收协作者在独立快照上复现出 5 组阻断缺陷。其中 3 组（D2 / D3 / D4）**改动面小、不碰任何业务链与共享库**，
被排为第 1 批：

| 编号 | 一句话 |
|---|---|
| **D2** | 门店账号能打开别家门店的销售订单详情；经销商账号一个 GET 就把全部采购单连供应商、单价拉走 |
| **D3** | 采购与销售都接受 `price = -5`，落库成一张**负金额单据**，全链路无人报错 |
| **D4** | MCP 高危操作的"人工二次确认"形同虚设：可越权批准、确认不绑参数与令牌、header 方式可无限重放、resources 绕过白黑名单、幂等键跨令牌跨载荷 |

D1（销售退货闭环）依赖 `lib/ar.js`，D5（MCP 工具复用领域服务）涉及全部领域服务 —— 分别排在**第 2 / 第 3 批**，
本轮**不碰**。

### 这三组缺陷的共同形状

它们不是"三个 bug"，是**同一个 bug 的三个样本**：

> **同一份判据/校验被写了两遍以上，于是只改了一处、漏了一处。**

- 销售订单**列表**走了数据范围（`scopeFilter`），**详情**手写了第二套判断，且只写了 `dealer` 分支 → 门店分支缺失；
- 采购订单**创建**校验了数量、**详情/列表**既没有权限门也没有数据范围、**修改**连数量都没校验；
- MCP **tools/call** 走了白黑名单，**resources/read** 是另一段独立代码，完全不走；
- 幂等键**写**的时候带了 `token_id`，**读**的时候只按 `key` 查。

所以本轮的修法不是"补三个 `if`"，而是**把每一类判据收敛成一个出处**，
再用**矩阵式的回归**（`scripts/test-guards.mjs`）确保"漏掉的那一个"会被抓到 ——
因为按接口逐个手写用例，挡不住这类问题：**漏掉的那个永远不会出现在用例清单里。**

## 二、三条修复原则

| 原则 | 落实为 |
|---|---|
| **一处判据** | 数据范围只有一个定义 `scopePairs()`，列表 SQL（`scopeFilter`）与详情判定（`assertCanRead`）都从它派生 |
| **一处校验** | 金额/数量只有一个校验器 `numField()`（含 `numAmount` / `numQty` 两个语义化包装），建单与改单、销售与采购共用 |
| **一个入口** | 工具/资源的可用性只有一个判定 `checkToolAccess()`，`tools/call` 与 `resources/read` 共用；资源只是"工具的一个别名" |

外加一条**反向**的配套：**资格与状态是两类判据，资格先答**。
MCP 确认接口里，「你有没有资格批」排在「这张单是不是 pending」之前 —— 否则本人去批一张别人已批过的单，
得到的是"状态不对"，看起来像"批晚了"，而不是"轮不到你批"。

## 三、D2 越权读

### 3.1 收敛后的接口

`server/middleware/auth.js`：

```js
/** 数据范围谓词：一组 { 字段, 取值 }，全部命中才可见 —— 唯一的定义处 */
export function scopePairs(req, { dealerField = 'dealer_id', storeField = 'store_id' } = {}) {
  const u = req.user || {}
  const out = []
  if (u.role === 'dealer' && u.dealer_id) out.push({ field: dealerField, value: u.dealer_id })
  if (u.role === 'store' && u.store_id) out.push({ field: storeField, value: u.store_id })
  return out
}

/** 列表用：翻译成 SQL 片段（前导 AND） */
export function scopeFilter(req, alias = 't') { /* 由 scopePairs 派生 */ }

/** 详情用：同一份规则在 JS 侧判定 */
export function assertCanRead(req, row, opts = {}) { /* 由 scopePairs 派生 */ }
```

### 3.2 外部主体与内部单据

数据范围管的是「**看哪些行**」；还有一类是「**这类单能不能看**」——
采购单是内部单据，经销商/门店在任何范围下都不该看到。两者不能混成一个判据：

```js
export function isExternalUser(req) { /* role ∈ {dealer, store} */ }
export function requireInternal(label) { /* 外部主体一律 403 */ }
```

采购域的读接口改为**功能权限门 + 数据范围**双闸：

```js
const PO_READ_PERMS = ['purchase.order.view', 'purchase.inbound', 'purchase.return']
r.get('/orders', requireAuth, requirePerm(...PO_READ_PERMS), ...)
```

权限表里 `dealer` / `store` 一个采购权限点都没有 → 一律 403；
`viewer`（内部只读演示角色）持有 `purchase.order.view` → 演示不受影响。

### 3.3 覆盖到的路径

| 路径 | 原状 | 现状 |
|---|---|---|
| `GET /api/sales/orders/:id` | 手写判断，只有 dealer 分支 | `assertCanRead`（store + dealer 两支） |
| `GET /api/sales/deliveries` | 无范围 | `scopeFilter(req,'so')`（发货单挂在订单上） |
| `GET /api/sales/deliveries/:id` | 无范围 | 带出 `so.dealer_id/store_id` 后 `assertCanRead` |
| `GET /api/sales/returns` | 无范围 | `scopeFilter(req,'t')` |
| `GET /api/sales/stats` | 汇总全量（**该漏就漏在汇总里**） | 各查询按别名分别套范围 |
| `GET /api/purchase/{orders,orders/:id,receipts,receipts/:id,returns,stats,orders/:id/receive-suggest}` | 只有 `requireAuth` | `requirePerm(...PO_READ_PERMS)` |

> **导出路径**：本系统没有单据导出端点（导出在前端由列表数据生成），故无"导出绕过"面；
> 这一点会在回执里明确告知验收方，避免"以为覆盖了其实没这个面"。

## 四、D3 负价

### 4.1 唯一的校验器

`server/middleware/auth.js`：

```js
export function numField(v, { name, min = 0, positive = false, max, decimals = 2, required = false })
//  numAmount(v, name, extra)  → 金额：非负、最多 2 位小数
//  numQty(v, name, extra)     → 数量：必须 > 0、最多 4 位小数
```

判定顺序（每一步都必须有）：

1. 空值：必填则拒，非必填返回 `null`（由调用方决定兜底值）；
2. 类型：`boolean` / 数组 / 对象一律拒；
3. **形状**：字符串必须是十进制字面量 —— `Number('1e3')` 会得到 1000、`Number('0x10')` 会得到 16，
   这些都不是用户输入的东西，先做形状检查再转数；
4. 有限性：拒 `NaN` / `±Infinity`；
5. 下界 / 上界；
6. **精度**：金额 2 位、数量 4 位（用 `n * 10^d` 与整数比较，容差 1e-6 吸收浮点误差）。

**校验过的值就是写库的值**：建单时把校验结果组成 `lines` 数组，事务里只消费 `lines`，
不再二次解析请求体 —— 否则"校验了 A、写进去的是 B"，校验等于没做。

### 4.2 落库前最后一道闸：总额非负

行级单价已非负，但**整单折扣 / 运费**参与运算，仍可能把应收推成负数：

```js
// sales.js::recalcOrder
if (receivable < -0.001) { throw Object.assign(new Error('销售订单应收金额为负…'), { status: 400 }) }
// purchase.js::recalcOrder
if (Number(agg.amt) < -0.001) { throw Object.assign(new Error('采购订单金额为负…'), { status: 400 }) }
```

负金额单据只允许由红冲这类**特定单据类型**产生，普通订单不能"算"出负数。

### 4.3 覆盖到的入口

| 入口 | 原状 | 现状 |
|---|---|---|
| `POST /api/purchase/orders` | 只判 `Number(it.qty) > 0`；单价**完全不校验** | 单价/数量/税率全量校验 |
| `PUT /api/purchase/orders/:id` | 同上，且未校验 SKU 存在 | 与建单同一套（**只在 create 上拦等于没拦**） |
| `POST /api/sales/orders` | 只判数量 > 0；单价、行折扣、运费、整单折扣直接入库 | 全部走校验器 |
| `PUT /api/sales/orders/:id` | 连数量都没校验 | 与建单同一套 |

## 五、D4 MCP 安全闸

### 5.1 4a 确认接口的权限门与"不得自批"

```js
r.post('/confirmations/:token/approve', requireAuth, requirePerm('system.mcp.confirm'), handler)
```

两道闸：

1. **功能权限门** `system.mcp.confirm`（`026` 迁移新增，**刻意不授予** `viewer` / `dealer` / `store`）；
   授予 `admin / boss / purchase / sales / warehouse / finance`。
   *为什么不复用 `system.mcp.manage`*：那是"签发令牌"的运维权，与"放行一次高危业务动作"是两件事；
   混用一个权限点等于把"能建令牌的人"和"能批准付款/调价的人"绑成同一批人。
2. **禁止自批**：确认单的申请人是**发起该 Agent Token 的那个人**，不是令牌名。
   原表 `requested_by` 存的是令牌名，拿它跟登录用户名比是比不出来的 —— 要顺着 `token_id` 查 `agent_tokens.owner_user_id`。

审批/驳回都加了**条件更新 + 按 `changes` 判定**，并发下只有一次能从 `pending` 翻过去。

### 5.2 4b 确认单绑定三元组

原来只比 `tool_name`，于是实测可以「A 令牌申请（price 111）→ 人工批准 → B 令牌把参数改成 price 999 再执行」，
落库的是 **999** —— 被批准的 111 只是一张纸。

现在绑定 **`tool_name` + 参数指纹 + `token_id`** 三元组，任一不符即拒；
并且**执行时用确认单里存的参数**，不是本次请求的参数：

```js
const claim = db.prepare("UPDATE mcp_confirmations SET status='used', used_at=?, used_by=? WHERE confirm_token=? AND status='confirmed'").run(...)
if (claim.changes !== 1) return toolError(..., 'CONFIRM_ALREADY_USED', ...)
execArgs = { ...confArgs, __confirmed: true }   // ← 批准了什么就执行什么
```

**参数指纹**（`argsFingerprint`）用稳定序列化（键排序、递归）算 sha256，并**剔除控制字段**
（`confirm_token` / `__confirmed`）—— 控制字段不属于"业务参数"，否则永远比不平。

**比对失败不消耗确认单**：参数不符时在占用之前就返回，原地保持 `confirmed`，
换回原参数仍可执行（有回归用例覆盖）。

### 5.3 4c header 方式的一次性

```js
const confirmToken = args.confirm_token || req.headers['x-confirm-token']   // ← 只取一次，全程用它
...
db.prepare("UPDATE ... SET status='used' WHERE confirm_token=? AND status='confirmed'").run(String(confirmToken))
```

原来置 `used` 用的是 `args.confirm_token` —— 走 header 时它是 `undefined`，
**该行永不置 used，确认单可以无限重放**。现在：

- 用**实际命中的那个 `confirmToken` 变量**；
- **原子条件占用**（`WHERE ... AND status='confirmed'` + `changes` 判定），防并发双花；
- 新增 `used_at` / `used_by` 两列，回答"谁在什么时候用掉的"；
- 执行失败时把确认单**退回 `confirmed`**（并把失败原因写进 `reason`）——
  否则"批准了一次、执行时踩到业务错误"就得重新找人批，人工确认会被逼成走过场。

### 5.4 4d resources 与 tools 同一套判定

```js
function checkToolAccess(tool, { scopes, allow, deny })
const RESOURCES = [{ uri, name, tool }]          // 资源 = 工具的一个别名
const RESOURCE_TOOL = Object.fromEntries(...)
const VIRTUAL_TOOLS = { 'inventory.meta_params': {...} }   // 没有业务工具的直读资源
const resolveTool = (name) => TOOL_MAP.get(name) || VIRTUAL_TOOLS[name] || null
```

`resources/list`、`resources/read`、`tools/call` 三处都走 `checkToolAccess`：

| 入口 | 原状 | 现状 |
|---|---|---|
| `tools/call` | 白黑名单 ✓ | 不变（抽成共享函数） |
| `resources/read` | **完全不走** | 与 `tools/call` 完全一致 |
| `gml://meta/params` | 连映射表都不经，直读 `inv_params` | 走虚拟工具 `inventory.meta_params`，照样过闸 |
| `resources/list` | 固定 4 条 | 只列**本令牌真的拿得到**的资源 |

### 5.5 4e 幂等键加令牌与载荷指纹

幂等判定的依据从「`key` 本身」变成「**令牌 + 工具 + key**（唯一键）**+ 载荷指纹**（比对列）」。

⚠️ **不要把载荷指纹放进唯一键**：唯一键**仍是 `(idempotency_key, tool_name, token_id)` 三元组**
（`006_mcp.cjs` 的 PK 至今仍是单列 `idempotency_key`，`026` **只加列、不动键**）。
真按四元组建 UNIQUE，`同 key + 换载荷` 就**变成一个新键**，约束反而拦不住它 ——
等于把「换载荷再执行一次」合法化。**键管"是不是同一次"，比对列管"内容对不对得上"。**

原表 `mcp_idempotency` 只有 `idempotency_key` 一个主键与结果，**没有可比较的对象** ——
无论代码怎么写都判不出"同 key 不同载荷"。所以这一条必须动数据层（`026` 加 `args_hash` 列）。

```js
const sameCall = Number(cached.token_id) === Number(row.id)
              && cached.tool_name === tool.name
              && cached.args_hash === argsHash
if (!sameCall) return toolError(..., 'IDEMPOTENCY_CONFLICT', '…换一组参数必须换一个新的幂等键')
```

**幂等的意思是"同一次调用重放"，不是"同一个字符串重放"。**

新增 `scripts/test-guards.mjs`（读 `process.argv[2]`，三库各跑一遍，**83 条断言**）：

| 段 | 内容 | 为什么按矩阵写 |
|---|---|---|

| G4 | 金额/数量边界（负、零、`NaN`、`Infinity`、`"1e3"`、3 位小数、5 位小数、税率越界） | 逐维度穷举，而不是"测一个负数就行" |

| G6 | 幂等：跨令牌 / 跨载荷**不命中**，同令牌同载荷仍重放 | 4e |
| G7 | 确认单：自批 403、viewer/dealer 403、header 方式置 `used`、重放拒、换令牌拒 | 4a/4b/4c |

**基线上升是正确的，不要"补数"**：`regress-all.mjs` 自动 glob `test-*.mjs`，
新增一套 × 三库后每轮从 **57 → 60**、3 轮从 **171 → 180**。

`test-mcp.mjs` 的 T6 同步改写：原用例是 **admin 签令牌 → admin 自己批准**，
在 4a 修复后**必须被拒**。改成三条正向断言 + 四条反向断言（自批 403 / viewer 403 /
