## 一、这六条的共同点：**账面上都"平"，错的是口径与归属**

| 项 | 错在哪一类 |
|---|---|
| A06 | **归属**：占用写在 SO 名下、释放写在 RCP 名下 ⇒ 一笔释放流水都写不出来 |
| A07 | **口径**：`Math.min` 截平 ⇒ 用户说"我核了 600"、库里是 400，而两边都不报错 |
| A08 | **归属**：指定这张单回款，钱抵到了同主体的另一张单 |
| A11 | **口径**：跨批次出库照抄末批单价 ⇒ 材料成本按错价算 |
| A12 | **隔离**：参数缓存不按库分桶 ⇒ 先读哪个库决定后面所有库的行为 |
| A13 | **权威**：检验结论只落在单据上、批次字段是死的 ⇒ 同一批货两套结论 |

它们**都不会报错、也不会让试算不平** —— 这正是这一类最难发现的原因：
所有"两边相等"的断言都会通过，因为错的那一侧自己和自己相等。

## 二、A06：占用在哪里，释放就在哪里

`sales.js` 的订单确认按 `sourceType='SO'` 写占用台账；而 `ar.js` 的收款确认按
`sourceType='RCP'` 去释放：

```js
creditSettle(db, { account, amount: r.amount, sourceType: 'RCP', sourceId: id })
```

`credit.settle()` 内部先算 `open = openAmountOf(accountId, sourceType, sourceId)` ——
**那张收款单名下从来没有占用过**，`open` 恒为 0 ⇒ `amt = 0` ⇒ 直接 `return null`。
**一条释放流水都写不出来**，SO 的占用永远挂着：客户还了钱，可用额度不回来。

修复：**按这笔核销对应应收单的来源**分别释放。

```js
for (const a of allocations) {
  const ar = ...
  if (ar.source_type === 'OC') continue          // 订货中心在下面的循环里释放自己那本台账
  if (ar.source_type && ar.source_id)            // SO / SI …
    creditSettle(db, { ..., sourceType: ar.source_type, sourceId: ar.source_id, docNo: ar.source_doc_no || ar.doc_no })
  else releasedByRcp += a.amount                 // 没有来源的应收（手工补账）仍按收款单释放
}
if (releasedByRcp > 0.005) creditSettle(db, { ..., sourceType: 'RCP', sourceId: id })
```

**这个形状在代码里已经有先例**：同一段 if 下面就写着订货中心的正确做法
（`ocReleaseByOrder`，按订单释放它自己那本台账）—— SO 这一支是漏的。
**"同一个函数里已经有一处做对了"是最值得警惕的信号**：说明规则是清楚的，
只是没被套用到另一条分支上。

## 三、A07：要"拒绝"，不要"截平"

三处 `Math.min` 把冲突悄悄抹平：

| 位置 | 原写法 | 后果 |
|---|---|---|
| 显式分摊 | `can = Math.min(want, ar.amount - ar.allocated_amount)` | 填 600、系统按 400 核销，**没有任何痕迹** |
| 显式分摊 | （**没有**限制收款单剩余额） | 一张 500 的收款单分摊出 1200（超收 700） |
| 写明细 | `INSERT OR REPLACE` | 同一 `ar_id` 出现两次 → 前一条被静默覆盖 |
| 重算应收 | `allocated = Math.min(alloc, row.amount)` | 明细合计 160，界面显示 100 且状态 `closed` —— **看起来完全正常** |

修复：

1. 显式分摊逐条校验：`want > 应收未结` → 409 `RC_ALLOC_EXCEEDS_AR`；
   `want > 收款单剩余` → 409 `RC_ALLOC_EXCEEDS_RECEIPT`；同请求内重复 `ar_id` → 400 `RC_ALLOC_DUPLICATE_AR`；
2. 写明细改回 `INSERT`（配 `UNIQUE(receipt_id, ar_id)` 的自然语义），重复就报错；
3. **确认前的硬校验**：草稿阶段的"计划核销"不算数，所以两张草稿可以**各自合法地**答应核销同一张应收 ——
   真正冲突的是**确认的那一刻**。所以判据放在 `confirmReceipt`：
   逐条比「已确认核销合计 + 本次」与应收金额，超了就 409 `AR_OVER_ALLOCATED`；
   同时拒绝核销**已作废**的应收（原来只在建单时判，而建单之后应收可能被作废）；
4. 重算应收**不再裁剪**：明细是唯一真相，超了就是超了，让它显示出来。

**为什么不能保留 `Math.min`**：截平的本质是"系统替用户把冲突决定掉，并且不告诉他"。
在钱的问题上，**宁可拒绝并让他改**。这与模块 07（应付）侧"已付金额由明细 SUM 算出、不累加"是同一条原则的另一面。

## 四、A08：指定订单回款，就要真的抵到那张单

`sales.js` 的 `/orders/:id/payment` 调 `createReceipt` 时**不传 `allocations`**，
于是走到 FIFO 分支：按**同主体的全部未结应收 + 到期日**自动摊。
结果是「给这张单回款」实际抵到了同客户的**另一张单**上 ——
两张单的状态都变了，而没有任何提示。

修复：

```js
const openOfThis = ar.amount - ar.allocated_amount
const toThis = Math.min(amount, Math.max(openOfThis, 0))
createReceipt(db, { ..., allocations: toThis > 0.005 ? [{ ar_id: ar.id, amount: toThis }] : [] })
```

- **只抵这张单**；多出来的部分**停在预收**，不替客户决定"这钱该抵哪张"；
- 回执里如实回报 `{ allocated, unallocated, ar_id }`，预收有出处；
- `createReceipt` 的判据从 `Array.isArray(allocations) && allocations.length` 改为
  `Array.isArray(allocations)` —— **空数组是一个有意义的输入**（"就按这几条核销，一条也没有"），
  不能再退回 FIFO 兜底。

## 五、A11：跨批次出库，金额必须由各批次汇总

`applyStockOut` 的拆批分支原来：

```js
const last = parts[parts.length - 1]
return { ...last, batches: parts.map(r => ({ batchNo: r.batchNo, qty: r.qty })) }
```

`unitCost` 只来自**末批**，`batches[]` 连单价/金额都不带。
上游 `mfg.js` 用 `qty × unitCost` 算整行材料成本 ——
「10 元 5 件 + 20 元 5 件」被算成 10 × 20 = **200**（应为 150）。
**两批差价越大错得越多，而且出库流水按批次是对的、只有汇总口径错** ——
所以"平账但错数"，最难发现。

修复：拆批分支返回**汇总量**：

```js
qty        = Σ parts.qty
outAmount  = Σ parts.outAmount        // 新增：本次出库总额（此前只有结存额 costAmount）
unitCost   = outAmount / qty          // 加权平均，使 `qty × unitCost` 恰好等于总额
batches[]  = [{ batchNo, qty, unitCost, outAmount }]
```

顺带给 `applyStockOut` 的返回补上 `qty` 与 `outAmount`（都是**本次出库**的口径）——
`costAmount` 仍然是"出库后的结存额"，`mfg.js` 里那条"不要用 costAmount"的注释继续有效，
现在多给了正确的选择。

## 六、A12：参数缓存必须按库分桶

```js
const paramCache = new Map()                       // 原：全局一张表
const cacheKey = `${key}::${scopeValue}`           // 键里不含"哪个库"
```

三个行业是**三个 SQLite 文件**、却共用同一个模块实例 ⇒
「美妆库 `pick_rule=fifo`」会被当成"全局事实"，在餐饮库的拣选里生效。
先读哪个库，就决定后面所有库的行为；交错调用时结果来回变。

修复：缓存改成 `WeakMap<db, Map<key, value>>` —— **键里带上"这是哪个库"**。

- 用 `WeakMap` 而不是往键里拼库名：同一份文件被两个连接打开时本来就该各读一次，
  且连接销毁后缓存自动释放（不会泄漏）；
- `clearParamCache(db)` 只清那个库，不传参则整体重置（"所有库都可能变了"）。

## 七、A13：检验结论要落回批次；"指名要这个批次"不是万能钥匙

两条同时存在：

1. `inventory_batches.qc_status` **从建表那天起没有被任何代码写过**（一直是默认 `pending`）。
   所以"不合格批次仍可拣选"的根因**不是少判了一个 if**，而是**检验结论根本没有落回批次**。
   结论落在单据上只回答了"这张单判过没"，回答不了"这批货还能不能卖"。
2. 只要调用方**显式传 `batch_no`**，`applyStockOut` 就直接去那行库存扣数，
   完全不看批次的冻结、效期与检验结论 —— 同一批货"自动拣选时不可用、指名要用时可用"。

修复：

- **`submitInspection` 把结论写回批次**：`unqualified → qc_status='rejected'`，
  否则 `'qualified'`（行上没批次号则跳过，那批货还没定位到批次）；
- **`confirmHandling` 报废后**：若该批次在全仓已无结存 → `status='scrapped'`
  （**只标"全仓都没了"的情形** —— 部分报废不能整批作废，那会把还能正常卖的部分一起冻掉）；
- **`pickBatches`** 增加检验结论过滤；
- **`applyStockOut`** 在显式指定批次时过 `assertBatchUsable`。

### 放行清单（很重要，否则会把自己拦住）

闸门**只拦"把货当可售货消耗掉"的那几类出库**：

```js
const SALEABLE_ONLY_OUT = new Set(['SAL_OUT', 'SHP_OUT', 'MR', 'WWS_OUT', 'POS_OUT', 'MALL_OUT'])
```

报废（`SCRAP_OUT`）、退料/退货（`QC_RET_OUT` / `PUR_RET`）、盘亏调整（`ADJ_OUT`）、
调拨（`TR_OUT`）**一律放行** —— 它们的目的本来就是"把不可用的货弄出去/挪走"。
**不加这个清单，就变成"发现不合格 → 报废"这条路被自己拦住。**

### 两个可选参数（缺省即默认值，不需要迁移灌数据）

| 参数 | 默认 | 含义 |
|---|---|---|
| `inv_params.block_rejected_qc` | `1` | 检验不合格的批次不可拣选/出库 |
| `inv_params.block_pending_qc` | `0` | **待检**批次是否隔离 |

`pending` 默认放行是**业务策略**，不是偷懒：本项目的质检不是必经环节
（模块 07 的到货单质检是轻量的、模块 13 的独立成单是可选流程），
演示数据里批次全部是 `pending` —— 若默认拦待检，整条链路一步都走不动。
真实的"待检区隔离"场景把该参数置 1 即可（**数据配置，不改代码**）。

## 八、回归与反例（`test-guards` G12）

| 段 | 断言 |
|---|---|
| 12a/12c | 一次真实回款同时验两件事：额度按**占用时的来源(SO)**释放（原来一条流水都写不出来）· 同主体的**另一张应收没被动过**（原来按 FIFO 串过去）· 回执说明钱抵在哪张应收、多少是预收 |
| 12b | 超应收余额 → 409 `RC_ALLOC_EXCEEDS_AR` · 超收款单金额 → 409 `RC_ALLOC_EXCEEDS_RECEIPT` · 重复 `ar_id` → 400 `RC_ALLOC_DUPLICATE_AR` · **两张草稿各抵 60% 同一张应收：第一张确认成功、第二张 409** · 已确认核销合计不超应收 |
| 12d | 改 B 库参数不影响 A 库 · 交错重复读稳定 · 用例自还原 |
| 12e | 造两个不同价批次（10 元×5 / 20 元×5）跨批出库：`qty=10`、`outAmount=150`、`qty × unitCost = 150`、`batches[]` 逐批带单价与金额、逐批之和 = 总额 · 用例自还原 |
| 12f | 批次置 `rejected` 后**不再被自动拣出** · 显式指定该批次做**销售出库** → 409 `BATCH_NOT_SELLABLE` · **对照：报废类出库仍放行** · 用例自还原 |

**12e 为什么自己造批次**：跨批次成本要验的是"两个不同价批次被一起出库"，
而演示库里没法保证某个仓×SKU 恰好有这种组合。所以先找一个**当前没有任何库存的仓×SKU 组合**，
自己灌两个批次，跑完**精确删掉**（组合原本为空，删完即回到原状）。
这比"在已有库存上做实验再想办法还原"可靠得多。
