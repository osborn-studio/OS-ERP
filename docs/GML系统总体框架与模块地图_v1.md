## 一、这次要解决什么问题

（**v1.27 快照，当时的 GML 已能演示**）**152 张表 / 7 个视图 / 31 个后端路由模块 / 69 个前端页面 / 后端约 41,700 行 + 前端约 26,900 行**（另有测试脚本约 10,600 行），覆盖采购（**九环节完整**）、销售、库存、OMS、经销商、门店 POS、H5 商城、委外、计划与生产、**BOM 与报工领料（制造中心）**、**订货中心**、**质量检验独立成单**、**单据内核可视化与编码规则配置**。

> 规模变化（2026-10-15）：初版框架文档记录的是「66 张表 / 17 个路由 / 48 个页面 / 后端约 8,500 行」。此后 P0 底座（库存三层、单据内核、组织权限、价格中心、编码规则）、模块 12A 订货中心、模块 07 采购域、模块 08A/21/24 销售链（**后端 + 前端**）、模块 09 存货核算与成本、模块 13 质量检验、模块 10B BOM 与报工领料相继落地，表数与代码量持续增长（v1.5 记为 119 表 / 20 路由 / 58 页面 / 后端 23,400 行；v1.7 记为 147 表 / 5 视图 / 30 路由 / 68 页面 / 后端约 38,500 行 + 前端约 24,800 行；**v1.35 记为 193 表 / 10 视图 / 37 个路由模块 / 78 个页面 / 后端 60,325 行 + 前端 35,425 行 + 测试脚本 20,710 行**，实测于 2026-10-16，命令：`find server -name '*.js' -not -path '*/node_modules/*' | xargs wc -l | tail -1` · `find src -name '*.tsx' -o -name '*.ts' | xargs wc -l | tail -1` · `ls scripts/test-*.mjs | xargs wc -l | tail -1`；⚠️ 行数是**移动靶**（同一台机器 17 分钟内后端就从 60,141 → 60,325，因为**另有线在并行提交**），引用时**连时间戳一起引**）。

但它离"能直接用"差得不是功能数量，而是**一套框架**。具体差在六处：

| # | 缺什么 | 现在是什么样 | 直接后果 |
|---|---|---|---|
| 1 | **统一领域边界** | 模块是按"菜单"长出来的，同一件事散在多处 | 库存扣减、单据状态、取价逻辑各写一遍，改一处漏三处 |
| 2 | **通用单据内核** | 状态值是散落的字符串（现有 21 种：draft/pending/confirmed/shipped/…） | 没有状态机、没有业务流、没有环节关闭，单据流转靠 if 判断 |
| 3 | **组织与权限纵深** | 只有 8 个**扁平角色** + dealer/store 两个数据范围 | 无法表达"某组织某岗位只能看某仓库的某类单据" |
| 4 | **价格与结算引擎** | 采购取价靠手填，返点是独立模块 | 价格优先级、账期、信用、返利无法在开单时统一生效 |
| 5 | **可运维性** | 单文件 `schema.sql`、无迁移、无幂等、无重试、无备份策略 | 改表无脚本可回溯；接口重放会重复扣减；数据无备份 |
| 6 | **前后端契约** | 前端直接拼接口地址 | 无类型契约、无 OpenAPI 消费，改动即连锁失效 |

**结论**：先立骨架（L0–L4 分层 + 六个共享能力中心），再逐模块填肉。骨架一旦立住，后面每加一个模块的成本都会下降；不立骨架，每加一个模块都要复制一遍现有毛病。

## 二、参考系（学到的三套口径）

### 2.1 用友口径 —— 我们的术语与流程基准

**采购管理**（取自 YS 采购课件）
- 单据链条：请购单 → 采购订单 → 到货单 → 采购入库单 → 采购发票 → 采购结算单 → 付款单
- **交易类型**决定业务场景（同一张单据可有多个交易类型，如"普通采购 / 退货订单 / 固定资产采购"）
- **业务流设计**决定单据流转路径（预置两条：订单→入库→发票；订单→到货→入库→发票），可自定义、可**版本控制**（改流程只影响新单据）
- 核心单据必须设置交易类型；退货分**有来源**（订单直推红字入库单）与**无来源**（负数订单）
- 取价方式三种：手工录入 / 最新采购价 / 价格表（价格目录 + 价格调整单）
- 控制参数：超量控制与超上限比例、供货目录（限定供应商-物料对照）、最小起订量
- **订单环节关闭**：到货关闭 / 入库关闭 / 开票关闭 / 付款关闭，可自动（调度任务）或按参数触发
- 采购结算：自动结算 / 手工结算 / **费用折扣结算**（三单结算，入库成本 = 费用发票 + 采购发票；入库单金额为暂估，差异进存货核算）
- 报表：采购订单执行统计表、未完成业务明细表、采购订单预警与报警

**销售管理**：报价单 → 销售订单 → 销售发货单 → 销售出库单 → 销售发票 → 收款单；业务类型支持普通销售 / 委托代销 / 分期收款 / 直运 / 零售 / 销售调拨；含客户信用控制与价格监控。

**库存管理**：单据类型齐全 —— 采购入库、产成品入库、其他入库、销售出库、材料出库、其他出库、配比出库、限额领料、调拨、盘点、组装、拆卸、不合格品记录/处理、货位调整；能力含**货位管理、批次管理、保质期管理、出库跟踪入库、可用量管理、序列号管理**。

**存货核算**：入库成本 / 出库成本 / 结余成本；计价方式支持加权平均、先进先出、个别计价。

**计划与制造**：MPS / MRP / LRP、BOM 与工艺路线、生产订单/派工/报工/领料、委外（发料 + 收货）、产能负荷、质量（进货检验 / 过程检验 / 成品检验 + 不良品处理）。

**营销与渠道**：营销云（B2C 会员/零售/电商 + B2B 全渠道营销中台与渠道交易）、零售云（门店销售与店存）、B2C 订单中心（电商店铺库存、发货、退货）、多级渠道管理。

**技术底座**：数字化建模层 —— 权限管理、组织管理、基础数据、流程管理、模板管理、系统管理、消息平台、报表平台。

### 2.2 零售中台口径 —— 共享能力怎么切

业务中台的经典切法是**五大中心 + 支付中心**：

- **商品中心**：全域唯一商品数据源，"一处管理、全域生效"；三层模型（基础物料层 / 销售商品层 / 渠道商品层）
- **库存中心**：线下线上多仓统一，实时同步与合理分配（"一盘货"）
- **订单中心**：全渠道订单归一，生命周期管理（创建、支付、履约、售后），支持拆单合单
- **会员中心**：One-ID 打通各触点，统一画像、积分、权益
- **营销中心**：优惠券、活动引擎、积分，配置化上线（券/满减/秒杀）
- **支付中心**：多渠道聚合、统一收单、对账

配套的**数据中台**负责汇聚与分析，产出"唯一客户视图"与统一口径。

### 2.3 DMS 与 POS 口径

**经销商管理（DMS）八项核心能力**：全渠道数据整合、智能订单管理（库存/信用/价格自动校验 + 异常与窜货识别）、经销商全生命周期与分级（战略/核心/潜力 + 360 画像 + 健康度评分）、终端动销监控（对接终端 POS、缺货率预警、促销执行分析）、智能物流与调拨、规则引擎驱动的返利（阶梯销量/回款账期/新品推广达标）、智能对账（订单-回款-费用三方关联）、合规与税务。

**POS 六层能力**（按业务链路而非菜单切）：
1. **前台交易层**：商品快查（扫码/编码/分类）、挂单取单、会员识别与权益匹配、多支付与组合支付、整单优惠与改价、退货、交接班
2. **商品库存层**：商品档案与多包装、批次效期、收货/销售/退货/调拨/盘点/报损均可解释库存变化
3. **采购供应层**：总部统采 / 门店自采 / 仓库配送三条线，要货单 → 他店要货出库单 → **要货差异单**
4. **会员营销层**：开卡、储值、积分、券核销、导购归属与提成
5. **门店连锁管理层**：门店档案、**价格本与价格组**、总部调价单（带生效时间）、促销下发、门店结算与分账、分级权限
6. **经营分析层**：销售看板、商品动销、会员活跃、门店对比、异常预警（长短款、报损率、营业额突变）

**日结口径**：交班 → 缴款 → 长短款核对 → 每日台账单 / 日结单（统计上日结存与本日销售）→ 上传总部。

## 三、GML 目标架构（五层两横）

```
┌──────────────────────────────────────────────────────────────────┐
│ L0 接入层                                                          │
│  总部后台 Web │ 门店 POS(触屏) │ 线上商城 H5/小程序 │ 经销商门户     │
│  开放 API(奇门 + OpenAPI) │ AI 承接台                              │
├──────────────────────────────────────────────────────────────────┤
│ L1 业务应用层（四大子系统）                                          │
│  ① 供应链 ERP   ② 线上商城 B2C   ③ 线下 POS 连锁   ④ 经销商 DMS     │
├──────────────────────────────────────────────────────────────────┤
│ L2 共享能力中心（中台）                                              │
│  主数据/商品 │ 库存 │ 订单 │ 价格促销 │ 结算对账 │ 会员渠道          │
│  组织权限 │ 工作流审批 │ 编码规则 │ 审计日志 │ 消息待办              │
├──────────────────────────────────────────────────────────────────┤
│ L3 领域内核（引擎）                                                  │
│  单据引擎(状态机+业务流) │ 库存引擎(可用量+批次+成本) │ 取价引擎       │
│  返利引擎 │ 促销引擎 │ 计划引擎(净需求/MRP) │ 成本引擎               │
├──────────────────────────────────────────────────────────────────┤
│ L4 数据层  SQLite（演示级 · 目标 ≤ 万条 · 已定，不引入 PG）          │
│  主数据 · 单据(头/行) · 库存流水 · 成本层 · 维度 · 日志              │
├──────────────────────────────────────────────────────────────────┤
│ L5 集成交互  奇门/OpenAPI · 支付 · 物流 · 电子发票 · 钉钉/企业微信待办 │
└──────────────────────────────────────────────────────────────────┘
  横切：安全与权限 ｜ 可观测与运维
```

**一句话读法**：L1 是"卖什么"，L2 是"四套子系统共用什么"，L3 是"共用的规则怎么算"，L4 是"数据怎么存"，L5 是"怎么跟外面说话"。

**当前 GML 的落点**：L1 已粗具；L2 **几乎为空**（能力都直接写在 L1 各路由里）；L3 只有库存引擎一半（`server/lib/stock.js` 的批次扣减）；L4 是 SQLite 单文件（**演示定位下已足够，保留**）；L5 已通奇门但缺 OpenAPI 契约。

## 七、数据模型骨架（统一约定）

**主数据族**：组织 / 部门 / 人员 / 岗位 · 仓库 / 货位 · 商品（SPU→SKU）/ 条码 / 多单位 · 供应商 / 客户 / 经销商 / 门店 · 平台 / 店铺 · 币种 / 税率

**单据族统一骨架**（所有业务单据共用一套头表约定）：

```
doc_no          单号（编码规则生成）
doc_type        单据类型（PO / SO / DL / RT / TF / CK …）
trade_type      交易类型（决定业务场景与业务流）
flow_id         业务流实例
status          状态（由状态机驱动，不再散落）
org_id          业务组织
warehouse_id    仓库（如适用）
party_id        往来单位（供应商/客户/经销商/门店）
biz_date        业务日期
total_amount    金额
version         变更版本
creator / approver / created_at / approved_at
```

**行表**：`doc_no + line_no + sku_id + qty + price + amount + batch_no + location_id + tax_rate`

**库存三层**：
- 实物层：仓库 / 货位 / 批次 / 序列号 → 现存量
- 逻辑层：占用 / 在途 / 冻结 → **可用量 = 现存量 − 冻结 + 预计入库 − 预计出库**
- 成本层：入库成本 / 出库成本 / 结余成本 / 暂估差异

**前端契约**：由 OpenAPI 生成 TS 类型，页面不手拼接口。

**数据库约定**：SQLite（better-sqlite3）为唯一数据库，定位**演示系统**，数据量目标 ≤ 万条。配套要求：

- 单文件 `data/*.db`，按行业分库（沿用现有双行业设计）
- **建表只写标准 SQL**，不用 SQLite 私有语法，将来若需上量可低成本切换
- `schema.sql` 之外增加**版本化迁移脚本**（`migrations/000x_*.sql` + 一张 `schema_migrations` 表），保证演示机之间、以及换机重建时结构一致
- 定时 `VACUUM INTO` 备份 + 演示前一键重置，避免演示数据被改乱
- 索引只建在真正被查询用到的字段（单号、状态、SKU、仓库、日期），不做过度优化
- **PRAGMA 现状（2026-10-14 实测）**：`journal_mode = WAL` ✅、`foreign_keys = ON` ✅；**缺 `busy_timeout`** ⚠️ —— 门店 POS 多终端 + 总部同时写入时会直接抛 `SQLITE_BUSY`，建议补 `busy_timeout = 5000`。当前化妆品库销售订单 247 条，距万条上限空间充裕
- 并发策略：SQLite 是单写者模型。演示场景（同时几个终端）足够，但**所有写操作必须走事务**，且避免长事务持有写锁

## 十、口径与边界

1. 本文是**内部框架底稿**，不是客户方案、不是报价依据、不是上线承诺。
2. 所有模块边界以双方确认的输入为准；文中"已有/部分/待建"基于当前代码实际状态判断，随代码演进需同步修订。
3. **主数据单一来源、交易双向留痕、异常可回查** —— 任何"两边都能改"的字段，先约定以哪边为准。
4. 涉及资金的动作（付款、退款、分账、返利入账）保留人工确认，系统只做建议与校验。
5. 报表指标以《口径字典》为准，先定口径再建报表。
