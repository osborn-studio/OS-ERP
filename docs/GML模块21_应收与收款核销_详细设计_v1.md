## 0. 一句话定位

应付（采购付款）已经有付款单 + 核销明细 + 作废保护，应收却只有 `sales_orders.paid_amount` 一个数 —— 追不到"这笔钱抵了哪张单"，也算不出账龄。本模块把应收侧补成与付款侧同一形状：**应收单记"谁欠我多少"，收款单记"钱到账"，核销明细记"抵了哪几笔"**。

---

## 1. 三条硬口径

1. **已收金额永远由核销明细 SUM 算出，不累加**
   付款侧踩过的坑是 `paid_amount` 自加，作废一笔就对不上账。这里 `ar_documents.allocated_amount` 一律由 `receipt_allocations`（且仅统计 `status='confirmed'` 的收款单）重算，`recalcAr()` 是唯一写入口。

2. **核销生效点 = 收款单确认**
   草稿收款单上的核销明细只是"打算怎么抵"，不计入已收、不释放授信。钱没到账，额度就得继续占着 —— 与信用控制同一条口径。

3. **单据金额必须能由明细重算出来**
   `auditAr()` 做四查：已收 vs 明细漂移、状态与金额是否相符、是否超额核销、收款单分摊是否漂移。任何一查不通过即为 bug。

## 2. 数据模型（迁移 019）

```
ar_documents        应收单：谁、因为哪张单、欠多少、什么时候到期
  doc_no(AR) / subject_type(dealer|oc|store) / subject_id / subject_name
  source_type(SO|OC|MANUAL) / source_id / source_doc_no
  biz_date / due_date / credit_days
  amount / allocated_amount / status(open|partial|closed|voided)

receipts            收款单：钱到账才生效
  doc_no(RCP) / subject_* / receipt_date / method(transfer|cash|bill|online)
  amount / allocated_amount / status(draft|confirmed|voided)
  bank_account / serial_no / confirmed_by / confirmed_at

receipt_allocations 核销明细：收款单 ↔ 应收单 多对多
  receipt_id / ar_id / amount   UNIQUE(receipt_id, ar_id)
```

**销售订单新增列**：`ar_id` / `ar_doc_no`（记住这张订单生成了哪张应收，避免重复生成）。

**到期日**：`due_date = biz_date + credit_days`（账期 0 视为当天到期＝现结）。实现上用本地日期自增，不经 `toISOString`（否则按时区回退一天，会出现"1/1 + 30 天 = 12/31"）。

---

## 3. 单据内核与状态机

- **AR 应收单**：`open → partial → closed`，`voided` 为单独出口；状态由已收金额推导，不是人工点出来的。
- **RCP 收款单**：`draft → confirmed`（确认＝核销生效 + 释放授信），`confirmed → voided`。
  `confirmed` **不标终态** —— 作废是一次会计事件，不能因为"已收款"就封死；内核的"终态无出边"不变量会抓出这一点。
- 业务流 `FLOW_RECEIVABLE`：生成应收 → 到期日计算 → 登记收款 → 确认核销 → 释放授信 → 对账与账龄。
- **单据码 RCP**：`RC` 已被"门店日结单"占用，故收款单取 RCP。踩过的坑：008 里给 STATES/ACTIONS 加同名 key 会**静默覆盖**已有定义（日结动作把收款动作顶掉），改名必须全库检索确认无重名。

## 4. 核心流程

### 4.1 生成应收（幂等）
`ensureAr()` 按 `(source_type, source_id)` 唯一：订单确认、发货、补单都会调它，重复生成等于凭空多一笔应收。路由 `POST /api/ar/documents/generate` 可批量补生成（不传 `items` 自动取未生成应收的销售订单）。

### 4.2 登记收款（草稿 + 计划核销）
- 不传 `allocations`：按 `due_date, id` **FIFO 自动摊**（到期日在前的先抵）；
- 传 `allocations`：手工指定抵哪几笔（单笔可抵金额自动截断到剩余应收）；
- 超收部分记为**预收**（`receipts.allocated_amount < amount`，差额即 `unallocated`）。

### 4.3 确认收款（唯一有后果的动作）
事务内一次做完：内核流转留痕 → 状态置 confirmed → 相关应收重算 → 调 `credit.settle` 释放授信 → 回写销售订单 `paid_amount`。

### 4.4 作废收款
内核流转留痕 → 状态置 voided → 相关应收重算（已收回退）。**不自动回收已释放的授信** —— 作废本身是一次会计事件，要不要补一笔反向占用由调用方决定，避免静默改账。

### 4.5 账龄与对账
- 账龄四桶：未到期 / 1-30 / 31-60 / 60+，按未结余额计；可按客户汇总（`by_subject=1`）出风险榜；
- 客户对账单：期初/本期应收 − 本期核销 = 期末余额，期末余额必须能由明细重算。

## 6. 演示数据（ar-seed.js，三库同构）

每库固定造出可讲的故事：
1. 由 12 张销售订单生成应收，其中**两笔故意造逾期**（超账期 12 天与 78 天）；
2. 一笔款**跨两单 FIFO 分摊**（回答"这笔钱抵了哪几笔"）；
3. 一张**部分收款**（停在 partial）；
4. 一张**草稿**收款单（票据待背书，界面上要能看到"未生效"）；
5. 一张**已作废**收款单（重复入账作废，金额回到未收）；
6. **预收场景**（第二阶段）：客户凑整付款多付 5000，转为预存，再用"预收转应收"抵到另一张未结应收上；
7. **订货中心并入**（第二阶段）：`seedOrderCenter` 走「确认收货」时自动生成 OC 应收，`seedAr` 末尾再用 `syncOcAr` 兜底补齐历史遗留 —— 三库待并入数最终为 0。

> 幂等细节：`seedAr` 的"已造过就跳过"判断只看 `source_type='SO'`。若把 OC 应收一并计入，seed 会被自己的上游挤成空跑，演示数据（逾期 / 跨单分摊 / 作废）就都不见了 —— 这是本轮踩到的坑。

## 8. 前端页面（v1.2 六个页签）

路由 `/finance/receivables`，六个页签对应财务一天里真正会用到的六种动作：

| 页签 | 回答的问题 | 关键交互 |
| ---- | ---------- | -------- |
| 总览 | 一共该收多少、收回来多少、逾期多少 | 五张 KPI + 账龄分布 + 逾期风险榜（点行直接开对账单）+ 自洽审计（auditAr 四类检查结果） |
| 应收单 | 每笔还欠多少、到期日、抵的是哪张收款 | 状态/余额/逾期筛选，详情弹窗列核销明细，支持手工补录与由销售订单批量生成（幂等） |
| 收款单 | 钱收到了、生效没有 | 登记草稿（可选手工指定核销，留空则 FIFO 自动分摊）→ 确认生效（核销 + 释放授信）→ 必要时作废（需填原因） |
| 账龄与对账 | 哪几家该催了 | 账龄四桶占比条 + 客户账龄榜 + 客户对账单（应收明细 / 收款明细 / 核销关系三段，可打印） |

| **预收** | **客户多付的钱在哪、能抵哪笔** | 预收清单（累计已收/已核销/预收余额）→ 明细弹窗：可用的预收（逐张收款单）+ 抵扣目标（按到期日自动 / 指定应收单）+ 可抵未结应收；下方「订货中心待并入应收」一键并入 |

## 9. 数据库加固（v1.2 · 迁移 020）

本阶段**不新增业务表**（结构在 019 已定），补的是"把口径下沉到库里"与"可运维"：

### 9.1 三个派生视图（界面展示与库内可算永远同源）

| 视图 | 口径 | 用途 |
| --- | --- | --- |
| `v_ar_aging_detail` | 余额 = `amount − allocated_amount`（SUM 重算，不读缓存列）；逾期天数 = `julianday(今天) − julianday(到期日)`；桶名 b0~b3、settled 与 `lib/ar.js` 的 `aging()` 完全一致 | 逐笔账龄页 + 客户级汇总 |
| `v_oc_ar_pending` | `oc_orders` 处于 allocated/shipped/received/completed 且 `ar_documents` 中无 `source_type='OC' AND source_id=该单` | 订货中心待并入清单 |
| `v_ar_prepay` | 预收 = `SUM(confirmed 收款单 amount) − SUM(其核销明细 amount)`，`HAVING > 0.005` | 预收清单页 |

**为什么用视图而不是在 JS 里算**：口径只要写两遍就会漂移。视图是唯一写法，`/aging/detail` 只做筛选与组装，且测试里有一条断言专门比对"函数结果 == 视图行数"。

### 9.2 派生索引

```
idx_ar_open_due         ar_documents(status, due_date, subject_type)     -- 账龄/逐笔账龄主查询
idx_rc_subject_status   receipts(subject_type, subject_id, status, receipt_date)  -- 预收与核销
```
只建被真实查询用到的列，不做过度优化。

### 9.3 运维参数（落 settings 表，不活在代码注释里）

| key | 默认 | 含义 |
| --- | --- | --- |
| `backup_dir` | data/backups | 备份输出目录 |
| `backup_keep` | 10 | 每库保留备份份数 |
| `ar_source_of_truth` | SO | 应收生成口径（SO 订单确认即生成 / SI 开票后生成） |
| `ar_oc_enabled` | 1 | 订货中心订单是否自动并入应收 |
| `ar_prepay_auto` | 0 | 预收是否自动抵新应收 |

### 9.4 权限点

`finance.ar.aging`（查逐笔账龄）、`finance.ar.prepay`（预收管理与转应收）；admin / boss / finance / sales 按职责授予。

### 9.5 运维脚本

- `scripts/db-backup.mjs`：三库 `VACUUM INTO` 在线快照（不停服、无 WAL 半写污染），按 `backup_keep` 裁剪（只删自己命名规则生成的文件），`--verify` 打开备份库做 `integrity_check` 并比对结构；
- `scripts/db-reset.mjs`：**先备份 → 删库文件（含 -wal/-shm）→ 迁移 → 重灌**，默认需要交互确认（`--yes` 供无人值守），备份失败即中止；
- `scripts/db-inventory.mjs`：三库结构盘点（表/视图/迁移数/PRAGMA），用于快速核对三库是否同构。

**踩到的坑（已修）**：`resetDatabase()` 只 DROP 表、不 DROP 视图，视图会一直引用已被删除的 `ar_documents`，SQLite 在之后任意一次 DDL 解析 schema 时报 `error in view v_ar_aging_detail: no such table` —— 报错点还会落在完全无关的迁移上（本次炸在 002 的 `db.exec`）。修法是先动态枚举并 DROP 所有视图（不硬编码清单），视图由 020 迁移的 `verify` 自检负责重建。
