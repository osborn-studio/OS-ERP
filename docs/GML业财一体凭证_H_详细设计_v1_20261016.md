# GML 业财一体凭证（批次 H · 模块 27）详细设计

> 版本 v1 · 2026-10-16 · 批次 I 第 12 批 · 迁移 `032_voucher`
> 上游依据：`docs/GML剩余模块开发计划与进度安排_v1_20261015.md` 批次 H（5 步：科目表 → 凭证模板 → 凭证生成与试算平衡）
> 结论：**H 收口 —— 业务事实第一次能翻译成借贷分录，且"平不平"由不变量说了算。**

---

## 一、一句话

这一批之前，系统里**有货、有钱、有单据，但没有一张会计凭证**：

| 业务事实 | 之前 | 之后 |
|---|---|---|
| 采购入库（到货单） | 库存加了，**存货科目没动** | 借 库存商品 / 贷 应付暂估 |
| 销售出库（发货单） | 货走了，**收入与成本没确认** | 借 应收 / 贷 主营收入 + 贷 销项税额；借 主营成本 / 贷 库存商品 |
| 收款 / 付款 | 改了单据状态，**银行与往来没动** | 借 银行 / 贷 应收 + 贷 预收；借 应付 + 借 预付 / 贷 银行 |

于是"这批货值多少钱、这个月赚了多少"在系统里**答不出来**，
而每一个单据看起来都是正常的、状态都对。

## 二、四条硬口径

### 2.1 凭证只能由已发生的业务事实生成，不能人工编

`vouchers` 上 `UNIQUE (biz_type, source_type, source_id)`；
**界面上没有"新建凭证"按钮，接口上也没有"新建凭证"端点**，只有「生成」。

> 手工编分录的口子一开，"这张凭证是哪来的"就再也答不出来；
> 而编出来的账**同样是平的** —— 平账骗得过所有不变量。

生成器还会校验来源单据的**状态已允许入账**（`BIZ_TYPES[*].okStatuses`）：
草稿的收款单是意向不是事实，报 `SOURCE_STATUS_INVALID`。
"货没发出去就确认收入"这类错必须在记账这一步被拦住，而不是等对账时才发现。

### 2.2 不平即拒绝，且**整张不落库**

```js
const totalDebit  = ...; const totalCredit = ...;
if (Math.abs(totalDebit - totalCredit) > 0.005) {
  throw new AccountingError('VOUCHER_NOT_BALANCED', ...)   // ← 抛在 tx 之外，库里不留半张
}
```

**半张凭证比没有凭证更糟**：没有凭证是"漏了"，半张凭证是"错了"。
过账时**再校验一次**（`postVoucher`）—— 生成之后有人动过分录，必须在那里被拦住。

### 2.3 方向由模板决定、金额恒 > 0、只能挂叶子科目

| 约束 | 违反时报 | 为什么 |
|---|---|---|
| 分录 `amount > 0` | `VOUCHER_NEGATIVE_AMOUNT` | 允许负数金额的账，任何汇总都能被"负负得正"地做平 |
| 只能挂 `is_leaf=1` 的科目 | `SUBJECT_NOT_LEAF` | 挂父科目不会报错，只会让「父科目 = 子科目之和」**悄悄不成立**，而报表仍然很好看 |
| 科目须 `active` | `SUBJECT_INACTIVE` | 停用科目的历史凭证要能读、但不能记新账 |

`is_leaf` **由结构推导、不人工维护**：`saveSubject` 在每次写入后按
「谁有孩子谁就不是叶子」重算全表。父科目一旦挂上子科目，就自动不可记账。

### 2.4 只有 `posted` 计入账

`draft`（已生成未过账）**不进试算平衡表** —— 否则"生成"就是"入账"，审核这一步没有位置。
演示数据**刻意留一张 draft**，界面上必须能同时看到两种形态。

作废已过账凭证**必须写理由**（`VOID_REASON_REQUIRED`）：作废会改变当期发生额，
账少了钱得有人知道为什么；理由与"作废前是否已过账"（`was_posted`）一并留痕。

## 三、为什么模板里存的是「取数键」而不是「表达式」

计划书写的是"支持取数表达式"。实现上**刻意改成受控取值键** `amount_key`：

> 模板是**可被界面编辑的配置**。一旦模板里能写任意表达式，就等于**配置能改账**，
> 而改账的错不会报错，只会让某一张凭证的金额悄悄变成另一个数。

取值键是一个**封闭字典**（`FACT_KEYS`，6 个键），每个键回答"这个数从哪来、有没有被算过"：

| 取数键 | 含义 | 关键约束 |
|---|---|---|
| `total_amount` | 单据总额（价税合计 / 收付款金额） | — |
| `net_amount` | 不含税金额 | `total ÷ (1 + 税率)`，四舍五入到分 |
| `tax_amount` | 税额 | **用减法**：`total − net` |
| `cost_amount` | 出库成本 | **只从库存成本流水取**，不用售价估 |
| `settled_amount` | 已核销金额 | 收付款单的核销额 |
| `offset_amount` | 未核销部分 | **用减法**：`total − settled` |

加一个新键要走代码评审，而不是改一条数据库记录。

## 四、金额一律「末行兜底」

只要一张凭证里有「总额拆成几份」的结构（含税 → 不含税 + 税额），
就**必须用减法算最后一份**，而不是各自四舍五入：

```
100.00 × 13% → 88.50 + 11.50   平
 99.99 × 13% → 88.49 + 12.50 = 100.99   ← 各自四舍五入就差 0.01，凭证平不了
 99.99 × 13% → 88.49 + 11.50 = 99.99    ← 用减法，恒等
```

这个差额不会报错，只会让"这张凭证平不了"，而被误判成生成器有 bug。
本项目的分摊一贯如此（批次 F 的优惠分摊、批次 G 的核销冲减分摊、本条），**同一条手法第四次使用**。

## 五、迁移 `032` 清单

### 5.1 五张表

| 表 | 关键列 |
|---|---|
| `accounting_subjects` | `code`(UNIQUE) / `name` / `parent_id` / `category`(5 类) / `direction`(借/贷) / `level` / `is_leaf` / `aux_type` / `status` |
| `voucher_templates` | `code`(UNIQUE) / `name` / `biz_type`(**UNIQUE**) / `doc_type` / `status` |
| `voucher_template_entries` | `template_id` / `seq` / `summary` / `direction` / `subject_code` / `amount_key` / `aux_key`；`UNIQUE (template_id, seq)` |
| `vouchers` | `doc_no`(UNIQUE) / `biz_type` / `source_type` / `source_id` / `source_doc_no` / `voucher_date` / `period` / `status` / `total_debit` / `total_credit` / 过账与作废留痕；**`UNIQUE (biz_type, source_type, source_id)`** |
| `voucher_entries` | `voucher_id` / `seq` / `summary` / `subject_id` / `subject_code` / `subject_name` / `direction` / `amount` / `aux_type` / `aux_name`；`UNIQUE (voucher_id, seq)` |

**为什么分录要冗余 `subject_code` / `subject_name`**：科目改名或迁移之后，
**历史凭证仍然读得出"当时挂的是哪个科目"** —— 只存 `subject_id` 的话，
一次科目改造会把所有历史凭证的科目名一起改掉，而账是不能再改的。

### 5.2 七个索引 + 六个权限点 + 一个设置

- 权限：`finance.subject.view/edit`、`finance.voucher.view/gen/post/void`
  —— **过账与作废必须分开授权**：能记账的人不应该同时能把记好的账作废掉。
- 设置：`settings.voucher_default_tax_rate = 13`（税率必须有一个出处，不能每处各写一个 13）。

### 5.3 单据内核

`VOUCHER` 是第 **39** 种单据类型（`PZ` 前缀）：

```
draft（已生成，不计入试算平衡）→ posted（已过账）→ voided（已作废）
```

`posted` **刻意不是终态**：一张过账的凭证写错了必须能作废，否则"平不了的账"
只能靠再补一张反向凭证去硬凑。`void` 登记为**高危动作**。
另加业务流 `FLOW_VOUCHER`（业务事实 → 按模板取数 → 借贷试算 → 生成 → 过账 → 试算平衡表）。

### 5.4 `verify()` 的六条结构不变量

分录金额为正 · 方向取值合法 · **已生成/已过账凭证必须借贷平衡** ·
期间 = 记账日期前 7 位 · 模板分录的方向与取数键非空 · 科目 `parent_id` 不能自指。

## 六、接口、界面与演示数据

### 6.1 接口（`/api/accounting/*`，15 条路径）

字典 · 科目（列表 / 树 / 建改 / 启停）· 模板（列表 / 详情）·
凭证（列表 / 详情 / **试算** / **生成** / 过账 / 作废 / 按来源反查）· 试算平衡表 · 域自证。

**试算与生成走服务端同一个函数 `planVoucher`** —— 两处各算一遍必然分叉，
而"预览说 A、入账是 B"这种错没有任何界面能看出来。

### 6.2 界面 `/finance/accounting`（财务中心，四个页签）

1. **凭证与过账** —— 试算面板（先试算再生成）· 列表 · 行内展开分录明细 · 过账 / 作废（作废强制填理由）；
2. **试算平衡表** —— 按科目汇总，给借合计 / 贷合计 / 差额；
   差额不为 0 时显示「试算**不平**，差 ¥x」，而不是四舍五入到两位就当平了；
3. **会计科目** —— 缩进树形，标出"不可记账（有子科目）"、辅助核算与状态；
4. **凭证模板** —— 逐行显示摘要 / 方向 / 科目 / **取数键**（含中文释义）—— 回答"这个数从哪来"。

### 6.3 演示数据 `db/finance-seed.js`

- **科目表 23 个**（两层，含 `2221 应交税费 → 222101/222102` 的父子样本）；
- **凭证模板 5 套**（采购入库 / 销售出库 / 成本结转 / 收款 / 付款）；
- **演示凭证 10 张**：全部**从真实业务单生成**（2 到货单 + 2 发货单 + 2 成本结转 + 2 收款 + 2 付款），
  **不平即拒绝、不手工插分录**；过账 9 张、**刻意留 1 张 draft**。

模板分录**整体重建而不是逐条 upsert**：改了行数（三行变两行）时，
逐条 upsert 会留下上一版模板的残留行，而**残留行还在参与生成**。

**样本选择上的两个刻意**：
① 断言用**增量**（`total_debit` 的前后差）而不是某个具体科目 ——
演示数据里已有一批已过账凭证，按科目名断言会被它们污染，得到的红/绿与本次改动无关；
② 幂等断言**捕获异常而不让它穿透** —— 幂等做漏时第二张会被唯一索引拦成
`SQLITE_CONSTRAINT_UNIQUE`，那是"炸了一条语句"，而断言要报的是"有没有重复记账"这件事本身。

### 7.2 `verify-seed` 新增第 15 节「财务凭证自洽」（16 条）

分录金额为正 · 方向合法 · **凭证借贷平衡** · 头合计 = 分录合计 ·
**只挂叶子科目** · **同一事实只入一次账** · 期间 = 记账日期前 7 位 ·
**来源单据真实存在（跨代引用）** · 作废必写理由 · 科目无自指 ·
**总账试算平衡** · 科目/模板/凭证样本齐备（五种场景都有、两种状态都有）。
