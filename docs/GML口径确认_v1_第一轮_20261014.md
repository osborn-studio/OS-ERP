## 一、为什么先定口径

模块里的东西分两类：

| 类别 | 谁定 | 例子 |
|---|---|---|
| **业务口径** | **用户定**（只有业务方知道怎么管） | 账期几天、线上订单谁发货、哪些单据要审批 |
| **技术结构** | 设计方出方案，用户只看设计稿里的业务规则部分 | 表怎么建、字段叫什么、接口几个、迁移脚本、索引 |

业务口径里有 8 条是**横切**的——它们不归某一个模块，而是贯穿全系统。例如「库存能不能线上线下共享」这一条，同时决定模块 03（库存中心）、14（订单路由）、17（店存）怎么写。**这 8 条不定，每个模块都得停下来问一遍。**

所以推进方式是：**8 条横切口径先定 → 03~26 的模块设计直接往下走，不回头改。**

## 二、组织与主体模型（本轮重点）

### 2.1 组织即业务主体

后台要有**组织定义**与**新建组织**能力，与用友的组织单元一致。建组织时要指定：

- **组织类型**：直营门店 / 加盟门店 / 渠道商 / 线上商城 / 仓库（中心仓·门店仓·寄售仓）/ 工厂 / 法人主体
- **业务职能**（可多选，决定菜单与权限）：销售 · 采购 · 库存 · 门店 POS · 线上商城 · 生产
- **演示期约定**：法人只建 **1 个**，但**业务主体多个**——主体不是法人，是"谁在经营、谁持有货"

### 2.2 主体决定货主（本模块最核心的一条）

**货主 = 商品的所有权归属。库存与单据都挂在主体上，货主决定"卖货"这件事算谁的销售。**

| 主体 | 货主 | 卖货意味着什么 |
|---|---|---|
| 总部（中心仓） | 总部 | — |
| **直营门店** | **总部** | 货主不变，门店只是**销售触点**；只产生零售单与成本结转，**不产生内部销售** |
| **加盟门店** | **加盟商**（买断） | 总部卖给加盟店才是真销售，产生收入与应收 |
| **渠道商** | **渠道商**（买断） | 同上 |
| **寄售仓（在经销商处）** | **总部** | 货在别人那里，**产权仍是总部的存货**；售出后才确认收入 |
| **线上商城** | **总部** | 货从中心仓或就近门店发出 |

### 2.3 两处容易混的地方，已明确

**① 寄售 ≠ 普通销售。** 寄售仓里的货是**总部资产**，发货过去只是**移库**，不记收入、不记应收；只有按代销清单结算后才确认销售。

**② 多品牌矩阵放在商品属性里**，不占组织维度。品牌是商品的属性，不是"谁在经营"。

## 三、寄售（委托代销）专项

### 3.1 用友口径依据

工作文档《U8 产品调研问卷 · 库存管理》原文：

> 「受托代销是一种**先销售后结算**的采购模式，指其他企业委托本企业代销其商品，**代销商品的所有权仍归委托方**。」

用友公开口径（委托方视角）：

> 「委托代销业务，指企业将商品委托他人进行销售但**商品所有权仍归本企业**的销售方式，委托代销商品销售后，受托方与企业进行结算，并开具正式的销售发票，**形成销售收入，商品所有权转移**。」

### 3.2 单据链（用友标准流程）

```
销售订单（业务类型 = 委托代销）
   ↓
委托代销发货单          ← 核心单据；货发出，货权不转移
   ↓
销售出库单（参照发货单）  ← 货移到寄售仓；成本进"发出商品"
   ↓
受托方售出，提供代销清单
   ↓
委托代销结算单          ← 按实际售出数量与金额结算
   ↓
销售发票（审核结算单自动生成） ← 此时才确认收入、结转成本、生成应收
   ↓
应收款管理 → 收款结算
```

**成本核算方式**（用友两选一）：按"发出商品核算"（发货时记发出商品）或"按销售发票核算"。

### 3.3 对系统模型的强制要求

1. **库存必须两套维度**：产权看**货主**，物理看**库位**。两者可以分离——寄售仓就是"物理在经销商处、产权在总部"。
2. **仓库要加寄售类型**：`warehouses.type` 增 `consignment`（寄售仓 / 委托代销仓）。
3. **单据要带货主字段**：每张库存类单据记 `owner_org_id`（货主）与 `warehouse_id`（库位），不能只记仓库。
4. **要新增两张单据**：委托代销发货单、委托代销结算单；并支持"发出商品"形态的存货。
5. **收入确认时点写在单据类型上**：普通销售发货即确认；寄售在结算单生效时确认。

## 四、八条横切口径 · 结论

| # | 口径 | 结论 | 对设计的要求 | 传导模块 |
|---|---|---|---|---|
| **1** | 组织与核算主体 | **单法人 + 多业务主体**；组织可新建、可选类型、可勾职能 | `orgs` + `org_functions`；单据与库存挂主体 | 03·05·18 |
| **2** | 库存口径 | **全渠道共享一盘货**（线上可卖门店库存） | 库存按 货主 × 库位 × 批次 记账；线上占用要回写门店仓 | 03·14·17 |
| **3** | 单据与审批 | **多级审批**（按金额分级） | 状态机 + 审批流；额度分级规则可配 | 04·22 |
| **4** | 价格体系 | **价格组 + 调价单**（带生效时间） | 价格本按组织/区域分组；调价单带生效期与下发记录 | 06·13·18·20 |
| **5** | 渠道与履约 | **就近发货 + 门店自提** | 订单路由（按门店可售库存派单）；自提单与核销 | 12·14·19 |
| **6** | 结算与账期 | **账期 + 信用额度拦截** | 往来单位挂账期与额度；下单校验，超额拦截或特批 | 20·21 |
| **7** | 成本与存货核算 | **移动加权平均，成本算得清、毛利可查**；**不生成凭证** | 出入库结成本；发出商品（寄售）单独核算；凭证留到 P2 | 09·21 |
| **8** | 编码规则 | **后台可配置**（前缀 + 组织 + 日期 + 流水位数，按单据类型） | 编码规则表驱动，替换现有"前缀+日期+探测" | 06 |

## 五、衍生的四条结论

| 问题 | 结论 |
|---|---|
| 直营门店仓的货主 | **总部**（门店不独立核算，零售只记销售触点） |
| 渠道商是否建组织 | **建**，且带自己的门户——可登录下单、查自己的订单与对账 |
| 渠道库存管到哪 | 总部**卖给他们即可**；**加盟门店库存要有（做参考）**；经销商库存**不管**——但**寄售仓要管，那是总部的货** |
| 门店补货方式 | **要货制 + 配货制都要**：新品铺货由总部配货，日常补货由门店要货申请 |

## 六、这些结论逼出来的模型改动（相对当前代码）

| 项 | 现状 | 改成 |
|---|---|---|
| 组织 | 无 `orgs` 表；只有仓库与门店 | 新增 `orgs`（类型 + 层级 + 法人）+ `org_functions`（职能开关） |
| 仓库 | `warehouses.type` = central/region/store/ecom | 增 **`consignment`**（寄售仓），并加 `owner_org_id`（默认货主） |
| 库存 | 只记 `warehouse_id` + 批次 | 加**货主维度** `owner_org_id`，支持"产权 ≠ 物理" |
| 单据 | 无货主字段 | 库存类单据统一带 `owner_org_id` |
| 渠道商 | `dealers` 独立表，无门户 | 挂 `partner_id` + 建组织 + 门户（与模块 02 的往来单位统一衔接） |
| 成本 | 只有 `cost_std` 一个静态字段 | 成本流转 + 移动加权 + 毛利（模块 09） |
| 编码 | 前缀 + 日期 + 存在性探测 | 规则表驱动、按单据类型与组织配置（模块 06） |
