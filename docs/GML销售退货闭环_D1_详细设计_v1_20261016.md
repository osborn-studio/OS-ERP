## 一、缺陷的形状：**退货只有动作，没有依据**

验收侧实测（`audit-erp-results.json` 第 5 条）：

| 观察项 | 实测值 |
|---|---|
| 已发数量 | **94** |
| 本次退货数量 | **189**（= 94×2+1） |
| HTTP 语义 | **200 / code 0 / success true** |
| 入库 `unit_cost` | **9999**（直接取请求体 `price`） |
| 原 SO 应收 `amount` | 退货前 13355.52 → 退货后 **13355.52**（**未变**） |

三件事都没有依据：

1. **退多少没有依据** —— 明细不绑 `sales_order_items`，也不查"该行已发多少、已退多少"；
2. **按什么成本回库没有依据** —— `unitCost: price`，而 `price` 是请求体里的数；
3. **账怎么变没有依据** —— 函数体内没有任何 `ar_documents` 逻辑，只推了一下单据状态。

三件事有一个共同的形状：**每一件都在"接受输入"，没有一件在"核对事实"。**

## 二、修复：给每个动作接上一个"事实来源"

| 动作 | 事实来源 | 落点 |
|---|---|---|
| 能退多少 | `sales_order_items.shipped_qty` − 该来源行的**累计已退量** | `planReturn()` 的 `RETURN_EXCEEDS_SHIPPED` |
| 退的是哪一行 | `sales_return_items.order_item_id`（必填） | `SOURCE_REQUIRED` |
| 按什么成本回库 | 该订单该 SKU 的**原出库流水**（按批次加权） | `outLotsOf()` → `unit_cost` |
| 单价按什么算 | 订单行**净单价**（`amount / qty`，含行折扣） | `planReturn()` 的 `netPrice` |
| 账怎么变 | 该订单的应收单**未核销余额** | `offsetAr()` → `ar_offset_amount` / `refund_due` |
| 重放怎么办 | `idempotency_key`（非空唯一） | `createSalesReturn()` 的先查 + 唯一索引兜底 |

### 2.1 判据只有一处

全部集中在 `server/lib/returns.js` 的 `planReturn()`。
**销售退货（`routes/sales.js`）与门店退货（`lib/pos2.js`）共用它** ——
验收侧 §13.2 明确要求"销售退货与门店退货两处都要有上限"，
而两处各写一套判据必然分叉（本项目已经吃过很多次）。

### 2.2 "校验过的值就是写库的值"

`planReturn()` 返回的行**就是最终落库的行**：路由与门店退货都不再二次解析请求体。
`applyStockIn` 的 `unitCost` 直接取计划里的值 ——
这是"不得采信客户端价"的**结构性保证**，而不是在某个分支里加的 `if`。

## 三、退货成本追溯口径（验收侧点名要求）

### 3.1 一句话口径

> **退货入库成本 = 该订单该 SKU 在原出库流水中的、按批次加权的出库成本。**

### 3.2 取数方式

```sql
SELECT IFNULL(batch_no,'') AS batch_no,
       SUM(qty) AS qty,
       SUM(amount) / NULLIF(SUM(qty),0) AS unit_cost
  FROM inventory_transactions
 WHERE doc_type='SAL_OUT' AND counterparty = <销售订单号> AND sku_id = ?
 GROUP BY IFNULL(batch_no,'')
 ORDER BY MIN(id)
```

为什么这样取：

- **用 `counterparty`（订单号）而不是关联发货单**：出库流水里记的就是订单号；
  一张订单可能多次发货、跨多个仓，按"订单 + SKU + 批次"汇总才是"这批货当初出库花了多少钱"；
- **按批次加权（`SUM(amount)/SUM(qty)`）而不是取某一条的 `unit_cost`**：
  同一批次可能分多次出库、每次成本不同（移动加权），取任一条都会偏；
- **按批次回库**（而不是回一个空批次）：货从哪一批出去、就回哪一批，
  否则库存账面会凭空多出一个批次，而"批号追溯"从此断链。

### 3.3 批次余量不足时的退化

若**原出库批次的可退余量**（该批次出库量 − 已按该批次退过的量）不足本次退量，
剩余部分退化到**仓库当前加权成本**，并显式标注 `cost_source='current_fallback'`。

**为什么不是直接拒绝**：现实里存在"单据缺失/批次串号"的历史单，
一刀切拒绝会让这些单永远退不了。但**退化必须可见** ——
`createSalesReturn()` 的返回里带 `cost_sources` 数组，调用方能看出哪几行走的是退化口径。

### 3.4 无来源退货（walkin）

没有来源行的退货（顾客没带小票、老单据缺失）**不是禁止，而是显式标注**：

- `source_type='walkin'` —— 它**不参与来源追溯**、不占用任何订单行的退量上限；
- 成本取仓库**当前加权成本**（**不是售价**，更不是客户端传的值）；
- 单价由调用方给出（本就没有订单可依据），但**必须 ≥ 0**；
- **不允许**一张"有单退货"里混进没有来源行的明细 —— 那等于给上限开一扇后门（`SOURCE_NOT_ALLOWED`）。

## 四、应收口径：冲减 + 待退款登记（不生成负数应收）

```
退货额 X  ≤  该应收的未核销余额  →  全额冲减：ar.amount -= X
退货额 X  >  未核销余额（说明这部分已经收过款了）→
    冲减到未核销余额为 0；差额登记为 refund_due（待退款）
```

**为什么不生成"红字负数应收"**：账龄与客户汇总用的是 `amount - allocated_amount`，
而两处对负余额的处理并不一致（逐笔账龄会 `if (bal <= 0.005) continue` 跳过负值，
按客户汇总却会照算）—— 引入负数应收会让这两处口径当场分叉，
而那种分叉正是本项目反复吃过的坑（"同一份判据两个实现"）。
宁可用"冲减 + 待退款登记"，把口径保持在"应收金额只有一个方向"上。

**留痕**：退货单上记 `ar_id`（冲了哪张）+ `ar_offset_amount`（冲了多少）+ `refund_due`（待退多少），
应收单的 `updated_at` 随冲减更新。三处合起来可完整还原"这次退货动了哪笔账"。

**本次未做**：`refund_due` 只做**登记**，退款单（走收款单/付款单反向流程）尚未实现。
这是有意的范围裁剪 —— 见§八，在回执里也已如实说明。

## 五、迁移 028：加列 + 存量回填（不猜）

| 表 | 列 | 回答的问题 |
|---|---|---|
| `sales_returns` | `source_type` | 有单退货 / 无单退货 |
| `sales_returns` | `idempotency_key` | 同一次请求重放不得重复冲减（非空唯一） |
| `sales_returns` | `ar_id` | 冲的是哪张应收 |
| `sales_returns` | `ar_offset_amount` | 冲了多少 |
| `sales_returns` | `refund_due` | 应收不够冲的那部分 = 待退款 |
| `sales_return_items` | `order_item_id` | **来源行绑定**（退量上限的唯一依据） |

索引：`idx_sales_returns_idem`（部分唯一，`idempotency_key IS NOT NULL`）、`idx_sales_return_items_src`。

### 存量回填的两条原则

1. **`source_type`**：`order_id` 为空 ⇒ `walkin`，否则 `order`；
2. **`order_item_id`**：按 (退货单的 `order_id`, `sku_id`) 唯一匹配回填；
   **匹配不上就留 NULL —— 不猜**。

> 猜错会让"历史已退量"算到别的行头上，而那种错在界面上完全看不出来
> （退量上限从此对不上，且没有任何报错）。
> 实测：cosmetic 23 行中 18 行匹配上、food 38 行中 18 行匹配上（另 20 张是门店 walkin 单，本就没有来源行）。
> **这 5 行存量明细的来源行永远无法追溯** —— 这是有记录的缺口，也是"迁移不猜"的代价。

### seed 必须同步（否则重建不可复现）

`db/seed.js` 的退货段同步写入 `source_type` 与 `order_item_id`，
**并把退货入库成本从 `it.price`（售价）改为追溯原出库成本**。

原因要记清：迁移的回填只对**迁移执行前**就存在的行有效，
而整库重建的顺序是「建表 → 迁移 → 灌数」——
seed 造的行永远等不到那次回填。若 seed 不写，重建库与线上库从此不一样。

## 七、门店退货（A09b）

`lib/pos2.js` 的 `storeReturn` 原本已经做对了两件事：
**成本取门店仓当前成本（不是售价）**、**退款写负数 POS 单自然冲减班次应收**。
它缺的是**上限**。

修改：**关联了订单（`order_id`）的门店退货，走同一个 `planReturn()`** ——
上限、来源行绑定、成本追溯全部继承；没关联订单的仍是 walkin 分支（成本取当前成本）。

`ReturnError` 会被转成 POS 自己的错误形状（`bad()`），保持该路由既有的错误契约。

## 九、对外行为变更

| 变更 | 影响 |
|---|---|
| `POST /api/sales/returns` 明细必须带 `order_item_id`（有单退货时） | 旧调用方（不传来源行）会被 400 拒绝 —— **这是有意的破坏性变更**，因为不绑来源行就等于没有上限 |
