## 一、一句话

**`report_lines` 是会计政策，而改它的三个接口什么痕迹都不留。**
删除是**物理删除**，留下的只有一句 `report_line:37` —— 删完就查不出"删了什么"。
这一批把它变成一个有定义、有约束、**可重放**的口径系统。

```text
改前：DELETE FROM report_lines WHERE id=?
      audit(req, { action: 'finance.report.line.delete', target: 'report_line:37' })
      （37 已经不存在了；服务重启一次 id 还会被另一行复用）

改后：deleteReportLine(db, id, { reason, actor })
      ├─ 被小计行引用        → 409 LINE_IN_USE
      ├─ 危险改动没写理由    → 400 REPORT_CONFIG_REASON_REQUIRED
      └─ 同事务写一条只追加的 report_config_audit_log（**整行快照** snapshot_before）
     读取：listReportConfigAudit(db, …) —— 把差分摊成「字段名 + 改前 + 改后 + 是否危险」
```

## 二、摸底查出的七个真实缺口（这一批真正的起点）

这一批的起点是 `034_report` 留下的一句承诺：「会计政策，**可审计、可追溯改过什么**」。
摸底之后发现那句话的三个字（**改过什么**）一个都没有兑现，而且不止一处。

### 缺口 ①：报表口径在界面上**根本改不了**

三个写接口（`PUT /reports/defs/{code}` / `POST /reports/lines` / `DELETE /reports/lines/{id}`）
存在了至少两个批次，`openapi.js` 里登记着，而前端**一个调用点都没有**。
`db/seed.js` 里"为什么重建必须清 `report_lines`"的注释写的理由正是「**它们在界面上可改**」。
→ 与批次 R 的缺口 ③（`settings` 有接口没界面）是同一个病的第二次发作。

### 缺口 ②：`report_lines` **每次服务启动都被整段重建**

`seedReport` 在 `bootIndustry` 里无条件调用（不像 `seedAll` 有 `needSeed` 闸门），
而它第 2 步是 `DELETE FROM report_lines WHERE report_code=?` 再整段重插。
于是每重启一次服务：自增 `id` 换一代（实测 `1~44` → `45~88`），
且**人在界面上改过的口径被静默覆盖回去**。

### 缺口 ③：删除只留一个自增 id —— 物理删除之后"删了什么"不可考

`DELETE /reports/lines/{id}` 留下的唯一记录是 `target: 'report_line:37'`。
37 删完就不存在了；更糟的是它会被下一代的另一行**复用**，于是日志看起来指向一个真实存在的行。

### 缺口 ④：保存只留 `line_no` —— 三种截然不同的改动留下同一条记录

改科目区间、改 `sign`、加 `only_direction`，记录完全一样。

### 缺口 ⑤：报表定义只有 `basis` 有痕

`cover_categories`（必须穷尽覆盖的科目大类）改了无痕 —— 而少覆盖一个大类就是少一块钱。

### 缺口 ⑥：改行号撞车抛原始约束错，且**没有与删除同一条引用保护**

`UNIQUE constraint failed: report_lines.report_code, report_lines.line_no`；
而"改行号等于删掉旧行号"，却没有 `LINE_IN_USE` 那一条。

### 缺口 ⑦：留痕写在**路由层**

通用 `audit()` 吞异常、不同事务、只在路由这一层 —— 从 `lib` 直接调的路径（种子）自动没有痕。

## 三、六条口径

### 口径 1：危险是**差分驱动**的，不是"这一行危险"

这是与批次 R **最重要的一处不同，不是照抄**：

| | 批次 R（配置） | 批次 S（报表口径） |
|---|---|---|
| 危险的载体 | **键的属性**（`SETTING_RULES[key].is_danger`） | **这次改动动了哪个字段**（`changed_fields ∩ REPORT_CONFIG_DANGER_FIELDS`） |
| 为什么 | 一个键的含义是固定的（`closing_profit_subject` 永远是会计政策） | 同一行改 `line_name` 是展示、改 `subject_range` 是会计政策 |
| 规则条数 | 每个键一条 | **一条**，四种动作共用 |

一条统一规则覆盖四种动作，靠的是 `changed_fields` 的定义：

| 动作 | `changed_fields` | 危险？ |
|---|---|---|
| `baseline` | `[]` | 否（它不是谁的动作） |
| `create` | **全部字段** | **是**（新增一行会让报表多一块） |
| `delete` | **全部字段**（都消失了） | **是**（不可逆） |
| `update` | 真正变了的列 | 只有动了危险字段才危险 |

反面：只改 `line_name` / `display_no` / `level` / `order_no` / `remark` **不需要**理由 ——
它们不进任何金额。要求给它们写理由只会训练人写"调整显示"，
而理由一旦可以随便填就退化成噪音（与批次 R 拒绝给 `reset` 自动补一句"恢复默认值"同一条理由）。

危险字段集（**全项目唯一判据**，`lib/report-config-audit.js` 的 `REPORT_CONFIG_DANGER_FIELDS`）：

- `def`：`report_code` / `basis` / `cash_subjects` / `cover_categories` / `status`
- `line`：`report_code` / `line_code` / `line_no` / `line_type` / `subject_range` / `sign` / `only_direction` / `subtotal_expr` / `is_fallback`

### 口径 2：日志存**整行快照**，不是字段差分

期间审计链（批次 Q）存"四个指针字段的改后值"，因为期间的状态就是四个字段。
报表口径的状态是**一百多行**，差分表达不了 `create` / `delete`，
而 `delete` 恰恰是最需要留完整内容的那一种。

一份快照同时解决三件事：**删除后仍答得出"删的是什么"**、重放能重建整张表、"改前/改后"能并排显示。
代价是存储（一百多行 × 每行几百字节），换来的是"会计政策的历史"。

### 口径 3：唯一写入点落**在写函数里**，不在路由里

`lib/report.js` 的三个写函数（`saveReportDef` / `saveReportLine` / `deleteReportLine`）
在**同一个事务**里调 `logReportConfigChange`，而后者**当场断言** `db.inTransaction`。
路由层那三句通用 `audit(req, …)` 删掉 —— 它只是同一件事的第二份、且更差的说法。

### 口径 4：可重放 —— 从空状态重建整张表

```text
从空状态开始，按 id 顺序应用每一条日志，
得到的必须是今天 report_defs + report_lines 的全部内容（逐行、逐字段）。
```

两条路径出处不同（现状来自 `INSERT`/`DELETE`，历史来自唯一写入点），所以它抓得到
"改了没记""记了没改"。**盲区划清**（批次 P 的教训：先问两条路径共享什么）：

- 两者共享**身份键**（`report_code` / `line_code`）⇒ 由 `REPORT_CONFIG_FIELD_GAP`
  （表列必须全被 `SNAPSHOT_FIELDS` 声明）与 `REPORT_CONFIG_AUDIT_SNAPSHOT_MISSING`（快照必须整份）从侧面守着；
- 抓不到"既没改库也没写日志" —— 留痕上的这种情形不存在（没有状态可藏）。

### 口径 5：两个闸门互斥 —— 一条断言只被一个原因守着

"现状里有这一行、历史里没有"与"历史里有、两边的值对不上"都会让重放失败，但它们是**两种不同的病**：

- `REPORT_CONFIG_UNTRACKED` —— 初始化没跑 / 有人绕过写入点插入；
- `REPORT_CONFIG_AUDIT_DESYNC` —— 改了没记或记了没改（**只比对至少有一条历史的行**）。

二者互斥。如果两条都报，排障的人要在两条断言之间猜谁是真因。

### 口径 6：初始化入口是运行时的 `ensureReportConfigTrail`，不是迁移

迁移 039 **只建表**。基线与"补齐"统一交给运行时的一个入口，与批次 R 的 `ensureSettings` 同构，理由也一样：

- **升级路径与重建路径走同一条代码**（重建会把口径与日志一起清掉，之后由它重新补基线）；
- 迁移里**不需要抄一份字段清单**（迁移是 CommonJS、定义是 ESM）。

调用点两处：`bootIndustry`（每次启动 / 切行业）与 `seedReport`（口径刚写完那一刻，**必须早于它自己的关账**）。

## 四、数据结构：`report_config_audit_log`

| 列 | 为什么非它不可 |
|---|---|
| `target_type` / `report_code` / `line_code` | 记的是**一张报表的定义**还是**其中的一行**，以及身份键。`line_code` 对 def 记录为 NULL。**不做外键**（报表或行可以整张消失，历史必须留下） |
| `action` | `baseline` / `create` / `update` / `delete`（唯一写入点认的名字） |
| `action_label` | 动作的**当时**中文名，刻意冗余落库：日志是不可变事实，措辞不该随后续代码改名而变 |
| `snapshot_before` | 改动前**整行 JSON**。`delete` 记录的它是这一行唯一还能被查到的地方 |
| `snapshot_after` | 改动后**整行 JSON** |
| `changed_fields` | JSON 数组，`update` 时给出真正变了的列。界面靠它显示"改了哪几列"，判据靠它算危险等级 |
| `is_danger` | 这次改动**当时**是否危险（**必须在日志里冻结**：危险字段集以后会调整，而"这次改动当时该不该写理由"是历史问题） |
| `reason` | 危险改动必填 |
| `actor_source` | `web` / `mcp` / `script` / `system` —— 区分"人改的"与"初始化补的" |

索引三条：`(target_type, report_code, line_code, id)` / `(created_at)` / `(action, is_danger)`。
迁移的 `verify()` 守四条结构不变量：`is_danger ∈ {0,1}`、`target_type ∈ {def,line}`、
**快照完整性**（`create` 有 after、`delete` 有 before、`update` 两侧都有）、`delete` 必须带理由。
**不加权限点**：改口径限 `finance.report.config`、看历史复用 `finance.report.view`
（能看报表的人已经能看到口径本身），与批次 Q / R 同一条理由。

## 六、探针八条（`auditReportConfigTrail`）

| # | code | 判据 | 只读什么 |
|---|---|---|---|
| ① | `REPORT_CONFIG_AUDIT_UNKNOWN_ACTION` | 动作名必须是代码认识的 | 日志 |
| ② | `REPORT_CONFIG_AUDIT_SNAPSHOT_MISSING` | `create`/`baseline` 有 after、`delete` 有 before、`update` 两侧都有 | 日志 |
| ③ | `REPORT_CONFIG_AUDIT_SNAPSHOT_BROKEN` | 快照必须是可解析的 JSON（坏的那条会被重放**安静地跳过** = "这条记录不算数"） | 日志 |
| ④ | `REPORT_CONFIG_AUDIT_REASON_REQUIRED` | 危险改动必须写理由 | 日志 |
| ⑤ | `REPORT_CONFIG_UNTRACKED` | 现状里有行、历史里一条都没有 | 日志 + 现状 |
| ⑥ | `REPORT_CONFIG_AUDIT_DESYNC` | 有历史的行重放不出来（**与 ⑤ 互斥**） | 日志 + 现状 |
| ⑦ | `REPORT_CONFIG_LINE_ORPHAN` | 有一行口径挂在不存在的报表上 | 现状 |
| ⑧ | `REPORT_CONFIG_FIELD_GAP` | 表里有列没被 `SNAPSHOT_FIELDS` 声明（**安静扩大的盲区**） | `PRAGMA table_info` + 清单 |

**第 ⑧ 条是"显式代价"的机械守卫**：以后给 `report_lines` 加一列而没人登记它，那一列就
既不在留痕范围、也不在重放比对范围 —— 那是一个不会报错、只会慢慢变大的洞。
「唯一出处」必须能被机器核对，不能只写在注释里（批次 P 的教训）。

八条全部接在 `auditReport` 的**第 ⑫ 条**上 ⇒ **关账前置会检查它们**
（与 ⑩ 期间链、⑪ 配置链同一条理由：只在用户点开某一期时才跑的探针等于不跑）。
**这一条不做初始化** —— `auditReport` 是只读自证，在"检查"里写库会让"没补基线"这件事被检查本身掩盖掉。

## 七、界面：报表口径页（`/finance/report-config`）

```
报表口径                                                   [资产负债 23 行][现金流量 16 行][利润 6 行]
报表结构（科目区间 / 方向口径 / 小计表达式）是会计政策，不是展示配置 —— 改一行能让同一份账算出不同的利润。
  每一次改动都留一条只追加的变更记录（含改动前后的整行快照），可从日志重放出当前口径。

┌ 报表口径变更链自洽：核 47 条记录 / 定义 3 张 / 口径行 44 行，重放日志可得到当前口径。 ─┐
└──────────────────────────────────────────────────────────────────────────────┘

[报表口径 23]  [变更历史 47]

行号 行次 行名称           类型    科目区间 / 小计表达式   方向 系数 兜底
1    —    货币资金         科目行  1001~1002              —    1    —    修改 删除
8    —    流动资产合计     小计    1+2+3+4+5+6            —    1    —    修改 删除
```

页面上有一段**前端算出来的判断**：「这次会被判为**风险改动**还是**展示改动**」。
它的判据来自服务端（`/reports/config/meta` 的 `danger_fields`）——
**只有一份定义**，所以两边不可能分叉；而真正的闸门在服务端，界面判断错了也放行不了。
这一处正是"自动化断言管得住有没有、管不住对不对"（铁律 9）的地方，所以它有人眼看过的截图。

## 九、边界（如实记）

- **`report_lines` 没有"版本"概念**：改口径是就地改，历史只在日志里。想让库回到 seed 那份定义，
  走整库重建（`resetDatabase` 会把口径与日志一起清掉）；
- **`SNAPSHOT_FIELDS` 是一条显式代价**：以后给两张表加列必须同时登记进去，否则那一列不留痕
  （由探针 ⑧ 守着，所以它不会安静地发生）；
- **只追加，没有删除与归档**：日志没有 UPDATE / DELETE 路径，也没有"导出/归档"入口；
- **`detail` 是 JSON 文本、不做 schema 校验**：它只服务人读与排障，**任何判据都不读它**；
- **`created_at` 精度只到秒**，顺序的唯一真值是 `id`；
- **"半途而废的库"不会被自动修复**：如果口径写到一半崩了（定义写了、口径行只写了一半），
  探针会报出来（`UNTRACKED` / `DESYNC`），修它要走整库重建。**"半途而废"必须可见，不能被"顺手补一条基线"抹平**
  —— 那正是 `ensureReportConfigTrail` 拒绝给"有历史但值不对"的行补基线的原因；
- **⚠️ `report_lines`（报表行定义）变更留痕这一条**：批次 R 把"报表口径变更留痕"记作范围裁剪
  （理由写的是"那是 `audit` 中间件的职责域"）。**第 22 批做的是它的姊妹件、但对象是 `settings`（参数表）**；
  **本批（第 23 批）做的才是"报表口径"本身**（`report_lines` / `report_defs` 的结构变更）。
  两条差别不许含糊：参数表的变更与报表结构的变更是**两个对象、两套危险字段集**；
- **未做**：口径变更的**审批流**（改会计政策要不要走审批）—— 现在只要求写理由；
  口径的**生效时间**（预约生效 / 按期间生效）—— 现在改完立即生效；
  **口径的跨库比对**（三个行业库的口径是否一致）—— 现在没有这个探针。

## 十、这一批真正修掉的东西（一句话版）

**删掉一行口径之后"删了什么"永久不可考** + **三种截然不同的改动留下同一条记录** +
**报表口径每次服务启动都被重建（id 换代、撤销人的改动）** + **一个改不动的界面** ——
换成 **整行快照** + **差分驱动的危险判定** + **一条可重放的不变量（并且它上线后第一次重启就抓到了上面那条缺陷）**。
