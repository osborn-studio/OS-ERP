# GML 总体设计 · 第 0 层：配置底座与策略层

> 版本 v1 · 2026-10-16 · **本文件是"最高层设计"**，模块级详细设计（模块 02–24、批次 A–S）都建立在它之上。
> 数据一律行业中性（美妆版 / 餐饮版 / 服饰版），不含任何真实客户名与品牌名。

---

## 0. 为什么单独成章（成因如实记录）

客户原话：

> "能不能卖由客户来决定，一般都是做一种类型的出库，然后这种出库对于一种类型的财务核算，
> 所以你也一定要地方设供应链参数，比如说出入库单据类型有哪些，是不是允许负库存，能以哪些仓库。等等。
> 简单来讲，**仓库是可以客户自己新建的，出入库单据类型也是客户新建的**，以应对多种情况。"

客户追问了一句关键话：**"这个是很重要的内容，要放进你的整体最高设计里。"**

**我的疏漏（如实写在这里，不让它消失）**：此前本项目只有**模块级**设计文档，**没有一份"总体设计"**；
于是"客户可自建的主数据 + 策略参数"这层东西在文档体系里**没有位置**，
它在实现上就被当成了**各模块各自的附属功能**（谁用谁硬编码）。这就是本层必须单独成章的原因 ——
它不是一个模块，它是**所有单据链共用的地基**。

---

## 1. 分层总览

```
第 3 层  财务核算 · 报表 · 审计
             ↑ 读口径
第 2 层  业务链（采购 / 销售 / 库存 / 制造 / 委外 / 质检 / 门店 / 订货 / 资金）
             ↑ 读单据类型与策略
第 1 层  单据内核（状态机 · 边 · 权限 · 留痕 · 通用流转闸门）
             ↑ 读单据类型登记
第 0 层  ★ 配置底座与策略层 ★（本文件）
             · 主数据（客户可自建）
             · 单据类型主数据（客户可自建）
             · 策略参数（客户可配）
```

**判据（本层存在的理由）**：任何"**能不能……**"的问题（能不能卖、能不能负库存、能不能用这个仓、
这种出库走哪种核算、这类单据要不要审批）都必须在**第 0 层有唯一出处**，
**不得在业务代码里硬编码**。业务代码只允许"读配置 + 按配置执行"。

## 2. 三大支柱

### 2.1 主数据（客户可自建）
组织 / 仓库 / 往来（客户·供应商·经销商）/ 商品与 SKU / 会计科目 / 计量单位 等。

- **仓库**：类型可扩展（总仓 / 区域仓 / 门店仓 / 电商仓 / **不合格仓** / **待检仓** …）；
  可新增、改名、改类型、改负责人、**停用**。
- ⚠️ **不许物理删除**：历史单据与库存流水按 id 引用着它；删除会让历史对不上账。停用即可。
- ⚠️ **停用后新建单据不许再选它**（要有断言守着）。

### 2.2 单据类型主数据（客户可自建）
**业务单据类型**（走内核 `008_doc_kernel` 的那批：采购订单、销售订单、发货单、退货单、对账单…）
＋ **出入库单据类型**（`inv_txn_types`，即"出库单/入库单的类型"）。

每一条出入库类型至少要能回答四件事：
| 字段 | 含义 | 客户语言 |
|---|---|---|
| 方向 | 入 / 出 / 双向 | "这是一种出库" |
| **是否受可售性闸门约束** | 这种出库是否只能出"可售"的货 | "这种出库能不能出待检/不合格的货" |
| **财务核算口径** | 这种出库走哪种核算 / 哪个科目 | "一种出库对应一种财务核算" |
| 启用状态 | 启用 / 停用 | "新单据还能不能选它" |

⚠️ **"是否受可售性闸门约束"这条必须从主数据读**，不能像现在这样写成代码里的一个集合 ——
否则客户新建一种出库类型时，**没有任何地方能声明"这种出库要不要守可售性"**，
只能改代码，这正是本层要消灭的东西。

### 2.3 策略参数（客户可配）
已有机制：`server/lib/settings.js` 的 **`SETTING_RULES`**（配置键的**唯一出处**，16 键 / 7 组 / 6 个危险键），
前端 `/system/settings`，**未登记键读写双拒**，**危险键改动必须写理由**，改动进留痕（批次 R）。

- **已有正面例子**（说明这层本来就该有，只是不全）：`ar_source_of_truth`（应收生成口径，默认 `SO`）、
  `fiscal.start_month`（会计年度起始月）、期末结转目标科目、报价审批阈值、交班长短款容忍阈值……
- **本层要补齐的**：**供应链参数组** —— 至少包含
  - **是否允许负库存**
  - **能以哪些仓库**（"某个操作 / 某类单据只能用哪些仓" —— 见 §7 待客户确认）
  - 以及与 2.2 联动的"**出库类型 ↔ 财务核算**"对应关系
- **反面例子（本层缺位的实证，必须记住）**：`block_pending_qc`（未检验成品能不能卖）
  现在是底层参数表里的一个键、**默认 0**，而**客户在界面上根本看不见它** ——
  一条决定"能不能卖"的策略，没有任何一处让客户知道它存在。这就是"参数没有唯一出口"的后果。

## 3. 每条配置必须满足的七条不变量

1. **唯一出处**：一处定义、多处引用。同一件事**不许有两份实现**（本项目最贵的一类缺陷）。
2. **默认值 = 上线前的实际行为**：新增开关时若默认值与现状不一致，
   等于**静默改变所有存量客户的行为**。必须有断言证明"默认值 = 改动前的实际行为"。
3. **可停用、不可物理删除**：历史单据引用着它。
4. **改动留痕；危险项必须写理由**：改了就动账 / 动库存 / 动口径的键，`is_danger: true`，强制理由。
5. **未登记键读写双拒**：不能出现"读不到就用默认值"的静默兜底（那个默认值 = 没人管的配置）。
6. **三行业一致**：同一能力在三套库（美妆版 / 餐饮版 / 服饰版）都要成立。
7. **客户新增的数据不得让守卫误红**：守卫是为"**只改一处**"设的，不是为"禁止新增"设的 ——
   客户新建类型后，**文案/口径缺省必须能回落到客户填的名字**，而"代码里写了一个字典里没有的码"
   仍然必须判红。

**第 2 条与第 7 条是本层最容易出事的两个地方**，都要求配**反例**（先红后绿）才算做完。

### 3.0 标记约定（2026-10-16 新增；由 fix-stmt 提议、team-lead 采纳）
本文件与**所有口径类文本**（设计/交付说明/报告）中：
- 凡**未实测**的条目，一律带 **`[未实测]`** 前缀；
- 实测过的写 **`[已实测 · <证据>]`**（证据 = 命令 + 计数或原文 + 落点）。

**理由**：起草人**不必先跑一遍才能提方向**（保留"先给方向"的效率）；**拍板人一眼能看出哪些还不能对外**；下一个人**知道该先验哪条**，而不是默认全都验过。
**一句话**：**"未实测"不是错误，"未标注"才是。**
（本条的来历：一条"在 `/tmp` 影子项目里跑反例"的配方，起草时是**按原理写的**，被升格为口径时**没有任何地方标注它没实测过** —— 实测后才发现"真正会炸的是数据库（指到空目录 ⇒ `no such table`），而不是模块系统"。）

**标记的生命周期（同轮补，fix-stmt 提、team-lead 采纳）**：`[未实测]` 必须带**归属或触发条件**，否则它会变成永久标签 —— 读的人分不清"**待验**"与"**已知验不了**"，比不标更糊。二选一：
- `[未实测 · 待 <谁> 复跑]`（有人认领）；或
- `[未实测 · 依赖 <外部条件>，本轮不验]`（**"不验"是结论，不是遗漏**）。

⇒ 于是只有三态：**已实测 / 待验（有人）/ 不验（有理由）**。交付前扫一眼即可决定放不放行。

## 4. 硬规则：判据怎么证明配置真的被接线

一条配置**被登记**不等于**被执行**。证明方式只有一种：

> **把这条配置改成另一个值 ⇒ 系统行为必须真的跟着变。**

只写"我在配置中心加了一个键"**不算完成**；必须给出"改了这个键 ⇒ 某条断言从红变绿 / 从绿变红"的实测。
（反面教材：`SETTING_RULES` 里已有 `wired: false` 的键 —— 登记了但没接线。）

## 7. 口径裁决记录（客户已拍，2026-10-16 23:23）

### 7.1 「能以哪些仓库」= **某一类单据进客户指定的仓库**（已拍）
⇒ 落法：**「单据类型 → 允许的仓库集合」**的配置（一个白名单）。
- **默认值 = 不限**（= 改动前的实际行为，满足 §3 第 ② 条）。
- **强制点在"选仓处"**（建单 / 指定仓库时）：选了不在许可集里的仓 ⇒ **拒绝**，给人话 + 稳定错误码。
- 与"不合格品必须进不合格仓"是**同一条控制**的两个用例（那条用同一张配置表达，不另造机制）。

### 7.2 「一种出库类型 → 一种财务核算」的粒度 = **一套凭证模板**（已拍）
⇒ 不是"一个科目"，而是**一套凭证模板**（借贷方向都可以不同）；并且**模板本身允许在后台自定义**。
⇒ 落法（先查清现状再落地）：**「出入库类型 → 凭证模板」的映射** + **模板的维护入口**。
⚠️ **先复用既有的凭证生成机制**（现有的 `biz_type` / 科目 / 模板结构），**不要新造第二套**；
若结论是"必须新造模板实体"，先出设计结论再动手。

### 7.3 人员权限 / 单据字段级控制 —— **本轮不做，只打标记（客户明确指示）**
> 原话："权限是要有的，但这个是**权限控制和数据安全**的范畴，人员对单据和数据有无能力改写，
> 包括单据上字段的控制等，我认为**先弄一个演示 demo，不需要先考虑那么多**，你可以**先放着后者标记**。
> **未来真的到生产环境要做的。**"

⇒ 记入 **「未来生产环境」待办**（不是本轮的缺口）：**行级/字段级的数据权限**（谁能改哪张单的哪些字段）。
本轮的权限仍是**接口级权限点**（`requirePerm` / 内核边的 `perm_code`），**不扩展到字段级**。

### 7.4 业务单据类型（采购订单、销售订单这类）要不要也让客户自建？
**本轮不做**（属内核语义变更：状态机 / 边 / 权限都在内核里写死）。本层先把**出入库类型**这条打通；
将来若要做，必须连带"客户自建的类型 → 状态机 → 边 → 权限"整套，不是加一行数据。

### 7.5 `block_pending_qc`（全局）与"成品启用质检"（商品属性）并存时的优先级
**商品属性优先（更细），全局参数作为缺省** —— 待最终确认（当前实现按此口径，默认都是"不拦"）。
