# 伴圆AI原生ERP 本地安装手册

适用版本：2026年10月24日修订。面向实施顾问、维护人员和演示人员。本手册分两条路径：**生产模式**（默认，空库、首次用 bootstrap 建管理员、不含任何样本数据）和**演示模式**（需显式设置 `GML_RUNTIME_MODE=demo`，才会灌入虚构样本与演示账号，见第九章）。

本系统仍处于开发阶段，**没有通过生产上线验收**：下文的生产步骤描述的是当前代码的真实行为（依据 ADR-0001、0002、0003、0008、0009、0016、0018、0019），不是已验收的商用承诺。恢复、升级回退和容量的数字必须在目标主机上实测后才能引用，见第七章末的边界说明。美妆连锁、连锁餐饮为业务验收范围，服装不在范围内。

## 一 安装前准备

| 项目 | 要求 |
|---|---|
| 运行环境 | Node.js 22.x LTS，安装时保留 npm；不使用 Node 18、20、24 或其他主版本 |
| 浏览器 | 能运行现代 JavaScript 的浏览器，例如 Chrome、Edge、Safari |
| 网络 | 首次安装需访问 npm 官方仓库及原生模块下载站点；不能保证断网首次安装 |
| 本地空间 | 建议预留至少 2GB，安装目录须可读写 |
| 数据库 | 无须单独安装数据库，SQLite 文件存放在本副本 data 目录 |
| 已验证平台 | 本次安装验证以 macOS Apple Silicon 为准；Windows、Linux 提供脚本和步骤，未做对应实机验收 |

从 Node.js 官方网站获取 22.x 安装程序。安装完重新打开终端，运行以下命令，第一行须是 v22 开头，第二行须返回 npm 版本号。

```bash
node -v
npm -v
```

不要把原机的 node_modules 复制到其他系统。better-sqlite3 包含原生模块，不同系统、CPU 和 Node 主版本不通用。首次安装会按当前电脑下载或编译对应版本。

## 二 解压及目录检查

完整解压 ZIP 到普通本地目录，不要在压缩包预览窗口中直接执行。避免同步盘、只读目录、系统保护目录和过长路径；目录名允许中文及空格。

| 目录或文件 | 用途 |
|---|---|
| src | React 前端完整源码 |
| server | API、业务服务、数据库结构和迁移、种子数据、MCP 服务 |
| scripts | 安装维护、代码检查、回归测试和重新打包脚本 |
| reusable | 可复用模块及相关说明 |
| public 和 dist | 静态资源及已构建前端；接收者不必先编译 |
| docs/本地交付 | 安装、操作、演示、开发及安全说明原文和验收记录 |
| 手册 | 可离线打开的 HTML 手册，双击 install.html 即可 |
| MANIFEST.json | 发布文件的 SHA256 清单 |
| package-lock.json | 锁定依赖版本，安装使用 npm ci |

包中不包含原机业务数据库、实际密钥、环境配置、录屏、日志、Git 历史或 node_modules。生产模式（默认）首次启动只建空库结构，不生成任何商品、订单或账号；样本库只在显式演示模式下生成。

## 三 运行模式（先读这一章）

系统用 `GML_RUNTIME_MODE` 区分三种用途；**缺省就是 production**（ADR-0001）。

| 模式 | 用途 | 数据 | 账号 |
|---|---|---|---|
| production（缺省） | 真实业务 | 空库，只有结构与系统配置；不造数 | 只有 bootstrap 创建的管理员 |
| demo | 演示与方案验证 | 灌入虚构样本 | 演示账号（见第九章） |
| test | 自动化测试 | 临时目录里的合成数据 | 测试自建 |

要点：

- 数据库在首次初始化时写入模式标记。**生产库不能被切换成演示模式重置**，演示库也不能被当成生产库接管；模式不符时服务拒绝打开该库。不要靠手工改标记绕过。
- 生产模式下，下列能力被整体关闭，访问返回 HTTP 503 与业务码 `FEATURE_DISABLED`（ADR-0002）：公开商城 `/api/mall`、奇门网关 `/api/qimen`、OMS 模拟同步/发货/退款、IM 同步与自检，以及 **MCP 与 Agent 凭据管理 `/mcp`、`/api/mcp`**。没有环境变量可以绕过；界面上可能仍能看到这些入口，点击会得到 503。
- 所有读写数据库的命令都要求**绝对路径**的 `GML_DATA_DIR`，不会隐式使用代码副本里的 `data/`（ADR-0001、ADR-0019）。通过 `local-manage.mjs` 启动时，该目录就是 `<实例目录>/data`。

## 四 安装与启动

### 4.1 macOS

1. 双击 install.command，出现 Ready 表示依赖安装完成。
2. **先完成第五章的管理员初始化**，再双击 start.command。生产模式下没有任何登录账号，不初始化就无法登录。
3. 默认访问 http://127.0.0.1:3001/login。保持启动终端窗口开启；停止按 Ctrl+C，日后再次启动数据保留。

脚本被系统拦截时，先确认来源与校验结果，再允许打开。也可在终端进入解压目录运行第 4.3 节命令。只有提示没有执行权限时，才对本包脚本添加权限：

```bash
chmod +x install.command start.command backup.command
```

### 4.2 Windows

安装 Node.js 22.x 并加入 PATH，完整解压后双击 install-windows.bat，完成第五章的初始化后双击 start-windows.bat。也可在 PowerShell 进入解压目录执行 4.3 的 node 命令。此路径尚未在 Windows 实机执行；遇到编译工具错误，先检查 Node 是否确为 22.x 及下载站点是否可达，不要关闭 TLS 校验。

### 4.3 Linux 与命令行通用

```bash
node scripts/local-manage.mjs setup
node scripts/local-manage.mjs start --no-browser
```

`local-manage.mjs` 只接受 `setup`、`start`、`doctor`、`backup` 四个子命令，可选参数为 `--no-browser` 与 `--instance=/绝对目录`。`setup` 需要联网安装运行依赖（`npm ci --omit=dev`），并确认 `dist/index.html` 存在。Linux 路径未在本次环境实机验收。

Dockerfile 与 docker-compose.yml 随源码提供，属 IT 可选部署路径：容器以 `GML_RUNTIME_MODE=production`、`GML_DATA_DIR=/data` 运行，**必须**自行提供强随机 `GML_JWT_SECRET`（缺失或为公开值时服务拒绝启动）。该路径未在本次环境实机验收。

## 五 生产初始化

按顺序做。每一步都不会创建样本数据。

### 5.1 选定实例目录

一个企业 = 一个实例目录 = 一份 `data/`、一份 `.local/config.json`（端口与签名密钥，权限 0600）、一份 `backups/`。实例目录必须是**绝对路径**，相对路径被拒绝；不指定时就是本代码副本的根目录。建议放在代码副本之外，便于升级时替换代码：

```bash
export INSTANCE=/srv/erp/company-a        # 示例路径，按实际替换
node scripts/local-manage.mjs setup --instance=$INSTANCE
node scripts/local-manage.mjs doctor --instance=$INSTANCE
```

`doctor` 输出里的 `instance`、`dataDirectory`、`backupDirectory` 三项说明当前实例落在哪里；Node、SQLite 或前端检查失败时退出码非零。`setup` 之后实例的 `data/` 还是空目录，库文件在首次启动或 bootstrap 时才建立。

### 5.2 创建首个管理员（bootstrap）

使用 `scripts/bootstrap-admin.mjs`（ADR-0003）。必须显式设置 `GML_RUNTIME_MODE=production` 与绝对路径 `GML_DATA_DIR`，并把 `GML_DB` 置空；密码**只能**通过非终端的标准输入传入一行，不接受命令行参数，也不接受环境变量。

```bash
python3 -c 'import getpass,sys; sys.stdout.write(getpass.getpass("首次管理员密码: ")+"\n")' |
  GML_RUNTIME_MODE=production GML_DATA_DIR=$INSTANCE/data GML_DB= \
  node scripts/bootstrap-admin.mjs \
  --industry=cosmetic --company-code=MY_COMPANY --company-name='企业名称' \
  --username=owner --name='管理员姓名'
```

参数逐项如下（查看用法：`node scripts/bootstrap-admin.mjs --help`）：

| 参数 | 含义 |
|---|---|
| `--industry` | 必填，`cosmetic`、`food` 或 `apparel`；每个要使用的行业库各执行一次 |
| `--company-code` / `--company-name` | 企业编码与名称，建立单一根组织（本位币固定 CNY） |
| `--username` / `--name` | 管理员登录名与显示名 |

密码规则：至少 16 个字符、最多 72 字节、至少 6 种不同字符、不含控制字符。成功时输出不含秘密的 JSON；失败时只给出稳定的 `BOOTSTRAP_*` 码。只有"用户表为空、没有业务组织、没有一次性标记"的新库才能执行；重复执行会被拒绝，**不会重置已有管理员的密码**，也不要手工删除标记来"找回管理员"。用 `echo '实际密码'` 或把密码写进命令行都会泄露到 shell 历史，不要这样做。命令不会启动服务。

> 注意：不要在任何生产或试点环境使用 `admin / 12345`。那是演示模式的样本账号，生产模式里根本不存在；生产登录只使用上面 bootstrap 建立的账号。

### 5.3 启动并登录

```bash
node scripts/local-manage.mjs start --instance=$INSTANCE --no-browser
```

启动工具把 `NODE_ENV` 设为 production，把数据目录钉在 `$INSTANCE/data`，签名密钥取自 `$INSTANCE/.local/config.json`，并且**不继承**调用环境里的 `GML_DB`、`GML_DATA_DIR`、`GML_JWT_SECRET`。健康检查通过后输出 ready 与登录地址。用 5.2 的账号登录；登录页在生产模式不展示演示账号。登录后先建立真实的组织、用户、角色与数据范围（见操作手册第十七章与"看不到数据怎么办"一节），再录入业务数据。

验证"没有造数"：新生产库中商品、销售订单、采购订单、Agent 凭据均为 0 行，唯一账号是 bootstrap 管理员。

### 5.4 密钥与敏感文件

| 项目 | 说明 |
|---|---|
| `$INSTANCE/.local/config.json` | 端口与随机签名密钥，权限 0600。不要发给他人、不要提交仓库；每次启动保留它，否则已签发的登录令牌全部失效 |
| 备份目录 | 备份含数据库内容（其中有已封存的渠道密钥）；`local-manage backup` 还含签名密钥，按敏感文件保管 |
| `GML_SECRET_KEY`（可选，至少 16 字符） | 通知渠道密钥的封存密钥；不设置时由签名密钥派生。设置后换签名密钥不会让旧封存值不可读 |
| `GML_SECRET_KEY_PREVIOUS`（可选，逗号分隔） | 只用于解密旧值，供轮换使用；轮换步骤见操作手册"通知渠道密钥" |
| `GML_WEBHOOK_ALLOWED_HOSTS`（可选，逗号分隔主机名） | 出站 Webhook 主机白名单，只能进一步收窄，不能放开私网 |
| `GML_BACKUP_KEY`（可选，至少 32 字节） | 备份加密密钥（AES-256-GCM），见 7.6；**必须与备份分开保管**，丢失即加密备份永久不可恢复 |
| `GML_TRUST_PROXY`（可选，默认 `off`） | 反向代理受信配置，见 6.1 |
| `GML_SESSION_TRANSPORT`、`GML_CSP_MODE`、`GML_COOKIE_SECURE`（可选） | 后台会话传输方式与安全响应头，见 6.2 |
| `GML_METRICS_TOKEN`（可选，至少 32 字符） | Prometheus 抓取令牌，只对 `GET /api/meta/metrics?format=prometheus` 有效，见 6.3；只经环境变量传入，不进仓库、工单和日志（`local-manage.mjs start` 会把环境里的该变量原样传给服务） |
| `GML_METRICS_TOKEN_NEXT`、`GML_METRICS_IP_LIMIT`、`GML_METRICS_IP_WINDOW_MS`（可选） | 指标令牌轮换用的第二把令牌，与指标抓取按来源 IP 的节流参数，见 6.3 与操作手册第四十章 |
| `GML_RELEASE_SIGN_KEY`（可选，只在**构建发行候选包的机器**上设置） | Ed25519 私钥 PEM 的**绝对路径**（不是密钥内容），`release-candidate.mjs` 用它给 `EVIDENCE.json` 签名；不是运行中服务的配置，服务实例上不要设置，也不要把私钥放进实例目录或仓库。见操作手册第三十五章 |
| `GML_DASHBOARD_CACHE_MS`、`GML_PROFILE`（可选） | 经营看板缓存时长与分段计时日志，见 6.3 |
| `GML_AUDIT_FTS`（可选） | 恰为 `0` 时审计日志关键词检索强制走 `LIKE`（止血开关），见 6.4 与操作手册第三十八章 |
| `GML_MCP_TOKEN_RPM`、`GML_MCP_WRITE_RPM`（可选） | 每个 MCP 令牌每 60 秒的总调用额度与写工具额度，见 6.5 与操作手册第四十七章 |
| `GML_MCP_RATE_STORE`（可选，`memory` 或 `db`，缺省 `memory`） | MCP 限速计数放在进程内存还是数据库（迁移 073 的表 `mcp_rate_buckets`），见 6.5 与操作手册第四十七章；其他取值服务启动即失败 |
| `GML_ANCHOR_INTENT_KEY`（可选，只在**执行保留清理 / 归档 / 隐私抹除脚本的机器**上设置） | Ed25519 私钥 PEM 的**绝对路径**，给审计锚点的操作意图签名；不是服务进程的配置，见 6.7 与操作手册第四十五章 |
| `GML_TEST_*`、`OS_ERP_SSH`、`OS_ERP_SCP`、`OS_ERP_GH` | **测试专用，生产与交付实例不要设置**，见 6.6 |
| 直接部署 / Docker | 必须自行设置强随机 `GML_JWT_SECRET`；缺失或公开值时服务拒绝启动 |

上表可选环境变量在启动时放在 `node scripts/local-manage.mjs start` 前面（会传给服务）。敏感值不要写进手册、聊天或工单。

### 5.5 迁移与健康核对

```bash
GML_RUNTIME_MODE=production GML_DATA_DIR=$INSTANCE/data GML_DB= node scripts/migrate.mjs --status
GML_RUNTIME_MODE=production GML_DATA_DIR=$INSTANCE/data GML_DB= node scripts/verify-migrations.mjs
curl -s http://127.0.0.1:3001/api/meta/health
```

`migrate.mjs --status` 只看状态不执行；`verify-migrations.mjs` 逐库打印迁移校验和"一致 / 未登记 / 不一致 / 文件缺失"，任一库不一致退出码为 1。健康检查返回版本与构建 SHA（发行包取自 `MANIFEST.json` 的 `baseCommit`，没有则为 null，不会编造）。生产模式下，已执行迁移文件被改动会得到 `MIGRATION_CHECKSUM_MISMATCH` 并拒绝启动。

## 六 端口、多实例与访问范围

默认端口 3001，默认只监听 127.0.0.1。端口被占用时启动会报错退出，不会结束占用进程。可编辑实例的 `.local/config.json` 的 `port` 字段（1024–65535），或使用临时环境变量：

```bash
GML_LOCAL_PORT=3011 node scripts/local-manage.mjs start --instance=$INSTANCE
```

```powershell
# Windows PowerShell
$env:GML_LOCAL_PORT="3011"
node scripts/local-manage.mjs start
```

同一份代码为**第二家企业**再开实例时，使用另一个绝对路径与另一个端口，各自独立执行 5.1–5.3；两个实例的数据、签名密钥、备份和账号互不相通（ADR-0019 的测试覆盖了这四个维度）。这不是多租户：同一数据库内没有租户隔离。

更换端口后，登录、POS 与手册链接中的端口同步更改；离线手册的"返回系统"链接默认仍指向 3001，此时手动输入实际地址。需要局域网或公网访问时，必须在前面加 HTTPS 反向代理与访问控制并自行做安全评估，本手册不提供代理本身的配置，仅说明程序侧的信任开关（6.1）。

### 6.1 反向代理后的受信配置（GML_TRUST_PROXY，ADR-0040）

- 默认 `GML_TRUST_PROXY=off`：程序忽略一切 `X-Forwarded-For` / `X-Forwarded-Proto` / `X-Request-Id`；登录节流与审计的来源 IP 是 TCP 对端地址，不发 HSTS，会话 Cookie 不带 `Secure`（除非 `GML_COOKIE_SECURE=always`）。
- 代理与程序同机：`GML_TRUST_PROXY=loopback`。代理在另一台机器或容器网络：填写代理**连接到程序时的来源地址**的 CIDR 列表，如 `GML_TRUST_PROXY=10.0.0.5/32,172.18.0.0/16`。不接受 `true`、`1`、`*`、`0.0.0.0/0` 等宽泛写法，非法值启动即失败（`TRUST_PROXY_INVALID`）。
- 只有对端命中该列表的连接，其转发头才被采纳：来源 IP 取转发链从右向左第一个不受信的地址；`X-Forwarded-Proto: https` 才使 HSTS 与 Cookie `Secure` 生效；`X-Request-Id` 才被透传。其余连接上客户端自带的这些头一律无效。
- 代理必须**覆盖**而不是透传这三个头（nginx：`proxy_set_header X-Forwarded-For $remote_addr; proxy_set_header X-Forwarded-Proto $scheme; proxy_set_header X-Request-Id $request_id;`），并且程序端口只对代理开放。若代理未覆盖 `X-Forwarded-For` 或程序端口可被绕过代理直连，节流键可被伪造。
- 未设置本项而放在代理后：所有用户共享代理 IP，来源 IP 限额会被整体触发；上线前必须设置并用不同客户端实测。
- Docker：`docker-compose.yml` 已把 `GML_TRUST_PROXY` 透传给容器（缺省 `off`），在同目录 `.env` 里设置即可；容器内看到的代理来源是网桥网关，`loopback` 在 compose 默认部署里无效，应填网桥网段 CIDR（用 `docker network inspect` 核对）。
- 依据与完整判据：ADR-0040 受信代理配置（`docs/implementation/ADR-0040-trust-proxy.md`）。ADR 自述未对真实 nginx / caddy 拓扑做过实机验证，本手册的 nginx 片段同样没有在真实代理上实测。

### 6.2 后台会话传输与安全响应头（GML_SESSION_TRANSPORT / GML_CSP_MODE，ADR-0036）

**安全响应头**：所有响应固定带 `X-Content-Type-Options: nosniff`、`Referrer-Policy`、`Permissions-Policy`、`X-Frame-Options: DENY`；仅当请求被判定为 HTTPS（直连 TLS，或来自 `GML_TRUST_PROXY` 命中的代理且带 `X-Forwarded-Proto: https`）才发 HSTS。内容安全策略由 `GML_CSP_MODE` 控制：

| `GML_CSP_MODE` | 行为 |
|---|---|
| `enforce` | 发 `Content-Security-Policy`，浏览器拦截违规。**生产模式缺省** |
| `report` | 发 `Content-Security-Policy-Report-Only`，只在浏览器控制台告警、不拦截。demo / test 缺省 |
| `off` | 不发 CSP（其余安全头仍发） |

写错值（如拼错）不会静默关闭，而是回落到该运行模式的缺省值。系统没有违规上报端点（无 `report-uri`），`report` 模式的违规只能在浏览器开发者工具里看；因此切换前建议先在 `report` 下用真实页面走一遍主要流程，再设为 `enforce`。

**会话传输**：`GML_SESSION_TRANSPORT` 取 `bearer`（缺省，任何其他值也等同）或 `cookie`。

| 传输 | 行为 | 何时用 |
|---|---|---|
| `bearer`（缺省） | 登录响应返回令牌，前端存浏览器 `localStorage`，请求带 `Authorization: Bearer`；服务端不读取任何 Cookie | 现状，与升级前完全一致 |
| `cookie` | 登录响应不含令牌，改下发 HttpOnly 的 `gml_session` 与可读的 `gml_csrf` 两个 Cookie；非读请求必须带与 Cookie 一致的 `x-csrf-token` 头，否则 403 `CSRF_TOKEN_INVALID`；登录拒绝跨站浏览器请求（403 `CROSS_SITE_LOGIN_REJECTED`）；全部退出（`logout-all`）或改密会清除两个 Cookie | 要避免登录令牌被页面脚本读走时 |

要点与限制：

- `cookie` 模式要求全程 HTTPS 且前后端同源：令 Cookie 带 `Secure` 的条件是请求被判为 HTTPS（见 6.1 配置 `GML_TRUST_PROXY`），或设置 `GML_COOKIE_SECURE=always` 强制 Cookie 带 `Secure`（该项只影响 Cookie，不触发 HSTS；只有 `always` 有意义）。
- 脚本、运维调用与 MCP 令牌继续使用 `Authorization: Bearer`，不受 CSRF 要求影响；`bearer` 模式下带 Cookie 的请求不会被当作登录凭据。
- 切换传输方式后，已登录用户需要重新登录。
- 如实边界：`cookie` 模式缩小的是"令牌被带走后在别处重放"的窗口，**不能防御**页面脚本注入（XSS）——同源脚本仍能以当前用户身份发请求；ADR 自述本批只有 Node 级测试，**没有**真实浏览器里的登录 / 刷新 / 多标签 / 退出验收。把 `cookie` 作为缺省之前，需要在目标环境做这一轮浏览器验收。
- 依据：ADR-0036 安全响应头与后台会话传输（`docs/implementation/ADR-0036-security-headers-and-session-transport.md`）。

### 6.3 监控令牌、抓取节流、看板缓存与分段计时（GML_METRICS_TOKEN / GML_METRICS_TOKEN_NEXT / GML_METRICS_IP_LIMIT / GML_METRICS_IP_WINDOW_MS / GML_DASHBOARD_CACHE_MS / GML_PROFILE）

以下都是可选环境变量，和 5.4 的其他变量一样放在 `node scripts/local-manage.mjs start` 前面（会传给服务）；改值后需要重启服务。

| 变量 | 缺省 | 取值与行为 |
|---|---|---|
| `GML_METRICS_TOKEN` | 未设置（令牌路径关闭） | 至少 32 字符（例如 `openssl rand -hex 32`）。设置后，Prometheus 可用 `Authorization: Bearer <令牌>` 读取 `GET /api/meta/metrics?format=prometheus`；令牌**只读**，对 JSON 形态、`/health` 和其他接口无效，不能放在 URL 里。短于 32 字符的令牌被忽略（本变量与 `GML_METRICS_TOKEN_NEXT` 都无效时令牌路径整体关闭，不会降级成弱口令）。未设置时仍可用管理员登录凭据读取该端点。令牌轮换 = 换值并重启。接入步骤见操作手册第三十一章 |
| `GML_METRICS_TOKEN_NEXT` | 未设置 | 轮换用的第二把抓取令牌，要求与 `GML_METRICS_TOKEN` 相同（至少 32 字符，短于 32 字符被忽略）。与 `GML_METRICS_TOKEN` **同时有效**，权限范围也相同（只对 `format=prometheus` 的抓取有效）。用于不中断抓取的轮换：先设 NEXT 并重启，抓取端换新令牌，再把新值写进 `GML_METRICS_TOKEN`、删除 NEXT 并重启。轮换步骤见操作手册第四十章 |
| `GML_METRICS_IP_LIMIT` | `120` | `GET /api/meta/metrics` 每个来源 IP 在一个窗口内允许的请求数，整数 1 至 100000。不在范围内或不是纯数字的值回落到缺省，不报错、服务照常启动。启动时读定，改值需重启。超限返回 429（`METRICS_RATE_LIMITED`，带 `Retry-After`）。计数在进程内存里，重启清零；与登录节流是各自独立的桶；来源 IP 受 `GML_TRUST_PROXY` 约束（6.1） |
| `GML_METRICS_IP_WINDOW_MS` | `60000`（60 秒） | 上述节流的窗口长度，毫秒，整数 1000 至 86400000；范围外的值同样回落到缺省。启动时读定 |
| `GML_DASHBOARD_CACHE_MS` | `30000`（30 秒） | 总部经营看板的进程内结果缓存时长，单位毫秒，适用于汇总、趋势、排行、待办、库存分布和渠道接口（`/api/dashboard/summary`、`trend`、`top`、`todos`、`inventory-dist`、`channel`）。`0` 关闭缓存（每次重新聚合）；未设置、为空、负数或不是数字都回落到缺省 30000，不会报错。命中缓存需同时满足：未过期、该行业库的连接自上次计算以来没有任何写入、没有其他连接或进程向同一数据库提交过写入（别的行业库的写入不影响它）、本地日期没变（今日/本月指标跨零点会重算），所以显示的数字最多比库内容旧一个有效期，而写入频繁的实例命中率会低。调试数字对不上时可先设为 `0` 排除缓存。最近订单（`/api/dashboard/recent`）不缓存。缓存接口的响应顶层带 `cached_at` 与 `cache_ttl_ms`，页面据此显示"数据截至"（操作手册第四十三章）。依据 ADR-0044 |
| `GML_PROFILE` | 未设置（关闭） | 只有值**恰好是** `1` 才开启；`true`、`on` 等都不算。开启后，看板各缓存接口每次请求写一行 `profile_blocks` 日志（含接口名、总耗时、各计时块毫秒数、`cache` 为 `hit` 或 `miss`）。缓存命中时不重新计算，只有缓存查找一块有耗时；要看各查询块，请同时设 `GML_DASHBOARD_CACHE_MS=0`。该行是 info 级，`GML_LOG_LEVEL` 设为 warn 或 error 时看不到，**不进接口响应**，也不改变任何业务结果。用于定位看板慢在哪一块；每个请求多写一行日志，**不要在生产长期开启**，排查完关闭并重启。日志格式和级别受 `GML_LOG_FORMAT`、`GML_LOG_LEVEL` 控制 |

上述缓存与计时只影响看板的响应速度和日志量，不改变数据；`GML_DASHBOARD_CACHE_MS` 的 30 秒缺省值适合大多数实例，没有必要调大。Docker 部署时 `docker-compose.yml` 的 `environment` 显式列出的只有端口、主机、运行模式、数据目录、`GML_TRUST_PROXY` 和 `GML_JWT_SECRET` 等少数变量，但同时通过 `env_file` 载入同目录 `.env`（可选），所以本节的变量都可写进 `.env`；未实际用 compose 启动验证过这些变量。看板缓存与分段计时在目标主机上的效果（缓存命中率、日志量）没有实测，缓存命中的耗时数字见 `docs/implementation/capacity-baseline.md`，且不是目标主机结果。

### 6.4 审计日志关键词检索开关（GML_AUDIT_FTS，ADR-0030）

| 变量 | 缺省 | 取值与行为 |
|---|---|---|
| `GML_AUDIT_FTS` | 未设置（正常使用 FTS） | 只有值**恰好是字符串 `0`** 才关闭：审计日志关键词检索一律走 `LIKE`；其他取值（未设置、空串、`1`、`false`）都不关闭。服务每次查询时读取，但已运行的进程拿不到事后改的环境，所以改值后**重启服务**。只影响查询路径：迁移 067 照常建表和触发器，写入照常维护索引，维护脚本 `audit-fts-maintain.mjs` 不读取它。用途是怀疑全文索引出问题时的止血，以及测试 |

没有这个变量时 FTS 是否可用由迁移 067 决定：数据库构建不带 FTS5（或不支持 trigram）时，迁移是空操作，检索自动走 `LIKE`，功能正确。变量设置方式同 5.4 的其他变量（放在 `node scripts/local-manage.mjs start` 前面）。索引检查、重建和止血流程见操作手册第三十八章。

### 6.5 MCP 令牌速率限制（GML_MCP_TOKEN_RPM / GML_MCP_WRITE_RPM，ADR-0056）

只对启用了 MCP 的实例有意义；**生产模式下 MCP 整体关闭**（`/mcp`、`/api/mcp` 返回 503 `FEATURE_DISABLED`），此时这两个变量没有作用。设置方式同 5.4 的其他变量（放在 `node scripts/local-manage.mjs start` 前面），启动时读定，改值需重启服务。

| 变量 | 缺省 | 取值与行为 |
|---|---|---|
| `GML_MCP_TOKEN_RPM` | `600` | 每个 MCP 令牌每 60 秒滑动窗口内允许的全部 `tools/call` 与对已知资源的 `resources/read` 次数，整数 1 至 1000000。不是纯数字或超出范围的值回落到缺省，不报错、服务照常启动 |
| `GML_MCP_WRITE_RPM` | `60` | 其中 `level: write` 工具的每令牌每 60 秒额度，范围与回落规则相同。写调用同时计入总额度 |

超限返回 HTTP 429、`Retry-After` 和业务码 `MCP_RATE_LIMITED`；缺省（`memory`）时计数在进程内存里，重启清零、多进程各自计数；想要多进程共享、重启不清零，用下面的 `GML_MCP_RATE_STORE=db`。另有可选的每令牌每日配额，不是环境变量而是设置键 `mcp_token_daily_quota`（`/system/settings` →"运维"，危险配置，缺省 0 = 关闭）。429 的响应结构、排查和告警见操作手册第四十七章。这些缺省值不是按真实 Agent 流量标定的，没有在目标主机上实测。

| 变量 | 缺省 | 取值与行为 |
|---|---|---|
| `GML_MCP_RATE_STORE` | `memory` | 只认 `memory` 与 `db`（区分大小写）；未设置或空串等于 `memory`，其他任何值（含拼错、大写）都让服务**启动即失败**（错误码 `MCP_RATE_STORE_INVALID`），不会悄悄退回"各进程各算各的"。`db`：每个令牌的窗口计数写进数据库表 `mcp_rate_buckets`（迁移 073，升级时自动建表，不需要手工操作），共用同一数据目录的多个服务进程**共享额度**，重启不清零。启动时读定，改值需重启 |

`db` 模式的取舍，部署前要知道：

- 每次放行的 MCP 调用多一个短写事务，和业务写入争用同一个 SQLite 写锁；高频 MCP 调用会拖慢业务写入，所以缺省不开。只有"同一数据目录上跑多个服务进程"或"重启后限流不能清零"才值得开。单进程的额外开销见 `docs/implementation/capacity-baseline.md` 的 AE9 一节（开发机数字，不是目标主机结果）。
- 计数写不进去时**拒绝调用**而不是放行：客户端收到 429 + `Retry-After: 5`，`detail.reason` 为 `store_unavailable`（操作手册 47.2、47.5）。
- 过期的桶由服务里的后台定时器每分钟清理一次，不需要也不应该手工删表里的行；`memory` 模式不碰这张表。
- 日配额与 `db` 模式无关，仍按审计表统计（操作手册第四十七章）。
- `db` 模式下每次限速判定的墙钟耗时（等写锁 + 重试 + 事务体）有直方图 `os_erp_mcp_rate_store_wait_seconds` 和告警 `OsErpMcpRateStoreWaitHigh`（5 分钟 p95 超过 100 毫秒、调用量大于每秒 0.1 次，持续 15 分钟），`synchronous` 的说明与何时该退回 `memory` 见操作手册第五十五章。该阈值没有按生产流量标定。

### 6.7 审计锚点操作意图的签名密钥（GML_ANCHOR_INTENT_KEY，ADR-0055 补充）

保留清理（`retention.mjs --execute`）、审计归档（`audit-archive.mjs --confirm <口令>`）、隐私抹除（`privacy-erase.mjs --confirm`）每次新增审计锚点时，会在同一事务里写一条"操作意图"。**这个变量只被这三个脚本读取，服务进程不读它**，所以它是"执行这些维护脚本的那台机器"的环境，不是服务实例的配置。

| 变量 | 缺省 | 取值与行为 |
|---|---|---|
| `GML_ANCHOR_INTENT_KEY` | 未设置 | Ed25519 私钥 PEM 的**绝对路径**（不是密钥内容）。设置后，三个脚本对每条意图签名。未设置时回落到 `GML_RELEASE_SIGN_KEY`；两者都没有则意图照写但**不签名**。路径必须在仓库之外、是普通文件、权限不得对组 / 其他人可读（`chmod 600`）、必须是 Ed25519。设置了却读不出来（路径不对、权限过宽、在仓库内、不是 Ed25519）时，脚本**在动手改库之前退出**，不会写出一条没签名的意图 |

- 密钥生成：`node scripts/release-keygen.mjs --out <新建空目录的绝对路径> --purpose anchor-intent`（产出 `anchor-intent.key.pem` 与 `anchor-intent.pub.pem`；不带 `--purpose` 生成的是发行 / 离机锚点用的 `release-sign.*`，两把**分开生成、分开保管**，不要共用）。保管规则见操作手册 45.1、53.1 与第三十五章。**生产建议把意图私钥只放在业务主机之外的操作机上**，并在那台机器上执行这三个脚本；私钥与库放在同一台机器上，签名只能挡住"只改了锚点表"的伪造，挡不住能同时写库的攻击者。
- 复核端用 `audit-verify-chain.mjs --offbox … --pubkey … --intent-pubkey … --require-signed-intents`（`--offbox` 模式下意图公钥缺省同 `--pubkey`，`--against-backup` 模式必须显式给 `--intent-pubkey`）；基线时存活的行后来被归档搬出过库的，还必须带 `--archive-dir`。完整命令集见操作手册 53.2、53.3。
- **轮换（指针，AG5 不在本分支）。** 每条意图记录了签名公钥的指纹，复核一次只能给一把意图公钥；多公钥校验和 `release-keygen --rotate` 是第十六批计划（AG5），**本分支没有，不要按计划描述操作**。本分支下能做的做法、局限和"旧公钥必须保留"的要求见操作手册 53.5。换钥后新的 `GML_ANCHOR_INTENT_KEY` 只需改操作机上的环境，不涉及服务实例。
- 不要把私钥路径写进 `.env`、compose 的 `environment` 或服务启动命令；不要把私钥放进实例目录或仓库。

### 7.1 日常校验备份

```bash
GML_RUNTIME_MODE=production GML_DATA_DIR=$INSTANCE/data GML_DB= node scripts/db-backup.mjs
echo $?
```

每个通过校验的快照旁还会写一个审计链清单 `<备份>.audit-manifest.json`（设了 `GML_BACKUP_KEY` 时另有 `.audit-manifest.enc`），记录当时审计日志链的链尾哈希和锚点；它们应随备份一起转存到别的机器，用法见操作手册 36.5。可选参数：行业名（`cosmetic`、`food`、`apparel` 之一，只备该库）、`--keep=N`（保留份数，N 不小于 1）、`--verify`（兼容旧用法，校验现在总是执行）。其他 `--` 参数被拒绝。退出码 0 全部通过；1 某库快照或校验失败（该库的旧备份不裁剪；明文模式下坏文件改名为 `*.db.failed` 保留排查，加密模式下明文临时文件被销毁；审计链清单写不出来时，新备份和本次创建的清单一并删除）；2 参数或环境错误。判据：退出码 0，且报告里每库 `status` 为 `ok`。备份目录默认是数据目录下的 `backups`（可经库内设置 `backup_dir` 改为绝对路径）。建议每日一次，升级前必做一次。

### 7.2 恢复演练

演练证明"这套备份在空目录里能真正把服务拉起来并登录"，并量出恢复耗时。**目标目录必须是不存在或为空的绝对路径，且不能是线上数据目录。**

```bash
TARGET=/srv/drills/restore-$(date +%Y%m%d-%H%M)
python3 -c 'import getpass,sys; sys.stdout.write(getpass.getpass("演练账号密码: ")+"\n")' |
  node scripts/db-restore-drill.mjs \
    --backup-dir=$INSTANCE/data/backups \
    --target-dir=$TARGET \
    --drill-username=<演练账号> --industry=cosmetic
```

支持的参数仅：`--backup-dir`、`--target-dir`、`--stamp=yyyyMMdd-HHmmss`（指定非最新备份集）、`--drill-username`、`--industry`、`--fault`（内部故障注入，运维不用）。备份里还没有任何账号时可省略 `--drill-username`，脚本在恢复副本里建临时管理员。结果在 `$TARGET/restore-drill-<stamp>.json`，需要 `passed` 为 `true`、`restored[].sha256_verified` 全为 `true`、`probes[].match` 全为 `true`；`timing.rto_ms` 是本机恢复耗时，`backup.age_seconds` 是备份年龄。退出码 0 通过，1 校验/迁移/启动/登录/探针不符，2 参数或目录被拒绝。演练结束归档报告并删除 `$TARGET`（里面是线上数据的副本）。建议每月一次并在每次升级前做。

### 7.3 升级失败回退演练

```bash
TARGET=/srv/drills/upgrade-$(date +%Y%m%d-%H%M)
node scripts/upgrade-rollback-drill.mjs --backup-dir=$INSTANCE/data/backups --target-dir=$TARGET
```

参数仅 `--backup-dir`、`--target-dir`、`--stamp`。它在恢复副本上施加一个必然失败的迁移，证明失败迁移整条回滚、不留半截结构，被篡改的迁移文件在改库之前就被拒绝，并从备份回退后服务可启动。要求退出码 0 且报告 `passed` 为 `true`；任一不变量失败，**不要升级**。

### 7.4 真实恢复与升级回退

真实恢复（停服、移走旧文件留证、核对 sha256、复制、运行 `migrate.mjs` 与 `verify-migrations.mjs`、启动并对数）与升级失败回退，步骤和判据以 仓库内 `docs/operations/restore-runbook.md`（恢复与升级回退操作手册）第 4、5 节为准，本手册不重复。恢复前先对该备份集跑一次 7.2 的演练。

使用 `local-manage.mjs backup` 的副本恢复时：停服并先备份当前 `data` 与 `.local`；将当前 data 改名保留，创建新的空 data；把备份中的 `gml_*.db` 放入，**不要**混入旧的 `-wal`、`-shm`；把同次备份的 `config.json` 恢复到 `.local/config.json`；启动后检查行业、近期单据、库存和角色。不要混用不同日期的数据库和配置，不要在服务运行中覆盖库文件。

### 7.5 边界（务必如实告知客户）

- 恢复演练的耗时来自演练机，**不是生产 RTO**；生产规模 RPO/RTO 要在目标主机（dmserver）上实测后才能承诺。
- 三个行业库在一个短暂写冻结窗口内依次快照，报告带共享的 `consistency_stamp`，这是**近似一致点，不是跨库事务**（7.6）；严格的跨库一致仍需要停服窗口内备份。
- 备份加密是**可选项，缺省关闭**（见 7.6）；没有异地副本机制，备份与数据在同一块盘时，盘坏即备份坏，需另行复制到异地并按敏感文件保管。
- 备份恢复会回退账号安全版本（`auth_version`），恢复后应让用户重新登录并轮换已签发的令牌。
- 演练探针只有用户、商品、采购单、收款单计数和应收未收余额，不是逐笔比对。

### 7.6 备份加密（GML_BACKUP_KEY，ADR-0022）

备份含密码哈希、令牌哈希、通知渠道密文和客户资料，备份盘外泄等于全库泄露。设置 `GML_BACKUP_KEY` 后 `db-backup.mjs` 输出 AES-256-GCM 加密的 `*.db.enc`，报告里 `encrypted` 为 `true`，`sha256` 与大小是**密文**的。

```bash
openssl rand -base64 48        # 生成密钥，存入密码管理器或离线介质，不要放在备份所在的盘
GML_BACKUP_KEY="$(cat /secure/backup.key)" GML_RUNTIME_MODE=production GML_DATA_DIR=$INSTANCE/data GML_DB= node scripts/db-backup.mjs
echo $?
```

- 未设置：行为不变，输出明文 `.db`。设置但短于 32 字节：直接退出码 2（`BACKUP_KEY_WEAK`），**不会**降级写明文。
- 恢复演练（7.2）和升级回退演练（7.3）读到 `.db.enc` 时需要在环境变量里提供同一个 `GML_BACKUP_KEY`；缺失为 `DRILL_BACKUP_KEY_REQUIRED`，密钥错误为 `DRILL_BACKUP_DECRYPT_FAILED`（备份文件被改动时通常先被报告里的 sha256 核对拦下，为 `RESTORE_SHA256_MISMATCH`），退出码 1，目标目录不留库文件。
- 明文窗口：SQLite 的快照只能写成文件，所以有密钥时快照先落在备份目录里 0600 权限的临时文件（名字以 `.` 开头、以 `.plain.tmp` 结尾），校验与加密完成后覆盖并删除。这不是"明文从不落盘"；在 SSD 或写时复制文件系统上覆盖不保证物理擦除，进程被强杀会遗留临时文件，发现时手工清理。更强的保证是把备份目录放在加密卷上。
- 三库在同一写冻结窗口内依次快照，报告顶层 `consistency_stamp` 记录冻结时长。冻结期间其他写入最长等待一次快照拷贝的时间，大库请在低峰执行；拿不到锁（5 秒）整次失败（`BACKUP_FREEZE_FAILED`），不产出文件、旧备份不裁剪。
- 密钥丢失 = 加密备份永久不可恢复，没有后门。旧备份仍须用旧密钥解密；轮换做法是用新密钥生成并演练通过新备份，旧密钥保留到旧备份过期。怀疑密钥泄露按明文备份泄露处理，同时按 ADR-0008 轮换 `GML_SECRET_KEY`，并让用户改密、轮换令牌。完整步骤见 `docs/operations/restore-runbook.md` 第 1.1 节。
- 未验证：大库加密耗时在目标主机 `dmserver` 上没有实测，报告里的 `encryption.ms` 是本机数字。
- 依据：ADR-0022 备份加密与三库一致点（`docs/implementation/ADR-0022-backup-encryption.md`）。

## 八 升级

升级顺序：①对当前版本做 7.1 备份；②对该备份集跑 7.3 回退演练，必须通过（它只证明"这份备份 + 当时运行演练的代码"能起来，**不证明新版本的迁移与回退兼容**）；③再在新目录解压新版本并 `setup`，用**新版本的代码**对同一备份集重跑 7.2 恢复演练与 7.3 回退演练，通过后才继续；④实例目录保持不变（`--instance=` 指向同一个绝对目录），停旧服务、启动新版本；⑤运行 `migrate.mjs --status` 与 `verify-migrations.mjs`，登录并对数。

迁移报错（含 `MIGRATION_CHECKSUM_MISMATCH`）时：**不要**重试、不要手工改 `schema_migrations`、不要使用 `--adopt-checksums`；停服、切回旧代码，按恢复手册第 5 节回退。`--adopt-checksums` 只用于经评审确认"库结构与新文件一致"的历史迁移文件修订。

可选的第 2.5 步：想在**你的**数据量上预先知道这批迁移要多久、会把写入者挡多久，在升级前用同一份备份集运行升级演练 `scripts/upgrade-rehearsal.mjs`（参数、判据和读报告方法见操作手册第三十二章）。它在隔离副本上重放迁移，不改动线上数据，但耗时数字来自运行它的机器，不是承诺。

行为变化提示：升级到包含 ADR-0008、0015、0017 的版本后，内置 `purchase` 角色默认的子树范围在账号没有组织归属时会看到空的采购工作台与待办，需管理员为账号挂组织或设置数据范围（见操作手册对应一节）；收款确认与付款执行默认需要凭证号和第二人复核（ADR-0018）。这些是收口的直接后果，不是故障。

## 十 常见故障

| 现象 | 检查及处理 |
|---|---|
| node 或 npm 找不到 | 安装 22.x，重新开终端；检查 PATH |
| npm 下载失败 | 检查官方 npm 仓库及原生模块站点网络；保留原始错误，不要关闭证书校验 |
| NODE_MODULE_VERSION 或 invalid ELF 错误 | 依赖混用了不同系统或 Node 版本；切到 Node 22，重新运行 setup |
| Port unavailable | 更换端口（`GML_LOCAL_PORT`），不要随意结束其他服务 |
| 登录页没有可用账号 | 生产模式默认无账号，先按 5.2 运行 bootstrap-admin |
| `DATA_DIRECTORY_REQUIRED` | 数据库相关命令要求 `GML_DATA_DIR` 是绝对路径。`DATA_DIRECTORY_IS_REPOSITORY`（不得指向代码副本 `data/`）只由 ADR-0019 列出的几个检查类脚本使用，退出码因脚本而异（`db-backup.mjs` 为 2，`bootstrap-admin.mjs` 为 1） |
| `BOOTSTRAP_*` 错误 | 按错误码核对参数、密码规则和模式；库中已有账号时不能再次 bootstrap |
| `MIGRATION_CHECKSUM_MISMATCH` | 部署的代码与建库时不一致；停服，按第八章回退，不要收养校验和 |
| 启动即失败，`TRUST_PROXY_INVALID` | `GML_TRUST_PROXY` 填了 `true`、`1`、`*`、`0.0.0.0/0` 等宽泛或非法写法；改成 `off`、`loopback` 或 CIDR 列表（6.1） |
| 备份退出码 2，`BACKUP_KEY_WEAK` | `GML_BACKUP_KEY` 短于 32 字节；换用 `openssl rand -base64 48` 生成的密钥（7.6） |
| 演练报 `DRILL_BACKUP_KEY_REQUIRED` / `DRILL_BACKUP_DECRYPT_FAILED` | 备份已加密，演练环境缺少或用错 `GML_BACKUP_KEY`（7.6） |
| cookie 会话下写操作 403 `CSRF_TOKEN_INVALID` | `GML_SESSION_TRANSPORT=cookie` 时非读请求必须带与 `gml_csrf` 一致的 `x-csrf-token`；脚本调用请改用 Bearer 令牌（6.2） |
| 接口返回 503 `FEATURE_DISABLED` | 该能力在生产模式下被关闭（商城、奇门、OMS 模拟、IM 同步、MCP），不是故障 |
| 登录成功但看不到采购数据 | 通常是组织归属或数据范围，见操作手册相应一节 |
| 校验报告 hash mismatch | 文件被改动或解压不完整；普通接收者应重新完整解压 |
| 备份没有数据库 | 至少完成一次首次启动或 bootstrap；确认操作的是正确实例目录 |
| 首次建库较慢 | 健康检查最多等待 180 秒，超时会停止本次子服务 |

## 十一 正式使用前的边界

本软件处于开发阶段，仓库自述"未达生产就绪"。当前代码已提供：生产与演示数据隔离、首个管理员 bootstrap、未验收网络能力关闭、通知出站策略与渠道密钥封存、校验备份与恢复/回退演练、收付款证据与二人复核。**尚未完成或未验证**：Windows/Linux 实机验收、目标主机上的容量与 RPO/RTO 实测、异地副本、严格的跨库同一时刻一致备份（现有的是近似一致点，备份加密为可选项且未在目标主机实测）、真实支付/短信/IM/电商平台连接器、HTTPS 与反向代理方案（程序侧开关已有，真实代理拓扑与 cookie 会话的浏览器端验收未做）、完整账号治理与会话策略，以及客户业务规则核验。在这些完成并有验收证据之前，不得对外宣称商业可用。

包中没有附带国外大模型账号、API Key 或额度。MCP 是 ERP 的能力接口，生产模式下整体关闭，不等于已经接通某个大模型。
