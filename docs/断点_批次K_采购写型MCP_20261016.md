## 一、这一批在做的事（一句话）

D5「MCP 工具复用领域服务」那一轮只收口了 `sales.cancel_order` / `approval.approve` /
`pricing.update_price`；**采购域在 MCP 上一个写型工具都没有** ——
整条链（请购 → 订单 → 收货 → 发票 → 结算 → 付款）在 MCP 上不可用。
本批补齐 13 个采购写型工具，并立一条硬口径：
**每个写型工具只做三件事 —— 校验入参、校验组织归属、把动作交给 `lib/purchase.js`；
一行业务 SQL 都不写进 `mcp/tools.js`。**

### 3. 新增的判据（都只有一份实现）
- `PURCHASE_DOC_SCOPE`：采购单据的组织归属列；**PO 那一项与 `purchase.list_orders`
  读列表用的是同一个对象**（不是"两处写了相同的一行"）。
- `entityScopeClause(e, spec, { alias })`：归属列改为**裸列名 + 传别名**，
  于是同一份 spec 既能喂 SQL 也能喂逐行 JS（`entityRowVisible`）—— 消掉了
  "SQL 侧写 `po.warehouse_id`、JS 侧写 `warehouse_id`"这对双写。
- `assertPurchaseDocInScope`：已有单据归属闸门，**越权按 404 处理**（不泄露存在性）。
- `assertPurchaseWriteScope`：建单前闸门，**只判这次真的会用到的内部主体**（组织/仓库/门店）。
- `mcpActor` / `actorPermCtx` / `assertMcpPerm` / `gatePurchaseEdge` / `advancePurchaseDoc`：
  执行人与权限只有一处 ——
  **write 级 = 令牌所有者（`agent_tokens.owner_user_id`）；danger 级 = 人工确认人**；
  权限判定复用 HTTP 那一个 `permContext` + `assertEdgePermitted`（错误码同 `PERM_DENIED`）。
- `PARAM_ONLY_ACTION` + `assertNotParamOnly`：`PRQ:convert` / `PO:receive` / `PO:partial`
  走简化入口一律 409 `EFFECT_REQUIRES_BUSINESS_API` 并指路。
- `server/mcp/server.js`：`buildContext` 增 `ownerUserId`（纯增量）。
- `server/mcp/tokens.js`：`ensureDemoTokens` **补 `ownerUserId`**（业务令牌→`purchase` 用户，
  全权令牌→`admin`），否则演示令牌办不了采购单。

## 三、⚠️ 断点处的确切状态（接手时请看这段）

### 3.1 新增的 `org_id` 透传（**一半**）
为了让"发票/结算/付款"也有可判的组织归属，给三个领域服务加了可选的 `orgId` 并写入 `org_id`：
- ✅ `createInvoice` / `buildSettlement` / `createPayment` 已接 `orgId` 并写入。
- ❌ **`server/routes/purchase.js` 还没传 `orgId`**（应传 `req.user.org_id ?? null`）——
  于是 HTTP 建的 PI/PST/PAY `org_id` 仍为空。**不影响现有功能**（该列此前一直为空），
  但**受限令牌的 org 闸门对这三张单会一律拒绝**（安全默认，见 `PURCHASE_DOC_SCOPE` 注释）。

### 3.2 `test-mcp-purchase.mjs` 当前红，根因已定位（**两个都是测试侧问题**）
1. **"全局令牌"其实不是全局**：`POST /api/mcp/tokens` 会
   `orgId: org_id ?? req.user.org_id` → admin 的 `org_id = 1`（总部 `/1/`），
   于是 API 签发的令牌被绑到总部子树（36 个组织）。
   而 **供应商主体的组织是总部子树的兄弟**（`/37/`），所以早期版本用
   `suppliers.org_id` 做归属判据 → 所有内部令牌恒被拒（**正向误伤，已废掉该判据**）。
   → 测试改造：全局令牌改用 `createToken(db,{orgId:null})` 直接建；
   组织边界令牌仍走 API（绑 `org_id`）。
2. **级联红**：第 1 条导致建单失败 → `prqId` 为 undefined → 后续 `MISSING_ARGS` 级联，
   末尾 `items.open` 崩溃（应在用前判空）。
