## 一、缺陷的形状：**能力缺口，而不是错误**

D5 那一轮把 `sales.cancel_order` / `approval.approve` / `pricing.update_price` 从
"裸 UPDATE" 改成"调领域服务"，同时立下判据：

> 判断标准：**这个工具有没有"写"或"改变状态"的语义**？有就必须走领域服务。

但那一条只修了**已经存在**的工具。D5 收口时如实记了一条尾巴：

> `purchase` / `sales` 的**其余写型 MCP 工具**（如 `purchase.create_order`）仍走各自的 SQL ——
> 它们本批未动，列入下一轮的清单核对范围。

摸底之后发现，实际情况比那句话更彻底：**这些工具根本不存在。**

| | 批次前 |
|---|---|
| `purchase.*` MCP 工具 | **只有 1 个**：`purchase.list_orders`（read） |
| 采购整条链在 MCP 上 | **完全不可用** —— 请购 → 订单 → 收货 → 发票 → 结算 → 付款，一个写型入口都没有 |
| 采购订单的建单逻辑 | 只存在于 `routes/purchase.js` 的**内联事务**里 |
| 采购收货的逻辑 | 同上（建 GR + 批次入库 + 推订单状态，一整段塞在路由里） |

所以这一批要解决的是**两个叠在一起**的问题：

1. **能力缺口**：采购域在 MCP 上没有写型入口。
2. **背后真正的坑**：想补这个缺口，只有两条路 ——
   **在 MCP 里抄一遍 SQL**（= 同一件事两个实现，D5 的原文缺陷），
   或者**把业务抽成领域服务、两个入口都调它**。

> **本批的铁律**：**每一个采购写型工具只做三件事** ——
> 校验入参、校验组织归属、把动作交给 `lib/purchase.js`。
> **一行业务 SQL 都不写进 `mcp/tools.js`。**
>
> 证据不是"代码看起来薄"，而是**按后果验**：建单真的落库、转单真的出 PO、
> 收货真的写库存与成本、付款真的核销结算单（`test-mcp-purchase.mjs` 逐条断言）。

## 二、先消除"平行实现"：把路由里的内联业务抽成领域服务

这一批改动的**第一件事不是加工具，是搬代码**。搬出来 6 个函数（全部落在 `lib/purchase.js`）：

| 新领域服务 | 原来在哪 | 谁在调 |
|---|---|---|
| `getPurchaseOrder(db,id)` | `routes/purchase.js` 的私有 `loadOrder` | 路由 5 处 + MCP |
| `recalcOrder(db,id)` | 路由私有（含"总额为负"断言） | 路由改单 + 建单 + 收货 + MCP |
| `normalizePurchaseOrderLines(db,items)` | 路由内联（建单一份） | **建单与改单共用**（改单原来自己又写了一遍） |
| `createPurchaseOrder(db,{...})` | `POST /orders` 内联事务 | 路由 + `purchase.create_order` |
| `transitionPurchaseOrder(db,{...})` | `POST /orders/:id/status` 的 `tryTransition` | 路由 + `purchase.advance_order` |
| `receivePurchaseOrder(db,{...})` | `POST /orders/:id/receive` 整段事务 | 路由 + `purchase.receive_order` |

搬完之后 **`routes/purchase.js` 只做「HTTP 入参 → 领域服务 → 响应」的翻译**；
MCP 工具调的是同一批函数。**入口可以有两个，实现只能有一份。**

> 回归证据：搬完之后先跑既有的 `test-purchase.mjs` —— **cosmetic 103/103、food 103/103**，
> 即"重构本身零回归"，再开始加工具。

顺带修掉一处同形问题：`routes/purchase.js` 与 `routes/purchase-chain.js` 各有一个 `guard()`，
前者把业务码放在 `detail.code`、后者把 `DocFlowError` 漏给全局中间件（业务码跑到顶层 `error`）。
现在**两份 `guard()` 一样**（都翻 `PurchaseError | DocFlowError` → `failFromError`），
即"权限不足"与"数据校验不过"在采购域返回**同一形状**。

## 三、13 个新工具：级、执行人、判据

### 3.1 清单

**write 级（建草稿单据，强制幂等键）**

| 工具 | 领域服务 |
|---|---|
| `purchase.create_requisition` | `resolvePurchasePrices`（取价链）→ `createRequisition` |
| `purchase.create_order` | `createPurchaseOrder` |
| `purchase.create_invoice` | `createInvoice` |
| `purchase.build_settlement` | `buildSettlement` |
| `purchase.create_payment` | `createPayment` |
| `purchase.create_return` | `createPurchaseReturn` |

**danger 级（推进状态 / 动货 / 动钱，必须人工二次确认）**

| 工具 | 领域服务 | 额外闸门 |
|---|---|---|
| `purchase.advance_requisition` | `dispatchTransition`（PRQ） | 边 `perm_code` |
| `purchase.convert_requisition` | `convertRequisitionToOrder` | `purchase.order.edit` |
| `purchase.advance_order` | `transitionPurchaseOrder` | 边 `perm_code` |
| `purchase.receive_order` | `receivePurchaseOrder` | `purchase.inbound` |
| `purchase.advance_invoice` | `dispatchTransition`（PI） | 边 `perm_code` |
| `purchase.advance_settlement` | `dispatchTransition`（PST） | 边 `perm_code` |
| `purchase.advance_payment` | `dispatchTransition`（PAY，含核销） | 边 `perm_code` |

工具总数：**23 → 36**；`purchase.*`：**1 → 14**（1 read + 6 write + 7 danger）。

### 3.2 为什么"建单"是 write、"推进"是 danger

沿用 D5 给三级开放程度定的语义，但把界线画在**"这件事要不要签字"**上：

- **建草稿单**没有业务后果（不占库存、不生成应收应付、不动钱），所以按 write 处理 ——
  幂等键保证重放安全即可，不引入确认摩擦；
- **推进单据状态**一律是"代表公司做了一个决定"：批准请购、把请购转成采购订单、
  收货入库、报销发票、核销付款。这些动作**要么改变账、要么改变货、要么留下签字**，
  所以一律 danger（人工二次确认）。

这一条也顺带回答了"Agent 凭什么批准采购单"——与 `approval.approve` 同一个答案：
**它不代替，它转呈**。第 4 条（执行人）就是这个答案的落实。

### 3.3 执行人：「是谁在办」必须答得出来

| 级别 | 执行人 | 判据 |
|---|---|---|
| write | **令牌所有者**（`agent_tokens.owner_user_id`） | 无主令牌 → 403 `AGENT_OWNER_REQUIRED` |
| danger | **人工确认单上的真人**（`ctx.confirmedBy`） | 缺失 → 403 `AGENT_ACTOR_REQUIRED` |

**为什么写型也要求一个真人**：采购单据上要落 `created_by` / `approved_by`。
"谁买的、谁批的"如果是空，这张单在事后追责时就只剩一个令牌名字，
而令牌是可以被复用、被共享、被改名吊销的 —— **令牌不是责任人**。

配套改动：`ensureDemoTokens` 补 `ownerUserId`（业务令牌→`purchase` 用户、全权令牌→`admin`）——
否则**演示令牌自己就办不了采购单**，而这正是"改了规则忘了改数据"的典型症状。

### 3.4 权限：与 HTTP 走**同一份**判据

`danger` 级工具执行前，用确认人的权限点过该条边的 `perm_code`：

```
assertEdgePermitted({ db, docType, fromState, action, permCtx: permContext(db, { uid: 确认人 }), entry: 'MCP' })
```

用的是 `middleware/auth.js` 的 `permContext` 与 `lib/docflow.js` 的 `assertEdgePermitted` ——
**与 `POST /api/docflow/transition`、`POST /api/purchase/requisitions/:id/:action` 是同一个函数**。

> **为什么要这一道**：MCP 的 danger 级本来就要人工确认，看起来"有人看过了"。
> 但**"确认"不等于"有权"** —— 一个仓储主管可以点确认，却不一定有权批准采购订单作废。
> 没有这道闸，"找一个能点确认的人帮忙过一下"就成了一条绕开 RBAC 的路。
>
> **入口一致性的可验证形态**（K8 用例）：同一个动作、同一个没有权限的人 ——
> HTTP 走业务路由、MCP 走确认流 —— 两边都必须 403 且返回**同一个业务码**
> `PERM_DENIED` 与同一个 `perm_code`（`purchase.req.edit`）。

### 3.5 组织归属：读与写**同一份定义**

新增 `PURCHASE_DOC_SCOPE`：每种采购单据"归谁管"的**列**。

```js
PRQ: { orgs: ['org_id'], warehouses: ['warehouse_id'] }
PO:  { warehouses: ['warehouse_id'], stores: ['target_store_id'] }   // ← 与 purchase.list_orders 完全一致
GR / PRT: { warehouses: ['warehouse_id'] }
PI / PST / PAY: { orgs: ['org_id'] }
```

三处配套：

1. **读列表直接复用同一个对象**：`purchase.list_orders` 从"传一串字面量"改为
   `entityScopeClause(scopeEntityIds(ctx,db), PURCHASE_DOC_SCOPE.PO, { alias: 'po' })` ——
   不是"两处写了相同的一行"，是**同一个对象**。
2. **消掉 SQL/JS 双写**：`entityScopeClause` 原来只接受已加前缀的列（`po.warehouse_id`），
   而 `entityRowVisible`（逐行判定）读的是 `row[列名]`（必须裸列名）。
   现在统一为**裸列名 + `alias` 参数**，同一份 spec 既能喂 SQL 也能喂逐行判定。
   *这正是本项目"列表挡得住、单条挡不住"那条老缺陷的写法根源。*
3. **越权按 404 处理**：`assertPurchaseDocInScope` 对范围外的单据返回
   `DOC_NOT_FOUND`（不是 403）—— 报 403 等于确认"这张单存在，但不是你的"，
   与 `order.trace_document` 的口径一致。

### 3.6 简化入口驱动不了"后果在参数上"的动作

单据内核里的**边是"状态之间"的事**，而有些动作的**全部意义在参数上**：

| 动作 | 后果在哪 | 简化入口（只有 doc_type/id/action）的问题 |
|---|---|---|
| `PRQ.convert` | 转到哪张订单、转哪些行、哪个供应商/仓 | 只改状态 → 请购单显示"已转单"，`purchase_orders` 里查不到 |
| `PO.receive` / `PO.partial` | 批次、库存、成本流水、最近成交价 | 只翻状态 → 订单显示"已收货"，仓库里没这批货 |

新增 `PARAM_ONLY_ACTION` 闸门：这三个动作走简化入口一律
**409 `EFFECT_REQUIRES_BUSINESS_API`**，并在 `detail.entry` 里指出该用哪个工具。

## 四、本批顺带修掉的一条已登记残留（INBOX §23.3）

验收侧实测记录过：

> `POST /api/docflow/transition {doc_type:'PRQ', id:6, action:'convert'}` → **200**，
> 状态 `approved → converted`，**但采购订单总数 42 → 42（一张 PO 都没生成）**。

根因是三层叠加，其中最关键的一层是：**效果归属登记只到"类型"粒度**
（`claimTransitionEffect('PRQ', …)` 把 PRQ 的**所有**动作一揽子交给 `transitionRequisition`），
而被委托的函数**没有实现 `convert` 的副作用**。

**修法（采纳 §23.6 的方案 A）**：在**归属执行器内部**拒绝 `convert` 并指路正式入口。

- 为什么放在归属执行器里、而不是"在通用入口写一个 if"：
  **归属类型的每个动作都在归属执行器里被回答**，所以通用入口与 MCP 入口**都不会漏**；
  而"只在通用入口拦"正是 A01 那批已经证伪过的写法（本项目已有两条缺陷证明这个形状）。
- 正式入口不受影响：`convertRequisitionToOrder` 内部走 `applyTransition`，不经过 `transitionRequisition`。
- **本批新增断言**：通用流转入口对 `PRQ.convert` 必须 409 且状态不变；
  并且"已转单的请购单必存在对应采购订单"由 `purchase.convert_requisition` 的正向用例覆盖。

## 五、本批最值钱的三条教训（已进框架决策记录）

### 1. 「收紧一条门之前，先跑一遍这条门原本该放谁进来」——第二次生效

我最初的归属判据里带了 `suppliers: ['supplier_id']`（"供应商也要在我范围内"），
听起来更严、更安全。实测**建单全部 403**：

```
采购订单的供应商 #1 所属组织 #37 不在本令牌的组织范围内（visibleOrgCount: 36）
```

原因：供应商在组织树上是**总部子树的兄弟**（`/37/` vs `/1/…`），而
`POST /api/mcp/tokens` 会把令牌绑到签发人的组织（`admin` → 总部 `/1/`）。
于是"供应商组织必须在范围内"这条判据**对所有内部令牌恒为假** ——
一个**100% 误伤**的门，而界面上没有任何线索指向"是供应商的组织不对"。

⇒ 判据已废掉：**供应商是外部伙伴，不用于判"这单归不归我管"**；
归属只认内部的**货主组织 / 仓库 / 门店**。
（§27.2 的教训第二次生效：**正向误伤与越权一样是缺陷**，只是它不报错、只挡住自己人。）

### 2. 「令牌能被借来做事，不是因为它叫这个名字」——`x-industry` 与令牌分库

写测试时踩到："Agent Token 无效"。根因不是令牌错，而是**MCP 端点的行业由 `x-industry` 头解析**，
而令牌是**三库各存一份**的 —— 漏了那个头，服务端就去默认库里查 food/apparel 的令牌，
查不到，报的是 `invalid_token`。

⇒ 观察记录：**这个错误码有误导性**（"令牌无效"会让你去查令牌，而真实原因是行业没传）。
本批不改它（改错误码属于行为变更、且不在本批目标内），但在
`test-mcp-purchase.mjs` 里写明了原因，并**列入本批新增边界**。

### 3. 「断言详情不能成为新的失败源」

`JSON.stringify(undefined)` 返回 `undefined`（不是字符串），后面接 `.slice()` 直接抛 TypeError。
food 库实测：一个顺手写的 `JSON.stringify(a2.body?.result).slice(0,160)` 把整套测试**崩掉**，
而崩的位置（K10 第 649 行）离真正的失败点（K1 令牌无效）很远。

⇒ 统一 `safeJson()`，并且这条对**所有**测试脚本都成立：
**失败信息本身必须是"不可能失败"的代码。**

## 八、本批新增边界（如实记）

- **PI/PST/PAY 的存量行 `org_id` 为空**：受限令牌推不动这些**历史**单据
  （安全默认：拿不到归属就不放行）。新建行已随单写入 `org_id`；
  历史数据**不回填**（回填口径要"猜"是哪一级组织，属于下一轮的事）。
- `x-industry` 缺失时报 `invalid_token`（见 §五.2）。
- 简化入口对 `PO.receive|partial` / `PRQ.convert` 是 409 指路，
  **不是**"自动补默认参数转单"（§23.6 的方案 B 未采纳：语义面更大、风险更高）。
- 未做：采购订单的**改单**（`PUT /orders/:id`）没有对应 MCP 工具
  （改单的判据已与建单共用 `normalizePurchaseOrderLines`，但入口未开放）；
  采购**收货单**的独立流转（GR.inspect / GR.close）未开 MCP；
  MCP 侧的采购**审批流**（`require_approval=1` 的边）仍走 `approval.approve` 或业务入口。
- 不阻塞（与前批相同）：容器内实测 · Windows / 真机 Pad·手机 · 钉钉飞书真实联调。
