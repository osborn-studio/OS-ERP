## 一、这一批修的是什么

验收复核把 A01 列为 P0，它不是一个接口的 bug，而是**一类入口的形状问题**。

| 入口 | 原来的门 | 它能做什么 |
|---|---|---|
| `POST /api/docflow/transition` | 只有 `requireAuth` | 传 `doc_type + id + action` 就改**任何**单据的状态 |
| `POST /api/purchase/requisitions/:id/:action`（PRQ） | 只有 `requireAuth` | 请购单任意动作 |
| `POST /api/purchase/invoices/:id/:action`（PI） | 只有 `requireAuth` | 采购发票任意动作（含**过账**） |
| `POST /api/purchase/settlements/:id/:action`（PST） | 只有 `requireAuth` | 采购结算任意动作（含**结清**） |
| `POST /api/purchase/payments/:id/:action`（PAY） | 只有 `requireAuth` | 付款单任意动作（含**付款核销**） |
| `POST /api/order-center/orders/:id/:action`（OC） | 只有 `requireAuth` | 订货单任意动作（含**占/放授信、分仓、收货并应收**） |

这六个入口的共同形状是：**"分支路由 + 只有登录态"**。
只要路径里那个 `:action` 是合法的，谁都能点。

### 为什么最危险的是"通用流转入口"

前五个至少还锚定在某个域上；`/docflow/transition` 连域都没有，它接的是**内核**：

```
内核 applyTransition() 只做三件事：
  ① 校验这条边是否存在（doc_actions）
  ② 改业务表的状态字段
  ③ 写一条 doc_events 留痕
```

它**不知道这条边有没有业务后果**。于是下面这些都能成立：

| 走通用入口做 | 状态会变成 | 但账上发生了什么 |
|---|---|---|
| `SO · ship` | 已发货 | **库存没出库**、成本没结转 |
| `RCP · confirm` | 已收款 | **应收没核销**，钱挂着 |
| `MR · issue` | 已领料 | **材料没出库**，生产成本凭空少一截 |
| `PS · void` | 已作废 | **库存与支付都没退** |
| `PAY · pay` | 已付款 | 结算单已付金额没动 |

这些单据**不会报错，也不会看起来异常**。而所有下游报表（库存、账龄、成本、授信）
都建立在这个状态上。等发现的时候，已经无法分辨"哪几张是走正门进来的"。
**这是最坏的一类缺陷：它污染的是别人赖以判断的结论。**

## 二、修复的四道判定 + 一处语义收窄

### 2.1 四道判定（每次调用都过）

```
POST /api/docflow/transition
  ① 单据级越权 —— 这一行是不是"我能动的"
  ② 外部主体隔离 —— 这类单外部主体能不能碰
  ③ 功能权限门 —— 这一次动作的 perm_code 我有没有
  ④ 执行归属 —— 交给归属服务 / 纯状态走内核 / 拒绝
```

### 2.2 语义收窄（刻意的行为变更）

**这个接口现在只驱动"纯状态、无业务后果"的流转**，其余一律 409 并指出该走哪个业务入口：

```json
{
  "code": 1, "success": false,
  "message": "「销售订单」的流转带业务后果（库存/往来/授信/成本），通用流转入口不驱动它。请走：销售订单接口 /api/sales/orders",
  "error": "EFFECT_REQUIRES_BUSINESS_API",
  "detail": { "code": "EFFECT_REQUIRES_BUSINESS_API", "docType": "SO", "action": "ship", "entry": "销售订单接口 /api/sales/orders" }
}
```

**为什么敢收窄**：全仓搜索 `docflow/transition` 与 `/transition`，
除路由自身定义外**没有任何调用方**（前端、脚本、MCP 都没有）。
它原先唯一的作用就是"让任何登录者改任何状态"—— 在带账务的 ERP 里，这个能力本身就不该存在。

要放开某个**纯状态**单据类型（改了它不影响任何数字），把策略表
`doc_transition_policy.allow_generic` 置 1 即可 —— **数据配置，不改代码**。

## 三、效果归属登记：为什么"委托"优于"再加一段 if"

`lib/docflow.js` 新增登记表：

```js
/** 声明某单据类型的流转由哪个业务服务负责执行（副作用与状态在同一段代码里） */
export function claimTransitionEffect(docType, run, { entry, canAccess })
```

`dispatchTransition(p)` 的判定次序：

```
① 有归属执行器 → owner.run(db, p)        // 与业务入口**同一段代码**
② 策略 allow_generic=1 → applyTransition  // 纯状态
③ 其余 → 409 EFFECT_REQUIRES_BUSINESS_API（带指路）
```

**为什么不是"在通用入口里再抄一遍副作用"**：
抄一遍就变成两份实现，而两份实现只会在其中一份上更新 —— 本项目已经用三条缺陷证明过这个形状
（列表挡得住 / 详情挡不住、create 拦得住 / update 拦不住、tools/call 拦得住 / resources/read 拦不住）。
**委托的是函数本身，不是函数的结论。**

**为什么不是"干脆拒绝一切"**：拒绝会让通用入口彻底变成废接口。
委托让它保住了"统一入口"的价值，同时把执行落到唯一一处；
而且这正是 **D5（MCP 复用领域服务）**需要的形状 —— MCP 也调同一个 `dispatchTransition`，
不需要第二条平行实现。

当前登记了五项（对应已存在的领域服务门面）：

| docType | 归属服务 | 业务入口 |
|---|---|---|
| PRQ | `transitionRequisition` | `POST /api/purchase/requisitions/:id/:action` |
| PI | `transitionInvoice` | `POST /api/purchase/invoices/:id/:action` |
| PST | `transitionSettlement` | `POST /api/purchase/settlements/:id/:action` |
| PAY | `transitionPayment` | `POST /api/purchase/payments/:id/:action` |
| OC | `transitionOrder` | `POST /api/order-center/orders/:id/:action` |

> **登记放在模块加载时**（`lib/purchase.js` / `lib/order-center.js` 顶层调用），
> 而不是启动流程里的一个注册步骤：只要模块被 import 过就一定生效，
> 不会出现"忘了调注册函数"这种**静默失效**。

## 四、权限检查为什么不下沉到内核（本批最重要的一条）

第一反应是把 `edge.perm_code` 的判定放进 `applyTransition`，这样"所有调用点自动被覆盖"。
**这条是错的**，理由是实测出来的：

一次用户动作常常在内部触发**多个**状态变更 ——

| 用户动作 | 内部还会发生 |
|---|---|
| 付款单「执行付款」 | 自动把**采购结算单**推进到 `settled` |
| 订货单「收货」 | 自动**并入应收**（模块 21） |
| 调拨「入库」 | 结束在途、结转成本 |

这些**内部**流转的 `perm_code` 属于别的角色。若把 perm_code 判定下沉进内核，
一个完全合法的付款动作会被判成"越权"，因为它顺手触发了自己没有权限的结算单流转。

**结论：判据函数共用，调用点放在"用户请求"这一层。**

```
判据只有一个实现：lib/docflow.js 的 assertEdgePermitted()
判据的使用者有三处：通用流转入口 · 采购后段四个分支路由 · 订货中心分支路由
（将来 MCP 是第四处 —— 复用同一个函数，不是复制同一段判定）
```

同理，"这个人有哪些权限点"也只有一个实现：`middleware/auth.js` 的 `permContext(db, user)`。
`requirePerm` 已改为使用它 —— 原来它自己写了一段"查角色 → 查 role_permissions"，
现在两个使用者共用一份，避免"一人多角色 / admin 全开"的口径只在其中一侧更新。

## 五、策略表：默认拒绝，逐类型放开

```sql
CREATE TABLE doc_transition_policy (
  doc_type      TEXT PRIMARY KEY,
  allow_generic INTEGER NOT NULL DEFAULT 0,  -- 1 = 通用入口可直接驱动（纯状态）
  effect_owner  TEXT,                        -- 有后果时归属的业务入口（用于报错指路）
  note          TEXT,
  updated_at    TEXT
)
```

### 为什么是数据而不是代码里的清单

① **清单会过期**：新增单据类型 / 新增流转边时没人会想起来改它，漏了就是静默开口子；
② **判定分散**：会被写成散落的 `if`，与内核既有的
「合法状态与合法流转是**数据**，不是散落的 if」这条设计相冲突。

数据化之后，**新增单据类型不写策略 = 自动拒绝**（fail-closed），
并且"要放开哪一类"这件事有了唯一的落点。

### 为什么单开一张表，不给 `doc_types` 加列

`doc_types` 是定义表，`008_doc_kernel.cjs` 的 `up()` 是「先 DELETE 再 INSERT」的同步写法。
整库重建或 008 自愈重跑时**会把行整行替换掉** —— 加在它上面的策略列会**连值一起被抹掉**，
而且这种失效是静默的（列还在、值没了）。

**教训**：**给"别人的同步重灌会整行替换"的表加列，等于把自己的数据寄存在别人手里。**

### 当前取值

- `allow_generic = 1` 的类型：**空**。
  连 PRQ 的 `convert` 也没放开 —— 走通用入口把状态改成 `converted` 并不会真的生成采购订单，
  结果是"请购单显示已转单、而采购订单不存在"。**宁可严一点**，要放开是数据配置。
- 38 个单据类型**全部**有策略行（自检不变量一）。漏一行虽然安全（fail-closed），
  但会让人把"策略没写"误读成"策略禁止"，所以要求写全 —— **拒绝必须是声明过的拒绝**。

## 六、`canAccess`：域自己的越权口径也要登记

订货中心判"这张单能不能动"用的是 **`customer_id`**（订货方视角）：
经销商看自己的单、门店看本店的单、内部按 `org_id` 范围。这套口径只属于那个域。

所以 `claimTransitionEffect` 的第三个参数是 `canAccess`：

```js
claimTransitionEffect('OC', run, {
  entry: 'POST /api/order-center/orders/:id/:action',
  canAccess: ocAccessCheck      // 与列表 scopeCond 同一份规则
})
```

没登记就退回通用判据（`assertCanRead` + 组织范围）。

**为什么不能省**：如果通用入口自己再写一套，
就会出现「同一个人，列表里看不到这张单、却能动它」—— 这正是 D2 的原形。
顺带把 `selfCustomerId` 从路由**移到 lib**：它现在有两个调用方（列表与流转入口），
放在路由里只有路由能用，另一边必然再写一遍。

**本批实测抓到的真实问题**：第一版把 `order-center` 也放进了"外部主体不得驱动的内部域"清单，
于是**经销商动自己的订货单也被 403**（把功能砍了）。
反例（「经销商动自己的单 → 不是 403」）当场把它打红。
`order-center` 正是外部主体该动的地方，已从清单里移除并写明理由。

## 七、外部主体隔离按模块判定

```js
const INTERNAL_MODULES = new Set(['purchase', 'inventory', 'produce', 'outsource', 'quality', 'finance'])
```

- 这一条**刻意不含 `order-center`**（经销商下单、门店要货正是它该做的事）。
- 这一条与"数据范围"是**两件事**：范围管"看哪些行"，这条管"这类单能不能碰"。两者不合并
  （与第 1 批 `requireInternal` 的口径一致）。

## 八、错误形状统一

同一个业务码因为**入口不同**而出现在不同字段里，调用方就得写两套判断，所以本批统一：

| 入口 | 谁翻译错误 | `error` | `detail.code` |
|---|---|---|---|
| 通用流转入口 | `handleFlowError` | ✅ 本批补上 | ✅ |
| 领域路由 | 全局错误中间件 | ✅ | ✗（本来就没有） |

`handleFlowError` 改为同时给出 `error` 与 `detail.code`（顶层 `code` 保持数字 1，遵循项目约定）。
**这是纯增量**：原有字段一个都没动。

反例里因此可以断言「**两个入口返回同一个业务码**」——
这条断言的价值是：它验证的不是某个接口，而是"两个入口用的是同一份判据"。

## 九、迁移 027 与重建登记

| 动作 | 对象 | 为什么 |
|---|---|---|
| 建表 | `doc_transition_policy` | 策略是数据，要能被查询、被自检、被数据配置修改 |
| 灌数 | 38 个单据类型的策略行 | 每个类型都要有"声明过的"策略 |
| 自检 | `up()` 末尾校验策略表里没有未注册的 doc_type | 拼写错误会**静默失效**，必须在写库时就拦住 |
| 指纹 | `stampDef(db,'027_transition_policy',{POLICY,GENERIC_ALLOWED})` | 改策略定义后 `verify` 判脱节 → runner 自愈重跑 |

`verify()` 的四条不变量：

1. 每个已注册单据类型都有策略行；
2. `allow_generic=1` 的集合必须等于显式声明的白名单（当前为空），且被放开的类型**不能有 danger 边**；
3. 不允许存在"既不放开、又没有归属入口"的策略行（否则报错指不了路）；
4. 定义指纹一致。

**重建登记**：`doc_transition_policy` 已加入 `server/db/seed.js` 的 `TABLES`
（与 `doc_types` 同一处、同一理由）。整库重建时会 DROP 它，
由 027 的 `verify()` 判为脱节、runner 自愈重跑 `up()` 重灌策略行。
**已实测**：三库 `reseed-all --force` 后策略表恢复 38/38 行。

## 十、回归与反例（`scripts/test-guards.mjs` G8）

**没有反例的修复不算修完。** 本批新增 G8 一节、八段：

| 段 | 断言的东西 |
|---|---|
| 8a | 策略表不变量：38/38 行 · 放开集合为空 · 没有"没归属也没放开"的行 · 无孤儿 |
| 8b | **矩阵**：20 个非归属类型 × 真实存在的 danger 边 → 一律 409 `EFFECT_REQUIRES_BUSINESS_API`；**拒绝时状态与留痕都不变**；报错必须**真的写出业务入口** |
| 8c | **委托**：OC.allocate 走通用入口 → 200，且 `ship_warehouse_id` 被写入 —— **这条能分辨"裸状态翻转"**（内核只会改 status）；随后快照还原 |
| 8d | **两个入口同一判据**：viewer 走通用入口与业务入口都 403，且**返回同一个业务码**；两次都没改状态 |
| 8e | **越权**：经销商动别人的订货单 → 两个入口都 403；动自己的单 → 不被越权判定挡住 |
| 8f | **外部主体隔离**：经销商走通用入口提交采购单 → 403，采购单状态未变 |

三库实测：**112 / 112 / 112，0 失败**；连续复跑同样通过（用例自带快照还原）。

**8b 为什么值得写成矩阵**：漏掉的入口永远不会出现在手写的用例清单里。
矩阵的样本是**从 `doc_actions` 里挑真实存在的 danger 边**，所以新增单据类型时它会自动覆盖。

## 十一、本批未做 / 未验证

### 未做
- **D1 退货闭环**、**D5 MCP 复用领域服务（含 A19 / A03 / A04b）** 未开始；
  它们要动 `lib/ar.js` / `lib/stock.js` / `mcp/tools.js`，与本批不重叠。
- **其余单据类型的效果归属未登记**（SO / RCP / MR / TF / CK / AS / SI / DL / SR / GR / PS / CA …）：
  它们的副作用目前**内联在路由里**，要登记必须先抽成领域服务门面 ——
  那是 D5 的工作量。**在这一步完成之前，通用入口对它们是"拒绝"而不是"委托"**，
  这是有意的最保守选择。
- **`doc_types` 的 `effect_owner` 文案与实际路由子路径**未逐条实测（写明的是"接口 + 前缀"，
  例如「销售订单接口 /api/sales/orders」）。文案只用于报错指路，不影响判定。

### 未验证
- **Windows / 真机 Pad·手机**：仍只能标"未验证"。
- **钉钉 / 飞书真实联调**：等待凭据，不在本批范围。
- **A20（撤权不即时生效）**：本批新增的权限门同样依赖 JWT 里的 `role`
  （`permContext` 会把 `user.role === 'admin'` 视为全开）。**一个已降权的 admin 令牌在 12h 内仍会通过**。
  这与既有全部权限检查的行为一致，属 A20 范畴，**未在本批修**。
