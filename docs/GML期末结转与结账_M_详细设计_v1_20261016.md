> 版本：v1 · 日期：2026-10-16 ｜ 模块 28（财务报表）的续 ｜ 迁移 **035_period_closing**
> 性质：**内部设计底稿**。相关文档：批次 L 报表体系、批次 H 业财一体凭证。

---

## 一、这一批补的是什么

批次 L 让三张报表算得出来，但它在自己的注释里留了一句实话：

> 本系统**没有做期末结转**，损益类科目期末仍有余额。
> 不把它计入权益，资产负债表必然差一个「本期利润」。

于是资产负债表上用了一行「未结转损益」（`BS_UNCARRIED_PL`，科目区间 `6001~6999`）把损益类科目的余额兜进所有者权益。
**这是权宜之计，不是会计上正确的事**，代价有三：

| 代价 | 具体表现 |
|---|---|
| 收入科目余额跨年不清零 | `6001 主营业务收入` 的余额会是**开业至今的全部收入**，而它本该每个期末被转到 4103 |
| 答不出「账上累计利润」 | 利润表答的是**本期发生额**；而 `4103 本年利润` 的余额才是"累计已结转的利润" |
| 「结账」失去落点 | 账不结平，所谓"这一期定稿了"就只是一个状态字 |

本批把这三件事补齐：**期末结转**（`lib/closing.js`）+ **结账前置**（`closePeriod`）+ **结转从发生额口径中剔除**。

## 二、为什么期末结转**不能走凭证模板**（本批最重要的一个判断）

批次 H 立过一条铁律：

> 凭证只能由「已发生的事实」生成，且金额只能取 `FACT_KEYS` 那个**封闭字典**里的键。
> 因为模板是**配置**，配置能改账。

期末结转看起来在违反它。它的金额不是"某张来源单据的某个字段"，而是**一组科目余额的聚合**；
更麻烦的是它的**分录行数不固定**（有几个损益科目有余额就有几行），而模板的分录是固定行。

正确的结论不是"把模板放宽"，而是认出这里根本不是同一类东西：

| | 回答的问题 | 形态 | 所以 |
|---|---|---|---|
| 凭证模板 | 「**这笔业务**该记成哪几笔分录」 | 业务形态无穷 | 要配置 |
| 期末结转 | 「**把损益科目余额搬到 4103**」 | 是一个算法，没有可选项 | 写进代码 |

所以结转走代码，且它的正确性不靠"配置得对"，而靠**恒等式自证**（见第五节）。
唯一保留的配置是"结转到哪个科目"（`settings.closing_profit_subject`，默认 4103）—— **那是会计政策**。

> 副作用：`verify-seed` 里那句"六种业务场景都有凭证样本"变成了**七种**。
> 差的这一种就是结转 —— **模板 6 套，业务场景 7 种**，这个差额本身就是上面这条判断的可见证据。

## 三、结转凭证必须从「发生额」口径里剔除（否则结账之后利润表变成 0）

结转的分录是「借 6001（冲平贷方余额）/ 贷 4103」。它一旦计入 `6001` 的**本期发生额**，
利润表算出来的营业收入立刻变成：

```
贷方发生 − 借方发生 = 本期收入 − 本期收入 = 0
```

于是 `subjectBalances` 把发生额拆成**两套**，各自服务于一个明确的问题：

| 口径 | 含结转凭证？ | 回答的问题 | 谁在用 |
|---|---|---|---|
| `period_*` | **是** | 这一期**账上**发生了什么 | 试算平衡表、科目余额表 |
| `operating_*` | **否** | 这一期**经营**上发生了什么 | 利润表、经营分析 |

两者都是对的，只是问题不同。**混用才会出错**，而它的表现是"结账之后利润表全 0"，
看起来很像"结转账算错了"。

**试算平衡表必须含结转**：它的恒等式是「期初 + 本期借 − 本期贷 = 期末」，
把结转剔除掉这条等式立刻不成立。**利润表必须不含结转**：它是"经营事件"的统计，
而结转是"把损益搬走"的记账动作。

### 附赠的一条强自证

> **结转前后，利润表给出的净利润必须完全相同。**

因为它剔除了结转账，而结转只是把同一笔金额从 6xxx 搬到 4103。
这条被写进 `test-closing.mjs`（M3 恒等式③），与下面这条并列：

> **结转前后，资产负债表的资产 / 负债 / 所有者权益三项合计也必须完全相同。**

（因为结转只在权益内部搬动：`BS_UNCARRIED_PL` 减少的正好是 `BS_RETAINED` 增加的。）

这两条把"结转是记账动作、不是经营事件"从一句注释变成了可以随时复算的断言。

## 四、四条硬口径

### 4.1 结转日期取**期间末日**，不是"今天"

`monthEnd('2026-02')` → `'2026-02-28'`。为什么必须算而不是写 `-31`：

- 2 月有 28/29 天，小月 30 天；
- 写死 `-31` 会让二月的结转凭证**落在一个不存在的日期上**，而 SQLite 不校验日期合法性 ——
  它会安静地存下 `'2026-02-31'`，于是这张凭证既不属于 2 月（月末对账扫不到），也不属于 3 月。

`lib/dates.js` 新增 `monthEnd(period)`（`new Date(y, m, 0)` 取"下个月的第 0 天"）。

### 4.2 结转**当场过账**，不留 draft

理由两条：

1. 一张没过账的结转凭证**不会改变任何报表数字**（`draft` 不计入），
   于是界面上会显示"已结转"而账上什么都没变；
2. `closePeriod` 的前置要求「本期没有未过账草稿」——
   留 draft 会让关账**必然失败**，把结转变成一步半的动作。

### 4.3 幂等：来源是**期间本身**，且**以凭证表为准**

`vouchers` 上有 `UNIQUE (biz_type, source_type, source_id)`（迁移 032）。
结转的来源是 `accounting_periods`（一张期间只能结一次），幂等天然成立。

但幂等判断**看凭证表，不看期间列**。理由：

- 只看期间列的话，"期间列被清空而凭证还在"会**撞数据库约束**，
  调用方拿到的是一个 `SqliteError` 而不是业务错误 —— 数据库约束不该是最后一道防线（它连"该怎么办"都说不出来）；
- 凭证表承载的是**实际发生过的事**，期间列只是它的一个指针。两者不一致时，以"发生过的事"为准，并把不一致报出来。

### 4.4 撤销结转 = **物理删除**，不是作废

`vouchers` 的唯一约束让"撤销后再结转"必须选一条路径。选物理删除，理由不是省事，
而是**这两类凭证的性质根本不同**：

| | 业务凭证（采购/销售/收付款） | 结转凭证 |
|---|---|---|
| 承载什么 | **人工录入的事实** | **派生结果**（可由当前科目余额完全重算） |
| 作废要留原票吗 | 必须 —— "当初为什么记这一笔"只存在于那张票上 | 不必 —— 留一张 voided 的派生凭证没有审计价值，而它挡住重结却是实打实的 |

配套三道硬约束（少一条它就会变成一把"谁都能删凭证"的钥匙）：

1. 必须写理由（记进 `accounting_periods.closing_reverse_reason`）；
2. **期间已关账时不许撤销**（先反关账）—— 这条保证"已关账期间的凭证"永远不会被删；
3. 只删 `biz_type='profit_carry'` 的凭证 —— 期间列就算被改坏了也删不掉业务凭证。

## 五、关账与反关账的联动（**一个在设计测试时才发现的死锁**）

### 5.1 关账新增一条前置

「关账」的定义变成：**这一期的账已经结平、定稿了**。所以 `closePeriod` 增加：

> ③ 本期已结转（或本期损益本来就为 0）

最后半句是刻意的：空期间没有可结转的东西，不结转也能关账 ——
否则每个空月都要先"结转 0 元"，荒谬。

**不做"自动结转"**：结转会生成一张已过账凭证（动账），而"关账"这个动作不该顺手往账里塞一张票。

### 5.2 死锁是怎么发现的

最初的实现里，`reopenPeriod` 也加了一道前置："本期已结转时不许反关账"（理由看起来很充分：
反关账之后期间重新可变，而结转还挂着，新补的发生额进不了本年利润）。

写测试时才发现：**这两道前置互相锁死**。

```
反关账  ← 要求：本期未结转
撤销结转 ← 要求：期间未关账
⇒ 已关账 + 已结转的期间，两条路都走不通
```

修正后的顺序只能是：

```
反关账（写理由）→ 撤销结转（写理由）→ 改账 → 重新结转 → 关账
```

即：**反关账不要求先撤销结转**（否则谁也走不了第一步），
而**撤销结转要求期间未关账**。

反关账之后、撤销结转之前，那一期处于"已结转但账又可变了"的中间态 ——
这个状态由 `closingStatus`（`carried && pending`）与自证探针 `CARRY_INCOMPLETE` 如实报出来，
**而不是靠一道会锁死流程的前置检查来避免**。

`reopenPeriod` 的返回值里因此多带了一个 `carried` 标记与一句 `notice`，让界面能提示这条路怎么走。

## 六、数据结构与新增面

### 6.1 迁移 035（不新建表，只往「期间」上加结转留痕）

| 列 | 含义 |
|---|---|
| `accounting_periods.closing_voucher_id` | 本期结转凭证 id（NULL = 未结转）。**只存 id 不存金额** —— 金额是派生量，存下来就有两个真值来源 |
| `closing_by` / `closing_by_name` / `closing_at` | 谁在什么时候结的 |
| `closing_reverse_reason` | 撤销结转的理由 |

另有 1 个索引、1 条设置（`closing_profit_subject` = `4103`）、1 个权限点（`finance.period.carry`）。

**权限点为什么与关账分开**：结转会生成一张已过账凭证（真的动账），而关账只是"把这一期封起来"。
让"能关账"的人自动获得"能动账"的能力是不对的。

迁移 `verify()` 的两条结构不变量：

- `closing_voucher_id` 非空 ⇒ 那张凭证必须存在、必须是 `profit_carry`、必须落在**同一个期间**；
- 结转目标科目必须存在、是叶子、是**权益类**（科目表非空时才查 —— 迁移先于 seed 跑）。

「已关账的期间必须已结转」这条**刻意不放迁移**：它是数据口径检查，而升级老库时
历史上"没结转就关账"的期间本来就存在（035 之前就是这么干的）。把它当迁移失败，
等于要求迁移去改业务数据 —— 迁移不该做这件事。

### 6.2 `lib/closing.js`

| 函数 | 作用 |
|---|---|
| `closingSubjectCode` / `closingSubject` | 结转目标科目（会计政策，唯一出处 `settings`）；三条校验：存在 / 叶子 / **权益类** |
| `planClosing` | **只算不写**：逐科目的余额与结转方向、完整分录、待结转净额、本期经营净利润 |
| `carryForward` | 生成 → 过账 → 回写期间；幂等 |
| `reverseClosing` | 撤销（物理删除 + 清指针 + 记理由）；三道硬约束 |
| `closingStatus` | 状态（`carried` / `pending` / 明细）——**界面与关账前置共用同一份判据** |

### 6.3 判据分离（同一份判据只有一个实现）

| 判据 | 唯一实现 | 调用方 |
|---|---|---|
| "本期有哪些损益科目挂着余额" | `lib/report.js` 的 `uncarriedProfitSubjects` | `closePeriod` 前置 / `lib/closing.js` 的结转账 / 自证探针 |
| 凭证平衡与科目合法性 | `lib/accounting.js` 的 `assertBalancedLines` | 模板路（预览）与结转路（落库） |
| "凭证怎么写进库里" | `lib/accounting.js` 的 `persistVoucher` | 同上 |
| 期间与结转类型常量 | `lib/period.js`（**依赖图最底层**，避免 `closing → report → period` 成环） | 三处 |

> `uncarriedProfitSubjects` 放在 `report.js` 而不是 `closing.js`：`closing.js` 依赖本文件，
> 反向 import 会成环；而"有余额未结转"只用得到科目余额，是报表域的知识。

## 七、自证探针（本批新增 5 条）

| 探针码 | 什么时候响 | 为什么单独报它 |
|---|---|---|
| `PERIOD_CLOSED_NO_CARRY` | 已关账、本期有损益发生额、但没结转 | 账没结平就定稿了 |
| `CARRY_INCOMPLETE` | 已结转、但损益科目仍有余额 | **报表靠「未结转损益」行凑平，所以别的检查都不会响** —— 这条是唯一会说话的 |
| `CLOSING_VOUCHER_BAD` | 期间记录的结转凭证不存在 / 不是结转账 / 已作废 / 挪了期间 | 期间说"已结转"、凭证说没有 |
| `CARRY_VOUCHER_ORPHAN` | 结转账还在、但期间没记它 | **反方向**的坏状态；要单独扫凭证表才看得见（从期间出发的遍历看不到） |
| `PL_MISMATCH`（既有，本批**修了它的公式**） | 利润表净利润 ≠ 损益类科目发生额复算 | 见第八节 |

## 八、本批抓到的一个既有缺陷（潜伏了两批）

批次 L 的自证探针 ③「利润表的净利润必须等于损益类科目发生额的按方向取号之和」
把公式写成了：

```js
direction === 'credit' ? -signed : +signed   // ← 费用类取了正号
```

正确公式是 `−Σ(全部损益类科目的 signed)`（"收入取正、费用取负"正好等价于"全部取负"，
这是借贷平衡的推论，**不需要按方向分支**）。

它**只在损益非 0 时才现形** —— 而演示库里 `busy` 期间（2026-10）的损益发生额恰好是 0，
于是这条探针长期恒真（`0 === 0`）。直到本批在测试里造出真实的损益发生额才被抓住。

这是「探针不响等于没有」的**第三种形态**：不是探针没跑，而是**它的公式写反了**。
前两种分别是"探针没被调用"（批次 J）与"断言参数顺序写反导致恒真"（批次 L）。
