## 0. 一句话

连锁餐饮的 ERP 不是“进销存 + 收银”，它的核心是**一条闭环**：

> 菜品卖出 → 按配方算出“理论上应该用掉多少食材” → 门店盘点得出“实际用掉多少” → 差异（AvT, Actual vs Theoretical）定位浪费/损耗/偷漏/配方错误 → 据此订货、调整配方和管理动作。

做到“能被初步使用”，标准是：**一家试点门店的店长、厨师长、收货员每天真的用它订货、收货、盘点，财务每周用它对供应商账，老板每周看它的食材成本率，并且这些数字能和 POS、银行、供应商单据对得上。**

## 1. 现有仓库与目标的差距（基于 main 代码核对，不是推测）

OS-ERP 继承自 GML（面向化妆品/食品分销的通用 ERP），已有大量可复用的地基，但餐饮核心能力缺失：

| 领域 | 现状（main `bea2d2d`） | 对餐饮的差距 |
|---|---|---|
| 门店/仓库 | `stores`（直营/加盟）、`warehouses.type=store` | 可复用 |
| 要货/配送 | `store_requisitions` / `store_shipments`、`stock_transfers` | 可复用，缺订货指南、配送日历、截单时间 |
| 批次/效期 | `inventory_stocks` 五维（含 `batch_no`、`expire_at` 精确到小时） | 可复用；但 `products.shelf_life_months` 按月，生鲜需按天/小时 |
| 盘点 | `stock_checks` | 缺盘点模板（按库位/动线排序）、日/周/月频次、移动端 |
| BOM | `boms` / `bom_items`（制造领料），已有 `version`、`effective_from/to`、`loss_rate` 并按生效期筛选 | 缺餐饮语义：菜品配方、出成率、发布后不可变版本与销售时点绑定、半成品库存边界、按销售计算理论消耗 |
| POS | `pos_orders`，且 `pos.js` 只允许 `item_type='product'` 成品销售 | 门店通常已有收银系统（美团/客如云/哗啦啦等），需要**导入**销售而不是替换收银；需处理套餐、加料、退菜 |
| 单位 | 每个商品只有一个 `unit` | 缺**多单位换算**（箱→袋→kg→g，采购单位≠库存单位≠配方单位） |
| 金额/数量 | `REAL` 浮点列，仓库内无定点/分为单位的统一工具 | 食材成本按克累计，浮点误差会在 AvT 和对账中累积，需定点方案 |
| 损耗 | 无原因码化的报损 | 缺报损（过期/操作失误/员工餐/试菜/赠送）与原因分析 |
| 成本 | `stock_cost_ledger`、`cost_periods` | 可复用；缺门店维度的食材成本率、AvT 报表 |
| 应付 | 采购、结算、付款释放台账、资金复核 | 可复用；缺供应商对账单三单匹配（订单/收货/发票） |
| 平台安全 | 审计哈希链、备份加密与恢复演练、能力门禁、数据范围、迁移校验 | 直接复用，这是现有仓库最大资产 |

结论：**不是从零开始**，而是在现有安全/审计/备份/库存地基上，补上“配方—理论消耗—盘点—差异—订货”这条餐饮主线。

## 2. 顶尖餐饮 ERP 专家会怎么做

参照对象是成熟的餐饮后厨/供应链系统的设计思路（如 Restaurant365、MarketMan、CrunchTime、Apicbase 一类的“back-of-house”系统，以及国内连锁常用的供应链+收银组合）。这里只取其方法，不复制任何具体产品。

### 2.1 他们的架构原则

1. **POS 是销售事实的唯一来源，ERP 不抢收银台。** 门店已有的收银系统负责点单/支付/会员；ERP 每日（或准实时）拉取明细，做幂等导入，并与 POS 的日汇总对账。
2. **配方是系统的“编译器”。** 菜品 → 配方（可嵌套半成品）→ 原料，配方带版本和生效日期，带出成率/净料率；理论消耗由“销售 × 生效配方”计算，可追溯到当时版本。
3. **三套单位，一张换算表。** 采购单位（箱）、库存单位（袋/kg）、配方单位（g/ml/个）分离，换算按物料定义，盘点允许按“整箱+散装”录入。
4. **营业日 ≠ 自然日。** 每店配置营业日切点（如 04:00），所有报表、盘点、日结按营业日归属。
5. **库存以“实物事件流水”为真，余额是投影。** 收货、退供、调拨、报损、加工转换、盘点调整是实物流水，可重建账面余额（现有仓库已具备基础）；理论消耗单独存放，只用于“预计余额”和 AvT，不进实物流水，避免与盘点重复扣减。
6. **结算金额用“分”，单价/成本用更高精度，数量用定点。** 单据金额整数分；单价与平均成本用微元等更细尺度（否则按克成本会被截断）；数量用千分位整数；换算系数用有理数；只在单据结算时舍入并归集尾差。
7. **门店端移动优先、弱网可用。** 收货和盘点在冷库/后厨用手机或平板完成，离线排队、恢复后提交、服务端裁决冲突。
8. **单企业单实例先行，数据范围按门店/区域隔离。** 总部、区域督导、店长看到的数据范围不同；加盟店的价格与结算口径与直营分离。
9. **异常驱动，而不是报表驱动。** 首页是“今天要处理什么”：未收货、到货差异、临期、AvT 超阈值、未盘点门店、价格异常。

### 2.2 他们会主动做、但你没有要求的事

| # | 事项 | 为什么重要 |
|---|---|---|
| 1 | 定义**营业日切点**与跨午夜订单归属 | 夜宵/烧烤店不定义会让日报全错 |
| 2 | **期初数据迁移**方案（物料、配方、期初库存、供应商价、未结应付） | 绝大多数上线失败死在期初 |
| 3 | **实测出成率**（到厨房称重），而不是相信配方卡 | 配方卡出成率普遍偏乐观，AvT 会被误判 |
| 4 | **SKU 帕累托/ABC**：前 20% 物料约占 80% 成本，A 类日盘、B 类周盘、C 类月盘 | 让盘点在 30 分钟内可完成，否则门店不会坚持 |
| 5 | **报损原因码** + 员工餐/试菜/赠送单独口径 | 否则 AvT 差异无法解释 |
| 6 | **订货指南/安全库存（par）** + 供应商**配送日历与截单时间** | 订货是门店每天最频繁的动作 |
| 7 | **收货验收**：数量/重量差异、拒收、温度、拍照、索证索票 | 食品安全法要求进货查验记录；也是供应商对账依据 |
| 8 | **效期标签/日期标签打印** | 后厨 FEFO 落地靠标签，不靠系统里的字段 |
| 9 | **价格变动监控**：供应商单价超阈值告警，配方成本自动重算 | 食材涨价是成本率失控的头号原因 |
| 10 | **新店开店模板**（物料集、配方集、订货指南、库位、角色一键复制） | 连锁的规模化能力 |
| 11 | **纸质应急流程**：系统宕机时的纸质收货/盘点单与事后补录 | 门店不能因为系统停摆停业 |
| 12 | **上线前基线 KPI**：现在的食材成本率、盘点耗时、订货耗时、缺货次数 | 没有基线就无法证明系统有价值 |
| 13 | **培训与 SOP**：一页纸岗位卡、视频、试点陪跑 | 门店流动性高，SOP 决定能否持续使用 |
| 14 | **过敏原/营养字段**（预留） | 合规和顾客询问，成本很低先留字段 |
| 15 | **数据留存期**：进货查验记录保存期限按食品安全法要求（保质期满后至少 6 个月，无保质期的至少 2 年） | 合规；需与备份/保留策略一致 |
| 16 | **月结与盘点绑定**：月末全盘 → 成本结转 → 期间锁定 | 财务口径可信的前提，现有期间结账可复用 |
| 17 | **POS 对账**：导入明细合计必须等于 POS 日报，不等则阻断成本计算并告警 | 防止“导入少了一页”导致虚假 AvT |
| 18 | **支持与运维手册**：谁接电话、如何恢复、如何回滚 | 能用 ≠ 可运营 |

### 2.3 他们会从哪些**最原始的素材**入手（而不是整理好的需求）

专家不从“需求文档”开始，而是从一线原始单据和现场开始（以下均为真实业务数据，**收集前**须取得用户书面数据授权，见 02 §8 门禁 G0）：

1. **POS 原始导出**：至少 3 个月、按订单行的明细（含套餐、加料、退菜、赠菜、折扣、营业时间戳），以及 POS 日结报表。
2. **供应商送货单、发票、对账单**（纸质拍照即可）：单位、包装规格、价格、配送频次的真实形态。
3. **门店现在的订货表、盘点表**（多半是 Excel 或纸）：真实的 SKU 数、命名混乱程度、盘点顺序。
4. **厨师长的配方卡/SOP**，以及**现场称重记录**（进货毛重→粗加工净重→成品份量）。
5. **现场观察（Gemba Walk）**：跟一个收货班、一个盘点、一个订货全过程，计时、拍照、画动线。
6. **门店库位布局**：冷藏/冷冻/干货区，决定盘点模板排序。
7. **门店 P&L 与银行/支付渠道结算单**：食材成本率的财务口径、渠道手续费。
8. **报损/废弃记录**（若有）、员工餐规则、试菜规则。
9. **卫生/食药监检查记录与整改单**：合规要求的真实来源。
10. **人员与角色表**：每店人数、谁收货、谁有订货权、排班。
11. **一线访谈原话**：店长、厨师长、收货员、区域督导、采购、财务各 2–3 人，“最近一次出问题是什么情况”。

### 2.4 具体方法

| 方法 | 用途 | 产出 |
|---|---|---|
| Gemba Walk / 跟班观察 + 计时 | 真实流程与耗时 | 现状流程图 + 基线耗时 |
| JTBD 访谈（Jobs To Be Done） | 每个岗位真正要完成的任务 | 岗位任务清单、优先级 |
| Event Storming / BPMN 流程建模 | 识别领域事件与单据流转 | 事件清单、状态机、单据关系 |
| 出成率实测（称重试验） | 校准配方 | 物料出成率表（含区间） |
| ABC/帕累托分析（POS × 价格） | 决定盘点频次与管控重点 | A/B/C 物料分级 |
| AvT 差异分析 | 系统核心价值的计算口径 | 差异公式、阈值、归因维度 |
| 期初数据清洗与映射 | 上线可行性 | 物料主数据、POS 菜品 ↔ 配方映射表 |
| 纸面/可点击原型 + 可用性测试（SUS） | 门店端可用性 | 原型 + SUS 分数 + 任务完成时间 |
| 影子运行（Parallel Run） | 证明数字可信 | 新旧并行一个完整自然月的差异报告（周报为过程产物，退出标准见 02 §8） |
| 黄金数据集 + 不变量/性质测试 | 计算正确性 | 可重复的回归夹具 |
| 混合负载与长稳（V05 框架，PR32 未合并） | 容量与稳定性 | 精确 SHA 的托管证据 |

### 2.5 具体工具（与现有技术栈一致，避免引入新运行时）

- **数据侧**：POS/供应商单据先落 CSV；用 Node 脚本（不在本机运行 Python）做清洗、映射与 ABC 统计；SQLite 合成库沿用 main 上的 `scripts/synth-data.mjs` / `scripts/synth-pipeline.mjs`。
- **建模**：BPMN/Mermaid 画流程与状态机（仓库内 Markdown 管理）；ADR 记录决策（沿用 `docs/implementation/ADR-*`）。
- **原型**：现有 React + Vite 前端做可点击原型，门店端为 PWA；移动端用 Playwright 设备仿真跑可用性脚本。
- **测试**：`node:test`；性质测试（如 fast-check，引入前需通过依赖审查与锁文件策略）；黄金数据集夹具；浏览器端到端沿用现有 browser 场景；负载沿用 `synth-data`/`synth-pipeline`，混合负载待 PR32 的 `mixed-soak` 合入后扩展。
- **验证环境**：GitHub-hosted Linux CI（当前公开仓库阶段的规定）；付费服务启动后切回 `dmserver`；macOS/Swift 相关在 `eva`。
- **独立审计**：Codex CLI 只读沙箱审计（见 03）；Haiku 等独立模型复审只审给定文本。
- **现场**：手机拍照（单据、库位）、电子秤（出成率）、秒表/录屏（计时）、温度计（收货验收）。

## 3. 除了你和我，还有什么能证明结果是正确的

“正确”分成四层，每层都需要**第三方或外部事实**作证，而不是开发者自证：

| 层 | 证据来源（非你我） | 判定方式 |
|---|---|---|
| **计算正确** | 黄金数据集（手工可算的小样例，由财务/厨师长签字确认的期望值）；性质测试（库存守恒、金额守恒、幂等导入）；独立模型审计 | 自动化测试 + 签字的期望值表 |
| **数据对得上外部事实** | **POS 日报**、**银行/支付渠道结算单**、**供应商对账单/发票**、**实物盘点** | 导入合计 = POS 日报；应付余额 = 供应商对账单；系统库存与盲盘差异在阈值内 |
| **业务上真的有用** | 试点门店**影子运行**（新旧并行）、上线前后 KPI 对比（盘点耗时、订货耗时、食材成本率、缺货次数）、店长/厨师长 SUS 可用性评分 | 有基线的前后对比；非开发人员能独立完成任务 |
| **可运营且安全** | GitHub-hosted / `dmserver` 的精确 SHA CI 与长稳证据；恢复演练记录；外部会计师对月结口径的确认；食药监检查时进货查验记录可调取 | 托管运行记录 + 外部角色签收 |

具体“证人”：

1. **POS 系统本身**（日报总额）——销售导入是否完整。
2. **银行与支付渠道账单**——收入口径是否真实。
3. **供应商**（对账单/发票）——应付与采购单价是否正确。
4. **实物**（盲盘，由非本店人员如区域督导执行）——库存是否真实。
5. **厨房电子秤**——配方与出成率是否真实。
6. **外部会计/财务负责人**——成本结转和月结口径是否可接受。
7. **试点门店员工**——能否在无人陪同下完成每日任务（可用性测试）。
8. **监管检查**——进货查验记录能否按要求调出。
9. **托管 CI/长稳运行记录**——精确 SHA 的可重复证据。
10. **独立审计模型/人员**——只读审阅设计与代码，不由作者自审替代。

## 4. 修改后的题目（可直接作为下一轮任务书）

> **任务：把 OS-ERP 落地为连锁餐饮门店可试点使用的轻量 ERP（后厨供应链与食材成本）**
>
> **背景**：OS-ERP（`osborn-studio/OS-ERP`，main `bea2d2d`）已具备库存流水、批次效期、门店要货、采购应付、审计哈希链、备份恢复和能力门禁等地基，但缺少餐饮核心闭环。目标客户是 5–50 家门店的中式连锁餐饮（直营为主、可含加盟），门店已有收银系统。
>
> **目标**：12 周开发准备后，让**一家试点门店 + 总部**在真实（经书面授权、脱敏处理）的业务中进行一个完整自然月的影子运行并完成月结（含等待月初，共约 18–22 周），使用以下闭环，而不是演示：
> 菜品与配方（含半成品、出成率、不可变版本与生效区间、门店加工转换）→ POS 销售幂等导入与多维对账（金额、订单数、行数、数量、赠菜、退菜、映射覆盖率）→ 理论消耗（账面/预计/实盘三数量模型，退菜按是否已制作区分） → 门店订货（订货指南、安全库存、配送日历/截单）→ 总部/中央厨房配送或供应商直送 → 收货验收（差异、拒收、温度、拍照、索证索票）→ 批次效期与 FEFO → 报损（原因码）与调拨 → 分级盘点（A 日/B 周/C 月，移动端，30 分钟内，离线冲突需复核）→ 以两次盘点为周期的 AvT（总实耗 = 理论 + 报损 + 非 POS 耗用 + 未解释差异）与食材成本率报表 → 供应商对账三单匹配与应付 → 月末全盘与期间结账。
>
> **你需要像顶尖餐饮 ERP 专家那样工作**：
> 1. 从原始素材入手：3 个月 POS 订单行导出与日报、供应商送货单/发票/对账单、现有订货与盘点表、配方卡、现场称重的出成率、门店库位布局、门店 P&L 与支付结算单、报损记录、岗位与人员表、一线访谈原话。缺什么素材，列清单向我要，不要自行假设或编造。
