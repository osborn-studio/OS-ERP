## 第 0 条（最高优先级）｜系统设计目的：MCP 原生开放

### 用户原话
> "先从设计这个系统目的来讲，是为了取代传统 ERP 系统，因为他们像金蝶和用友都不开放他们的 MCP，都需要购买 yonwork，或者他们智能体，才能使用他们 MCP，才能调用他们数据，这个是对市场阻碍，历史的倒退，所以我们现在开放的所有系统，都是从一开始就可以提供 MCP 的，可以完整给任何智能体调用的。"

### 结构化
| 项 | 内容 |
|---|---|
| 定位 | 取代传统 ERP |
| 动机 | 传统 ERP 的 MCP / 数据能力被产品绑定，需额外购买才能调用 |
| 判断 | 这是市场阻碍、历史的倒退 |
| **设计原则** | **本系统所有能力，从第一天起即为 MCP 原生，任何智能体可完整调用** |

### ⚠️ 助手核实：需要修正的表述（重要，涉及对外话术）

**事实核查结论：用友已公开支持 MCP，"不开放 MCP"这个说法会被客户当场反驳。**

用友 YonSuite 官方口径（2026-03 公开报道）：
> "智能体构建平台**对外开放，支持 MCP 协议**，打通第三方系统与伙伴应用，初步建成企业 AI 开放生态。"

**但是 —— 用友自己说出了更致命的问题，这段可以直接拿来用。**

用友官方文章《企业AI原生一体化：用友YonSuite如何让AI长进业务里？》（yonsuite.com/news/7149.html）原文：

> "而当前很多企业的 AI 往往采用'**外挂式 AI**'架构……当 AI 系统通过 MCP 协议或标准 API 对接现有 ERP、CRM 时，**权限体系需要手工映射，数据需抽取清洗后分析，执行结果需外部回写才能进入业务系统。AI 无法识别这种跨系统的身份同一性，不仅造成脏数据风险，更使得过程不可审计、错误不可追溯。**"

用友自己承认："企业 AI 从 Demo 到生产环境，中间隔着一整套工程化能力的缺失。"

**修正后的话术（更准确、更难反驳）：**

> 传统 ERP 的 MCP 是**外挂**的——ERP 本体不动，MCP 只是事后加的一层适配。
> 后果是他们**自己都承认**的：权限要手工映射、AI 认不出跨系统的身份同一性、过程不可审计、错误不可追溯、结果要外部回写才能进业务系统。
>
> GML 反过来做：**MCP 不是接口层，而是与业务同源的能力层**。
> 权限、主体、货主、审计是同一套；智能体调用走的是和人一样的规则，不是另一套旁路。

差别一句话讲清：**他们是在 ERP 外面套一层 AI；我们是从内核长出来的 AI 接口。**

### 这条对架构的传导（P0，会改框架文档）

1. **MCP 不是"最后一个模块"，而是"第 0 条原则"。**
   L1 表现层要开**第二入口**：`Web UI` 与 `MCP 能力层` **平级**，共享 L2 能力中心（不是 UI 层下面挂个接口）。

2. **L2 能力中心从"内部函数"升格为"对外契约"。**
   工具的输入 / 输出 schema 就是公开契约，不能随手写。这反过来说明 L2 必须真的存在——**现在它基本是空的，所以 MCP 层无东西可挂**。

3. **权限模型必须能表达「主体 + 动作 + 数据范围」，且不依赖页面 / 菜单。**
   MCP 调用没有"页面"这个概念，现有 8 个扁平角色 + 菜单可见性的玩法在这里失效。
   已定口径「组织 = 业务主体」正好提供锚点：**每次智能体调用必须携带主体身份。**

4. **幂等从 P2 升级为 P0。**
   原框架把幂等放在 P2。智能体重放、重试是常态，写操作必须幂等，否则一次网络抖动就是两笔单。

5. **审计必须记「哪个 Agent / 哪个主体 / 做了什么」，与人工操作同一条审计链。**
   不能是两套日志——否则"AI 干的不算数"的质疑无法回应。

6. **货主模型（已定口径）必须在 MCP 层可见。**
   智能体查库存若不能区分货主，委托代销 / 寄售仓会查错，这是业务性错误不是技术性错误。

7. **协议版本：直接建在现行规范 2026-07-28 上。**
   该版是 MCP 发布以来最大一次修订，核心变化：
   - **无状态核心** —— 取消 `initialize/initialized` 握手与 `Mcp-Session-Id`（任何请求可落到任意实例，无需共享存储）
   - 新增可选 `server/discover`（能力发现），每个请求自带协议版本与客户端身份（`_meta`）
   - **Streamable HTTP** 传输入口为 `POST /mcp`，需带 `Mcp-Method` / `Mcp-Name` 头（便于网关路由与鉴权）
   - 三大原语：**tools**（模型可控）/ **resources**（应用可控）/ **prompts**（用户可控）
   - 多轮往返（MRTR）取代服务端发起的 sampling / elicitation
   - 上一版 `2025-11-25` 仅为兼容旧客户端保留

### 现状差距（实测，非推测）

| 项 | 实测结果 |
|---|---|
| 全仓搜索 `mcp \| modelcontextprotocol \| jsonrpc` | **0 命中 —— 没有任何 MCP 实现** |
| 现有 `/api/ai/manifest` | **私有约定**的自描述清单（列模块 + 11 个 intent），调用方必须读我们的文档才能用 |
| 现有 `/api/openapi.json` | REST 描述，**不等于 MCP** |
| 结论 | MCP 层需**新建**；但可复用现有业务逻辑——先做**能力抽取**，把路由里的逻辑下沉成 L2 能力函数，再挂 tools |

**关键判断**：`/api/ai/manifest` 这种"私有自描述清单"，恰恰是我方要反对的形态（每个系统一套私有约定）。它是好的过渡，但不能作为终点。**新系统的 MCP 层要能被任何标准 MCP 客户端零文档直接发现、直接调用。**

### 待用户明确（不阻塞，可后续回答）

1. **开放程度**：MCP 工具集**只读查询**，还是**含写操作**（下单 / 审批 / 发货）？
   若含写，需先定「智能体权限与人工权限的关系」：同级 / 受限子集 / 高危动作需人工确认。
2. **鉴权方式**：MCP 客户端如何取得身份？复用现有 JWT，还是**独立签发 Agent Token**（可绑主体 + 权限范围 + 有效期）？
3. **多主体**：一次 MCP 会话能否切换主体（如同时看总部与门店），还是绑定单一主体？
4. **对外承诺边界**：'完整给任何智能体调用'——是否包含**全部业务动作**，还是**已实现的业务动作**（未实现的模块自然无法开放）？这关系到对外表述的严谨性。

### 1.2 本次 demo 的三条行业线
| 行业线 | 商品特征 | 对模型的强要求 |

## 第 2 条｜委外加工 + BOM + 简单生产

### 用户原话
> "刚才漏了委外加工，各种委外的处理情况都要覆盖，详细你可以看下用友的相关资料，里面各种情况说明了，有发料的，不发料的，等等，有委外核算单，然后整个系统要有一个 bom 情况的概念，有简单生产，bom 一个为了适应美妆里的组合妆几个商品合在一起组成一个新的商品啊，其中有几个需要委外的什么的。这种情况，下，如果需要采购这样的单子就可以有生产订单，生产模块也是要有的，bom、生产订单都是需要，mrp 以后再考虑暂时不考虑，简单来讲就是为了解决应对美妆的组合套，零食食品的组合套，餐饮的每个菜品的组合，服装的下料等。"

### 2.1 ⚠️ 对第 1 条的修正（重要）
第 1 条我记的是"不深入制造业"，并据此在 1.4 建议"生产/委外保留但隐藏"。**本条推翻该建议。**

**修正后的准确边界：**

| | 内容 |
|---|---|
| **要做（L2）** | **BOM**（多层，含组合/自制/委外三种用途）· **简单生产**（生产订单：领料 + 完工入库）· **委外全场景**（发料 / 不发料 / 委外入库 / 加工费结算 / 委外成本归集） |
| **不做（L3）** | **MRP 运算**（用户明确"以后再考虑"）· 工艺路线 · 工序派工报工 · 车间作业 · 产能与设备 · 凭证生成 |

> 一句话定性：**不做重型制造（MES 那一套），但要做"轻型加工与组合"（BOM + 简单生产 + 委外）。**

### 2.2 用友口径（摘自用户工作文档原文）

**《YS 生产制造 YDIC 实务题手册》**
- 模块四块：**数字化建模 / 生产计划 / 生产管理 / 委外管理**
- **生产计划**："针对计划物料，依据客户订单或产品预测单的需求，通过**物料清单展开**，并考虑现有库存和未关闭订单，而计算出各采购件及自制件的需求数量和日期"（☞ 这就是 MRP，本期不做）
- **生产管理**："以**生产订单**为核心，主要的业务处理包括生产订单日常维护、**生产备料领料及完工入库**等"
- **委外管理**："从签订**委外订单**开始，到**委外发料**、**委外加工品入库**，再根据**入库收票结算**，最后计算**委外成本**"
- 物料计划属性：产品 / 半成品设**自制**，原材料设**采购**，委外品设**委外**
- **BOM 类别**=「主BOM」，**BOM 用途**分「**自制**」与「**委外**」；母件 BOM 只有一个版本；**BOM 必须审核**；有**生效日期**
- 单据流实测：委外订单 —【下推·领料】→ **材料出库单**；委外订单 —【下推·入库】→ **委外入库单**；委外入库单 —【下推】→ **采购发票**

**《某美妆企业 YS 项目业务解决方案 V2.0》（同行业真实项目，最有参考价值）**
- 委外覆盖：**委外加工订单 → 原料发出 → 加工进度跟踪 → 委外收货 → 加工费结算 → 应付及成本归集**
- 目标："将当前依赖 Excel 和人工分摊的委外成本，纳入 YS 供应链、库存、应付和存货核算体系，形成**订单级、批次级、加工商级**的可追溯闭环"
- 场景原文："业务部门根据销售、库存或生产计划产生委外加工需求，向加工商下达委外订单。仓库按委外订单**发出原料，形成在外物资**；加工商完成加工后送货，仓库和**质检确认合格数量**并办理收货入库；采购或财务根据委外订单、收货记录和加工协议进行**加工费结算**；存货会计按订单**归集原料成本、加工费、损耗和异常费用**，形成委外成品或半成品成本。"
- 三句关键：①"按委外订单备料并办理**委外发料出库**" ②"**加工费结算关联委外订单**" ③"委外成本计算结果、总账凭证"
- 附带印证第 1 条缺口："当企业发生一些**非典型（非采购、生产）的入库**，以及**非典型的（非销售、领料）的出库**业务，需要由仓库管理员录入"（☞ 即其他出入库）

**委外两种供料模式（用友通用口径）**

| 模式 | 别称 | 含义 | 成本构成 |
|---|---|---|---|
| **委外发料** | 供料委外 / 委托加工 | 我方提供原材料，供应商只出工 | **材料成本 + 加工费 + 损耗** |
| **委外不发料** | 包工包料 / 全委外 | 供应商自购材料并加工，我方只收货付款 | **采购价**（含材料 + 加工） |

### 2.3 核心洞察：用户列举的四种场景，本质是三类业务

| 用户场景 | 业务本质 | 可逆性 | 成本规则 |
|---|---|---|---|
| 美妆**组合妆**（几个商品合成一个新商品） | **组合装** | **可逆**（拆开还是原商品） | 组件成本**加总**，无加工费、无损耗 |
| 零食**组合套**（礼盒） | **组合装** | **可逆** | 同上 |
| 餐饮**每道菜品的组合** | **加工 / 生产**（原料→成品） | **不可逆** | 原料成本 + **损耗**（+ 工时） |
| 服装**下料**（面料→裁片） | **加工 / 形态转换** | **不可逆**，有**用量与损耗** | 原料成本 + **损耗率** |

**这个区分决定单据与成本引擎怎么写：**
- **组合装** → 组装拆卸单语义：**可拆可还原**，成本 = 组件加总
- **生产/加工** → 生产订单 + BOM：**投入产出**，有损耗率，产出是新物料
- **下料/形态转换** → 形态转换单或生产订单：**用量 + 损耗**是核心

**⚠️ 食品的特殊硬规则（必须实现）**：加工产出的**效期由投入物料的最短效期决定**（餐饮菜品当日有效）。产出时必须自动计算并回写批次效期，否则食品线不成立。

### 2.4 ⚠️ 现状：现在有 **4 套重复的**投产出结构（必须合并）

| 结构 | 现有表 |
|---|---|
| 组合装定义 | `bundles` + `bundle_components` |
| 组装拆卸单 | `assembly_orders` + `assembly_order_items` |
| 生产订单 | `production_orders` + `production_order_items` |
| 委外订单 | `outsourcing_orders` / `outsourcing_order_items` / `outsourcing_materials` / `outsourcing_material_items` / `outsourcing_receipts` / `outsourcing_receipt_items` |

**四套结构在描述同一件事：「投入什么、产出什么」。** 这正是你说"整个系统要有一个 BOM 概念"要解决的问题——不合并的话，将来促销、成本、渠道映射每加一处都要写四遍。

### 2.5 建议：统一成「一个 BOM + 三类执行单 + 一张核算单」

**一个 BOM**
- `boms`：母件 `item_id` + **用途 `bom_type`**（combo / produce / outsource）+ 版本 + 生效日期 + 审核状态 + 基础数量
- `bom_items`：子件 `item_id` + 用量 + **损耗率** + 是否关键件 + 序号
- 支持**多层**（子件本身也可以是某个 BOM 的母件）——你说的"组合妆里有几个需要委外"正是两层的典型：**组合 BOM 的某个子件，本身是委外 BOM 的母件**

**三类执行单（都从 BOM 展开）**

| 单据 | 用途 | 关键动作 |
|---|---|---|
| **组装拆卸单** | 组合装（可逆） | 组装 / 拆卸两个方向 |
| **生产订单** | 自制加工 | 领料 → 完工入库（带损耗、自动定效期） |
| **委外订单** | 外部加工 | **发料（或不发料）** → 委外入库 → **加工费结算** |

**一张委外核算单**
- 新增 `outsourcing_settlements`：关联委外订单 + 入库单 → 加工费 + 应付事项；联同原料成本 → **委外成本归集**（订单级 / 批次级 / 加工商级）
- 现有 `outsourcing_orders` 补**供料模式**字段（发料 / 不发料）
- 承接第 1 条缺口：**委外收货必须过质检**（该方案口径原文"仓库和质检确认合格数量"）

### 2.6 BOM 用途枚举（写进口径，供后续模块引用）
```
bom_type:
  combo      组合装 —— 可逆，组件成本加总（美妆组合妆、零食礼盒）
  produce    自制   —— 不可逆，领料产出（餐饮菜品、服装下料）
  outsource  委外   —— 外部加工，发料或不发料（美妆半成品委外）
```
对齐用友「BOM 用途分自制和委外」，**我方多一个「组合」**——因为组合装在零售场景是独立的高频业务，且是**可逆**的，成本规则与生产完全不同。

### 2.7 待确认（不阻塞，可后续回答）
1. **组合装是否并入统一 BOM 体系？**（我建议**并入**；用友原生是"组装拆卸"独立成单，你也可以选择保持分离）
2. **服装"下料"用哪种单据？**（建议生产订单 + BOM，因为有明确用量与损耗；若只算形态变化不算加工，则用形态转换单）
3. **发料 / 不发料**是做成两种单据类型，还是同一单据带模式字段？（建议**同一单据 + 模式字段**）
4. **生产订单要不要报工？**（简单生产可只做"领料 + 完工入库"，不做工序报工——建议这样）
5. **餐饮的"菜品当日效期"要不要做？**（决定批次时间精度到**小时**还是天）

## 第 3 条：独立审批流设计系统 + 三端（钉钉/飞书/企微）对接 + 全端适配

### 3.1 用户原文

> 然后整套系统要有独立审批流设计系统，这个你参考下网上有没有现场开放代码的，还有可以参考泛微的，审批流设计。总之要能覆盖一个中型企业的审批流情况，其次所有审批流式可以和钉钉，飞书，企微对接的是可以同步的，账号可以同步，然后审批信息到代办，代办可以打开，一种适配原生钉钉，飞书，企微的单子，还有一种代办点开链接是我们的 h5 页面，直接跳出按我们的页面，二种方式你都衡量下开发难度。这个也意味着，系统开发出来的内容是适配三端，手机端，pad 端，pc windows mac 端的，是一个移动互联网系统。

**拆成五件事**：
1. 独立**审批流设计系统**（可视化流程设计器 + 引擎），覆盖中型企业审批场景
2. 与**钉钉 / 飞书 / 企业微信**对接：账号同步、审批同步、待办同步
3. 待办打开方式**两种**：A 原生适配对方平台的审批单；B 跳转我们自己的 H5 页面 —— **要求衡量两者开发难度**
4. 全端适配：**手机 / Pad / PC（Windows + macOS）**
5. 定位升级：不是后台管理软件，是**移动互联网系统**

**性质判定**：这是**第二条第 0 条级原则**。第 0 条（MCP 原生）定义了"**机器**怎么调我们"；这一条定义了"**人**怎么在移动场景下用我们"。两条共同构成"开放式系统"的两个入口。

### 3.2 技术选型：开源引擎调研 + 一个必须先说清的约束

**⚠️ 关键约束：主流开源审批引擎全是 Java，GML 是 Node.js 栈。**

| 引擎 | 语言 | 许可 | 适配度 | 结论 |
|---|---|---|---|---|
| **Flowable** | Java | Apache 2.0 | BPMN 兼容强、Spring 嵌入友好、"国内普及率高、企业通用审批首选" | ❌ 需另起 Java 服务 |
| **Camunda 7/8** | Java | 7 开源 / **8 是 SSPL** | 工具链与治理最强，金融制造大量落地 | ❌ 另起 Java 服务 + 8.x 协议风险 |
| **Activiti 7** | Java | Apache 2.0 | 迭代放缓、"新项目逐步被 Flowable 替代" | ❌ 不推荐新项目 |
| **JFlow / CCFlow** | Java | Gitee 开源 | **中国式审批配置化强**（加签/退回/分合流/组织权限）、自带表单+组织+待办门户 | ❌ 另起 Java 服务（业务口径可参考） |
| **泛微 e-Builder 流程引擎** | 商业 | 闭源 | 能力最全（见 3.3），但**不开放源码** | ❌ 仅作**能力清单参考**（用户已指定参考） |
| **bpmn-engine**（npm） | **纯 JS** | MIT | BPMN 2.0 执行引擎，Node ≥18，2026-09 仍在发版（v26.0.5），零运行时依赖 | 🟡 **可用，但见下** |
| **bpmn-server**（npm） | JS | MIT | 含建模器 + 持久化 + 监控 UI，但**默认强依赖 MongoDB** | ❌ 与 SQLite 冲突 |

**结论：不引入任何 Java 引擎。** 理由三条：
1. **技术栈一致性**——引入 Flowable/Camunda 意味着 GML 变成"Node + Java 双栈"，对演示系统是灾难：两套部署、两套运维、两套日志、两套发布。
2. **GML 要的不是通用 BPM**——BPMN 的完整能力（边界事件、消息事件、子流程、补偿、定时器）对零售供应链审批是**过度设计**。我们要的是"单据驱动的审批"，节点类型不超过 6 种。
3. **BPMN 用 XML 存流程定义**，与"审批流要能配置、要能把审批状态映射给三家 IM 平台"这两个需求不匹配——三家 IM 需要的是"外部实例 / 外部任务"这种**扁平的键值对**，不是 XML。

**选型建议：自建轻量审批引擎（表驱动），参考泛微的能力清单，不照抄其实现。**

- **流程定义用表存，不用 XML**：`flow_definitions`（流程头）+ `flow_nodes`（节点）+ `flow_edges`（连线）+ `flow_conditions`（条件表达式）。好处：可以用普通 SQL 查、可以出报表、可以被 MCP 直接读写（对齐第 0 条）。
- **备选方案**：若后续确实需要 BPMN 标准，`bpmn-engine`（MIT / 纯 JS）可作为**执行内核**挂进来，流程定义仍存表、导出时生成 BPMN XML。**建议先自建，把这条路留着。**
- **工作量量级**：引擎 + 设计器 + 待办中心，估计 1500~2200 行后端 + 1 个设计器页面 + 4 个待办页面。相比引入 Java 引擎的部署与联调成本，这是更省的路径。

### 3.4 ⭐ 核心：两种待办打开方式的开发难度衡量

用户明确要求"二种方式你都衡量下开发难度"。逐家核实后的结论如下。

**先看三家平台各自提供了什么**

| 平台 | 原生集成路径（方式 A） | 跳转路径（方式 B） |
|---|---|---|
| **钉钉** | ①创建/更新**业务分组**取 `dirId` ②保存**外部集成审批模板**取 `processCode` ③创建**外部集成审批实例**取 `processInstanceId` ④**保存外部集成审批任务**生成待办 `taskId` ⑤审批人在钉钉审批中心操作 → **回调**我方 → 我方**回写任务状态**<br>⚠️ 步骤④"保存流程中心外部集成审批任务"标注为**高级版专享接口** | 创建待办/流程中心待处理任务，传一个 `url` 即可；点击跳我方页面。**官方原文**："钉钉的待办页面也同时支持移动端和 PC 端，所以本接口传的 url 参数，它所对应的页面需要适配好移动端和 PC 端" |
| **飞书** | ①创建**三方审批定义**（含回调 URL）②**同步三方审批实例**（实例+任务+抄送）③发**审批 bot 消息** ④配置**三方快捷审批回调**（审批人可在飞书内直接批）→ 回调我方 → 再同步新状态回飞书，形成闭环<br>官方原文："审批中心不负责审批的流转，审批的流转在三方系统" | `links` 字段：审批实例链接集合，用于【已发起】列表跳转**回三方系统**；或发 bot 卡片消息带链接 |
| **企业微信** | 审批 API：`/cgi-bin/oa/applyevent`（发起/更新审批单）、`getapprovaldetail`（读详情）+ 审批状态变化**回调事件**<br>待办 API：`/cgi-bin/oa/todo` 系列（创建/更新/获取/更新状态待办）<br>应用消息推送 | **待办**系列直接支持带 URL 创建待办；应用消息（文本卡片）带 URL 跳转 |

**两种方式的难度对照**

| 维度 | 方式 A：适配原生单子 | 方式 B：跳转我们 H5 页面 |
|---|---|---|
| **需要适配的平台数** | **3 套**（三家 API 语义、鉴权、回调机制各不相同） | **1 套**（同一份 H5，三家只是"发消息 + 带链接"） |
| **需要在对方平台复刻什么** | **审批模板**（表单字段定义）+ **审批实例** + **审批任务**三件套，每家各一次 | 什么都不用复刻，只传一个 URL |
| **表单字段权限** | 要按对方平台的模板语法重新声明一遍 | 不需要（字段权限在我们页面里控制） |
| **回调与幂等** | **必须做**（审批结果回调 → 回写我方 → 再同步回对方，需要处理并发与重放） | **不需要**（审批动作在我们页面完成，天然一致） |
| **状态一致性风险** | 高（两端状态可能不一致，要有对账与修复机制） | 无（单一数据源） |
| **用户体验** | ⭐⭐⭐⭐⭐ 在钉钉/飞书里直接批，原生一致 | ⭐⭐⭐ 跳出应用，但页面可控、体验统一 |
| **演示冲击力** | 强（"在钉钉里就能批"最有说服力） | 中（"点开就是我的系统页面"） |
| **主要门槛/风险** | ⚠️ 钉钉该能力为**高级版专享接口**（可能涉及版本与费用）；三家 API 均可能变更；回调需要公网可达地址 | 无平台门槛；只需公网可达的 H5 地址 |
| **估算工作量** | 每平台约 1 套完整对接，**三家共约 3 倍** | **1 份**（两端就绪） |

**建议策略：B 为主 + A 选一家做样板（渐进式）**

| 期 | 做什么 | 理由 |
|---|---|---|
| **一期** | **方式 B 全三家**：待办/消息推送到钉钉、飞书、企微，点击跳我方 H5 审批页 | 一次开发覆盖三端 + PC + 移动浏览器，**边际成本≈0**。且这正好满足"适配手机/Pad/PC"的三端要求——H5 天生就是三端 |
| **二期** | 选**一家**做**方式 A 深度原生适配**（建议飞书，因其文档最规范、三方审批接入路径最清晰；或钉钉，若用户企业生态在钉钉） | 作为"原生集成"的样板与演示亮点，避免一开始就背三家 |
| **三期** | 其余两家按需补方式 A | 客户实际用哪家不确定，**不该提前绑死三家** |

**一句话**：**B 是"一套页面打三家"，A 是"三套适配打三家"。** 先用 B 把闭环跑通、把审批中心做扎实，再用 A 挑一家做深度亮点。

### 3.5 账号与组织同步：必须先定"谁是主数据"

用户说"账号可以同步"——这里有个**方向性决策**必须先定，否则会出现"同一个员工两个账号 / 部门层级打架"。

| 方案 | 含义 | 评价 |
|---|---|---|
| **IM 为身份来源 + GML 为业务主档（推荐）** | 员工账号与部门从钉钉/飞书/企微同步进来，**GML 的组织主体（第 1 轮定的"组织=业务主体"）由 GML 自己维护**，两者用映射表关联 | ✅ 分工最清晰：身份跟着 IM 走（员工入职离职 IM 最先知道），业务主体跟着 GML 走（总部/门店/渠道商是业务概念，不是 IM 概念） |
| GML 为主，推送至 IM | GML 建组织与账号，推到 IM | ❌ 与 IM 的事实地位冲突（员工入职 IM 先知道） |
| 双向同步 + 冲突策略 | 双向，遇冲突按规则选边 | 🟡 复杂且易出错，演示期不建议 |

**映射设计**：
- 新增 `im_user_map`：`gml_user_id` ↔ `platform`（dingtalk/feishu/wecom）+ `external_user_id` + `union_id` + `synced_at`
- 新增 `im_dept_map`：`org_id`（GML 组织/部门）↔ `platform` + `external_dept_id`
- **一个人可以在三家 IM 都有账号**（现实如此），映射表按 `platform` 分多行
- **注意企业微信的特殊性**：企微的 `userid` 与 `open_userid` 需要转换（其更新日志明确提到"支持第三方应用与企业智能机器人 open_userid 的转换"），映射表要两个字段都存

**同步内容**：新增 / 更新 / 停用启用 / 部门调动 / 离职冻结。**离职必须同步冻结账号**（这是安全底线，也是三端对接最容易被问的合规点）。

### 3.6 全端适配：从"后台管理软件"到"移动互联网系统"

用户圈定四类终端：**手机 / Pad / PC(Windows) / PC(macOS)**。技术上这实质是两件事：

**① 响应式设计（一套代码适配四端）**
- 现有基础：POS 端已触屏化、商城已手机优先、后台侧栏已抽屉化、`viewport-fit=cover` + iOS PWA meta 已配
- **要补的**：后台管理页现在是**桌面优先**，需补移动断点；**审批待办页必须移动优先**（待办大多在手机上处理）
- 三档断点：手机 `<768` / Pad `768~1024` / 桌面 `>1024`

**② 审批场景的移动端专属能力**
- **手写签名**（触屏签批）—— 移动端审批的标配，桌面用鼠标涂鸦体验差，需按端区分
- **审批意见快捷短语**（手机上打字慢，"同意，按合同执行"这类应有预设）
- **拍照上传凭证**（移动端审批常需补附件，调用相机）
- **消息推送**：除三家 IM，还需**浏览器 Web Push**（PC 不装 IM 的场景）

**③ 定位升级带来的连带要求**
- 既然叫"移动互联网系统"，**全站必须 HTTPS**（否则相机、推送、PWA 全部不可用）
- 需要**域名与公网可达地址**（否则三家 IM 的待办点不回来、回调收不到）—— 这是**部署形态的硬要求**，与当前"localhost 演示"有本质区别

### 3.7 架构传导：这条口径会改掉的三处

**① 审批与单据解耦（最重要）**

现状是**审批动作直接改单据状态**：
```
server/routes/purchase.js:204
const flow = { submit: ['draft','submitted'], approve: ['submitted','approved'], close: ['received','closed'] }
...
db.prepare("UPDATE purchase_orders SET status='submitted' WHERE id=?").run(id)
```
这是**把两件事揉在一个字段里**：单据的**业务状态**（草稿/生效/已收货/已关闭）和**审批状态**（待提交/审批中/已通过/已驳回）。后果：加一个审批层级就要改一次单据表；审批记录无处可存（`audit_logs` 只有 8 行且只记动作，不记审批人/意见/节点/耗时）。

**改法：两轴正交 + 引用关联**
- **业务轴**（单据自己的字段）：`draft → effective → closed`（按单据类型各自定义）
- **审批轴**（审批中心的字段）：`none → pending → approved / rejected / cancelled`
- 单据只加两个字段：`flow_instance_id` + `approval_status`，**不存审批过程**
- 审批中心用 `biz_type + biz_id` 挂接任意单据（采购订单、销售订单、调价单、返利单、要货单……）
- **好处**：新增一个要审批的单据，**不改审批引擎**；改审批流，**不动单据表**

**② 审批中心升格为共享能力中心（L2）**

框架文档第五节列的共享能力中心里，**新增「审批流中心」**，归属 L2。它对外提供：
- 流程定义管理（CRUD + 版本发布）
- 实例启动 / 推进 / 终止
- 任务查询（待办 / 已办 / 已发起 / 抄送我）
- 条件求值、审批人解析（含角色/主管/组织主体解析）
- 字段级权限判定
- **三家 IM 适配器**（统一成 `IPlatformAdapter` 接口，各自实现）

**③ 三家 IM 对接必须是"适配器"而非"三份代码"**
- 定义统一内部模型：`ExternalInstance`（实例）/ `ExternalTask`（任务）/ `ExternalMessage`（消息）
- 三家各写一个 adapter，把内部模型翻译成各家 API
- 好处：加第四家（如飞书国际版、自研 IM）= 加一个 adapter，不改核心
- **这也正是 MCP 第 0 条原则的同一种做法**：能力同源，出口适配

| 项 | 现状 | 差距 |
|---|---|---|
| 审批引擎 | **完全没有** | 从零建 |

### 4.7 餐饮版视觉 —— **已定：米白 + 靛蓝（和风素雅）**
