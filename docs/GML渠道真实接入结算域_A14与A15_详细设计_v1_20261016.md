# GML 渠道真实接入结算域（A14）与撤单逆向闭环（A15）详细设计

> 版本 v1 · 2026-10-16 · 批次 I 第 10 批（**重开批次 F：渠道闭环**）
> 上游依据：`docs/GML验收阻断缺陷登记_v1_20261016.md` §A14 / §A15；`INBOX_给主编写.md` §十四 第 4 步
> 结论：**A14 动态复现成立 ⇒ 按验收侧要求重开 F 渠道闭环**；A15 同期收口。

---

## 一、一句话

营销中心（模块 18）早已是一个完整模块 —— 促销引擎、会员等级、券生命周期、积分与储值、结算分摊层全都在，
但**真实的商城与 POS 下单根本没有接进来**：`checkout.settle` 全仓只有两处调用
（后台人工端点 `routes/promo.js` 与演示造数 `db/promo-seed.js`）。

于是出现了这个系统最不该出现的形态：**同一件事有两套算法，而界面上一分钱都看不出来。**

| 事项 | 商城自己的算法（`routes/mall.js`） | 营销域的算法（`lib/member.js`） |
|---|---|---|
| 积分 | `UPDATE mall_customers SET points = points + FLOOR(实付)` → **1 元 1 分** | `settings.promo_points_per_yuan` 默认 **10 分/元**，再乘等级倍率 |
| 价格 | `price_member × 数量 + 满 199 免运` | 等级折扣 → 促销 → 券 → 积分抵扣（顺序固定） |
| 留痕 | 无 | 优惠留痕 + 使用登记 + 券核销 + 积分流水 |
| 撤单 | 无 | 承诺"成对回退"（实际只做了一半，见 A15） |

## 二、A14 动态复现（**走真实前端下单路径，不用 seed 造单**）

验收侧特别点名：「**A14 若复现须重开 F，不得用 seed 造单证明真实渠道已集成**」。
所以复现一律走 HTTP：`POST /api/mall/login` → `POST /api/mall/cart` → `POST /api/mall/orders`。

修复前实测（美妆库，SKU#1 会员价 ¥993.6 × 2）：

```
mall_customers.points      1987 → 3974     （Δ 1987 = FLOOR(1987.2)，1 元 1 分）
member_accounts            该客户不存在     （这辈子没进过会员账本）
member_points_ledger       []               （赠分无流水，对账时无从追溯）
promotion_adjustments      0 条             （促销完全没参与）
promotion_usages           0 条
oms_orders.discount_amount 0                （pay_amount = 商品额 + 0 运费）
```

四条同向证据：**钱算错了（无任何优惠）· 分送错了（差 10 倍）· 账没留（无流水无留痕）· 会员账本里没这个人**。

> 结论：A14 **成立且为 A 级（动态复现）** ⇒ 重开批次 F。

## 三、修法的取舍：谁决定价格

一个必须先回答的问题：**基准单价由谁定？**

若营销域自己查 SKU 价格，就会出现"货架上标 ¥993.6、结算按 ¥1177.6 算门槛"这类分叉。
所以本批确立一条口径：

> **通道决定基准单价（取价引擎的出口），营销域只在这条基准价之上做折扣。**

- 商城：基准价 = `price_member || price_retail`（就是货架上标给客户看的那个数）；
- 门店：基准价 = 有会员手机号则取 `price_member`，否则 `price_retail`（与旧口径一致）；
- 之上依次是 **会员等级折扣 → 促销 → 券 → 积分抵扣**（顺序由 `checkout.quote` 固定，不在通道里重排）。

**运费不参与折扣**：它是履约成本，不是商品。所以它是 `quote` 之外的加项
（`应付 = quote.payable + freight`），而不是塞进明细 —— 塞进去会被会员折扣与促销一起折掉。

### 3.1 「取价」只留一处（本轮第二个真实缺陷）

试算与落单原来分别取价：试算走 `buildItems` 的默认值（= `price_retail`），
落单用 `price_member || price_retail`。**同一个购物车在试算页与落单时是两个金额** ——
促销门槛按 A 价判、钱按 B 价收。

实测差异：试算算出应付 ¥1714.24，落单时因基准价不同导致促销档位变化，`DEDUCT_EXCEEDS_LIMIT`
把客户"最多能抵的积分"从 21665 分改判成 19064 分。

修法：商城侧加**唯一取价入口** `mallLineItems(db, items)`，购物车展示 / 试算 / 落单全走它；
门店侧对应 `pos2.posQuote()`。并以一条断言锁死：**试算的 `pay_amount` 必须等于落单的 `pay_amount`**。

## 四、来源通道 `source`：迁移 `030_settlement_source`

### 4.1 为什么必须加这一列

把商城与 POS 都接到 `checkout.settle` 之后，立刻冒出一个必须先解决的问题：

> `promotion_adjustments.order_id` / `promotion_usages.order_id` / `member_points_ledger.source_id`
> **只存了一个整数**，而 `oms_orders.id` 与 `pos_orders.id` 是两张**独立自增**的表，都会从 1 开始。

于是"商城第 418 单"与"门店第 418 单"在这些表里长得一模一样，四条串号路径全部不报错：

| 串号路径 | 后果 |
|---|---|
| `revertUsage(orderId=418)` | 把两张单的优惠留痕**一起撤掉** |
| `persistAdjustments(orderId=418)` | 先 `DELETE ... WHERE order_id=418`，清掉另一张单的留痕 |
| `releaseCoupon(orderId=418)` | 把另一张单核销掉的券**退回去** |
| `redeemPoints/earnPoints` 的幂等判重 | 让"第二张 418 单送分"被当成重复而**静默不送** |

（同类事故在本项目已有先例：`purchase_settlement_items.source_id` 在 `receipt` 下是入库单 id、
在 `invoice` 下是发票 id，漏了 `source_type` 就联出了一批不存在的关系。）

### 4.2 加列与回填

```
promotion_adjustments.source  TEXT NOT NULL DEFAULT 'oms'   -- 'oms' / 'pos'
promotion_usages.source       TEXT NOT NULL DEFAULT 'oms'
member_points_ledger.source   TEXT                          -- source_type 仍是 'order'，source 才是通道
coupon_instances.source       TEXT
member_points_ledger.base_cents INTEGER                     -- 赠送积分对应的消费基数（分），见 §5.2
pos_order_items.{member,promo,points}_discount_cents         -- 门店单的行级优惠三段，与 oms_order_items 对称
```

- 索引：四张表各加 `(source, order_id)` 组合索引；
- 存量回填：迁移前**只有一个真实来源**（人工端点与演示造数都按 `oms_orders.id` 归属）⇒ 一律 `'oms'`；
- `base_cents` **留 NULL 不猜**：老数据那笔消费当时没被记下来，反推不出来；
- `verify()` 自带不变量：留痕/登记的 `source` 不得为空。

### 4.3 幂等键也要带通道

`promotion_usages.idempotency_key` 由 `order:<id>:promo:<code>` 改为
`<source>:order:<id>:promo:<code>` —— 不带通道时，第二张同号单会被判成重复而**静默少登记一个名额**。

## 五、A15：撤单的逆向必须成对

### 5.1 旧实现漏了什么

`checkout.unsettle` 撤销一笔订单时，积分上其实发生了**两件方向相反的事**，旧实现只做了一件：

| 事 | 旧实现 | 后果 |
|---|---|---|
| ① 该单**赠送**的分扣回 | 做了（按可用余额封顶，且如实报 shortfall） | — |
| ② 该单**抵现用掉**的分退回 | ❌ **完全没做** | 客户撤单**白丢一笔积分**，且丢得没有任何痕迹 |
| ③ 累计消费回退 | ❌ 没做 | 一张撤掉的 ¥1 万订单**继续顶着他的会员等级**，下一单按金牌折扣结算 |
| ④ 逆向幂等标记 | ❌ 没有 | 重复撤单会把积分退/扣两遍 |

### 5.2 「回退多少」不能靠调用方再算一遍

修法上有一个容易走错的分岔：让调用方把"当初计入的消费额"再算一遍传进来。

**这条路是错的**，实测立刻暴露：餐饮库客单价约 ¥28，不满 ¥199 要收 ¥12 运费，
而**送分基数不含运费** —— 调用方按 `pay_amount`（含运费）反推，
撤单时就会**多退 ¥12 = 1200 分**的累计消费（实测 `200000 → 198800`）。

> 所以：`earnPoints` 把**本次计入累计消费的基数**写进流水 `member_points_ledger.base_cents`，
> `reverseOrderPoints` 从流水里**读回来**。判据只有一处，调用方算错也不会污染账。

（老数据 `base_cents` 为 NULL 时退回调用方给的名义金额 —— 如实降级，不假装精确。）

### 5.3 累计积分只增不减：撤单为什么**不动** `points_total`

`levelOf` 用「累计积分 + 累计消费」两个门槛的**与**关系判等级，所以只要累计消费回退，
等级自然会掉下来。而 `points_total` 的口径是"**历史累计获得**"，退回的抵现积分是
"把之前扣掉的还回去"，不是新赚的 ⇒ 不进 `points_total`。

为此同步调整 `auditMember` 与 `verify-seed` 的口径：
**「累计获得 = 正变动之和」但排除 `source_type='order_reverse'`** —— 两处必须一起改。

### 5.4 五条一起成败的事由一段代码划定边界

撤单要同时做：撤留痕、退使用登记与预算、退券、**退抵现分 + 扣回赠送分 + 回退累计消费**、改单状态。
所以 `POST /api/mall/orders/:id/cancel` 与 `pos2.voidPosOrder` 都把它们包在**同一个事务**里：
只成功一半的后果是"券退了、分没扣"，而错误信息只会说"积分不足"，与操作者按的"撤单"看不出关系。

## 六、顺带收口的一个漏网入口（A16 遗留）

`/api/promo/shop/member`、`/api/promo/shop/quote`、`/api/promo/shop/claim` 三个端点
原标注是「**免登录，手机号即身份**」：`phone` 直接从查询串/请求体取。

**手机号是公开标识（印在快递单上），不是凭据** —— 知道一个手机号就能读他的会员等级、积分、
储值、券包，还能替他领券。A16 收口时只改了 `routes/mall.js`，这三个是**漏网的那一个入口**
（正是"逐个接口手写用例挡不住"的那类漏）。

修法：把 C 端会话抽成**唯一实现** `middleware/mall-session.js`（登录签发 / 会话校验 / 取会员档案），
`routes/mall.js` 与 `routes/promo.js` 都用它，身份一律取 `req.mall`，请求里的 `phone` 一律忽略。

## 九、三条硬口径（写死在代码里）

1. **算钱只有一处**：`checkout.quote` 是唯一的算钱判据；通道只提供基准单价与运费。
   试算与落单必须给出同一个数 —— 商城有 `落单应付 = 试算应付`、门店有
   `SETTLE_PREVIEW_MISMATCH` 当场抛错两道闸。
2. **留痕必须能定位到唯一一张单**：`source` 必填（`settle`/`unsettle`/`revertUsage`/`registerUsage`/
   `redeemCoupon`/`releaseCoupon`/订单积分流水），`promotion_usages` 的幂等键带通道前缀。
3. **撤单成对**：留痕、使用登记与预算、券、积分（赠送扣回 + 抵现退回）、累计消费，
   五件事在**同一个事务**里做完；回退额度以流水 `base_cents` 为准，不靠调用方再算。

## 十、连带影响与清理纪律

- **营销留痕不随业务单级联删除**：门店开单现在会落 `promotion_adjustments`/`promotion_usages`
  并把 `promotions.used` 加一，而 `test-pos2` 的清理只删 `pos_orders`
  ⇒ 留下 11 行指向已删订单的留痕，`verify-seed` 的「来源通道自洽」**永久失败**。
  修法：清理时先 `revertUsage` 成对回退，再删订单行；并**兜底清孤儿 + 按现存明细重算两个计数器**
  （只删留痕不重算 `used`，下一条不变量会接着失败）。
- **`verify-seed` 第 9 节「跨代引用自洽」** 新增两条，覆盖 `source` 指到不存在单据的情形 ——
  这正是"oms 418 与 pos 418 撞号"的守卫。
- **旧演示库遗留的冗余列漂移**（`mall_customers.points` ≠ `member_accounts.points`）
  来自修复前的旧算法，重建（`reseed-all --force`）后自然消除。
