## 0. 一句话定位

门店 POS 在批次 E 之前只有**半个闭环**：能开单、能出库、能把当天的单子打包传到总部。
但**钱对不对得上，在库里没有位置**。

`pos_shifts` 原来只有四个字段（门店、收银员、日期、状态），`pos_orders` 上也没有任何字段指向班次。
于是：

- 「这个钱箱今天该收多少现金」要临时用「同门店 + 同营业日 + 同收银员」把订单捞出来现算；
- 「收银员报了数没有、店长数过没有、长短款多少」在库里根本没有列可以落；
- 长短款与现金缴款之间没有任何约束，缴两次、缴错人都不会报错。

一个开在真实门店的系统，最不能含糊的就是这一段。本模块补齐的正是它：

```
开班 PSF ─────► 收银开单 ─────► 报数交班 ─────► 核款 ─────► 缴款 JKD ─────► 总部点收
定备用金        订单绑 shift_id   收银员报数      店长实点     缴款单         在途归零
                                  （第二段钱）    （第三段钱）
                                                              └──► 日结上传（有核款门禁）
```

同时把门店侧另外两条**进出现金与实物**的路径接上：
门店退货（顾客退货 → 货回门店仓 + 冲减班次应收）与门店盘点（复用 `stock_checks`，`scope='store'`）。

## 1. 三条硬口径

这三条不是实现细节，是**会算错数**的地方。任何一条放松，报表都会给出看起来合理的错数。

### 口径一：长短款 = 实点 − 系统应收（方向不能反）

```
variance = counted_cash − sys_cash
         = 店长实点数 − 本班次订单按现金方式汇总的应收
```

- **长款（variance > 0）**：钱比账多。找零数错、漏记退款、顾客不要找零。
- **短款（variance < 0）**：钱比账少。找零多给、漏收款、飞单。

方向写反的后果不是「数字差一个负号」—— 报表会把**短款读成长款**，
于是「亏钱的店」在报表上和「正常的店」长得一模一样，直到盘点日才发现窟窿。
所以界面上不出现「差异方向下拉框」，方向永远由减法决定；界面上只让人填**原因**与**归属**。

### 口径二：必须按支付方式拆分

`pos_shift_payments` 一个班次一种支付方式一行（`UNIQUE (shift_id, method)`）。

为什么不能只记一个总额：

| 差异出现在 | 金额含义 | 该谁查 |
| --- | --- | --- |
| 现金 | 收银员手上真的多/少了纸币 | 门店店长 → 追收银员责任 |
| 微信 / 支付宝 / 银联 | 支付流水与订单不一致 | 总部 → 查网络、查对账、查重单 |

把两者合成一个「今日差异 −35 元」，店长会去盘问收银员，而真实原因可能是下午断网导致
一笔微信收款没回调。**两类问题的排查路径完全不同，所以必须在数据层就分开。**

另外还有一条更细的：**报数阶段现金差异恒为 0**。
收银员报数时现金是「照系统应收报的」（他没数钱，数钱是店长的活），
所以那一刻现金差异必然是 0，非现金差异却立即成立（读支付流水就知道）。
把这件事落到数据上，报数阶段就不给现金行算 diff —— 否则会凭空造出一个
「收银员自己承认短款 200」的假结论。

### 口径三：备用金不参与长短款

`opening_float`（钱箱备用金）单列，不进 `sys_cash`，也不进 `counted_cash` 的比对。

理由：备用金是店里的**零钱本金**，不是销售收入。若把它算进应收，
每天开班金额一变，长短款就跟着变 —— 差异不再是「今天哪里出了问题」，
而变成「今天开了多少备用金」。核款时用 `float_returned` 决定这笔钱是否已归位钱箱。

## 2. 数据模型（迁移 024）

### 2.1 三张新表

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `pos_shift_payments` | 一个班次 × 一种支付方式的三段金额（系统应收 / 报数 / 实点）与差异 | `UNIQUE (shift_id, method)` —— 一种支付方式一行，重复报数只能覆盖不能追加 |
| `pos_cash_drops` | 缴款单（`JKD` 前缀）：某门店某日把若干班次的现金交出 | 缴款人 / 接收人 / 凭据号 / 状态 |
| `pos_cash_drop_items` | 缴款单 ↔ 班次 | `UNIQUE (shift_id)` —— **一个班次只能缴一次款** |

`UNIQUE (shift_id)` 这条不是洁癖。没有它，同一个班次的现金可以被缴两次，
而在途看板只按 `cash_drop_amount` 求和，多缴的那笔会**把别的班次的欠款抵掉** ——
表现为「有的店在途金额比实际少」，且不报错。

### 2.2 扩列

`pos_shifts`（`SHIFT_COLUMNS`）：

```
doc_no / device_no / closed_by(_name)
sys_cash / declared_cash / counted_cash / variance / variance_note / variance_handled
approved_by(_name/_at) / cash_drop_amount / daily_close_id / opening_float_done / updated_at
```

`pos_daily_closes`（`CLOSE_COLUMNS`）：
`shift_ids / closed_shift_count / sys_cash / counted_cash / cash_variance / drop_amount / variance_note / created_by(_name) / updated_at`

`stock_checks`：`scope`（默认 `'hq'`）+ `store_id` —— 门店盘点与总部盘点**同表不同范围**，
不另起一张表，因为两者的行结构、差异过账逻辑完全一样，分开只会让「盘点」这件事有两个定义。

`pos_orders`：`shift_id` —— **订单归属靠外键，不靠现算**。

> 这一列是本模块最关键的一次口径修正。原来「这个班次的应收」是用
> 「同门店 + 同营业日 + 同收银员」去捞订单。门店一天两班（早班 / 晚班）时，
> 两个班次会捞到**同一批订单**，现金应收直接翻倍 —— 而且**不报任何错**，
> 只是两个班的核款都不对。改成 `shift_id` 之后，归属是一个确定的引用，
> 算错的可能性从「口径写错」降级为「外键写错」，后者会被约束拦住。

### 2.3 两个视图与唯一口径

| 视图 | 用途 |
| --- | --- |
| `v_pos_shift_variance` | 班次一屏：三段钱 + 支付方式条数 / 差异条数 / 差异合计 + 有效订单数与金额 |
| `v_pos_cash_inflight` | 门店资金在途：待缴现金 / 长短款合计 / 待核款班次数 / 营业中班次数 |

**门店端与总部端读同一个视图** —— 资金在途只有一个定义，不允许多算一遍。
总部总览里的 `cash_to_drop` 也是走 `cashInflight()`。

### 2.4 索引 / 权限 / 编码规则 / 设置

- 唯一索引 `uq_pos_shifts_doc_no ON pos_shifts(doc_no) WHERE doc_no IS NOT NULL`
  （部分唯一索引：历史班次在回填前 `doc_no` 为空，不能用全列唯一索引）。
- 权限点：`pos.shift.review`（核款）、`pos.cashdrop`（缴款）、`pos.store.check`（门店盘点），
  随 `ROLE_GRANTS` 分配给店长 / 收银 / 总部角色。
- 编码规则：`PSF`（班次）、`RC`（班次出库单，`doc_no_field = batch_no`，前缀 `RBJ`）。
  单据类型总数 36 → 38。
- 设置项 `pos_variance_limit`（默认 `500`）：**门店自结上限**。

  超过这个金额的差异，`approveShift` 会**强制**把归属改成 `pending`，交总部处理。
  门店不能自己把一笔 3000 元的短款写成「公司承担」了事 —— 这条限制写在服务端，
  界面上那三个归属按钮在超限时是灰的，但就算绕过界面直接打接口也一样被拦。

## 3. 单据内核与状态机

班次 `PSF` 进内核（第 37 种单据类型），业务流 `FLOW_POS` 六步：

```
open ──declare──► declared ──approve──► closed
  │                   │
  │                   └──reject──► open（退回，清空本次报数）
  └──cancel──► cancelled   ◄──cancel── ┘
```

四个状态：`open / declared / closed / cancelled`。

**`close` 动作已被删除**。旧的「直接关班」等于绕过核款 —— 只要有一个入口能绕过，
长短款就会有一半的单子不产生差异，而报表上看不出少了什么。现在唯一的路径是
`declare → approve`。

`closed` 是**终态**，但长短款的归属可以在其后变更：`settleVariance` 不是状态流转，
它是直接改 `variance_handled` 字段 + `logEvent` 留痕。总部把一笔挂账的短款
判给责任人承担，这件事本身不改班次的状态（它已经结完了），只改归属。

`cancelShift` 有一条硬拦：**有有效订单的班次不许作废**。
否则那些订单会挂在一个不存在的班次上，而它们已经扣过库存了。

## 4. 核心流程

### 4.1 开班（`openShift`）

单号 `nextDocNo(db, 'PSF', 'pos_shifts', 'doc_no', bizDate)`。

重复开班的判据是**收银员**而不是门店：同一收银员同日已有 `open` / `declared` 班次时拒绝。
一家店允许几个收银员各管一个钱箱 —— 判据写成门店，第二个人就开不了班，只能共用钱箱，
而共用钱箱的长短款永远说不清是谁的。

### 4.2 报数交班（`declareShift`）

收银员按支付方式逐项报数。服务端 `upsert` 进 `pos_shift_payments`：

- **没报的行按系统应收原额补齐** —— 所以只报差异行也行，未提及的方式默认「与系统一致」。
- 现金行 `diff` 恒为 0（口径一的那条推论）。
- 非现金行 `diff = declared − sys` 立即成立。

### 4.3 退回重报（`rejectShift`）

必填原因，**并清空该次报数明细**。不清干净的后果是：下一次核款会把上一轮的旧报数
当作新一轮的输入，店长数完钱发现「差异还在」，但界面上看不出那些数字是上一轮的。

### 4.4 核款（`approveShift`，唯一算出长短款的动作）

入参 `counted_cash` 必填 —— 不传就核款，等于让长短款凭空消失。
服务端按支付方式回填 `counted_amount`，现金行 `counted = 实点`，其余行 `counted = sys`，
于是 `variance = counted_cash − sys_cash`。

- 有差异（`|variance| ≥ 0.005`）时，`variance_note`（原因）与 `variance_handled`（归属）**都必填**。
- `|variance| > pos_variance_limit` 时，归属**强制**为 `pending`。

### 4.5 长短款落案（`settleVariance`）

总部把 `pending` 改成 `charge`（责任人承担）或 `absorb`（公司承担），附说明与留痕。
不是状态流转（见 §3）。

### 4.6 缴款（`createCashDrop` / `receiveCashDrop` / `cancelCashDrop`）

- **只有已核款的班次能缴款**（没核款就不知道这一天该交多少现金）。
- **一个班次只能缴一次**（`UNIQUE (shift_id)`）。
- **缴款人与接收人不能是同一人** —— 钱从谁手里交到谁手里，账上要留两个名字。
  这条在 `receiveCashDrop` 里校验，界面上的「总部点收」按钮对同一账号登录时会失败。
- **取消缴款必须把班次的 `cash_drop_amount` 退回去并删明细**。
  只删缴款单不退班次金额，那笔钱会在在途看板上永远悬着，
  而门店那边显示「已缴」、总部这边显示「没收」,两边都认为自己没错。

### 4.7 日结上传（`dailyClose`）—— **核款门禁**

`dailyCloseGate` 检查该营业日是否还有未核款的班次，有就**整批拒绝**。

为什么这条门禁是硬的：日结会把当天的本地单传成总部 SO，并在 `pos_daily_closes` 上
落这一天三段现金数（系统应收 / 实点 / 缴款）。未核款的班次没有 `counted_cash`，
它的现金去向在账上**没有位置**；若允许日结，这一天的现金汇总数会天然不等于各段之和，
而这种不等不会报错 —— 它只会变成「对不上的那部分」。

日结只上传**本营业日**的本地单（营业日 ≠ 自然日，跨零点后仍算前一天）。

### 4.8 门店退货（`storeReturn`）

两件事必须同时发生，否则账实分叉：

1. **货回门店仓**：`sales_returns` + 门店仓入库，**入库成本取该 SKU 在门店仓的当前成本**，
   **不是售价**。用售价当退货成本会让门店库存金额虚增一整块毛利，
   而这笔虚增会一路带进库存报表，看起来「门店赚钱了」。
2. **钱退出去**：写一条**负数 `pos_orders`**，自动冲减该班次的系统应收
   （`computeShiftSystem` 对负额是天生的净额），于是退款自然进入长短款口径。

必须挂在营业中的班次上 —— 挂不上就没有任何班次承担这笔负额。

### 4.9 门店盘点（`createStoreCheck` / `submitStoreCheckItems` / `adjustStoreCheck`）

复用 `stock_checks` + `scope='store'`。

- 建单时只带**账面数**；
- 录实盘数时，**账面数一律从库里现取，不信客户端传来的 `book_qty`**。
  信它的后果不是「算错一次」：客户端只要把 `book_qty` 报成 `actual_qty`，
  差异就恒为 0 —— 盘点单上完全看不出异常，货却已经对不上了。
- 过账是**唯一动库存的动作**（盘盈 `ADJ_IN` 入库 / 盘亏 `ADJ_OUT` 出库），且只能落在门店仓。

## 6. 演示数据（`pos-seed.js`，三库同构）

原来的 5 个班次是**裸 INSERT** 出来的（`seed.js` 内联段），没有单号、没有支付方式明细、
订单不带 `shift_id`。这样的样本无法演示本模块的任何一条口径，所以整段迁到 `pos-seed.js`，
全部走 `lib/pos2.js` 的服务函数（与真实操作同一条路径，避免「seed 能过、真操作过不去」）。

按灌数时刻的 D-2 / D-1 / D0 造数：

| 日期 | 内容 | 覆盖的状态样本 |
| --- | --- | --- |
| D-2 | 早晚两班（同一天两个钱箱），都已核款、都已缴款、已日结 | `dropA` 已点收 / `dropB` 待点收 |
| D-1 | 单班，现金短款交由责任人承担，**不缴款** | 留「资金在途」样本 |
| D0 | 营业中主班（含一笔门店退货）+ 已报数待核款副班（支付宝多报 25 元） | 演示核款入口 + 非现金差异 |
| 每店 | 一张**已过账**门店盘点单 + 一张**未过账**（只录了一行）抽样盘点单 | 两种状态都有样本 |

最后一行是补过的：样本若全是「已过账」，界面上「保存实盘数 / 过账调整库存」两个入口
永远处于隐藏态 —— 演示和截图看到的都是一个只能看的盘点页，
与「这张单还没做完」长得一模一样，看不出到底是没做还是做完了。

短款金额用 `countedWith(sysCash, want)` 做**比例扣减 + 下限保护**：
餐饮 / 服装线的客单价小，写死「扣 6.5 元」会算出负现金，而且**单跑美妆库完全看不出来**
（整库重建在第二个行业才炸 `COUNTED_NEGATIVE`）。

### 8.3 前端与截图实现上踩到的坑

- **弹窗取数不能顺手 `onClose()`**。班次详情弹窗的动作按钮（核款 / 退回重报 / 落案）
  原本在自己被点击时先关掉详情弹窗，可核款弹窗正是从 `detail` 里取
  「系统应收 / 收银员报数 / 阈值」的 —— `detail` 被清空后，核款弹窗会显示一整套 **0.00**
  并给出「现金持平，无需说明」，于是店长会在一个假的「没问题」上按确认核款。
  修法：详情弹窗改 `{detail && !modal && ...}`，动作按钮不再调 `onClose()`，
  落案弹窗拆成独立组件由 `shift` prop 接数。

- **表格合计不能只认本地编辑态**。门店盘点的「合计差异」最初只汇总本地的 `_diff`（用户改过的行），
  未编辑的行没有 `_diff`，于是出现「每行差异都对、表头合计是 0.00」。
  修法：`_diff ?? diff_qty`，本地编辑值优先、否则回退服务端值。

- **底部页签不能模糊匹配文字**。截图脚本里若用「包含」去点按钮，
  「待核款」既是一个筛选标签也是一个状态徽标，会先点中筛选器，
  于是拍出来的「核款弹窗」其实是筛选后的列表。改成弹窗内查找 + 精确匹配。

- **同一页面拍两次「整页截图」会得到逐字节相同的两张图**。`goto()` 会把视口高度撑到整页高度，
  之后为「同页面下半段」再拍一次，`captureBeyondViewport:true` 拍到的还是同一张整页图。
  修法：下半段先把视口缩回 1100、`scrollIntoView` 滚到位，再用
  `captureBeyondViewport:false` 只拍视口；脚本收尾对 9 张图做 **md5 查重**，
  有重复直接 `exitCode=1`，不再靠人眼看。

- **受控输入必须走原型上的原生 setter**。`inp.value = x` 不会触发 React 的 `onChange`，
  截图脚本里「把实点数改成系统应收 − 3」会静默不生效，拍出来的核款弹窗永远是「现金持平」。
  正确写法：`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set` 写值，
  再派发 `new Event('input', { bubbles: true })`。

- **契约漂移检查脚本按 `?` 切查询串**，所以请求路径的模板串里**不能写可选链**：

  ```
  api.post(`/pos/shifts/${detail?.shift?.shift_id}/reject`)   // ✗ 被切成 /pos/shifts/${detail
  const sid = detail?.shift?.shift_id                          // ✓ 先落局部变量
  api.post(`/pos/shifts/${sid}/reject`)
  ```

  这个坑的表现是「前端调用未登记在 OpenAPI」的假报警，实际接口是对的。

## 10. 已知边界与下一步

- **支付方式枚举目前是全局静态的**（`PAY_METHODS` 6 种）。真实连锁会按门店开放子集
  （如加盟店不收储值），下一步应做成门店级配置。
- **长短款只到「归属」为止，未生成会计凭证**。责任承担应形成对收银员的应收，
  公司承担应进管理费用 —— 这属于批次 H「业财一体凭证」的范围。
- **缴款只支持现金**。扫码 / 线上的钱走支付通道结算，不经过门店钱箱，
  所以不产生缴款单；将来若要覆盖「聚合支付 T+1 到账」，需要另建一条对账链。
- **日结只按营业日粒度**。跨营业日补单（隔天补录昨天的单）目前会被算进今天，
  将来需要「补单标识 + 归属营业日」两列。
- `v_pos_shift_variance` 里的 `order_count` 仍是「同门店 + 同营业日 + 同收银员」的旧口径，
  仅作信息展示用。**真正的应收一律走 `shift_id`**（`computeShiftSystem`）。
  这个残留是为了兼容早期页面；正式报表不应引用它。
