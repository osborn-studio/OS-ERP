## 二、结构化：这是模块地图的一次重组

### 2.1 修正前（问题所在）

| 事 | 原本放在哪 |
|---|---|
| 门店要货 | 挂在"门店要货 → 总部发货 → 门店收货"闭环（`server/routes/requisitions.js`） |
| 经销商订货 | 模块 19「经销商 DMS：档案分级与渠道订货」 |
| 线上商城 | 模块 12~14（面向 C 端消费者） |

**问题**：门店要货与经销商订货**本质是同一件事**（下级向总部订货），却被放在两处分别做——口径会分叉、代码会重复、将来加一条渠道规则要改两边。

### 2.2 修正后

新增 **订货中心（B2B 订货平台）** 作为**统一订货入口**，承载：

```
订货方（客户）                       供货方（我方）
├─ 直营门店       ─┐
├─ 加盟门店       ─┼─→  订货中心  ─→  审核 / 信用校验 / 分仓  ─→  发货
├─ 经销商公司     ─┤
└─ 经销商下属门店 ─┘
```

- 原模块 **19/20 归入订货中心的"渠道管理侧"**（档案分级、价格政策、返利对账）
- **零售商城（12~14）保持不变**，它面向 C 端消费者
- 现有 `requisitions.js`（门店要货）**升级为订货中心的一部分**，不再单独演进

## 三、参考标准形态（U 订货 / B2B 订货平台调研）

### 3.1 多级渠道——U 订货的核心特征

> 品牌商 → 经销商 → 终端门店，**每一级都能在平台上向其上级订货**；同一实体可"既是客户又是商家"。

原文口径（U 订货公开案例）："将 450 家核心经销商建立为**客户兼商家**，经销商作为平台入驻商家，可自行维护自己下游渠道/客户以及销售价格。"

**这条对我们的意义**：订货中心**不是单向的**，而是**多级**的——经销商也能当"供货方"。这是数据库设计上的关键差异。

### 3.2 标准功能模块（8 大块）

| # | 模块 | 关键能力 |
|---|---|---|
| 1 | **商品与价格中心** | 多级目录、按客户等级 / 区域 / 渠道 / 数量 / 活动匹配价格；商品**按客户等级与区域控制可见性** |
| 2 | **客户与信用管理** | 客户档案与层级、收货地址、开票信息、业务员归属；**授信额度 + 账期 + 逾期风控**，下单前校验 |
| 3 | **订货与审批流** | 购物车、常购清单、历史订单复制、Excel 批量导入；**超授信 / 超等级价 / 缺货交期 / 特批自动触发审批** |
| 4 | **订单与履约协同** | 下单 → 审核 → 拆单 / 改单 → 分仓 → 发货 → 签收 → 退换；**智能分仓**（按库存 + 收货地址远近匹配发货仓） |
| 5 | **结算、信用与资金** | 在线支付 / 账期、**在线对账（确认、差异申诉）**、返利与折扣自动计提 |
| 6 | **政策与营销工具** | 促销、组合、阶梯政策，可配置下发、执行可追踪 |
| 7 | **数据看板与经营分析** | 客户 / 区域 / 品类 / 履约维度分析；客户端看采购统计与授信余额 |
| 8 | **开放接口与集成** | 与 ERP / WMS / 财务 / 物流对接；标准 API |

### 3.3 从调研提炼的 6 个硬设计点

1. **价格因人而异** —— 客户等级价 / 区域价 / 阶梯价 / 促销价，同一商品不同客户看到不同价。
2. **下单前必须校验** —— 信用额度、账期状态、库存可得量（可售 / 锁定 / 在途区分）。
3. **审批是有条件的** —— 不是"下单即成立"，而是**按规则触发**。
4. **对账是 B2B 最核心功能** —— 不是附属，是主功能。
5. **智能分仓** —— 按库存 + 地址远近自动匹配发货仓（呼应第一轮"就近发货"口径）。
6. **多端 + 多种下单方式** —— PC / 移动 / 小程序；批量导入、历史订单复制、常购清单。

## 四、关键辨析：订货平台 ≠ 零售商城（必须分开）

| 维度 | **订货平台（B2B）** | **零售商城（B2C）** |
|---|---|---|
| 定价 | 因人而异（等级 / 区域 / 阶梯） | 统一定价 |
| 支付 | **账期 + 信用额度** | 在线即付 |
| 审批 | 常有（信用 / 价格 / 库存 / 特批） | 无 |
| 对账 | **核心功能** | 无 |
| 客户 | 需审核入驻、分级分权 | 注册即用 |
| 商品可见性 | 按等级 / 区域控制 | 全公开 |

**结论**：两条产品线，**共享同一套商品 / 库存 / 订单内核，但不共用前台**。
> 调研原文的"避坑指南"第一条正是：把零售商城直接改成订货系统会失败——因为价格体系、审批流、账期、对账完全不同。

## 五、对架构与模块地图的影响

### 5.1 模块清单调整

| 原编号 | 原名称 | 调整 |
|---|---|---|
| 12~14 | 线上商城（渠道商品 / 促销引擎 / 订单路由） | **保留**（C 端，不变） |
| 19 | 经销商 DMS：档案分级与渠道订货 | **拆分** → 订货侧并入订货中心；渠道档案归属渠道管理 |
| 20 | 经销商 DMS：价格政策与返利对账 | **归入**订货中心的渠道管理侧 |
| — | **新增**：订货中心（B2B 订货平台） | **统一承载门店要货 + 经销商订货** |

### 5.2 与已定口径的衔接

| 已定口径 | 在订货中心的落点 |
|---|---|
| 第三轮 B2（加盟店是独立主体） | 加盟店是**订货方**且货权独立 → 订货中心必须支持**货权转移型订单** |
| 第三轮 B5（经销商两级开户） | 订货中心天然支持**多级渠道** |
| 第一轮（价格组 + 调价单） | 订货中心的**取价规则** |
| 第一轮（账期 + 信用额度拦截） | 订货中心的**下单前校验** |
| 第一轮（就近发货 + 门店自提） | 订货中心的**智能分仓** |

### 5.3 技术落点

- `server/routes/requisitions.js`（现有门店要货）→ **升级**为订货中心的订货侧
- `server/routes/dealers.js` → 保留**渠道管理**职责（档案、分级、返利）
- 订货中心与零售商城**共用**商品 / 库存 / 订单内核，前台分开
