## 一、这一批解决的问题

在批次 T 之前，钉钉与飞书在这套系统里的角色只有**一个**：消息出口
（`lib/notify.js` 的机器人 webhook，且只发「待办摘要」一种消息）。它们**不是身份来源**。

于是三件事做不了：

| 想做的事 | 为什么做不了 |
|---|---|
| 「钉钉里把人调了岗，系统里跟着变」 | 全库**没有任何外部 id 列**（`external_id` / `dingtalk_id` / `feishu_open_id` 一个都没有），也没有部门表 —— `orgs` 是"单法人 + 多业务主体"，不是 IM 意义的部门树 |
| 「审批在钉钉走完，系统里跟着过」 | `approval_instances` 只有内部写入路径，**没有外部单号、没有回调入口** |
| 「这个人到底是谁」 | 只能靠姓名，而姓名会重 |

这一批把「**映射**」做成**可查、可重放、有留痕**的数据结构。

## 二、六条硬口径

### 2.1 映射是**多行**的，不是往 `users` 上加列

一个人可能在钉钉、飞书、将来的企业微信上都有账号，而 `users` 只有一行。
加一列意味着"加一个平台就改一次基础表结构"，而且第二列几乎永远是空的
（"你的飞书 open_id 是多少"这个问题对钉钉用户没有意义）。

所以三张映射表：`im_dept_map`（外部部门 → 本地组织）、`im_user_map`（外部成员 → 本地用户）、
`im_approval_map`（外部审批单 → 本地审批实例）。

三张表都带 `UNIQUE(platform, external_id)` —— 这是**幂等的地基**：
同一个外部实体同步一百次也只有一行（upsert，不是 insert）。

### 2.2 `org_id` / `gml_user_id` **允许为空**，但空必须**可见**

外部部门拉回来了、本地还没决定它对应哪个主体（是门店还是仓库？）——
这种情况**必须能表达**，否则只能"不落库"或"瞎猜一个"。

所以：允许 NULL，但**每一次同步都会把"未挂接"补记成一条冲突**
（`DEPT_UNMAPPED` / `USER_UNMAPPED`），探针 `IM_UNMAPPED_SILENT` 再守一遍：
"有 N 个没挂接，冲突台账里却一条都没有" ⇒ 报错。

### 2.3 空快照 ≠ 大家都离职了（**这一条最重要**）

缺失判定（"快照里没有的，标记为 `missing`"）只在 `snapshot.complete === true` 时才做。
transport 不声明 `complete` 时，一次同步**不做任何缺失判定**，并留一条
`SNAPSHOT_INCOMPLETE` 冲突。

为什么：一次网络抖动拉回空列表，会把**全公司的人标记为已离职** ——
破坏性、且**看起来完全正常**（`status = ok`，`missing = 137`）。
这与批次 O 的「没有期初登记 ≠ 从零开始」是同一个病。

### 2.4 `missing` 不是删除

外部部门消失了，映射行**保留**，只把 `status` 改成 `missing`。
判据：**"他曾经属于哪个部门"是一个历史问题，历史要留下。**

### 2.5 映射与流水**同生共死**

每次落映射都在**同一个事务**里写一条 `im_sync_runs`，并把 `sync_batch` 记到映射行上。
写入点当场断言 `db.inTransaction`（与 `logSettingChange` / `logReportConfigChange` 同族）。

于是"这一行是哪一次同步写下的"永远答得出来；否则事后看见一行孤儿映射，
既不知道谁写的、也不知道该不该删。
探针 `IM_MAP_WITHOUT_RUN` 同时查两种：**批次为空** 与 **批次指向不存在的同步**。

### 2.6 不代替人签字

外部审批通过了，本地要执行 `decideApproval`，而它要一个**真实用户**当 actor
（`canApproveStep` 会核他的角色）。所以：

- 外部操作人**必须**先映射到本地用户（`im_user_map.gml_user_id`）；
- 映射不上 ⇒ 记 `APPROVER_UNMAPPED` 冲突，**不决策**；
- 映射上但引擎判定"不是当前级审批人" ⇒ 记 `APPROVER_NOT_ASSIGNED` 冲突，**本地状态不变**，
  并在 `im_approval_map.local_status` 如实写下 `rejected_by_engine:<码>`。

用"系统"或"任意管理员"顶替，会让审批记录里出现一个**从没点过同意的人的名字** ——
那比不同步更糟。

## 三、数据模型

| 表 | 作用 | 关键列 |
|---|---|---|
| `im_platform_cfg` | 平台接入配置（**密钥不落库**） | `platform`（唯一）· `secret_ref`（**环境变量名**）· `enabled`（默认 0）· `base_url` |
| `im_dept_map` | 外部部门 → 本地组织 | `UNIQUE(platform, external_dept_id)` · `org_id`（可空）· `status(active/missing)` · `sync_batch` |
| `im_user_map` | 外部成员 → 本地用户 | `UNIQUE(platform, external_user_id)` · `union_id` · `mobile`（用于排重）· `gml_user_id`（可空）· `status` · `sync_batch` |
| `im_approval_map` | 外部审批单 → 本地审批实例 | `UNIQUE(platform, external_instance_id)` · `external_status`（**原文**）· `local_status`（读成了什么）· `approval_id` |
| `im_sync_runs` | 同步流水（**只追加**） | `kind(org/approval)` · `status(ok/partial/failed/not_configured)` · `pulled/created/updated/skipped/conflicts` · `cursor_before/after` · `started_at/finished_at` |
| `im_sync_conflicts` | 冲突台账（**只追加**） | `reason_code`（封闭字典）· `external_id` · `local_id` · `message`（**一句人话**）· `payload` |

**索引 11 条**；权限点 2 个（`system.im.view` / `system.im.sync`）。

### 3.1 冲突码是一本**封闭字典**

12 条，每条都带"人该做什么"：`SNAPSHOT_INCOMPLETE` · `DEPT_UNMAPPED` ·
`DEPT_PARENT_UNMAPPED` · `USER_UNMAPPED` · `USER_DUPLICATE_MOBILE` · `USER_DEPT_UNMAPPED` ·
`EXTERNAL_DEPT_MISSING` · `APPROVAL_INSTANCE_NOT_FOUND` · `APPROVAL_NOT_PENDING` ·
`APPROVER_UNMAPPED` · `APPROVER_NOT_ASSIGNED` · `APPROVAL_DECISION_UNKNOWN`。

字典定义在 `lib/im-sync.js`（唯一定义），探针 `IM_CONFLICT_CODE_UNKNOWN` 抓"字典外的码"。
**只有码没有话的冲突不算合格** —— 排障的人得去读代码才知道发生了什么，
迁移 `verify()` 里就有一条"冲突必须带 message"的结构不变量。

### 3.2 重建清单（`db/seed.js`）

- `TABLES`（**重建时清掉**）：`im_sync_conflicts` → `im_sync_runs` → `im_approval_map` →
  `im_user_map` → `im_dept_map`。
  理由：三张映射表存的是**外部 id → 本地自增 id**。重建会重排本地 id ⇒
  上一代的映射会**看起来指向一张真实存在的组织/用户/审批**，而它其实是另一代的东西。
  这是"跨代引用"最坏的形态：**没有一行是孤儿，所以任何孤儿检查都发现不了**。
- `KEEP_TABLES`（**重建不清**）：`im_platform_cfg`。它是**配置**不是数据 ——
  "这个平台接没接、凭据在哪个环境变量"是运维的事实，不该被一次重建抹掉。
  运行时由 `ensureImPlatforms()` 幂等补齐（**刻意不覆盖 `enabled`**：
  有人手工停用了某个平台，重启一次不该把它又打开）。

## 四、不依赖真实租户，怎么证明它是对的

这是本批最需要交代的一件事。答案是**把"真实 HTTP 调用"从"同步语义"里切出来**：

```
        ┌─────────────────────── 与租户无关（本批全做，可测可自证） ───────────────────────┐
快照 ──▶│  计划（纯函数）──▶ 落库（单事务 + 留痕）──▶ 冲突（封闭字典 + 一句人话）──▶ 自证探针  │
        └───────────────────────────────────────────────────────────────────────────────┘
   ▲
   └── transport（可注入）──▶ 没凭据时**明确抛 IM_NOT_CONFIGURED**（不返回空快照）
                              ▲
                              └── 真实调用：本批**未实现**（401/501 之外没有别的分支）
```

- **`/api/im/self-test`**：用一份固定快照，在**一个会回滚的事务里**把整条链跑一遍
  （首次同步 → 二次幂等 → 不完整快照不做缺失判定 → 未知审批状态留冲突），
  然后**主动抛异常回滚**，返回 `rolled_back: true` 与前后计数对比。
  判据：**库里一行都不多** —— 否则自检本身就成了污染源。
- **`POST /api/im/sync/org`**（真同步）：没配凭据时返回 **409 `IM_NOT_CONFIGURED`**，
  消息里指出要填哪个环境变量。**绝不静默返回空快照。**

## 五、六条自证探针（`auditImTrail`）

| # | 探针码 | 回答的问题 |
|---|---|---|
| ① | `IM_RUN_UNFINISHED` | 有没有"没结束的同步"（进程死在半路 ⇒ 游标可能已推进、集合没拉全） |
| ② | `IM_MAP_WITHOUT_RUN` | 每一行映射答不答得出"我属于哪一次同步"（**批次为空也算**） |
| ③ | `IM_CONFLICT_CODE_UNKNOWN` | 有没有字典外的冲突码（防绕过唯一写入点写库） |
| ④ | `IM_UNMAPPED_SILENT` | 有未挂接 / 未开户，但冲突台账里一条都没有 ⇒ "挂空"被静默了 |
| ⑤ | `IM_USER_DANGLING` / `IM_ORG_DANGLING` / `IM_APPROVAL_DANGLING` | 映射指向的本地行还在不在 |
| ⑥ | `IM_MAP_STATUS_INVALID` / `IM_APPROVAL_RAW_MISSING` | 状态取值域 / 外部原文有没有丢（丢了就事后无法核对翻译对不对） |

接进 `verify-seed` 第 **26** 节（每次重建都跑）。**探针要放在会被定期调用的地方**，
不然它只是"一个可以跑的脚本"，不会有人跑。

## 八、边界（如实记）

1. **真实租户调用未实现**（无凭据）。`IM_PLATFORMS[*]` 里已经有决策映射字典，
   但**没有接口路径** —— transport 里刻意不写"看起来能跑"的假实现，
   那会让"未测"变成"测过了"。下一步：填入凭据后补 `fetchDepartments/fetchUsers/fetchApprovalInstances`。
2. **不做双向同步**：本系统**不往**钉钉/飞书写组织与审批，只读。往外写会引入
   "两边同时改同一字段"的冲突，那需要一套完全不同的设计（版本向量或最后写入胜出）。
3. **不做增量游标**：`cursor_before/after` 已经落库并展示，但 transport 拿到的永远是全量快照
   （固定快照即如此）。增量要等真实接口形态定了再设计 —— **先留位置，不先猜形状**。
4. **不做冲突的自动消解**：`USER_DUPLICATE_MOBILE` 之类只报不判，等人确认。
   自动合并两个身份是**不可逆**的，做错一次就再也分不开。
5. **不迁移历史审批**：只同步"当前 pending 的实例"，已决的本地实例**外部结论不覆盖**。
6. **`im_platform_cfg` 的密钥不落库**：只存环境变量名。
   代价是"配置在哪启用"要人去环境里设 —— 这是刻意的取舍（SQLite 文件在开发机上人人可读）。

## 九、与其它留痕族的关系

`im_sync_runs` / `im_sync_conflicts` 与 `period_audit_log`（批次 Q）· `setting_audit_log`（批次 R）·
`report_config_audit_log`（批次 S）**同族**：**只追加 · 无 UPDATE/DELETE 路径 ·
唯一写入点 · 与它记录的改动同事务 · 可重放/可自证**。

不同的是它们记的东西：
Q 记「期间定稿」· R 记「参数改了」· S 记「报表口径改了」· **T 记「这一次同步做了什么」**。
四者的共同点是一条已经被写过四遍的口径：
**"改了但没记"和"记了但没改"都必须是可检测的**，而这只能靠两条出处不同的路径互证。
