伴圆AI原生ERP 操作手册

本手册供管理员、业务关键用户及实施人员使用，2026年10月24日修订。范围包括总部后台、门店 POS、线上商城、经销商订货及 MCP 管理。

运行模式提示：系统缺省是生产模式（空库、无样本数据、只有 bootstrap 建立的管理员，见安装手册第五章）；第一至第十八章中的样本账号（admin、scm、store01、dealer01 等）、固定验证码、商城、奇门与 MCP 演示仅在显式的演示模式（GML_RUNTIME_MODE=demo）下可用，数据均为虚构样例。生产模式下商城、奇门、OMS 模拟、IM 同步和 MCP 返回 503 FEATURE_DISABLED。第十九章起是生产模式的专项说明。

一 登录和通用操作

  1. 启动系统，打开 /login，先选美妆连锁或连锁餐饮。
  2. 选择角色卡片或手工填账号密码，点击登录。生产模式只用 bootstrap 建立的管理员及其创建的账号；下文及演示手册里的 admin、scm 等样本账号与初始密码仅限演示模式，不得在生产使用。
  3. 从左侧进入对应业务模块。门店账号从 /pos 进入本店业务，经销商从订货中心进入本人数据。
  4. 退出后重新选择行业即可切换独立行业库。不同角色比较建议使用不同浏览器用户配置或无痕窗口，避免同一浏览器会话相互覆盖。

列表通常支持关键词、状态筛选、分页及详情。新增后先保存草稿，核对后再提交或确认；行内按钮随状态、权限变化。遇到拒绝提示，应核对前置单据、可用库存、当前角色和数据范围，不要反复点击。

操作成功后，返回列表刷新，核对状态和数量金额；对库存和财务操作再查看流水或来源单号。已过账单据不得靠删除来撤销业务，应走系统提供的退货、红冲或作废路径。

二 角色和数据范围

下表是演示模式样本账号的职责示例；生产模式由管理员自行建立用户并分配角色与组织。

账号工作入口范围提醒
admin全部模块和系统设置管理员权力大，不作为日常业务账号
scm采购、库存、计划生产、质量、委外查看及操作仍取决于具体权限点
purchase / warehouse / sales本岗位模块不等于具备全流程审批权限
finance应收、收款、会计和报表票、款、凭证分别核对
store01门店 POS 和门店业务必须绑定门店，只处理本店数据
dealer01美妆版订货中心必须绑定经销商，只看本人订货及对账
boss / viewer授权查询与部分审批 / 只读不应展示未授权的修改能力

门店、经销商登录若缺少实体绑定会被拒绝。隐藏菜单不等于安全边界，后台接口也会检查范围。新增用户、换角色后，管理员应使用目标账号复核。

三 经营看板

入口：/。管理员或总部授权角色可查看销售、库存、采购、应收、线上订单及待办。

先看行业和统计期间，再看 KPI、趋势和渠道结构。待办可引导进入对应列表；如需查明细，从销售、库存、应收等菜单进入，不要把所有 KPI 当成可点击的明细链接。总部看板不向外部门店、经销商开放。页面右上角的"数据截至 hh:mm:ss"与"刷新"按钮的含义见第四十三章。

四 主数据

入口：主数据下的商品、品牌品类、往来单位、仓库门店、组合装、条码及出入库类型。

  1. 新建商品时先维护商品信息，再维护 SKU 的规格、单位、条码、价格和成本。
  2. 新建供应商、经销商或门店后，核对主体、仓库及用户绑定。
  3. 组合装须维护成分及数量，实际拆装通过对应业务单处理。
  4. 改价或改档案后核对新建单据，不把档案修改当作对历史确认单据的追溯调整。

正常仓、门店仓与待检、不合格品等隔离仓用途不同。质检状态及货权会影响可用库存，不能只看账面数量。

五 订货中心

入口：/order-center。经销商账号展示本人客户身份、商品价格、购物车、订单及对账；总部账号按授权处理。

  1. 用 dealer01 登录美妆版，确认显示的是本人客户。
  2. 选有可用库存的商品，输入小数量，加入购物车并核对价格。
  3. 提交订货，记录系统实际生成的单号。
  4. 总部角色在销售订单中查询该单，确认、发货；客户再进入本人订单查看进度。
  5. 对账按期间核对应收和已收款，不把订货金额、开票额和实收混为一谈。

不能通过改地址、单号或请求参数查询其他客户单据。库存不足、客户停用或信用限制时按提示处理。

六 采购闭环

入口：/purchase/workbench。按待办进入请购、采购订单、收货、质检、发票、结算和付款。

6.1 请购与采购订单

新建请购，填写需求日期、SKU、数量和建议价；保存后提交，授权人员审批，再转采购订单。也可由有权限人员直接建采购订单。

采购订单核对供应商、仓库、明细和数量后提交及审批。已审批订单才进入收货链；已收与订单数量不一致表示仍有未到货数量。演示部分收货时填小于剩余量的数量，记录收货单号。

6.2 收货与检验

打开收货单，核对批次、效期、仓库及实收数量。到货不等于可用，涉及检验的货物进入质量流程后，根据合格、让步、拒收等结果处理。不要手动改库存绕过检验。

6.3 发票与结算付款

采购发票记录票据，结算单核对可结范围及退货影响，付款单记录实际付款并按流程确认。核对订单、到货、票、应付和已付，分别留存来源单号。系统付款操作是内部业务记录，不会自动向银行转账。

6.4 退货

选择来源收货及可退明细，填写数量和原因，按授权确认。查看库存出库及应付或结算变化。退货抵减政策以系统参数及实际规则为准，不能假设所有客户口径一致。

七 计划 生产与委外

入口：/plan/summary、/plan/production、/manufacture、/outsourcing/orders。

  1. 在净需求汇总核对门店或渠道需求，扣除可用量后查看采购、生产或委外建议。
  2. 生产流程先核对 BOM，再创建生产任务，领料、报工、完工和入库。
  3. 每次领料、完工须核对 SKU、仓库、数量及来源任务；库存不足时先处理补料，不要重复提交。
  4. 委外订单维护加工方、材料、加工费及交期，按页面可用动作发料、收回和结算。
  5. 完工涉及质检时，从质量中心追踪后续处置。

本地样本用于验证流程，不代表已覆盖客户的排产、设备、工艺及复杂成本需求。

八 质量管理

入口：/quality/qc。从采购到货、生产完工或在库检查等来源报检，填写检验数量及结果，提交后按处置动作处理。

核对合格、让步和不合格数量是否与检验总量一致。拒收、返工或隔离会影响库存和关联单据；操作后检查实际生成的退货、调拨或处置单及流转记录，不只检查一个状态标签。

九 销售 发货 开票及退货

入口：/sales/quotes、/sales/orders、/sales/deliveries、/sales/invoices、/sales/returns。

  1. 报价或新建订单：选客户、仓库、SKU、数量和价格，保存核对。
  2. 确认订单：检查信用及库存，成功后观察预留或占用变化。
  3. 发货：按剩余可发量填数量；部分发货后核对已发、未发及库存流水。
  4. 开票：从可开票来源创建发票，按允许数量开票并确认；内部发票记录不等于税控平台已经开出真实发票。
  5. 签收或完成：按订单当前可用动作推进，不跳过前置状态。
  6. 退货：选择原订单和可退明细，填数量及原因；确认后核对库存和应收；已收款部分可能另需退款处理。

订单金额、发货金额、开票金额、收款金额是不同口径。样本中有部分发货、部分开票、部分收款的中间态，不能只用“已完成”概括。

十 应收 收款和退款

入口：/finance/receivables、/finance/refunds。

应收先按客户及来源单核对；登记收款后，选择对应应收进行核销。部分核销应保留余额，累计核销不能超过允许金额。完成后同时检查收款单、核销记录和应收余额。

退款先核对来源退货、已收及可退金额，再登记并确认出账。系统不会因为点击确认自动执行真实银行或第三方支付退款。

十一 存货管理

入口：/inventory/stocks、/inventory/ledger、/inventory/availability、/inventory/transfers、/inventory/checks 等。

业务操作要点结果核对
现存与可用按仓库、SKU、批次筛选区分现存、占用、可用及隔离数量
出入库流水按日期和来源单过滤看数量方向、金额、批次及来源
调拨新建、出库或发运、收货发运后是“在途”，目标仓收货后才入库
盘点创建盘点、录实盘、审核调整差异、调整流水和金额须核对
预警与库龄看缺货、临期、超储或呆滞结合效期、仓库和业务处理，不直接改汇总
组合拆装核对组合与成分数量成分和成品出入方向正确
成本及货权按授权查询或处理数量、成本和货主分开核对

盘点调整、作废等有风险动作须按角色及审批要求处理；不要用直接改数据库来修正业务。

十二 门店 POS

店长使用 store01 登录 /pos；总部管理员从 /store/monitor 及门店业务菜单查看运营。两种角色不要混用。

12.1 收银及退货

进入本店收银，扫码或选商品，修改数量，核对优惠和应付，再选页面支持的付款方式完成演示收款。检查小票、零售单及库存变化。这里只模拟业务结算，不接真实扫码支付。

退货须选择原销售或系统允许的来源，核对可退数量和退款口径；退后查看零售记录及库存。不要直接删除已完成销售。

12.2 交班 核款 缴款及日结

按现金、微信、支付宝等实际展示渠道分别录交班金额，由授权店长核款，发现差异时填写原因及归属；缴款和日结继续按状态推进。总部查看日报、班次和渠道差异。现金差异与第三方渠道差异含义不同，不宜相加当作同一种损失。

12.3 门店补货及收货

门店查本店库存后提交要货，总部处理并生成发货，门店按实到明细收货。部分收货后保留剩余在途。门店不应看到其他门店及总部全量库存。

十三 线上商城及 OMS

消费者入口 /mall；后台订单入口 /oms/orders，营销入口 /marketing/promo。

  1. 打开商城浏览商品，选择规格并加入购物车。
  2. 需要登录时输入演示手机号，验证码固定为 1234。不要填写真实个人信息。
  3. 填演示收货信息，核对商品、优惠券、积分、运费和应付，提交订单。
  4. 记录商城生成单号，后台用 admin 或授权销售账号在 OMS 查该订单。
  5. 按可用状态处理发货、完成、取消或退款，消费者端刷新查看结果。

商城固定验证码、支付流程及奇门等对接为演示能力，不代表已接真实短信、支付和电商平台。促销、会员等级、优惠券及积分需与业务结算一起核验。

十四 经销商和渠道

美妆版总部入口：/dealers、/dms/channel、/dealers/rebates、/dealers/statements。餐饮版不做经销商演示。

总部查看经销商档案、销售和回款、信用、协议价及渠道政策。返利按页面可用流程计提、确认或核销；核销涉及应收影响，须在往来账核对。对账按期间生成并核对明细。

外部经销商使用 dealer01，只从订货中心看本人订货及对账；总部经销商总览不是外部经销商入口。

十五 会计与报表

入口：/finance/accounting、/finance/reports、/finance/report-config。

从业务单生成凭证后核对来源、科目、借贷及期间，按权限审核和记账。试算平衡用于检查借贷关系，不等于已经证明所有会计口径符合客户要求。报表要核对期间、配置及明细取数。

十六 AI 数据承接台和 MCP

AI 查询入口 /ai；管理员 MCP 控制台 /system/mcp。

本地未配置外部模型时，AI 数据承接台采用现有规则式解析，不能描述为已接通国外最优大模型。真正外部智能体通过 /mcp 调用工具，使用独立 Agent Token，不使用用户网页登录 JWT。

写工具需按输入模式传幂等键；高危领域工具需人工确认，通用单据推进中的高危边会拒绝，不能概括为“AI 任意修改所有单据”。详细接入示例见开发与MCP接手手册。

十七 系统管理

管理员维护用户、角色权限、组织绑定、配置字典、审批、通知及日志。改动权限或用户角色后，使用原账号重新验证可见和可操作范围；不要只看管理员页面上的勾选。

十八 操作异常处理

十九 收付款证据与二人复核

适用生产模式。依据 ADR-0018。系统是人工登记资金：确认收款、执行付款只是内部业务记录，不会自动向银行、支付平台转账或收款；但这两个动作现在必须有凭证，且默认由第二个人复核。

19.1 规则

项目说明
适用动作收款单确认（入口 /finance/receivables）、付款单执行付款（入口 /purchase/payments）
证据默认必填：银行流水号或凭证号，另可写说明。缺凭证号时服务端拒绝（FUNDS_EVIDENCE_REQUIRED）
二人复核默认每笔都要。发起人确认后单据进入"待复核"，此时应收、授信额度、结算单都没有变化
复核人须持有权限点 finance.funds.review（资金收付复核），内置角色默认只有 admin 与 finance 有；发起人不能复核自己（FUNDS_SELF_REVIEW）
复核结果通过：同一事务内完成原确认逻辑（核销应收、释放授信或标记付款已付）并写严格审计；驳回：必须写原因，单据回到可再次发起的状态
待复核期间收款单不能作废，付款单不能再执行或作废（FUNDS_REVIEW_PENDING）；要先由复核人驳回

19.2 操作

  1. 发起人（例如出纳）在收款单详情填写凭证号与说明，点击确认；付款单点击"执行付款"并在提示框填写银行流水号或凭证号。
  2. 单据显示"待复核"。收款单状态仍是草稿、付款单仍是已审批，这是正常的；列表以"待复核"标签区分。
  3. 另一位持 finance.funds.review 的用户打开同一单据，核对凭证与金额后点"复核通过"，或点"驳回"并填写原因。通过后单据才变成已确认 / 已付。
  4. 被驳回的单据，发起人补充凭证后可再次发起，复核记录会被覆盖，历史保留在审计里。
  5. 不要为了省事用同一个账号或共享账号完成两步；那等于取消了复核。

19.3 系统设置中的三个开关（危险项）

19.4 常见提示

FUNDS_NOT_READY 单据不在可确认状态；FUNDS_NOT_PENDING 单据不在待复核；FUNDS_COMMENT_REQUIRED 驳回没写原因；FUNDS_BAD_DECISION 复核结果不是通过或驳回。出现这些先刷新单据状态，不要反复点击。

二十 通知渠道密钥与出站策略

适用生产模式。依据 ADR-0008。入口 /system/notify（需要系统通知相关权限）。

20.1 渠道密钥

  • 渠道的"签名密钥"保存后不再回显：界面只显示"已设置"和末 4 位（密钥不少于 12 个字符时）。编辑时留空表示保持原密钥，填写表示设置或轮换，勾选"清除密钥"表示清空。
  • 库里的密钥是封存存储的，不是明文。封存密钥来自环境变量 GML_SECRET_KEY（至少 16 字符）；没有设置则由登录签名密钥派生。
  • 如果更换了登录签名密钥而没有设置 GML_SECRET_KEY，旧封存值会变成"密钥不可读"（响应里 secret_unreadable），发送失败并留日志，需重新录入或配置旧密钥。建议在生产启用时就明确设置 GML_SECRET_KEY 并安全保管。
  • 轮换步骤：①把旧值移入环境变量 GML_SECRET_KEY_PREVIOUS（逗号分隔，只用于解密）；②设置新的 GML_SECRET_KEY；③重启服务；④让每个渠道保存一次（重新写入即用新密钥封存）；⑤确认没有仍需旧密钥才能解开的渠道后，清掉 GML_SECRET_KEY_PREVIOUS。
  • 发送签名：钉钉、飞书、通用 Webhook 带时间戳和签名；企业微信没有签名方案。日志只记录发出的消息体，不含密钥。

20.2 出站策略

渠道地址和每次发送都经过同一套检查：

  • 生产只允许 https；禁止 URL 中带用户名密码；禁止 localhost、回环、私网、链路本地、云元数据地址等（含各种变形写法）。发送前解析域名，解析出的每个地址都要通过检查，并钉住该地址连接，不重新解析。
  • 不跟随重定向（3xx 一律失败，错误码 OUTBOUND_REDIRECT）；总超时默认 8 秒（OUTBOUND_TIMEOUT）；响应体上限 256KB（OUTBOUND_BODY_TOO_LARGE）。
  • 可选环境变量 GML_WEBHOOK_ALLOWED_HOSTS（逗号分隔主机名）只能进一步收窄；把内网地址写进去也不会放行。
  • 保存时被拒绝会提示原因，且不落库；库里已有但不再合规的地址在发送时失败并写 fail 日志，错误文本以 OUTBOUND_ 开头。
  • 这是应用层策略，不能替代网络出口防火墙；Teredo 地址段未做特殊处理。

20.3 摘要接口的数据范围

通知预览、推送、日志、总览（/api/notify/preview、/push、/logs、/overview）需要内部账号、对应通知权限且数据范围为全局。门店、经销商，以及只有子树、单组织、本人范围的账号返回 403（GLOBAL_DATA_FORBIDDEN 或角色 403）。原因是摘要来自没有组织列的采购订单和审批实例，无法诚实地按范围缩小。内置 purchase 角色默认是子树范围，如确需让某人预览或推送全库摘要，由管理员评估后将其数据范围设为"全部"。

二十一 Agent Token 有效状态与清扫

依据 ADR-0011、ADR-0015。

先确认能不能用：生产模式下 MCP 与 Agent 凭据管理整体关闭（/mcp、/api/mcp 返回 503 FEATURE_DISABLED），/system/mcp 控制台和本章的令牌接口在生产不可用。本章适用于演示或测试模式，以及未来经单独验收启用 Agent 能力之后。

21.1 令牌是所有者的委托

有主令牌的实际权限 = 令牌自身声明的范围与所有者此刻的权限点、数据范围的交集。所有者被停用、改密、被改角色或权限集、被调整组织或数据范围后，已签发的令牌立刻被拒（调用返回 TOKEN_OWNER_REVOKED、TOKEN_OWNER_INACTIVE 等）；重新启用账号不会让旧令牌复活，需要重新签发。令牌只从 Authorization: Bearer 头读取，查询串或请求体里的令牌不被接受。

21.2 有效状态

/system/mcp 的"人工确认与审计"页有令牌表，同时显示两列：

列含义
状态数据库里这一行的历史状态（active、revoked 等）
有效状态现状：active、revoked、expired、owner_missing、owner_inactive、revoked_by_owner_change

"状态"仍是 active 但"有效状态"不是 active，说明令牌实际已经不能用，只是数据库行还没追上现状。读页面本身不修改数据。

21.3 清扫

点"清扫失效令牌"（括号内是可清扫数量；没有可清扫行时按钮不可用），或由有 system.mcp.manage 权限的账号调用 POST /api/mcp/tokens/sweep。清扫把"状态仍 active、但所有者缺失或所有者安全版本已变化"的令牌标为已吊销，记录原因（owner_auth_changed、owner_missing 等）和时间，并在备注里写清扫人；操作幂等，可重复执行。清扫不会改变调用判据：清扫前旧令牌被拒是 TOKEN_OWNER_REVOKED，清扫后是 TOKEN_REVOKED，都是拒绝。过期令牌不改写。不做自动清扫，建议在人员变动、角色调整后手动清扫一次。管理员主动吊销走令牌行的吊销按钮。

21.4 注意

恢复备份会回退账号安全版本：已清扫的令牌不会复活，未清扫的可能重新显示为有效。恢复后应轮换或全局吊销令牌。

二十二 采购工作台或待办看不到数据怎么办（组织与数据范围）

依据 ADR-0015、ADR-0017。升级到包含这些收口的版本后，采购工作台（/purchase/workbench）、请购、发票、结算、付款、应付以及审批待办只显示你所属组织范围内的单据。账号没有组织归属时，列表是空的，而不是报错——这是有意的，空范围不会变成全库。

22.2 管理员核对步骤

账号的可见范围由两个字段决定：账号的组织归属 org_id，和数据范围 data_scope。账号上的 data_scope 非空时优先，为空则取其角色的默认范围；两者都没有时按"本人（self）"处理。可取值：all（全部）、subtree（本组织及下级）、org（本组织）、self（本人）、dealer（经销商）。

  1. 在 /system/roles 查看该账号角色的默认数据范围（内置 purchase、warehouse 默认为子树范围），在 /system/users 核对账号状态与角色。在 /master/org 确认目标组织存在且处于启用状态。
  2. 组织归属与账号级数据范围通过账号更新接口 PUT /api/auth/users/:id 的 org_id、data_scope 字段设置（新建账号的接口同样接受）。当前用户管理页面是否提供这两个字段的编辑入口，本手册未逐页核实；若页面没有，请由具备管理员权限的实施人员调用该接口，不要直接改数据库。
  3. 二选一：给账号设置正确的 org_id（推荐，最小授权）；或经评估后把 data_scope 设为 all（同时会开放通知摘要等全局口径，权力更大，须留痕并经管理层批准）。
  4. 这类安全字段变更会使该账号的登录会话与已签发令牌失效；保存后用该账号本人重新登录验证，不要只看管理员页面上的值。
  5. 仍然为空时，用管理员打开同一页面对比：管理员能看到而该账号看不到，是范围问题；管理员也看不到，是确实没有单据。

不要为了让页面有数据而临时把所有人改成管理员。

账号本人可以先在侧栏「我的数据范围」自查生效范围，见第二十六章。

  • 导出该手机号的商城客户、会员账户与积分流水、购物车、H5 订单（含明细）、收货地址（来自订单）、关联销售单（含 POS 日结上传生成的）与门店会员单，以及（Y8）关联的退款单、订货中心客户 / 地址 / 订单 / 对账单、含原号码或与其单据绑定的审计 / 通知日志行；仅凭遮盖号码命中的日志行只给行数。凭据类字段遮盖；手机号/姓名/地址按本人数据原样给出。

24.3 个人信息抹除（删除请求）

node scripts/privacy-erase.mjs <手机号> --confirm --actor <admin 用户名> [--industry cosmetic]

  • 先导出留存（24.2），再执行。必须带 --confirm，--actor 必须是该库中启用的管理员；没有 --confirm 退出码 2，什么都不改。
  • 做法是脱敏不删行：姓名、手机号、收货人/电话/地址换成 erased:<带钥哈希>；订单号、金额、数量、状态、积分流水、行 id 全部保留，财务对账不受影响。同一手机号在各表得到同一伪名（erased:<哈希>-<客户id>，同号再注册后再抹除会得到新的后缀）。哈希密钥取自 GML_SECRET_KEY（或非公开的 GML_JWT_SECRET）；生产环境用公开/缺省密钥会被拒绝。更换密钥后旧伪名不再可复算，抹除记录请以审计为准。
  • 有未完结订单（待发货/已发货/退款中等）时拒绝（退出码 1），完结后再抹除；确需先抹除可加 --allow-open-orders，在途订单将无法按原收货信息履约。
  • 重复执行是安全的：已抹除的号码返回 already-erased，不再写审计；跨库中途失败后直接重跑即可。每个行业库写一条 PRIVACY_ERASE 审计（不含原手机号）。
  • 先看影响面：node scripts/privacy-erase.mjs <手机号> --report [--industry cosmetic]（只读，不需要 --confirm / --actor）逐表打印“将改多少行、哪些列”、遮盖片段命中但默认不动的日志行数（ambiguous_masked）、执行后预计仍含该原号码的表.列及行数（raw_phone_not_covered，与执行输出的 residual_raw_phone 一致）、需人工复核的主数据电话（manual_review，如经销商 / 门店 / 供应商 / 员工表里恰好相同的电话）。--dry-run --actor <admin> 额外做真实执行的管理员与在途订单检查，同样不写库。报告数字与执行输出、审计里的行数是同一份计划，不一致会回滚。
  • 覆盖面（Y8）：除商城客户 / 订单 / 销售单 / POS 外，还抹除退款单客户名（会员退款，或关联主体销售单且名字等于主体姓名的退款）、电话等于主体的订货中心客户 / 地址及其订单、对账单、往来单据上的名称快照，以及审计与通知日志中出现的原号码和关联单据的部分遮盖号码（如 138****5678）。仅凭“前 3 后 4”命中的其它日志行无法证明是同一个人，默认不动；确认可接受误伤再加 --include-ambiguous-masked。金额、单号、状态、银行账号 / 流水号不会改。
  • 执行后输出里的 residual_raw_phone 列出库里仍含该原号码的列（如主数据电话、其它业务自由文本），这些没有被改，需要人工判断与处理。
  • 边界（如实告知申请人）：不改历史备份文件；Y8 之前已抹除过的号码不会被追补；残留扫描只认精确 11 位原号码，不认带分隔符或其它写法；姓名 / 地址出现在自由文本里发现不了。备份按第二十三章的保留份数自然过期。

二十五 奇门平台密钥签发与轮换

面向持有权限点 oms.platform.manage 的管理员（ADR-0033；首次迁移只授予 admin，其他角色需在 /system/roles 显式添加）。

先确认能不能用：奇门网关 /api/qimen（含本章的签发接口）属于生产模式关闭的能力，访问返回 503 FEATURE_DISABLED（见安装手册第三章）。本章适用于演示或测试环境，以及将来经产品负责人单独授权重新开放之后。ADR-0033 列出了重新开放前必须逐项拿到证据的验收清单，这里不重复，也不代表这些项已完成。

25.1 签发

  1. 在 /oms/platforms（平台店铺）找到对接平台，确认已填 AppKey（没有 AppKey 会返回 409 QIMEN_APP_KEY_MISSING）。
  2. 点「签发奇门密钥」。页面弹出一次性提示，显示以 qsk_ 开头的明文密钥。明文只出现这一次：库里只存封存值，关闭提示后无法再次查看。立即复制，通过非聊天、非邮件明文的渠道交给对方，并在台账记录签发人与时间。
  3. 列表里显示的是 **** 加末 4 位的掩码和签发时间；奇门调试页 /oms/qimen 里的「密钥」列只显示"已签发 / 未签发"。

25.1a 命令行签发与按安装生成的演示密钥（ADR-0033 补充，迁移 069）

  • 公开的奇门演示签名常量不再存在于代码，也不再留在库里：迁移 069 会把仍持有该常量的平台密钥（明文或封存形态）清空，平台回到"未签发"（网关 401 1005），并在 settings 写一条 qimen_demo_secret_cleared 记录清除次数（只有真的清除过才写；不含任何密钥）。
  • 取得密钥只有两条路：管理界面/接口（25.1），或命令行 GML_RUNTIME_MODE=… GML_DATA_DIR=/绝对路径 node scripts/qimen-issue-key.mjs --industry cosmetic --platform <平台 id 或编码> [--rotate]。密钥明文只在该命令的标准输出出现一次，已有密钥而没加 --rotate 会拒绝（旧密钥不变）。命令行所用的封存密钥（GML_SECRET_KEY，缺省由 JWT 密钥派生）必须与运行服务时一致。
  • 演示/测试模式下，服务启动时若 id 最小的有 AppKey 的平台还没有密钥，会为它生成一个随机的、本安装独有的密钥，只封存入库；启动日志只提示 AppKey 前 4 位与密钥末 4 位和上面的签发命令，不打印完整密钥，也不写入仓库。需要联调就对它执行 --rotate 取一个自己看得见的。已有密钥（含管理员签发的）重启不会被替换。
  • 生产模式不生成任何密钥：没有密钥的平台保持 401 1005，且网关整体仍由能力闸门 503 关闭。
  • GET /api/qimen/capabilities 与调试页平台列表里的 AppKey 只显示前 4 位（响应里带 app_key_masked: true）；完整 AppKey 请在 /oms/platforms 查看。

25.2 轮换

  • 平台已有密钥时，按钮变为「轮换奇门密钥」，会二次确认。轮换后旧密钥立即失效，没有宽限期；对方必须在你交付新密钥的同时切换，否则其请求返回 401。
  • 接口形式：POST /api/qimen/platforms/:id/secret；已有密钥而请求体没有 {"rotate": true} 时返回 409 QIMEN_SECRET_EXISTS，用来避免重复点击作废刚发出的密钥。平台不存在返回 404。
  • 签发 / 轮换写严格审计 QIMEN_SECRET_ISSUE / QIMEN_SECRET_ROTATE（只记 AppKey，不含密钥）；审计写不进去时密钥不变。

25.3 对接方需要知道的

签名契约是 ADR-0033 的 v2：请求体含 timestamp（UTC 毫秒，与服务器相差不超过 5 分钟）、nonce（16–64 位 [A-Za-z0-9_-]，不可重复）、sign（对 app_key、method、timestamp、nonce 与请求体摘要做 HMAC-SHA256，大写十六进制）；旧的 MD5 方式不再接受。常见 401 协议码：1005 平台尚未签发密钥、1006 时间戳超出窗口、1007 nonce 格式不合规、1008 nonce 重放。交付给对方的契约文档与测试向量由 ADR-0033 验收清单第 8 项要求，目前尚未产出。

25.4 如实边界

网关处理器是模拟承接方，不真实出入库，也未与任何真实平台完成对接；没有按平台的限速和 IP 白名单，需要由入口代理承担；备份含封存的密钥，生产启用前必须启用备份加密且备份密钥与 GML_SECRET_KEY 分管（安装手册 7.6）。

二十七 审计日志查看与导出

依据 Z7、ADR-0030。入口：侧栏「系统管理 → 审计日志」（/system/audit-logs）。

27.1 谁能用

  • 需要权限点 system:audit:view（查看与导出审计日志）。首次迁移只授予 admin；需要给审计员或财务经理时，由管理员在 /system/roles 为对应角色添加该权限点。
  • 侧栏「系统管理」分组目前只对管理员角色显示；被授予该权限点的非管理员看不到菜单入口，需要直接访问 /system/audit-logs（接口权限由服务端判定，不依赖菜单）。
  • 还要求账号数据范围为"全部"：受限范围账号返回 403 GLOBAL_DATA_FORBIDDEN，因为审计日志没有可靠的组织列，无法诚实地按范围缩小。
  • 旧接口 GET /api/auth/audit-logs 仍只对管理员开放，是无过滤的只读全量分页，不含新页面的脱敏二次处理和导出，日常请用新页面。

27.2 查询

过滤项（页面输入框与接口查询参数同名）：module、action、entity、entity_id、user（操作人名称或用户 ID）、keyword、from、to（日期格式 YYYY-MM-DD，from 不能晚于 to，格式错误返回 400）。每页最多 200 条；缺省按编号倒序，按 module 或按用户 ID（user 为 1 至 12 位纯数字）过滤时改按时间倒序（created_at、再按编号），但同时给了 entity 与 entity_id 时仍按编号倒序。要点：

  • keyword 只匹配动作（action）、对象（entity）和操作人名称，需要至少两个有效字符（三个及以上字符时可能走全文索引，两个字符走普通匹配，两条路径结果相同，见第三十八章）；模块与对象 ID 请用各自的精确过滤项，不搜索明细，避免通过关键字间接探测被脱敏的内容。
  • 明细读取时会再脱敏一次：密码、令牌、密钥类字段，以及自由文本里的 password: … 和 11 位手机号（显示为 138****5678），超长明细截断。写入时已脱敏，读取时再做是因为旧行或直接写库的行不保证。
  • 页面顶部的保留提示来自系统参数 retention_audit_days，同时说明哪些模块会被清理。
  • 总数是封顶估算，不是精确命中数。 接口为避免对大表整表计数，最多数到 10,001 行：响应里 total 最大为 10,001，has_more 为 true 表示命中超过 10,000 条（此时 total 只是下界），total_cap 固定返回 10000。页面在命中超过 10,000 条时会提示"总数是估算"，底部分页的"共 10,000 条"指可翻阅的范围（按当前排序的前 10,000 条），不是命中总数。翻页深度同样封顶：偏移量达到 10,000 的请求返回 400，要看更早的记录请加 module、user、from/to 等过滤条件缩小范围，或使用 27.3 的导出（单次上限 50000 行）。核对"本月到底有多少条"这类问题不要读分页总数。

27.3 导出 CSV

点页面上的「导出 CSV」按钮，或调用 GET /api/meta/audit-logs/export.csv（带同一组过滤参数与权限；需要带 Authorization: Bearer 令牌）。

  • 与列表共用同一过滤实现；UTF-8 带 BOM，便于 Excel 直接打开；列为 id, created_at, user_id, user_name, module, action, entity, entity_id, detail, ip。
  • 单次最多 50000 行。超出被截断，响应头 X-Export-Truncated: 1、X-Export-Max-Rows: 50000；需要完整数据时缩小日期范围分批导出。
  • 导出先写一条严格审计 AUDIT_LOG_EXPORT（含过滤条件、行数、是否截断、列清单），写不进去则不外发数据；导出文件不含这条导出自身的审计行，也不含导出期间新增的行。
  • 所有单元格加引号，以 =、+、-、@、制表符等开头的值前置 '，防止在电子表格里被当作公式。
  • 导出文件含操作人和 IP，属于个人信息：用加密渠道交付，用完销毁。

27.4 保留策略提示

导出只含当前库中尚存的行。审计日志仅 master（主数据维护）和 notify（通知渠道）两个模块会按 retention_audit_days 被 scripts/retention.mjs 清理；财务、资金、配置、账号权限、审批、隐私、保留摘要，以及采购 / 销售 / POS / 库存等业务单据模块的审计不会被清理（第二十四章）。

28.1 它是什么、不是什么

--ci-run=auto由脚本用 gh run list --commit <HEAD> --workflow ci.yml 查本提交最新一次结论为 success 的 run，记入 ci_run_id（只取 gh 返回的最近 30 条记录，更早的成功记录查不到时同样记为 null）。本机没有 gh、未登录、该提交没有记录或没有成功的 run 时，ci_run_id 为 null，原因写在 ci_lookup.reason，不会猜、不会让构建失败。这是"查到了"的证据，仍不是目标平台验收
--focused-result / --focused-source声明焦点测试结果（只接受 passed）及运行位置，必须成对出现；记为"操作者声明"，脚本不替你验证
--regression-result / --regression-source同上，针对隔离回归
--reuse-node-modules验收复用本检出的依赖而不联网安装，证据会如实记录
--log / --log=<文件>构建前校验证据透明日志并拒绝同名候选，自检通过后追加一行；不带值用 docs/release/EVIDENCE-LOG.jsonl，指定文件只能写 --log=<路径>。见 35.7

两个取值选项既接受 --k=v 也接受 --k v。--run-tests 与 --ci-run=auto 是互相独立的可选项：不带它们时对应字段仍是 not run / null。写 --*-result=failed 会被拒绝（不拿失败的运行造候选包）；未给 --*-result 的项在证据里记为 not run。另有仅供最小包测试用的 --skip-build、--skip-docs，运维不用。

要给证据签名，在命令前设置 GML_RELEASE_SIGN_KEY=<私钥 PEM 的绝对路径>（不是命令行参数），生成密钥、验签与保管见第三十五章。

28.3 脚本做了什么

  1. 拒绝脏工作树（已修改、已暂存、未跟踪文件均算），构建前后各查一次，没有跳过开关。
  2. 运行 npm run release 到临时目录，核对 MANIFEST.baseCommit 等于当前 HEAD、版本号与 package.json 一致。
  3. 对该 zip 的全新解压依次执行：verify-release、密钥与数据库文件扫描、生产模式验收（scripts/test-local-delivery.mjs）。任一步失败则删除本次产物并以非零退出。

3b. 给了 --run-tests 时，在第 3 步的 verify-release 与密钥扫描之后、守卫与生产模式验收之前运行焦点套件（对比工作树 tests/ 与包内 release/tests-tree.json 的哈希必须一致）；--run-guards 或 --run-tests 任一出现，才会运行五项守卫。

  1. 写出证据与发行说明，再用 verify-release --evidence 校验证据本身。接收方可在解压后的包根目录运行 node scripts/verify-release.mjs --evidence=<EVIDENCE.json> --artifact=<RC-….zip> 复核（见 28.6）。

28.4 读证据时的注意

  • EVIDENCE.json 只检查一致性，不检查真实性：操作者声明的结果只和操作者一样可信。
  • synthetic_drill 记录随包提供的合成容量演练文件哈希，是开发机上的合成演练，不是目标主机结果。
  • 候选包的验收在构建它的那台机器上跑，不是目标平台验收。
  • focused_tests.origin 为 produced 表示脚本自己跑过并解析了计数；为 operator-attested 才是操作者声明。看到 produced 时仍要核对 summary_counts（skipped、todo 不为零说明有未执行的用例）与 duration_ms。
  • ci_run_id 为 null 不是错误：看 ci_lookup（mode 为 auto 时读 reason，none 表示没给 --ci-run）。ci_lookup.gh_override 为真说明查询用的是测试替身而非真实 gh，验证脚本会警告，此类证据不可当作托管 CI 凭据。

28.5 仍需人工完成

在指定主机上跑焦点测试与隔离回归（Linux 在 dmserver，macOS 专属项在 Mac Studio）并用 --*-result 登记，或对照托管 CI；确认该提交的托管 CI 并用 --ci-run 记录；在目标平台做验收；审阅 RELEASE-NOTES.md、依赖公告和 backlog 未结项；打 tag、发布或部署需要所有者明确授权；传输 zip 时一并带 .sha256 并在接收端复核哈希。

28.6 接收方复核：verify-release 与 --evidence

在解压后的包根目录（有 MANIFEST.json 的那一层）运行：

node scripts/verify-release.mjs
node scripts/verify-release.mjs --evidence=<EVIDENCE.json 的路径> --artifact=<RC-…zip 的路径>

--evidence 与 --artifact 必须写成 --名称=值 的形式（空格分隔的写法不被识别）；验签用的 --pubkey 两种写法都行，见第三十五章。不带参数时只核对 MANIFEST.json 的文件清单与哈希、SBOM 结构、清单中的禁入文件（数据库、实例状态、.env）以及包根下清单之外的多余文件（运行态目录 node_modules、data、.local、backups 除外）。密钥内容扫描由 release-candidate.mjs 在构建时另做，verify-release 不做；带 --evidence 时再核对证据本身：必填字段齐全、version 与 commit 等于包内 MANIFEST.json、not_a_release 为 true、没有 failed 的结果、passed 的结果带来源、五项守卫齐全、produced 的焦点测试计数自洽且 tests_tree_sha256 与包内清单一致、演练文件哈希与包内文件一致；再加 --artifact 才会核对 zip 的名称、sha256 与字节数。成功时最后一行是 [verify] N files; 0 errors，退出码 0；任何一项不符都会逐条打印并以退出码 1 结束。

边界：它核对的是一致性，不是真实性。能同时改证据和包的人可以伪造它；操作者声明的结果只和操作者一样可信。通过也不是发布批准、不是目标平台验收。

二十九 夜间容量基线摘要的解读

面向运维与开发。依据 Z10，工作流 .github/workflows/nightly-capacity.yml，说明见 docs/implementation/ci.md 与 docs/implementation/capacity-baseline.md。

29.1 它是什么

每天定时（UTC 03:17，仅默认分支生效）或手动触发（输入 scale：small 2 000 SKU、medium 2 万 SKU 与 3 万单据、large 2 万 SKU 与 5 万单据、large-ci 10 万 SKU 与 100 万流水（见 29.4），缺省 medium），在 GitHub 托管 runner 上：生成合成库 → 明文与加密备份 → 恢复演练 → 索引审计（explain-audit）→ 接口压测读档 → 写档压测，最后由 scripts/capacity-summary.mjs 缩减为一个白名单摘要。Actions 产物名为 os-erp-capacity-summary-<run id>-<尝试号>（保留 30 天），只含 capacity-summary.json，数据库、备份和原始报告不上传。该工作流在 ci.md 中自述写成之初尚未在 GitHub 上执行过，首次运行以 Actions 页面实际结果为准。

29.2 怎么读摘要

scope_notice固定声明：托管 runner、合成数据、单次运行，只是趋势指示

失败原因码：pipeline_report_missing、pipeline_step_failed（流水线任一步失败）；explain_audit_missing、explain_audit_unreadable、explain_audit_violations（索引审计违规 > 0）；bench_read_missing、bench_read_unreadable、bench_read_errors；bench_write_missing、bench_write_unreadable、bench_write_errors、bench_write_integrity。

只有这三类情况会让作业标红：流水线步骤失败、索引审计违规、压测错误数大于 0（写档含完整性核对失败）。延迟只记录，不设阈值，所以作业绿并不表示性能好。

29.3 正确的使用方式

  • 把它当同一规模下逐日对比的趋势指示：看 p95 有没有持续恶化、违规数有没有出现。托管 runner 是共享虚拟机，单日数字波动大，读数字时连同 host.loadavg_* 一起看。
  • 它不是目标主机 dmserver 的结果、不是容量承诺、不是 RPO / RTO 证据，也不是发行包或生产验收。需要容量结论时，按 capacity-baseline.md 在目标主机上用生产规模副本实测。
  • 摘要里的恢复演练耗时同样来自合成库和托管 runner，不可对客户作为恢复时间承诺。
  • 开始收费后是否切回专用 Linux 主机，需要所有者单独决定。

29.4 large-ci 规模、partial / reached 字段与托管运行结果表

三十 库存列表分页

依据 Z3。库存查询页（/inventory/stocks）和接口 GET /api/inventory/stocks 已改为强制游标分页，翻页（第二页起）的代价不再随总行数增长。第一页仍要对满足条件的全部行做一次计数与合计，大库上进入页面或改过滤条件时仍有这一次整表聚合，目标主机上的实测尚未做。

  • 每页缺省 50 行，pageSize 上限 500（超出按 500 处理）。页面底部是「下一页」翻页，每页 50 行。
  • 接口翻页用游标：第一页不带游标；响应里的 has_more 为真时，把 next_after_id 作为下一次请求的 after_id 参数继续取，直到 has_more 为假。after_id 必须是非负整数，否则返回错误。行按库存记录编号升序。

  • 库存按你的数据范围过滤，范围外的仓库不出现（见第二十六章）。按商品汇总的 /inventory/stocks/by-sku 仍使用页码分页。

三十一 指标导出：接入 Prometheus

依据 ADR-0045（docs/implementation/ADR-0045-metrics-export.md）。完整抓取配置、指标清单和告警规则说明在仓库内 docs/operations/monitoring.md，规则本身是 docs/operations/alerts/ 下的两个 YAML 文件（见 31.5），这里给接入步骤和排障要点。指标只读，只含备份年龄、迁移校验和、磁盘、登录节流、严格审计写失败、写重试等数字，不含账号、路径和业务数据。

31.1 开启抓取令牌

  1. 生成至少 32 字符的令牌并交给密码管理器：openssl rand -hex 32（输出 64 个字符）。
  2. 只通过环境变量交给服务，和 GML_JWT_SECRET 一样不进仓库、工单和日志。本机安装在启动命令前面设置：GML_METRICS_TOKEN="$(cat /secure/metrics.token)" node scripts/local-manage.mjs start（安装手册 5.4、6.3）。令牌轮换 = 换值并重启服务，同时更新 Prometheus 侧的令牌文件。
  3. 未设置或短于 32 字符时，令牌路径整体关闭，不会因为"设了"就变成弱口令；此时只有管理员登录凭据能读指标。
  4. 令牌只对 GET /api/meta/metrics?format=prometheus 有效，只读。对 JSON 形态、/health 和其他任何接口无效；令牌不能放在 URL 查询参数里。

自测（令牌放在文件里读取，不进 shell 历史；注意命令替换仍会让令牌短暂出现在 curl 的进程参数里，共享主机上请改用 curl -H @文件 或在受控的会话里执行）：

curl -sS -H "Authorization: Bearer $(cat /secure/metrics.token)" 'http://127.0.0.1:3001/api/meta/metrics?format=prometheus' | head

端口按你的实例填写（安装手册第六章；Docker 的映射端口见 docker-compose.yml）。返回内容类型为 text/plain; version=0.0.4，指标名统一以 os_erp_ 开头。

31.2 Prometheus 侧抓取配置

scrape_configs:
  - job_name: os-erp
    metrics_path: /api/meta/metrics
    params:
      format: [prometheus]
    scrape_interval: 30s
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/secrets/os-erp-metrics-token   # 文件内容只有令牌本身
    scheme: https            # 经反向代理终结 TLS 时；内网直连则 http
    static_configs:
      - targets: ['erp.example.internal:443']

令牌放 credentials_file 而不是配置文件正文，配置文件才能入库；令牌走 Authorization 头，不会出现在访问日志的 URL 里。Prometheus 与服务之间不是回环或可信内网时必须走 TLS（反向代理配置见安装手册 6.1）。再加一条 up{job="os-erp"} == 0 监控抓取本身是否中断。

31.3 读指标的要点

  • 数值型指标（os_erp_backup_age_seconds、os_erp_disk_free_bytes、os_erp_migration_checksum_*）里 -1 表示未知，不要当成"0 秒前刚备份"。完全没有备份报告时，os_erp_backup_missing 为 1、os_erp_backup_last_failed 为 0、备份年龄为 -1。备份没跑（定时任务挂了）只有备份年龄/缺失告警能发现。
  • 计数器（*_total）在进程内累计，重启归零；用 increase()、rate()，不要比较绝对值。
  • os_erp_csp_violation_reports_total 恒为 0：当前内容安全策略没有违规上报端点，该指标表示"未采集"，不要据此告警或据此认为没有违规。
  • os_erp_security_audit_unavailable_total 增加意味着有业务变更因安全审计写不进去而回滚，任何一次都要查（审计表、磁盘空间、数据库只读或锁）。

31.4 排障与边界

  • 抓取返回 401：令牌与服务端 GML_METRICS_TOKEN 不一致、服务端令牌短于 32 字符、用了不带 format=prometheus 的地址（令牌对 JSON 形态无效），或未带 Authorization 头。错误令牌与没带凭据返回同样的 401，不提示令牌机制是否存在。format 取值不是 json 或 prometheus：已通过管理员登录认证的请求返回 400；只带抓取令牌的请求会先落到登录认证，得到 401。
  • 备份年龄为 -1 且 os_erp_backup_missing 为 1：指标读的是备份目录里最新的 backup-report-*.json，还没跑过 db-backup 就是这个状态（第二十三章）。
  • 计数器为 0 但日志里有对应事件：多半是进程重启过，或抓到的是另一个实例。
  • 如实边界：本节的抓取配置和告警规则是按 ADR 与端点实现写出的，没有在真实 Prometheus 实例上做过端到端验证；告警阈值需按你的备份周期、磁盘规模调整。Docker 部署时 docker-compose.yml 的 environment 显式列出的只有端口、主机、运行模式、数据目录、GML_TRUST_PROXY 与 GML_JWT_SECRET 等少数变量，令牌可写进同目录 .env（compose 通过 env_file 载入）；该路径未实际验证。

校验：仓库的 CI 在 docker 作业里用固定摘要的 prom/prometheus 镜像跑 promtool check rules docs/operations/alerts/*.yml（命令见 .github/workflows/ci.yml 的 "Alert rules" 步骤；容器无网络，仓库只读挂载）。你自己改过规则、而本机装有 promtool 时，可以在仓库根目录运行同样的检查：

promtool check rules docs/operations/alerts/*.yml

promtool 是 Prometheus 自带的工具，不是本仓库脚本，参数以其自身帮助为准。如实边界：本机开发环境没有 promtool，PromQL 语法检查只在托管 CI 上跑，而那一步尚未在 runner 上实际运行过；本地测试 tests/metrics-export.test.mjs 只做 YAML 结构检查，并核对规则引用的 os_erp_* 序列都真实存在于导出里。

三十二 升级演练：迁移重放与读报告

依据 scripts/upgrade-rehearsal.mjs 与 docs/implementation/capacity-baseline.md。它回答三个问题：这批迁移在你的数据量上要多久、会把写入者挡多久、失败后能不能退回去。它和第二十三章的升级回退演练（upgrade-rollback-drill.mjs）不同：回退演练在恢复副本上施加一个必败迁移，证明失败整条回滚、篡改被拒绝、从备份回退后服务可启动；本演练用真实待上线的迁移逐个重放并量耗时。恢复成功之后若升级或核对失败，本演练会自行回退并调用回退演练，把结论写进报告。

32.1 前提与输入

  • 在仓库（代码副本）根目录运行，Node 22。输入是 db-backup.mjs 生成的备份集（带 backup-report-<stamp>.json），库必须是生产模式库；加密备份需要环境变量 GML_BACKUP_KEY（同安装手册 7.6，缺失为 DRILL_BACKUP_KEY_REQUIRED）。
  • --target-dir 必须是不存在或为空的绝对路径，不能是线上数据目录、不能是备份来源数据目录，也不能位于仓库 data/ 内。演练在里面恢复一份副本并写报告，源备份和线上数据不会被改动。演练完归档报告，再删除目录（里面是数据副本）。
  • --from=N 的含义：编号不大于 N 的迁移视为已应用的基线，编号大于 N 的会被重放。N 取这份备份对应的库已应用的最高迁移编号（在线上实例上运行 node scripts/migrate.mjs --status 查看，环境变量同安装手册 5.5）。N 高于库里真实版本会被拒绝（REHEARSAL_BASELINE_NOT_APPLIED，退出码 2）；N 已经是仓库最高编号则没有可演练的迁移（REHEARSAL_NOTHING_TO_APPLY）。

32.2 命令

所有参数写成 --名称=值（空格分隔不被识别），未知参数直接拒绝（DRILL_USAGE）：

# 用真实备份集
TARGET=/srv/drills/rehearsal-$(date +%Y%m%d-%H%M)
node scripts/upgrade-rehearsal.mjs --from=58 --backup-dir=$INSTANCE/data/backups --target-dir=$TARGET

# 指定非最新的备份集
node scripts/upgrade-rehearsal.mjs --from=58 --backup-dir=$INSTANCE/data/backups --stamp=<yyyyMMdd-HHmmss> --target-dir=$TARGET

# 用合成库目录（须由 synth-data.mjs 生成，带合成指纹；多行业库目录被拒绝）
node scripts/upgrade-rehearsal.mjs --from=58 --synth-dir=/abs/synth-data-dir --target-dir=$TARGET

示例里的 58 只是占位，按 32.1 取你的库的值。可选参数：--stamp（只用于 --backup-dir）、--extra-migrations-dir=<绝对目录>（在大库上预演尚未合入仓库的迁移：目录里编号大于仓库最大编号的 NNN_名称.cjs 追加到序列末尾，只复制进暂存目录，不写进 server/db/migrations/）、--keep-post-baseline-indexes（不删除后续迁移创建的索引，默认会删，使这些迁移真的重新建索引）。--backup-dir 与 --synth-dir 必须二选一，--from 与 --target-dir 必填。

退出码：0 升级和全部核对通过；1 升级或核对失败（备份副本已恢复成功之后的失败会执行回退，见报告 rollback；在恢复之前就失败，例如加密备份缺少或用错 GML_BACKUP_KEY、sha256 不符，则不会回退，且可能没有报告文件，只能看屏幕上的错误信息）；2 参数、目录或基线被拒绝（尽力清理，不留下演练输出；处理过程中可能创建过临时文件，随后删除）。屏幕上逐库打印每个迁移一行（状态、耗时、净耗时、写锁区间、结构原本存在）和各项核对的 ✓/✗，末尾是回退结果和失败原因。

32.3 读报告 upgrade-rehearsal-<stamp>.json

报告写在 --target-dir 内，权限 0600，不含密码和密钥。先看顶层，再看每库：

字段看什么
passed、failures、warningspassed 为 true 且 failures 为空才算通过；warnings 要读，例如旧登记行无校验和、基线迁移被自愈
scope_notice、host固定声明：单次墙钟、运行它的这台机器当时的负载（loadavg_start/loadavg_end），不是目标主机结果，不是容量承诺，不是验收证据
input、baseline用了哪个备份集，baseline.from 和 baseline.replay[]（被重放的迁移编号）、extra_migrations、post_baseline_indexes
databases[].steps[]每个迁移一项：status（ok、failed、unexpected、pending）、duration_ms、overhead_ms、net_ms（约等于该迁移本身的执行加登记提交）、structure_preexisting、healed、lock、error
databases[].invariants[]升级后核对，每项 passed：all_steps_applied、checksums_verified、repo_files_match_registry、production_rerun_is_noop、registry_covers_all_migrations、replayed_rows_recorded_as_applied、integrity_ok、foreign_keys_not_worse、probes_retained（用户、商品、采购单、收款单计数和应收余额升级前后相同）、seed_invariants_not_regressed（不变量不得从绿变红）

timing恢复、升级等总耗时

判读要点：

  1. 只有 structure_preexisting 为 false 的步骤，耗时才代表真实升级成本。 为 true 说明这个迁移要建的表、列在副本里本来就存在（备份是用当前代码产生的），重放只是幂等空转，耗时偏低；为 null 表示该迁移没有自检。要演练真正的旧库，应使用旧版本代码产生的备份集，并把 --from 取为它的最高已应用编号。
  2. 写锁等待是区间，不是精确值。 lock.max_busy_span_ms 是探测到锁被占用的最长连续时间（偏小），lock.max_blocked_ms 是含调度噪声的近似值（偏大，高负载下可能明显偏大）；两者是采样观察值，不是严格上下界：探针约每毫秒试一次，极短的锁可能完全采不到（busy_attempts 为 0 并不等于没有锁），相邻的锁也可能被合并成一段。一个迁移是一个事务，迁移期间持有写事务的粗上界是 duration_ms。写入者在这段时间内会等待或遇到忙错误，WAL 模式下读者不被挡住，本演练不量读者。
  3. lock.other_errors 大于 0 表示探针本身出错，该步判失败（没有有效的锁时间证据），不要采信其锁时间。
  4. 失败原因码要对照 failures：PRE_UPGRADE_CHECKSUM_MISMATCH（升级前已登记迁移与当前文件校验和不一致，生产启动本来就会被拒绝，不要升级）、PRE_UPGRADE_REGISTRY_FILE_MISSING（版本表有登记而仓库没有对应文件）、MIGRATION_CHECKSUM_MISMATCH、ROLLBACK_CHECK_FAILED、ROLLBACK_DRILL_FAILED。演练不改写任何已登记的校验和，也不调用显式收养（--adopt-checksums）；但迁移运行器会按当前文件补登记旧行里为空的校验和（checksum_origin 为 adopted），这类情况会写入 warnings，请读。
  5. 一次通过只说明：在这份备份副本上，这批迁移能按顺序应用、核对项全绿。它不证明目标主机上的耗时（数字来自运行它的机器，需在 dmserver 或目标主机用生产规模副本实测后才能引用）、不证明业务回归、不代表生产就绪。失败时按第二十三章的"升级失败"处理：不重试、不手工改迁移登记表、不收养校验和，把报告交开发。

夜间容量工作流有一个默认关闭的手动输入 rehearsal，用合成库做同样的演练，只把各迁移一行摘要写进日志；定时运行永不执行它（第二十九章）。

三十三 审批模板维护权限与审批管理员的分离

依据 ADR-0037 的 AA3 补充与迁移 063。

33.1 两个权限点，两件事

权限点管什么
system:approval:template维护审批模板：新建/修改模板（含级次整体重建）POST /api/approval/templates，启用/停用 POST /api/approval/templates/:id/toggle。没有删除接口，模板只能新建、覆盖、启停，三者同一个门
system:approval:manage审批管理员"全见"：在"待我审批"、待办、列表、总览里看到全库的待审实例（受设置项 approval_manager_global 影响，见 ADR-0037 Z9 开关）。不再允许改模板

升级前持有 manage 就能改模板的账号，升级后改模板会得到 403，这是预期的收口。

33.2 谁能改模板

  • 迁移 063 只在这个权限点第一次出现时把它授给 admin；其他角色（财务经理、流程管理员等）需要时，由管理员在 /system/roles 为对应角色添加。管理员事后收回的授权不会被后续升级恢复。
  • 除权限点外还要求账号数据范围为全局：受限范围（组织、子树、经销商、本人、无组织）的账号即使持有 template，写模板也返回 403 GLOBAL_DATA_FORBIDDEN。原因：审批模板没有组织列，无法诚实地按范围缩小。
  • 指定审批人时：用户必须存在（否则 400 APPROVER_NOT_FOUND）。库函数里还有第二层防线（受限范围的维护者只能指定其组织范围内的人，否则 APPROVER_OUT_OF_SCOPE），但经这两个接口时受限范围账号在全局范围检查处就已返回 GLOBAL_DATA_FORBIDDEN，通常看不到这一条。
  • 读模板（GET /api/approval/templates）沿用原门：登录的内部账号即可（外部账号被拒绝），不要求上述权限点。

33.3 升级后的复核（存量）

升级不会自动清理升级前受限管理员已写入的"把自己设为审批人"的级次。请用全局范围账号做一次：

  1. 打开审批模板列表（接口 GET /api/approval/templates），检查各模板级次里 approver_type 为 user（指定人员）的指派，确认每个审批人确实应该处理该模板覆盖的单据。
  2. 在 /system/roles 里，对不需要的受限账号收回 system:approval:manage，需要改模板的少数人再单独授予 system:approval:template，并确认其数据范围为"全部"。
  3. 用被收权的原账号重新登录，确认改模板返回 403。注意：收回 manage 只去掉"全见"；仍被模板当前级次指定为审批人的账号，仍能在自己的待审队列里看到对应实例，提交人也仍能看到自己提交的单据。要彻底去掉存量自指派，需要由持 system:approval:template 的全局账号改写该模板的级次（改完再次核对待办）。

如实边界：角色型、权限型审批人"看得到、批不了"的口径不变；MCP approval.approve 的签字人范围口径不变；模板修改会写审计记录（尽力写入，审计本身写不进去时业务修改不会因此回滚，所以请抽查审计日志）。

三十四 POS 差异结案与作废订单的权限

依据 ADR-0025 的 AA9 补充与迁移 066。第十二章讲业务流程，这里讲谁能做、做不了时看什么。

34.1 长短款差异结案：pos.shift.settle

  • 班次核款时选择"挂账待查"的差异，由有 pos.shift.settle 权限的账号落案（charge 责任人承担，或 absorb 公司承担，按页面按钮选择），接口 POST /api/pos/shifts/:id/settle-variance。原来按角色名（admin、finance）放行，现在按权限点。
  • 迁移 066 在权限点首次出现时授予 admin、内置 finance（保持原有能力）和内置 store（店长）。店长默认就能结案本店的挂账差异，包括自己核款时挂账的那一笔。 若要保持"门店挂账、总部落案"，由管理员在 /system/roles 从 store 角色收回该权限点；收回后不会被后续升级恢复。
  • 范围规则：绑定了门店的非管理员账号只能结本店班次，结别家的返回 404 SHIFT_NOT_FOUND（班次状态不变）；没有门店绑定的账号，只有总部角色（admin、finance 等）可结任意门店，未绑门店的店长等账号返回 403。管理员不要求门店绑定。
  • 页面上"长短款落案"（班次详情）和"责任人承担 / 公司承担"（总部监控页）按钮在没有该权限时不显示。撤权后接口同样 403，状态不动。

34.2 作废订单：pos.refund

作废本地单 POST /api/pos/orders/:id/void 与退货 POST /api/pos/returns 同属权限点 pos.refund，另需账号绑定了门店（路由放行管理员，但处理时仍要求有门店绑定，未绑门店的管理员也是 403）。POS 本机单据列表里的"作废"按钮在没有 pos.refund（含权限还没加载完）时隐藏。作废会在同一事务里回退已用的营销优惠和积分，已完成的销售不要直接删除，按第十二章走作废或退货。

34.3 授权与排错

  1. 先用原账号复现：按钮不显示通常是缺权限点；按钮显示但提示无权限，多半是服务端判定（权限、门店范围、班次不属于本店）。
  2. 管理员在 /system/roles 核对该角色是否持有 pos.shift.settle 或 pos.refund；改完让用户重新登录，用原账号验证，不要只看管理员页面上的勾选。
  3. 结案返回 404 SHIFT_NOT_FOUND 时，先核对账号绑定的门店与班次所属门店是否一致；该提示对"不存在"与"不属于本店"文案相同，这是有意为之。

三十五 发行证据签名与密钥保管

依据 ADR-0047（docs/implementation/ADR-0047-evidence-signing.md）与 docs/release/README.md。面向负责交付的人员，接第二十八章。签名是可选的：不设密钥，候选包照常构建，EVIDENCE.json 里 "signature": null。

35.1 它证明什么、不证明什么

  • 签名证明"持有私钥的人在构建时批准了这份证据"：对整份证据（含 signature 元数据）的规范化 JSON 做 Ed25519 签名，任何值被改、换钥、删签名文件都会验不过。
  • 不证明证据内容为真：operator-attested（操作者声明）的结果仍然只是声明。本机私钥被盗即可伪造；没有硬件令牌，也没有第三方时间戳。仓库里有一份自建的追加式透明日志（35.7），它记录"某候选的证据哈希何时、由谁构建"，但不替代签名，也不是第三方锚定。
  • 托管 CI 不持有私钥，所以 CI 构建的候选包是未签名的；是否要求签名，取决于接收方验证时是否带 --pubkey 与 --require-signature（35.8）；验证未签名候选时即使不要求，也会打印醒目警告。

35.2 生成密钥对

在负责签名的那台机器上，对一个不存在或为空的绝对路径目录运行（该脚本没有 --help；未知或重复参数、缺少 --out 会打印用法行，相对路径等只打印对应的错误）：

node scripts/release-keygen.mjs --out /abs/path/to/new-empty-dir

--out 也接受 --out=<路径>；只允许出现一次。脚本以 0700 建目录，写出 release-sign.key.pem（私钥，0600）和 release-sign.pub.pem（公钥，请求模式 0644，实际受进程 umask 影响），并在标准输出打印 JSON：两个文件路径与 key_id（公钥 SPKI DER 的 sha256）。私钥内容从不打印。它拒绝：相对路径；本仓库或任何 git 工作树之内（含经符号链接绕进去）；已存在且非空的目录。失败时不留文件。

35.3 构建时签名

GML_RELEASE_SIGN_KEY=/abs/path/release-sign.key.pem node scripts/release-candidate.mjs [第二十八章的参数]

GML_RELEASE_SIGN_KEY 是私钥 PEM 的绝对路径（不是密钥内容）。成功时在 release/RC-<version>-<shortsha>.evidence/ 里多出 EVIDENCE.sig（64 字节签名的 base64），证据里的 signature 为 {algorithm, canonicalization, key_id, sig_file}。EVIDENCE.sig 不在 zip 内（证据含 zip 的哈希，放进去会自指），随 .evidence/ 目录一起分发。构建末尾脚本会用同一把钥派生的公钥自验一次，失败则删除本次产物。

变量设置了但密钥不可用（空值、文件不存在、不是 Ed25519、位于任何 git 工作树内、对组或其他用户有任何权限位，不只是可读；Windows 上不做这项权限检查）时，在构建开始前就失败，不会悄悄退回未签名。遇到时先 chmod 600 并检查路径，不要清掉变量了事。

35.4 接收方验签

在解压后的包根目录运行：

node scripts/verify-release.mjs --evidence=<EVIDENCE.json 路径> --pubkey <release-sign.pub.pem 路径>

--evidence 与 --artifact 只认 --名称=值；--pubkey 两种写法都认（--pubkey <pem> 或 --pubkey=<pem>），且只能出现一次。该脚本没有 --help。要点：

  • 给了公钥而证据 signature 为 null 或缺失 ⇒ 失败（防降级：已签名的候选不能靠把 signature 改成 null 蒙混）；缺 EVIDENCE.sig、格式不对、换钥、证据被改 ⇒ 失败；公钥参数其实是私钥 PEM ⇒ 直接拒绝。
  • 不给 --pubkey：其他校验照旧，若证据已签名，只打印"signature not verified"提示，不算验过签名；若证据未签名（signature 为 null），向标准错误输出 WARNING: UNSIGNED CANDIDATE 横幅，退出码不变（见 35.8）。
  • --pubkey 不带 --evidence 是用法错误。
  • 公钥必须带外取得（不要用候选包里或同一渠道附带的公钥）。核对 key_id 与签名方事先告知的值一致。

35.5 私钥保管

  1. 只在签名机器上生成并使用；目录在所有仓库之外。不要提交、发邮件、贴进工单或 CI 日志、放共享盘；密钥扫描与 .gitignore 只是兜底，不是控制手段。
  2. 在所有者的离线备份里留一份私钥。丢失私钥只意味着以后不能再用这把钥签新候选；已签发的候选继续可用旧公钥验证。
  3. 公钥与 key_id 带外交给接收方登记。
  4. 轮换：重新运行 35.2 生成新钥对，向接收方发布新公钥与 key_id；旧候选仍用旧公钥验。怀疑私钥可能泄露：接收方停止信任该 key_id，用新钥重新签发候选。

35.6 如实边界

签名、验签与透明日志的单元测试在 tests/release-signing.test.mjs；没有在接收方的真实交付流程里做过端到端演练，也没有用硬件令牌或 HSM 保管私钥。

35.7 发行证据透明日志：--log

依据 ADR-0052 与 docs/release/README.md。日志是仓库里的追加式哈希链文件 docs/release/EVIDENCE-LOG.jsonl：每个候选一行，记录候选名 RC-<version>-<shortsha>、规范化证据的 sha256、签名文件的 sha256（未签名为 null）、built_by、时间戳，以及上一行原文的 sha256。它让"某个候选在何时以什么证据哈希被构建过"可以事后核对，不让证据变得更真实。

构建端（release-candidate.mjs，参数见第二十八章）：

node scripts/release-candidate.mjs --log [第二十八章的其他参数]
node scripts/release-candidate.mjs --log=/abs/path/EVIDENCE-LOG.jsonl [其他参数]
  • --log 不带值时用仓库内的缺省路径；指定文件只能写成 --log=<路径>（--log <路径> 的空格写法不被识别为路径）。
  • 构建前先校验整条链并拒绝已有同名候选；链是坏的就失败，不会自动修复。证据自验通过之后才追加；追加失败则删除本次产物。
  • 追加会改动被 Git 跟踪的文件：下次构建前必须先提交（脏工作树检查照常生效）。追加时用独占锁文件 <日志>.lock，锁被占用就直接失败而不等待；进程崩溃残留的锁，要确认没有别的进程在追加后手工删除。
  • 候选名在日志里只能出现一次。同一提交想重新签发，需要一个新提交（新名称）。
  • built_by 记录构建进程的自述：环境变量 GITHUB_ACTIONS=true 时为 hosted-ci（脚本此时拒绝 GML_RELEASE_SIGN_KEY，托管 CI 不持钥）；用密钥签名的构建为 key-holder；其余为 local。它写进证据（被签名覆盖）和日志，是自述，不是认证。当前 ci.yml 并不构建候选包，托管 CI 产出候选是后续才有的流程。

验证端（接收方在解压后的包根目录运行，--evidence 必须以 --evidence=<路径> 书写）：

node scripts/verify-release.mjs --evidence=<EVIDENCE.json 路径> --log=<EVIDENCE-LOG.jsonl 路径>

检查：链完整；本候选名在日志里；证据哈希、签名摘要与 built_by 与手上的证据一致。--log 只能与 --evidence 同用且只能出现一次；不带值的 --log 默认指包根下的 docs/release/EVIDENCE-LOG.jsonl，而交付包（npm run release 的产物）不带 docs/release/ 目录，所以接收方通常要用 --log=<路径> 指向从仓库另行取得的日志副本。

如实边界：哈希链只能发现中间行被改，发现不了最新几行被截掉，也发现不了整个文件被另一条有效链替换——这要靠 Git 历史和带外保存的最新一行哈希来补。时间戳是构建者自述，不是时间戳权威。

35.8 未签名候选的警告与 --require-signature

  • 对 signature 为 null 的证据，verify-release.mjs --evidence=… 向标准错误打印 WARNING: UNSIGNED CANDIDATE 横幅，退出码不变。托管 CI 候选和没设密钥的本机候选都属此类，只能当开发候选。
  • 要把它变成失败：--require-signature，必须同时给 --pubkey（仅给 --require-signature 是用法错误），而且必须与 --evidence 同用：
node scripts/verify-release.mjs --evidence=<EVIDENCE.json 路径> --pubkey <release-sign.pub.pem 路径> --require-signature --log=<EVIDENCE-LOG.jsonl 路径>

未签名即失败；给了公钥时沿用 35.4 的验签与防降级。正式发行必须由持钥者在受控机器上从干净检出重建并签名（设 GML_RELEASE_SIGN_KEY，带 --log）；已被日志登记的提交（例如托管 CI 构建过的）重签需要新提交。接收方的正式验收用上面这条完整命令。

三十六 审计日志哈希链：校验、归档与"链断则拒绝"

依据 ADR-0049（迁移 068）与 docs/operations/audit-integrity.md（完整说明与排障在那里）。audit_logs 每行带 prev_hash / row_hash，串成一条链；哈希覆盖的列上，未登记的内容改动、中间行的删除或插入会被定位到第一处断点；覆盖不到的情形见 36.4。面向运维与审计人员；归档是不可逆操作。

两个脚本（audit-verify-chain.mjs、audit-archive.mjs；audit-fts-maintain.mjs 也用这套解析，见第三十八章）共用一套参数解析，只接受 --名称 值 的空格写法，不接受 --名称=值；未知参数退出码 2 并列出可用参数；两者都没有 --help。数据目录用 --data-dir <绝对路径> 给出（缺省才读 GML_DATA_DIR），不能是代码副本里的 data/；某个行业库文件不存在时只报 absent，不会创建。

36.1 日常校验（只读）

node scripts/audit-verify-chain.mjs --data-dir /abs/data                       # 所有行业库
node scripts/audit-verify-chain.mjs --data-dir /abs/data --industry cosmetic --json

可用参数：--data-dir、--industry（cosmetic、food、apparel）、--expect-tip <64 位小写十六进制>、--json，以及离机复核用的 --against-backup <备份或清单>、--archive-dir <目录>、--strict-anchors（见 36.5）。

  • 每库一行：OK cosmetic: <行数> 行，id <首>..<末>，锚点 <n>，tip=<链尾哈希>；有断点时 BREAK <行业>: 第一个断点 id=… 类型=…；库还没升级到迁移 068 时是 NOT-MIGRATED。
  • 退出码：0 全部 OK；1 有断点或库未迁移；2 参数或环境错误。
  • 断点类型：content（该行内容被改）、link（中间行被删或插入，且没有登记过的锚点）、unchained（有行没进链）、tip（与 --expect-tip 不符）。表尾的 unchained 会在下次服务启动或下一条审计写入时被接上，但在那之前就是告警；夹在已入链行中间的 unchained 系统不会自愈（避免把篡改洗白），会一直被报出。
  • 只读，不阻塞写入。建议随备份校验每天跑一次，并把输出里的 tip= 值带外保存（另一台机器、对象存储或工单）：链本身看不出"最后几行被删"，只有拿保存的 tip 对照才行。

发现尾部截断时，把同一时刻停写后记录的 tip 传回：

node scripts/audit-verify-chain.mjs --data-dir /abs/data --industry cosmetic --expect-tip <保存的 tip>

--expect-tip 必须同时给 --industry（它只对单个行业有意义），否则退出 2。服务在线写入时 tip 本来就会前进，日常以趋势为准：last_id 只增不减；这条用在停写对账，或拿归档当时的链尾对照。注意：归档摘要里的 tip_row_hash 是被搬走那一段的段尾，不是归档后库里链的尾部（归档还会追加一条 AUDIT_ARCHIVE 行）；归档后要用的是紧接着再校验一次所输出的新 tip=，把它带外保存。

36.2 归档（危险操作，先演练）

把 --before 日期之前的审计行搬出库，导出为 JSONL，并在库里重新锚定。不可逆：被归档的行只剩导出文件。

# 1) 演练：只读，不写任何东西，打印每个行业的计划和口令
node scripts/audit-archive.mjs --data-dir /abs/data --industry cosmetic --before 2025-01-01 --out /abs/archive-dir
# 2) 执行：把演练输出的口令原样传回
node scripts/audit-archive.mjs --data-dir /abs/data --industry cosmetic --before 2025-01-01 --out /abs/archive-dir --confirm ARCHIVE-XXXXXXXXXXXXXXXX

参数：--data-dir、--before <YYYY-MM-DD>（必填）、--out <目录>（必填）、--industry、--confirm <口令>、--actor <名字>（写进审计，缺省 audit-archive-script），以及中断后续做用的开关 --resume（见 36.6）。不给 --industry 时处理所有存在的库，演练会多给一个总口令（或者逐库归档用各自口令）。

  • 口令与计划绑定。 口令只绑定所选行业的归档计划（范围、段尾哈希），无关数据的变化不会使它失效。口令与当前计划不符（抄错，或演练后该段变了）报 CONFIRM_MISMATCH、退出 2，什么都不动；若变化发生在演练的只读计划与执行时拿到写锁之间（加锁后重算才发现），则该库以 PLAN_CHANGED（或计划的链错误码）失败、事务回滚、退出 1。两种情况都重新演练取新口令。
  • --out 必须在数据目录之外（否则 OUT_DIR_INVALID），不覆盖已有文件；产物是 audit-archive-<行业>-<日期>-<首id>-<末id>.jsonl（0600）与同名 .digest.json。
  • 先在低峰执行。 整个归档（验证、导出、读回、删除）在一个写事务里；100 万行约 28 秒（Mac mini，合成数据，非目标主机），期间其他写入等待 busy_timeout（默认 5 秒）。
  • 只搬走 id 前缀，库里永远至少保留最后一行；成功后库里写一条 AUDIT_ARCHIVE 审计（只含计数与摘要）。
  • 以下情况拒绝，什么都不动（退出码 1）：待归档段链校验失败；边界行与段尾不衔接且无锚点；导出文件读回校验失败；归档后剩余链校验失败（整个事务回滚、导出文件被删，可重试）。
  • 导出文件和 .digest.json 必须转存到带外介质——它们是被归档内容的唯一副本，也是以后证明"这一段没被改过"的依据。核对 .digest.json 里的 file_sha256 后再清理本机。anchors 字段是该段内保留清理或隐私抹除留下的合法断口，离线复核要一起用。
  • 归档后立刻按 36.1 校验一次：应为 OK，且锚点计数 ≥ 1。

36.3 保留清理与隐私抹除：链断则拒绝

  • node scripts/retention.mjs --execute 删除白名单模块（master、notify）的过期审计行时，会在每个被删区间之后登记锚点，校验仍为 OK，锚点计数增加。该库的哈希链有断点时，它拒绝登记锚点并拒绝删除（错误码 AUDIT_CHAIN_BROKEN，该库失败、不删任何行、退出码 1）：先按 36.1 查清断点。例外：删除前会先把表尾的 unchained 行接上链再校验，所以仅有表尾 unchained 的库可能被接上后继续清理（这一步本身不写审计，因此要先保留 36.1 的校验输出）；夹在中间的 unchained 和其他断点一律拒绝。锚点计数只在删除留下需要登记的边界时才增加。--dry-run 只读，不受影响。
  • node scripts/privacy-erase.mjs <手机号> --confirm --actor <管理员> 改写含号码的审计行 detail 时，会重算该行哈希并给下一行登记锚点；被改写行与其后一行之间的链已经断了，则以 AUDIT_CHAIN_BROKEN 拒绝并回滚该库（此时不会抹除）。
  • 其他任何直接改或删 audit_logs 的做法（手写 SQL、第三方工具）都会被报成断点。确需清理时，走归档或保留清理，不要手写。

遇到"链断"的处置顺序：保存 36.1 的校验输出作为证据 → 对照备份确认该 id 附近是谁在何时改动（链本身不能还原被改的内容）→ 再决定是否重试清理。备份恢复到旧快照后，链是自洽的旧链（last_id 回退）：保存的 tip 与现在不同只能说明「变了」，要知道回退了多少，需要同时保存当时的 last_id 与行数。

36.4 限制

能写库的人可以整链重算（含伪造锚点），链只有配合带外保存的 tip 与归档摘要才抵抗这一点；哈希不覆盖 user_name、module、ip 三列，这三列被改链上看不出来；整段尾部被删需要保存的 tip 才发现；表尾的裸插入在被接上链之前，校验会把它报成 unchained 断点（BREAK、退出码 1）。归档与校验的耗时数字来自合成数据与开发机，不是目标主机结果。

36.5 备份清单、链尾离机保存与 --against-backup

依据 ADR-0049 的 AC7 补充与 docs/operations/audit-integrity.md 第 6 节。链和锚点都在库里，能写库的人可以改内容后把整条链重算（含伪造锚点）；只有库外的记录能拆穿。

备份清单。 每次 db-backup.mjs 成功备份一个库，会对快照内容跑一遍链校验，把摘要（verified、行数、首末 id、tip_hash、锚点数、anchors_digest）写进备份报告条目的 audit_chain，并在备份文件旁写 <备份>.audit-manifest.json（含锚点明细和备份的 sha256）；设了 GML_BACKUP_KEY 时另写内容相同的 <备份>.audit-manifest.enc（认证加密）。清单写不出来，该库的这次备份就算失败并删除新备份；备份被裁剪时清单一并裁剪。备份时链就已不通过的，清单里记 verified: false（不挡备份，但这份备份之后不能当基线）。

每次备份后要做的事： 把新备份的 *.audit-manifest.json（加密模式连同 .audit-manifest.enc）复制到另一台机器、对象存储或只追加的介质，并把 tip_hash 记进工单或台账。不要只放在同一块盘上：能写库的人通常也能写本机备份目录。

复核（定期，或出事时）：把离机保存的清单取回，对比在用库。可以给备份文件本身，也可以给清单文件；行业取自清单，不必再给 --industry（给了而与清单行业不一致，退出 2）：

node scripts/audit-verify-chain.mjs --data-dir /abs/data --against-backup /path/to/gml_cosmetic_20261024-020000.db.enc          # 加密备份须在环境里提供 GML_BACKUP_KEY
node scripts/audit-verify-chain.mjs --data-dir /abs/data --against-backup /path/to/gml_cosmetic_20261024-020000.db.audit-manifest.json --archive-dir /abs/archive-dir --strict-anchors

（备份文件名以实际产物为准。）这三个新参数遵守 36 章开头的写法：只认空格写法；--archive-dir 与 --strict-anchors 只能和 --against-backup 一起用，否则退出 2。

输出里的判定及含义：

判定含义与处置
ok在用链是备份链尾的后代：同 id 行的 row_hash 相同；同时报出备份之后前进了多少行
manifest-mismatch清单与备份对不上（明文与密文清单不一致、清单与备份内容不一致、锚点明细与 anchors_digest 不符）：清单或备份被动过，先查来源
key-required清单或备份是密文，而环境里没有 GML_BACKUP_KEY（退出 1）；不会只凭明文清单放行
unverifiable无法证明：备份时链就不通过，或缺少归档摘要，或备份链尾已被保留清理删除。退出 1，不当作通过
rewrite/tip-row-differs同 id 的行哈希不同：链被改写并重算。备份之后若做过隐私抹除，要对照操作记录（合法抹除恰好改写备份链尾那一行时，会被报成这个，两者无法区分）
rewrite/behind在用链尾落后于备份：尾部被截断或回滚到更早状态
rewrite/anchors-removed备份里登记过、现在仍在 id 范围内的锚点消失了
anchors-changed只在加了 --strict-anchors 时出现：其他都通过，但备份之后有新增或消失的锚点
  • 备份链尾已被归档搬走时，必须加 --archive-dir（含对应 .digest.json 和 .jsonl）：脚本校验 JSONL 的 SHA-256、逐行哈希和链衔接，再沿 boundary_id 接到在用库的 archive 锚点。
  • 备份之后新增的锚点（保留清理、隐私抹除、归档都会产生，伪造的锚点长得一样）只列出来供对照操作记录；--strict-anchors 让新增或消失的锚点也算失败。
  • 退出码：0 全部通过；1 任一判定非 ok（含清单缺失、unverifiable、key-required）；2 用法错误。
  • 如实边界：同时改库、清单、备份和离机副本的人不在防护范围；清单明文含链尾哈希和锚点，不含审计内容；这套流程没有在真实的离机介质和目标主机上演练过。

36.6 归档被中断后续做：--resume

归档在一个写事务里先导出（fsync）再删除。进程恰好在"导出已落盘、删除未提交"之间被杀（kill -9、断电）时，库原样回滚，导出文件完整，原命令重跑会报 OUT_EXISTS，提示用 --resume。处理（和首次一样先演练取口令，再确认；--before、--out、--industry 必须与上次完全一致，因为导出文件名含日期和 id 区间）：

# 1) 演练：核对导出文件与库里这一段逐字节一致并给出口令，不改任何东西
node scripts/audit-archive.mjs --data-dir /abs/data --industry cosmetic --before 2025-01-01 --out /abs/archive-dir --resume
# 2) 确认：把演练输出的口令原样传回
node scripts/audit-archive.mjs --data-dir /abs/data --industry cosmetic --before 2025-01-01 --out /abs/archive-dir --resume --confirm ARCHIVE-XXXXXXXXXXXXXXXX
  • 续做不重写导出，只做核对、删除、登记锚点、写 AUDIT_ARCHIVE 审计，且在删除前再对导出文件和目录项 fsync。核对项：摘要字段与当前计划一致；JSONL 的 SHA-256 等于摘要；读回链校验通过；JSONL 与库里该段逐字节相同（user_name、module、ip 三列不进哈希，只有这一步能发现它们在崩溃后被改）；段内锚点与摘要一致。
  • 任何一项不符：退出 1，库与文件都不动，错误码 EXPORT_DIGEST_MISMATCH / EXPORT_VERIFY_MISMATCH / EXPORT_DB_MISMATCH。先查清谁动了文件或库，不要删导出文件。
  • RESUME_INCOMPLETE：只有 JSONL 没有摘要（崩在导出途中）。人工确认库未变后删掉残留文件，再按 36.2 做一次新归档。RESUME_NOTHING：--out 里没有对应导出，--resume 不会把它当成新归档。
  • 幂等：已经归档完成时再跑 --resume，输出 already-archived、退出 0，不再删除、不再写审计。
  • 环境变量 GML_TEST_ARCHIVE_PAUSE_AFTER_EXPORT=1 是测试专用的故障注入，只在 GML_RUNTIME_MODE=test 下可用，在其他模式设置会让脚本以退出码 2 拒绝；运维环境里不要设置它。

三十七 旧结构快照演练：先造"版本 N 的备份集"再演练升级

依据 ADR-0048（docs/implementation/ADR-0048-schema-snapshot-rehearsal.md）。第三十二章的升级演练在手头只有最新结构备份时，只能删掉版本表里编号大于 N 的行再重放：建表、加列、写字典行类的迁移因为结构早就存在而空转（报告里 structure_preexisting=true），耗时偏低。本章的 schema-snapshot.mjs 用今天的仓库重建"迁移 ≤ N 时的库"并产出备份集，让演练能真的重放 N 之后的迁移。

37.1 命令

OUT=/srv/drills/snap-$(date +%Y%m%d-%H%M)          # 必须是不存在或为空的绝对路径
node scripts/schema-snapshot.mjs --upto=<N> --out=$OUT [--synth=tiny|small|medium]
node scripts/upgrade-rehearsal.mjs --from=<N> --backup-dir=$OUT/data/backups --target-dir=/srv/drills/rehearsal-$(date +%Y%m%d-%H%M)
  • 两种写法 --upto=58 与 --upto 58 都认；未知参数、位置参数、重复参数、缺值一律拒绝（其中未知参数的报错会列出可用参数 --upto、--out、--synth）。该脚本没有 --help。
  • --upto 必须恰是一个现有迁移编号（编号有空号，如 044、051、054、064），这样快照版本表的最高编号就等于 N。--out 必须是显式绝对路径。
  • 第二条命令里的 --from 取同一个 N。库的版本表最高编号恰等于 N 时，演练不截断：不删登记行，也不删后续迁移的索引（结构本来就是旧的），报告每库多一个 baseline_registry: { max, truncation: 'skipped' }。最新结构的库仍走 truncation: 'applied' 的原路径。
  • --synth 可选：tiny（synth-data 缺省，测试用）、small（约 2000 商品 / 3000 单据 / 15000 流水）、medium（约 20000 / 30000 / 150000，与夜间容量工作流同口径）。不给则只有结构与指纹，没有业务数据。合成数据只进美妆（cosmetic）库；餐饮、服装库只带结构与指纹。
  • 退出码：0 完成；1 运行失败（只清理本次自己创建的文件）；2 参数或目录被拒绝（先于创建任何文件判定）。

37.2 安全判据

--out 不得位于仓库 data/ 内（含符号链接别名）、不得等于或位于调用方的 GML_DATA_DIR、不得是符号链接、必须不存在或为空目录——这些检查挡住的是仓库 data/ 与你当前环境里的数据目录，但脚本无法发现机器上别处的在用实例：请只给一个专门建来演练的新目录，不要指向任何实例目录内部。子进程环境是白名单，不继承 GML_*，也不带 GML_BACKUP_KEY：快照备份集是明文的（内容只有合成数据与空结构），不要把它当作真实备份的替身去走加密备份流程。产物只留 $OUT/data/backups（备份集）与 $OUT/snapshot-manifest.json（0600）。演练完归档报告后删除 $OUT。

37.3 怎么读结果

读报告的方法同 32.3。额外要点：快照路径下，迁移 N 之后的各步骤应出现 structure_preexisting=false——这才是真实的升级成本。但该字段是各迁移自己的预检结果：没有自检的迁移为 null，某些迁移在干净快照上预检本来就为 true（例如 069，库里没有要清的演示密钥时），所以不是每一步都会是 false，以报告为准；PRE_UPGRADE_CHECKSUM_MISMATCH 等校验和判据照常在截断之前执行，篡改过登记校验和的备份集仍被拒绝。

37.4 如实边界

  • 旧结构 = 今天的 schema.sql + 迁移 ≤ N，不是历史上 N 版本当时的 schema.sql；业务数据由今天的代码写入后拷入，只含新旧两边都有的列。它回答"在这个体量上 N 之后的迁移要多久"，不回答"旧版本程序写出的历史数据长什么样"。
  • 编号早于 038 的版本没有 setting_audit_log，设置项缺省值由读取方兜底。
  • 耗时是运行它的这台机器当时负载下的单次墙钟，不是 dmserver 或目标主机结果，不是容量承诺，不是验收证据。夜间工作流的手动输入 snapshot_upto 尚未在 GitHub 上实际运行过。
  • 想看真实旧库，最可靠的仍是旧版本代码产生的真实备份集，按第三十二章演练。

三十八 审计关键词检索：FTS 行为、维护脚本与 GML_AUDIT_FTS=0

依据 ADR-0030、迁移 067、docs/operations/audit-search.md（完整说明在那里）与 docs/implementation/capacity-baseline.md 的 AB3 / AC5 两节。这一章解释第 27.2 的 keyword 在大表上的表现、索引的维护脚本，以及出问题时的止血开关。

38.1 行为（用户可见的部分）

  • 迁移 067 建立 FTS5 外部内容表 audit_logs_fts（索引 action、entity、user_name 三列，trigram 分词，子串语义与 LIKE '%x%' 一致，含中文）。不索引明细，所以关键词仍然不搜索明细（27.2）。
  • 同时满足下面三条才走 FTS：库里有该表；关键词至少 3 个字符（2 个字符的关键词走原来的 LIKE）；探测到命中稀少（不超过 2000 条）。否则走 LIKE。命中很多时 FTS 反而更慢，所以这是有意的回退。审计日志页的输入框提示"关键字（≥3 字走全文检索）"，页面提示的阈值与服务端一致，满足不了时服务端自动回退，结果相同。
  • 两条路径返回的行完全相同，差别只在读量；用户看不到使用了哪条。FTS 只缩小候选集，候选行还会再过一遍同一个 LIKE 条件（trigram 对 Unicode 大小写不敏感，LIKE 只折叠 ASCII，以后者为准）。关键词里的 AND、OR、*、引号等都当作普通字符，不是检索语法。
  • 数据库构建不带 FTS5（或不支持 trigram）时，迁移 067 是空操作，表不存在，系统自动全部走 LIKE，功能正确，大表上关键词查询会慢一些。可用 node scripts/migrate.mjs --status（环境变量同安装手册 5.5）确认 067 已应用。

38.2 强制走 LIKE：环境变量 GML_AUDIT_FTS=0

  • 进程环境里 GML_AUDIT_FTS 恰为字符串 0 时，审计检索一律走 LIKE；其他取值（未设置、空串、1、false）都不关闭 FTS。服务每次查询时读取这个变量，但已运行的服务进程拿不到你事后改的环境，所以要重启服务才生效。设置方式同其他可选变量（安装手册 5.4 / 6.3），例如 GML_AUDIT_FTS=0 node scripts/local-manage.mjs start。
  • 只影响查询路径：迁移 067 照常建表与触发器，写入照常维护索引，下面的维护脚本照常可用。用途：怀疑 FTS 索引有问题（关键词检索漏行）时的止血开关——先切到 LIKE（结果以表为准，不受影响），再按 38.3 检查和重建索引，确认正常后去掉变量并重启。
  • 代价：LIKE 路径在命中稀少的关键词上要读全表（100 万行约百毫秒级，见 capacity-baseline "AB3"）。

38.3 维护脚本：audit-fts-maintain.mjs

索引是影子索引：触发器被删、裸 SQL 绕过触发器写入、崩溃或升级后，都可能让它与 audit_logs 不一致，表现是走 FTS 的关键词（≥3 字符且命中稀少）漏行；LIKE 路径不受影响。脚本有三个动作，必须且只能选一个：

node scripts/audit-fts-maintain.mjs --data-dir /abs/data --industry cosmetic --integrity-check
node scripts/audit-fts-maintain.mjs --data-dir /abs/data --industry cosmetic --optimize
node scripts/audit-fts-maintain.mjs --data-dir /abs/data --industry cosmetic --rebuild

参数：--data-dir <绝对路径>（必填）、--industry <行业>（必填，一次一个库）、动作开关三选一、--out <绝对路径>（报告位置）、--busy-ms <0..300000>（等写锁的上限，缺省 5000）。解析规则同 36 章（只认空格写法；未知参数退出 2 并列出可用参数）；该脚本没有 --help，缺参数时打印一行用法。

动作做什么写锁何时用
--integrity-checkFTS5 自检并与 audit_logs 对账一次短写事务，大库上与索引大小成正比每周 / 升级后 / 怀疑漏行时
--optimize合并索引段，不改内容与累积的未合并段成正比大批量写入或归档之后
--rebuild从 audit_logs 重建整个索引整个重建期间（单次写事务）--integrity-check 报 corrupt 之后；触发器被重建之后
  • 退出码：0 成功；1 失败（corrupt、busy、error，或表不存在时的 --optimize / --rebuild）；2 参数或环境错误（含仓库 data/ 被拒、--out 不合规）。表不存在时 --integrity-check 退出 0，报告 status: "absent"（无 FTS5 的构建上本来就没有）。拿不到写锁（等满 --busy-ms）时 status: "busy"、退出 1，索引不被改动。
  • 脚本不创建库、不跑迁移、不建 FTS 表；环境里的 GML_DB 被忽略；行业库文件本身是符号链接则拒绝；也不读取 GML_AUDIT_FTS（维护索引与是否使用索引是两件事）。
  • 报告默认写到 <data-dir>/audit-fts-maintain-<行业>-<动作>-<时间戳>.json（0600）；--out 必须是绝对路径、不能在仓库 data/ 下（含经符号链接）、不能是库文件或其 -wal / -shm / -journal、不覆盖已有文件。字段包括 status、rows、elapsed_ms（持写锁时间的粗上界）、lock_probe（另一条线程量出的写入者被挡时长）、triggers_present、bytes_before / bytes_after；报告不含绝对路径。

重建的建议步骤：

  1. 先 --integrity-check；只有报 corrupt 或触发器曾缺失才需要 --rebuild。
  2. --rebuild 期间其他写入（包括每一条审计写入）要等 busy_timeout（缺省 5 秒）：100 万行约数秒（Mac mini 合成数据数字，目标主机请自行实测）；超过 5 秒的重建会让同时到达的写入收到 SQLITE_BUSY。读不受影响（WAL）。请在低峰执行；条件允许时先在备份副本上演练。
  3. 重建后再 --integrity-check 应为 ok，然后（如果之前用了 GML_AUDIT_FTS=0）去掉变量并重启。

夜间容量工作流 nightly-capacity.yml 手动触发时可填输入 audit_fts=integrity-check（缺省空 = 不跑，定时触发永不跑），在合成库的副本上跑一次 --integrity-check，失败只告警，不改变夜间门禁；该工作流尚未在 GitHub 上跑过（见 29.4）。CI 的 checks 作业另有一步 GML_AUDIT_FTS=0 下重跑 tests/audit-logs-view.test.mjs，在带 FTS5 的构建上真实演练回退路径。

38.4 想量化时

开发或交付人员可以在隔离临时目录里跑基准（该脚本没有 --help，按 --名称 值 成对书写，不支持 --名称=值，未知参数或缺值报错）：

node scripts/bench-audit-logs.mjs --rows 1000000 --out /abs/result.json

可用参数：--rows、--export、--repeat、--writes、--out（缺省 100 万行、导出 50000、重复 3 次、写入 20000）。它在系统临时目录建合成库，不碰任何实例数据。数字是开发机、合成数据、有并行负载下的量级参考，不是目标主机结果。

三十九 奇门平台密钥：命令行签发与 app_key 掩码

依据 ADR-0033 的 AB8 补充（迁移 069）。奇门网关在生产模式仍受能力闸门限制（503），重新开放需要产品负责人单独授权；本章的操作适用于演示、测试环境联调，以及生产开放前的验收准备。

39.1 谁、何时需要

平台（platforms）要有 app_key，并且被签发过密钥，网关才会验签通过。没有密钥的平台返回 401，协议码 1005。取得密钥有两条途径，判据同一处：管理接口 POST /api/qimen/platforms/:id/secret，或命令行 scripts/qimen-issue-key.mjs。系统不再带任何公开常量密钥；迁移 069 会清掉旧库里残留的演示常量。

39.2 命令

GML_RUNTIME_MODE=production GML_DATA_DIR=/abs/instance/data GML_SECRET_KEY=<与服务一致> \
  node scripts/qimen-issue-key.mjs --industry cosmetic --platform <平台 id 或编码>
# 轮换（旧密钥立即失效）
... node scripts/qimen-issue-key.mjs --industry cosmetic --platform <平台 id 或编码> --rotate
node scripts/qimen-issue-key.mjs --help     # 本脚本有 --help，打印用法后即退出，不读取数据目录
  • 参数：--industry cosmetic|food|apparel、--platform <数字 id 或平台编码>（纯数字按 id，否则按 code 取 id 最小的一个）、--rotate、--help。写法 --industry=cosmetic 与 --industry cosmetic 都行；未知参数报错。
  • 环境：绝对路径的 GML_DATA_DIR 必填；GML_RUNTIME_MODE 不设时按 production，显式写错的值会被拒绝（同安装手册第五章）。封存密钥必须与运行服务时一致：GML_SECRET_KEY，不设则由 JWT 签名密钥派生（依次取 GML_JWT_SECRET、旧名 JWT_SECRET）；两者不一致时库里能写入，但网关读不出这把密钥。用 local-manage.mjs 安装的实例没有显式 GML_SECRET_KEY 时，服务用的是 $INSTANCE/.local/config.json 里的签名密钥；命令行签发时要用同一个值（或在服务端也显式设置 GML_SECRET_KEY，两边用同一个），否则请改用管理接口签发。
  • 输出：成功时标准输出一行 JSON：{"success":true,"platform_id":…,"app_key":…,"rotated":…,"secret":"qsk_…"}。明文密钥只在这里出现一次，库里只有封存值，日志和仓库里都没有。直接重定向进受限文件，再经安全渠道交给对接方，不要贴聊天或邮件：

```bash

(umask 077; GML_RUNTIME_MODE=… GML_DATA_DIR=… node scripts/qimen-issue-key.mjs --industry cosmetic --platform 3 > /secure/qimen-3.json)

```

  • 失败时标准错误一行 JSON {"success":false,"code":…,"message":…}，退出码 1。常见：QIMEN_SECRET_EXISTS（平台已有密钥而没带 --rotate，旧密钥保持不变）、QIMEN_APP_KEY_MISSING（先在平台档案页填 app_key）、PLATFORM_NOT_FOUND、QIMEN_CLI_INPUT（缺 --industry 或 --platform）、DATA_DIRECTORY_* / RUNTIME_MODE_* / INDUSTRY_*（环境或行业参数不对）。
  • 每次签发或轮换与凭据变更同一事务写严格审计 QIMEN_SECRET_ISSUE / QIMEN_SECRET_ROTATE，操作人记为 cli:qimen-issue-key，明细只记 app_key。轮换没有宽限期：执行后旧密钥签出的请求立即 401，必须与对接方约好切换时间。

39.3 掩码：/capabilities 里的 app_key 只有前 4 位

GET /api/qimen/capabilities 返回的 platforms[] 里，app_key 只给前 4 位，并带 app_key_masked: true；同时有 has_secret、secret_rotated_at。这够对号入座，不够冒充。完整的 app_key 在平台档案页（/oms/platforms）里按权限查看。调试页据此提示"这里显示的是掩码"。需要把完整 app_key 给对接方时，去档案页复制，不要从 /capabilities 的返回里找。接口不会返回密钥本身，平台列表里也没有封存值，只有 has_secret 与密钥末尾 4 位的掩码形态。

39.4 如实边界

没有按平台的网关限速（依赖入口反向代理），没有 IP 白名单，没有"只吊销不重发"的动作（停用平台即让网关 401）。生产重新开放前的 8 项验收清单在 ADR-0033 里，本章只覆盖密钥这一项。

四十 指标抓取节流与令牌轮换

依据 ADR-0045 的 AB10 补充与 docs/operations/monitoring.md。接第三十一章；安装手册 6.3 列出对应环境变量。

40.1 抓取节流

/api/meta/metrics 按来源 IP 限速，桶独立于登录节流（抓取不挤占登录额度）。计数发生在鉴权之前：令牌错误、没带凭据、JSON 形态、管理员登录态的请求都计数，猜令牌同样受限。

变量缺省范围
GML_METRICS_IP_LIMIT120（每个窗口内每 IP 次数）1..100000
GML_METRICS_IP_WINDOW_MS60000（毫秒）1000..86400000

超出范围或不是纯数字的值回落到缺省，服务照常启动（指标端点不该因笔误起不来）。策略在进程启动时读定，改值要重启。超限返回 429，业务码 METRICS_RATE_LIMITED，带 Retry-After 头（秒）。计数在进程内存里，重启清零，多副本各自计数。

来源 IP 取自 GML_TRUST_PROXY 约束下的连接来源（安装手册 6.1），不直接读 X-Forwarded-For。排障要点：反向代理在同机且 GML_TRUST_PROXY=off 时，所有请求的来源都是代理的回环地址，会共用一个桶，抓取与其他访问者互相挤占；这时设置正确的受信代理配置，而不是一味调大 GML_METRICS_IP_LIMIT。缺省值远高于 15 至 30 秒一次的抓取频率，只用来挡暴力猜令牌和写错的死循环。抓取突然间歇性 429：先查有没有第二个抓取端或脚本在轮询，再看窗口设置。

管理员在页面上看到的提示。 页面 /system/metrics（仅管理员）底部的「运维计数器」卡片读的就是这个端点，同样按来源 IP 计数。被节流时卡片显示"指标刷新过于频繁，已被节流（按来源地址限速，并非系统故障）。请等待几秒后再点「刷新」；上方已显示的数值是上一次成功取到的结果。"——这是 429 + METRICS_RATE_LIMITED 的正常表现，不是故障，也不表示没有数据；等几秒再点"刷新"。页面只按状态码和业务码判断，不解析文字。非管理员看到的是"只有管理员可以查看运维计数器"（403）。

40.2 令牌轮换（不中断抓取）

令牌 GML_METRICS_TOKEN（当前）与 GML_METRICS_TOKEN_NEXT（下一把）可以同时有效，各自须至少 32 字符，过短者被忽略。两把都做比较，不因命中其中一把而提前返回。步骤：

  1. 生成新令牌（openssl rand -hex 32），保存进密码管理器。
  2. 把新令牌设为 GML_METRICS_TOKEN_NEXT，保留旧的 GML_METRICS_TOKEN，重启服务。此时新旧令牌都能抓取。
  3. 把 Prometheus 侧的令牌文件（credentials_file）换成新令牌，确认抓取正常（up{job="os-erp"} 为 1，第三十一章的自测命令返回内容）。
  4. 把 GML_METRICS_TOKEN 改成新值，删除 GML_METRICS_TOKEN_NEXT，再重启一次。旧令牌从此失效。

怀疑令牌泄露时，不要走缓慢的两阶段：直接把 GML_METRICS_TOKEN 换新值、不设 NEXT 并重启，Prometheus 侧随后更新，中间会有一段抓取失败（401）。令牌泄露只暴露只读的运维数字（备份年龄、磁盘余量、事件计数），不能读写业务数据。

local-manage.mjs start 会固定 NODE_ENV、HOST、PORT、数据目录与签名密钥相关的变量（并清空旧名 JWT_SECRET、GML_DB），环境里的其余变量（包括上面几个指标变量）原样传给服务（安装手册 5.4）。单独设了 GML_METRICS_TOKEN_NEXT 而 GML_METRICS_TOKEN 未设或过短，也能用 NEXT 抓取（两把独立判断）；轮换结束后清理干净，避免长期留着第二把令牌。

40.3 如实边界

节流、轮换在真实服务进程上的测试在 tests/metrics-export.test.mjs（429 形状、Retry-After、错误令牌也计数、两把令牌均可抓取）。没有在真实 Prometheus 实例和反向代理后做过端到端验证；Docker 部署时变量写进同目录 .env，该路径未实际验证。

四十一 总部角色名单与单据流严格门店绑定开关

依据 ADR-0051（docs/implementation/ADR-0051-hq-roles-docflow-binding.md）。面向管理员与实施顾问，回答两个问题："哪些角色算总部角色？"和"为什么某个账号在单据流里看不到日结、门店要货、门店发货？"

41.1 总部角色名单（单一来源）

"总部角色"是不受门店绑定约束的角色。名单只有一份来源（server/lib/hq-roles.js），在三个用途上各自声明是否放行：

角色单据流（docflow）豁免严格绑定POS 总部接口（日结确认、跨店结算）门店要货 / 发货总部接口
admin（系统管理员）是是是
finance（财务）是是是
sales（销售主管）是是是
warehouse（仓储主管）是是是
purchase（采购主管）是否是
scm（供应链主管）是否是

要点：

  • 采购主管和供应链主管不参与门店现金，所以不在 POS 总部接口名单里；它们只是为了继续读到门店要货（YQ）的流转留痕而并入单据流豁免。这是有意的：把身份并集直接用在 POS 上会让这两个角色静默获得日结确认和全店现金接口。
  • 不在名单里的：boss（老板 / 总经理）、viewer（只读访客）以及任何自定义角色。dealer、store 是外部主体，本来就被内部接口先挡住。
  • 关于 boss 的说明（需要知道）： 老板账号不在名单里，是旧名单本来如此，不是新近的疏漏。默认开关（41.2）打开时，一个没有绑定门店、数据范围为"全部"的 boss 账号，在单据流的 /api/docflow/{events,overview,history,trace} 里看不到日结（RC）、门店要货（YQ）、门店发货（SH）三类单据和它们的流转留痕。"是否把 boss 作为总部角色并入"是产品决定，目前没有做出，也没有配置项可以改：并入需要改代码（在名单表里加一行并声明各用途是否放行）。在此之前不要手工改库或改角色名绕过；需要老板看到这三类时，只能走 41.2 的临时关闭，并明白它的代价。
  • 已绑定门店的总部角色账号仍只看本店（与门店路由一致）。admin 与超级管理员（is_super）不受此约束。

41.2 开关 docflow_strict_store_binding

入口：/system/settings，分组"运维"，设置项"单据流严格门店绑定"（键 docflow_strict_store_binding）。它是危险配置：修改必须写理由，并进入配置变更审计。

取值行为
开（缺省，值 1）对"未绑定门店、非总部角色、数据范围为全部"的内部账号，/api/docflow/{events,overview,history,trace} 不再返回 RC / YQ / SH 的单据与留痕（整类不可见）；POST /api/docflow/transition 对这三类，范围外的单据与不存在的单据同样返回 404"记录不存在"。总部角色、admin、超级管理员不受影响；已绑门店的账号只看本店
关（值 0）恢复本项出现之前的行为：docflow 只看数据范围，上述账号仍能读这三类
  • 关闭就是放宽读权限。 只在确认确有"非总部角色需要跨店只读"（例如上面说的 boss）时临时使用，写清理由，尽快用产品决定取代它。
  • 开关只管 HTTP 的 /api/docflow/*。MCP 一侧恒定严格且不带总部豁免（比 HTTP 更严），不受这个开关影响。
  • 取值口径：0、false、no、off、空串都算"明确关闭"，库里值缺失或写成非法值回落为缺省"开"（失败关闭）。通过设置页修改即可，不要手改库。

41.3 排障："为什么某账号在单据流里看不到日结 / 要货 / 发货"

  1. 先看该账号的角色和门店绑定：让账号本人打开「我的数据范围」（第二十六章），确认角色名、数据范围和绑定的门店。
  2. 角色是 boss、viewer 或自定义角色，且未绑门店、范围为全部：这是预期行为（41.1）。要么接受，要么按 41.2 评估是否临时关闭开关。
  3. 角色在名单里但仍看不到：看是否绑了某个门店（那就只看本店），再看目标单据是否属于别的门店。
  4. 刚改过开关或角色，请账号本人重新登录后再看。
  5. 仍不能解释：保存"我的数据范围"页面内容和单据号，交给开发，不要直接放宽开关。

41.4 如实边界

这是读范围的收紧，不是整体权限模型的验收。boss 是否应属于总部角色尚无产品结论；开关缺省打开后的客户侧影响面（有哪些现有账号会因此看不到这三类）没有在真实客户数据上评估过。

四十二 依赖安全门禁：check-audit-allowlist 与到期白名单

依据 docs/本地交付/06_依赖安全说明.md 与 docs/security/audit-allowlist.json。面向负责发版和依赖维护的人员。这是 CI 里的一道门禁：运行依赖里的高危公告必须在带到期日的白名单里，否则构建失败。白名单是限期豁免，不是"已修复"。

42.1 它检查什么

node scripts/check-audit-allowlist.mjs 运行 npm audit --omit=dev --audit-level=high --json --registry=https://registry.npmjs.org（显式指定官方源，因为仓库 .npmrc 指向的镜像不实现审计接口，所以需要联网），逐条看 high / critical 公告：

  • 每条必须在 docs/security/audit-allowlist.json 里有对应条目，否则退出码 1，FAIL: <GHSA 编号> (<包名>, <级别>) is not in the allowlist。
  • 审计接口报错、输出结构不对、白名单格式不合法、条目过期、重复条目，一律失败（失败即关闭），不会因为"查不到"而放行。
  • 只看运行依赖（--omit=dev），也只拦 high 和 critical；开发依赖和中低级别不在这道门禁里（相关说明见 06_依赖安全说明）。
  • 白名单里有、但审计里已不再出现的条目，只提示 note: allowlist entry … no longer appears in the audit; remove it，不失败，提醒删除。
  • 成功时最后一行是 audit-allowlist: OK (N allowlisted high/critical finding(s), none unlisted)，退出码 0；覆盖到的条目会逐条打印 allowlisted: <编号> (until <到期日>)。

参数（该脚本没有 --help，也不拒绝未知参数：它只按名字查找下面两个，其余一律忽略，所以拼错参数名会悄悄回落到缺省行为）：

参数含义
--allowlist <文件>使用另一份白名单，缺省 docs/security/audit-allowlist.json
--audit-json <文件>读取已有的 npm audit --json 输出，不联网（测试或离线复核用）

只认空格写法；--allowlist=… 不被识别，会静默用缺省白名单。参数后面缺值也会回落缺省（不给 --audit-json 值就会去联网审计）。

42.2 白名单条目的规则

文件是一个对象，allow 数组里每条：

字段规则
advisoryGHSA 编号，格式如 GHSA-xxxx-xxxx-xxxx（必填）
package可选；写了就必须与审计报出的包名一致，否则失败
reason至少 20 个字符；写清楚为什么现在不修、为什么当前不可达或风险可接受
expires真实存在的 YYYY-MM-DD 日期，必须晚于今天（UTC），且距今不超过 180 天；到期当天即失败

同一个公告不能重复登记。

42.3 处置流程

  1. CI 报 FAIL 时：在本机联网运行 node scripts/check-audit-allowlist.mjs，读 FAIL: 行，弄清是新公告、条目过期还是格式错误。
  2. 先修：能升级到修复版本、或能移除这个依赖，就去做，然后重新生成 package-lock.json 并跑回归。这是首选。
  3. 只有确实无法立即修复时才登记：先评估可达性（该包是否在运行路径上被引用；可以用 npm ls <包名> 看依赖链，用代码搜索看是否真的被导入），把结论写进 reason；expires 取尽量短、至多 180 天；由所有者批准后提交。不要在 GitHub 的依赖告警里把它标成"误报"或"已解决"（06_依赖安全说明 的口径）。
  4. 到期前：重新评估。能修就修并删除条目；仍不能修，要有新的评估内容再续期，不要机械地把日期往后改。
  5. 公告消失后：按 note: 提示删除对应条目。
  6. 离线复核（例如在没有 CI 的环境）：在联网机器上把审计输出保存成文件，再交给脚本：
npm audit --omit=dev --json --registry=https://registry.npmjs.org > /abs/audit.json
node scripts/check-audit-allowlist.mjs --audit-json /abs/audit.json

（npm audit 在发现漏洞时自身退出码非 0，但输出仍写入文件；对结果的判定看第二条命令。）

42.4 当前状态与边界

截至本手册修订，白名单只有一条：GHSA-mrhx-c7xc-m3w5（zod，高危，内存耗尽类），登记理由是 zod 写在 package.json 里但服务、脚本、前端都没有导入它，公告所述路径不可达；到期日 2026-12-15。到期前必须处理（移除依赖或重新评估），否则门禁会让 CI 变红。

如实边界：这一步在 CI 里的实际运行（需要联网访问官方 npm 源）还没有在托管 runner 上跑过；脚本对 npm audit 输出结构做了严格检查，npm 将来改输出格式时，它会"失败即关闭"而不是放行。门禁通过不代表业务代码、浏览器包和部署环境绝对安全。

四十三 经营看板的"数据截至"与刷新

依据 ADR-0044（含 AC4 补充）。入口 /（第三章）。面向管理员和总部使用者，回答"我看到的数字是什么时候算的、点刷新为什么没变"。

43.1 页面上看到什么

看板右上角有一行小字"数据截至 hh:mm:ss（缓存 30 s）"和一个"刷新"按钮：

  • 时间是服务端告诉页面的"这份数据是什么时候算的"（响应顶层的 cached_at），不是浏览器当前时间。看板的汇总、趋势、排行、待办四个接口各有一个时间，页面取最早的一个，所以"数据截至"从不比页面上任何一块数据更新。
  • 括号里是缓存有效期（cache_ttl_ms）。缓存被关闭（GML_DASHBOARD_CACHE_MS=0，安装手册 6.3）时显示"未缓存"，每次请求都现算。
  • 四个接口里只要有一个没带时间，这一行就不显示（宁可不写也不写错）。

43.2 点"刷新"会发生什么

"刷新"重新请求看板的全部接口（汇总、趋势、渠道、排行、待办、最近订单），按钮在请求期间显示"刷新中…"。但服务端缓存仍然有效时会返回同一份结果，所以时间可能不变，这是预期，正是这行字存在的原因。缓存命中必须同时满足：

  1. 没过有效期（缺省 30 秒）；
  2. 这个行业库的连接自上次计算以来没有任何写入；
  3. 没有其他连接或进程向同一个库提交过写入；
  4. 本地日期没变（"今日 / 本月"跨零点会重算）。

所以：库一有写入（包括审计和登录时间戳）缓存就失效，下一次刷新就会拿到新数据；库很安静时，最多等一个有效期也会过期。写入频繁的实例命中率本来就低，这不是故障。调试数字对不上时可以暂时把 GML_DASHBOARD_CACHE_MS 设为 0 并重启服务来排除缓存，排查完恢复。

43.3 刷新失败时

任何一个接口取数失败，页面会保留上一次成功取到的数据和时间，并显示"刷新失败，下方显示的是上一次成功取到的数据"，同时保留"刷新"按钮供重试（登录失效或无权限，即 401 / 403，属于重试解决不了的情况，页面不会为此单独画出重试入口）。那一行时间此时仍是诚实的：它就是这些数据的真实时间。

43.4 排查时可看的东西

  • 响应头 X-Dashboard-Cache: hit 或 miss（用浏览器开发者工具的网络面板看），命中与否不在响应体里。
  • 看板接口要求账号数据范围为"全部"，受限范围账号得到 403，并且不会预热缓存。
  • 指标 os_erp_dashboard_cache_total{result="hit|miss"}（第三十一章）统计汇总、趋势、排行、待办、库存分布和渠道的缓存命中；看板底部的最近订单（/dashboard/recent）不缓存也不计数。命中率长期很低会触发告警 OsErpDashboardCacheIneffective（31.5），那是提示"缓存在白跑"，不是服务故障。

43.5 如实边界

缓存和时间戳的效果（命中率、对大库的响应时间）在目标主机上没有实测，容量基线里的数字来自开发机与合成数据。
