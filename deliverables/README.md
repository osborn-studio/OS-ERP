
## 与源码的对应关系（**别改这里，改源头**）

| 交付物 | 源头 | 重新生成 |
|---|---|---|
| `01_演示程序/*.zip` | 仓库根（`server/` `public/` `dist/` `data/`） | `npm run release` |
| `02_演示手册/*.md` | `docs/演示手册_伴圆AI原生ERP_20261017.md` | 直接编辑源头，再复制过来 |
| `03_操作手册/*.md` | `docs/操作手册_伴圆AI原生ERP_20261017.md` | 同上 |
| `04_网页版手册/*.html` | `public/docs/{demo-flow,manual}.html` | `npm run docs:build` |
| `05_开发手册/*.md` | `docs/开发说明手册_伴圆AI原生ERP_20261017.md` | 直接编辑源头 |
| `05_开发手册/dev.html` | `public/docs/dev.html` | `npm run docs:build` |
| `02/03` 的 `.docx` | 由对应 `.md` 转换 | 见下 |

**Word 的生成方式**：把 MD 清理后（去代码围栏、去分隔线、块引用去 `>`）用本地 Office 通道
`create_doc → doc_insert_markdown → save_file` 转换。转换脚本在会话里临时执行，未入库。

## 为什么这里有两份 zip

- `01_演示程序/伴圆ERP-演示版-20261017.zip`：**真正的发行包**（源码 + 已构建前端 + 已灌数据的库 + 启动脚本）；
- `伴圆ai原生erp整体打包.zip`：把**整个交付目录**（含手册）再压一层，用于一次性发送 ——
  结构上它已经包含了前者，属于"方便"而不是"必要"。

## 入库策略（如实说明）

- **入库**：上述全部文件（约 12MB），保证 GitHub 上有一份完整备份，换机器能直接拿；
- **未入库**：`.DS_Store`（macOS 垃圾文件）、`归档/`（用户本机做的同内容副本，纯重复）；
- ⚠️ **二进制会累积历史**：每重新打一次包就多约 6MB 的 git 历史。少量发版没问题；
  若今后频繁发版，建议改用 **GitHub Releases** 挂附件，仓库里只留 `00_先看这里.md` 与手册。

## 发版时的更新顺序

```bash
npm run reseed          # 1. 还原干净的演示数据
npm run docs:build      # 2. 文档有改动时重编译网页版
npm run release         # 3. 打包 → release/伴圆ERP-演示版-YYYYMMDD-xxxxxx.zip
# 4. 解压包内目录名去掉时间后缀，替换 01_演示程序/ 下的 zip
# 5. 同步 02/03/04 的手册与网页版
```
