# 伴圆AI原生ERP系统 · 开发说明手册

> 面向：接手这套代码的程序员 / 实施顾问里的技术角色 / 做二次开发的合作方
> 目标：**看完能跑起来、能找到代码、能安全地改**。
> 版本：2026-10-17 ｜ 对应代码 `c16eb46`

## 一、30 秒认识这套系统

| 项目 | 内容 |
|---|---|
| 形态 | 浏览器访问的 Web 系统（B/S），单机一条命令跑起来 |
| 后端 | Node.js 18+ ｜ Express 4 ｜ better-sqlite3 11（同步 API） |
| 前端 | React 18 ｜ Vite 5 ｜ TypeScript ｜ Tailwind 3 ｜ Recharts |
| 数据库 | **SQLite × 3**（美妆 / 连锁餐饮 / 服装），同一套表结构，各存一个 `.db` 文件 |
| 规模 | 后端 119 个 js / 约 6.8 万行；前端 88 个 tsx / 约 3.9 万行 |
| 库规模 | 每库 **194 张表 / 10 个视图 / 372 个索引**；迁移 49 个文件 |
| 单据内核 | **40 种单据 / 190 个状态 / 215 条流转边**（其中 92 条高危） |
| 权限 | **137 个权限点 / 10 个角色** + 数据范围（组织 / 门店 / 经销商） |
| 配置 | 21 个业务配置项（唯一登记表 `SETTING_RULES`） |
| 对外 | REST（`/api/*`，契约 508 条路径） + MCP（`/mcp`，40 个工具） |

**一句话架构**：三条路由入口（REST / MCP / 前端），共用同一套 `lib/*` 领域服务与同一套判据。

## 二、跑起来（10 分钟）

### 2.1 安装与启动

```bash
git clone <repo> && cd gml
npm install              # 开发需要 devDependencies
npm run dev              # 前端 Vite + 后端 Express 一起起（推荐）
# 或分开：
npm run dev:api          # 只起后端 :3001
npm run dev:web          # 只起前端 :5173（代理 /api 到 3001）
```

生产/演示形态：

```bash
npm run build            # 产出 dist/
npm start                # 单进程，Express 同时托管 API 与 dist
# 打开 http://localhost:3001/login
```

### 2.2 数据从哪来

首次启动时 `bootIndustry()` 会自动建表 + 灌演示数据（约 2 秒/库）。想手动重建：

```bash
npm run reseed           # 三库全部重建（约 10 秒）
npm run seed -- cosmetic # 只重建美妆
```

### 2.3 改代码后要做什么

| 改了什么 | 要做什么 |
|---|---|
| 前端 `.tsx` | Vite 热更新，无需重启 |
| 后端 `.js` | **必须重启**（本机由 launchd `com.gml.server` 托管：`launchctl kickstart -k gui/$(id -u)/com.gml.server`） |
| 数据库结构 | 新增迁移文件 → 重启自动执行 |
| 接口签名 | `npm run gen:api` 重生成前端类型 → 再跑 `npm run check:api` |
| 业务配置项 | 改 `lib/settings.js` 的 `SETTING_RULES` → 重启（会补齐缺失键） |

### 2.4 环境变量

| 变量 | 作用 | 备注 |
|---|---|---|
| `PORT` | 服务端口，默认 3001 | |
| `GML_DATA_DIR` | 数据库目录 | **测试脚本必须设**，否则会写仓库 `data/` |
| `GML_SEED_NOW` | 冻结灌数时刻 | 用于"逐字节可复现"的重建比对 |
| `JWT_SECRET` | 令牌签名密钥 | 演示有默认值，**生产必须换** |

### 2.5 三个最常见的坑

1. **同步 API**：better-sqlite3 是同步的，别在事务里 `await`（事务外的异步会让事务边界失效）。
2. **`cp` 不是备份**：WAL 模式下 `cp x.db` 会丢 `-wal` 里的数据。备份用 `db.backup()`。
3. **`GML_DATA_DIR` 不设就跑测试**：会写到仓库 `data/`，把演示库搞脏。所有 `test-*.mjs` 都自带"非 /tmp 就 exit 2"的闸门。

## 四、架构分层：四层，从上到下依赖

```
┌──────────────────────────────────────────────────────────────┐
│ 第 3 层  财务与报表   凭证 / 试算平衡 / 三大报表 / 期末结转        │
├──────────────────────────────────────────────────────────────┤
│ 第 2 层  业务链       采购 · 销售 · 库存 · 门店 · 经销商 · 生产    │
├──────────────────────────────────────────────────────────────┤
│ 第 1 层  单据内核     doc_types / doc_states / doc_actions        │
│                       单据状态机 + 流转留痕（doc_events）          │
├──────────────────────────────────────────────────────────────┤
│ 第 0 层  配置底座     SETTING_RULES + settings + 变更留痕          │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向只能向下**：
- 业务代码可以读配置、可以推进单据状态；
- 单据内核**不知道**任何具体业务（它只认识"类型/状态/动作"）；
- 配置层不依赖任何上层。

违反这条的典型症状：在路由里写死一个状态判断，导致内核改了状态机而路由不跟。

## 五、一次请求怎么走（后端）

以「销售订单发货」为例：

```
POST /api/sales/orders/123/deliver
  │
  ├─ server/index.js         中间件：JSON / 静态 / 日志
  ├─ middleware/auth.js      requireAuth（验 JWT）→ requireRole('warehouse', ...)
  ├─ db/index.js             AsyncLocalStorage 取到当前行业 → getDb() 返回对应库连接
  ├─ routes/sales.js         参数校验 + 组装 actor → 调 lib
  ├─ lib/stock.js            pickBatches（FEFO 拣批）+ applyStockOut（扣库存、写流水）
  ├─ lib/docflow.js          advanceStatus（推进 SO 状态 + 写 doc_events）
  └─ lib/http.js             ok(res, data) 统一返回 { code, data, message }
```

**三条硬规则**

1. **路由不写业务**：只做"鉴权 + 取参 + 调 lib + 返回"。
2. **状态只走 `advanceStatus`**：任何地方都不许 `UPDATE sales_orders SET status=...`（会漏留痕、绕过状态机）。
3. **派生字段由服务层算**：`invoice_status` / `shipped_qty` / `received_qty` 这些不许手写。

## 六、数据库

### 6.1 三库与切库

```js
// server/db/index.js
export const INDUSTRIES = {
  cosmetic: { code:'cosmetic', label:'美妆连锁版', visible:true,  db:'gml_cosmetic.db' },
  food:     { code:'food',     label:'连锁餐饮版', visible:true,  db:'gml_food.db' },
  apparel:  { code:'apparel',  label:'服装版（开发中）', visible:false, db:'gml_apparel.db' }
}
```

行业来自登录签发的 JWT；请求进来后由 `AsyncLocalStorage` 带到 `getDb()`。
**业务代码里永远不要自己拼库路径**，一律 `const db = getDb()`。

### 6.2 迁移

- 文件：`server/db/migrations/NNN_名称.cjs`
- 导出：`module.exports = { name, up(db), verify(db) }`
- 规则：**只往后加，不改历史文件**；`verify()` 要在结构脱节时返回 `false`（会自动重跑 `up`）
- 新增表/列后，`verify-seed` 与 `seed.js` 的 `TABLES` 也要跟着登记（否则重建不可复现）

```js
// 最小模板
module.exports.name = '补一列 xxx'
module.exports.up = (db) => {
  if (!hasColumn(db, 'sales_orders', 'xxx')) db.exec("ALTER TABLE sales_orders ADD COLUMN xxx TEXT")
}
module.exports.verify = (db) => hasColumn(db, 'sales_orders', 'xxx')
```

### 6.3 表结构约定

| 约定 | 说明 |
|---|---|
| 主键 | `id INTEGER PRIMARY KEY AUTOINCREMENT` |
| 单号 | `doc_no`，由 `lib/docno.js` 的 `nextDocNo` 生成，**不要自己拼** |
| 时间 | `created_at` 用 `datetime('now','localtime')`；业务日期用 `lib/dates.js` |
| 金额 | 一律 `round2`（两位小数） |
| 数量 | 一律 `round4`（四位小数），与金额**不共用** |
| 留痕 | 每个状态变更写 `doc_events`（`doc_type / doc_id / action / from_state / to_state / actor`） |

## 七、单据内核（最重要的一层）

### 7.1 三张表定义一切

| 表 | 内容 | 例子 |
|---|---|---|
| `doc_types` | 单据类型 | `SO` 销售订单、`PO` 采购订单、`GR` 收货单…共 40 种 |
| `doc_states` | 每个类型有哪些状态 | `SO`: draft / confirmed / shipped / completed / cancelled |
| `doc_actions` | 状态之间的边 | `SO.confirm: draft → confirmed`，`is_danger=1` 表示高危 |

### 7.2 推进状态

```js
import { advanceStatus } from '../lib/docflow.js'

advanceStatus(db, req, {
  docType: 'SO',
  id,
  action: 'confirm',
  set: { /* 同事务要写的其他字段 */ },
  remark: '销售确认'
})
```

它做四件事：**查边 → 判权限 → 改状态 → 写留痕**。
非法来源态抛 `DocFlowError` → HTTP 409 `TRANSITION_NOT_ALLOWED`。

### 7.3 为什么路由里不许写状态白名单

```js
// ❌ 错：路由里再判一遍状态
if (order.status !== 'confirmed') return fail(res, '只有已确认的订单可以发货')

// ✅ 对：交给内核
const out = advanceStatus(db, req, { docType: 'SO', id, action: 'ship' })
```

第二份判据迟早与内核分叉 —— 内核加了新状态、路由没跟，就出现"界面能点、后端拒绝"。

### 7.4 高危边

`is_danger=1` 的边（作废已过账凭证、强平账等）**AI 一律不能执行**，必须人工在界面确认。
MCP 侧直接抛 `EDGE_REQUIRES_HUMAN`。

## 八、业务链：钱和货怎么串起来

| 域 | 主 lib | 关键链路 |
|---|---|---|
| 采购 | `lib/purchase.js` | 请购 → 订单 → 收货（部分）→ 质检 → 发票 → 结算 → 付款 → 退货 |
| 销售 | `routes/sales.js` + `lib/invoice.js` + `lib/ar.js` | 订单 → 发货（部分）→ 开票（部分）→ 应收 → 收款核销（部分） |
| 库存 | `lib/stock.js` | `applyStockIn` / `applyStockOut` / `pickBatches`（FEFO）/ `reserveStock` |
| 门店 | `lib/pos2.js` | 开班 → 收银 → 交班报数 → 核款 → 缴款 → 日结上传（生成销售单 + 出库） |
| 经销商 | `lib/dealer-statement.js` `lib/rebate.js` | 订货 → 对账单 → 结清；返利计提 → 确认 → 核销（冲应收） |
| 财务 | `lib/accounting.js` | 由业务单生成凭证（借贷必平）→ 试算平衡 → 报表 |
| 质检 | `lib/qc.js` / `lib/qc2.js` | 报检 → 检验（合格/让步/判退）→ 判退自动生成退货单并出库 |

**库存只在 `lib/stock.js` 里动**。绕过它直接 `UPDATE inventory_stocks` 的结果是：
现存量对、流水没有、成本报表错，而且**不会报错**。

## 九、权限体系

### 9.1 三个维度

| 维度 | 存在哪 | 决定什么 |
|---|---|---|
| 角色 | `users.role` → `roles` | 大类的职责 |
| 权限点 | `role_permissions`（137 个点） | 接口层放不放行 |
| 数据范围 | `roles.data_scope` | 这个角色能看哪些组织的数据 |

### 9.2 中间件

```js
r.get('/orders', requireAuth, requirePerm('sales.order.view'), wrap(handler))
r.post('/orders/:id/ship', requireAuth, requireRole('warehouse','sales','admin'), wrap(handler))
```

- `requireAuth`：验 JWT，挂 `req.user`
- `requireRole(...roles)`：粗粒度角色门
- `requirePerm(code)`：细粒度权限点
- **两者可以叠加**；新接口默认加 `requirePerm`，不要只加角色门。

### 9.3 前端菜单

菜单的可见性由 `src/components/Layout.tsx` 的**角色族**决定：

```ts
const ROLE_GROUPS = {
  exec: ['boss'], supply: ['scm','purchase'], stock: ['scm','purchase','warehouse'],
  sell: ['scm','sales'], money: ['finance'], shop: ['store'], dealer: ['dealer'], viewer: ['viewer']
}
{ key:'purchase', label:'采购管理', roles: rolesOf('exec','supply','stock','money'), children:[...] }
```

- **菜单隐藏只是界面收敛，不是权限边界**（接口层另有判据）；
- 加角色只改 `ROLE_GROUPS` 一处；
- 行业差异用 `industries: ['cosmetic','apparel']`（与角色维度正交）。

## 十、配置底座（"拿不准就做成配置项"）

### 10.1 一个配置项的完整形态

```js
// server/lib/settings.js
purchase_return_offset: {
  group: 'supply', label: '采购退货抵减结算', type: 'bool', default: '0',
  is_danger: true, wired: true,
  impact: '打开后结算金额会扣减同期退货；不影响历史单据'
}
```

配套三件事缺一不可：

1. **默认值 = 上线前的实际行为**（不改变既有账）；
2. **唯一一处读取**（`readSetting(db, 'key')`），并接进判据；
3. **反例**证明"改配置 ⇒ 行为真的变"（否则只是登记了，没接线）。

### 10.2 写入必须留痕

```js
writeSetting(db, { key, value, actor, reason })   // 内部同事务写 setting_audit_log
```

`is_danger: true` 的项**必须填理由**，否则拒绝。

## 十一、MCP 层（AI 能做什么）

### 11.1 两类工具

| 类型 | 数量 | 说明 |
|---|---|---|
| 领域工具 | 36 | 采购建单 / 收货 / 库存出入库 / 调拨 / 盘点 / 销售作废… |
| **通用单据工具** | 4 | `doc.list_types` / `doc.query` / `doc.get` / `doc.transition` |

通用这 4 个**只认内核**，不认具体业务 —— 内核里新增一种单据，AI 立刻能读能推，**不用改 MCP 代码**。

### 11.2 六条安全边界

1. **Agent Token**：可吊销、限频、绑行业；
2. **实体范围**：组织/门店/经销商/仓库，越界**当作不存在**（不泄露"有但你看不到"）；
3. **边权限**：与界面同一份 `assertEdgePermitted`；
4. **高危边**：一律拒绝（`EDGE_REQUIRES_HUMAN`）；
5. **幂等键**：`(token_id, tool_name, key)`，同键异参 → 409；
6. **全量留痕**：每次调用都记。

### 11.3 加一个 MCP 工具

```js
// server/mcp/tools.js
{
  name: 'sales.xxx',
  level: 'write',            // read | write | danger
  title: '……',
  description: '……',
  inputSchema: { ... },
  handler({ db, args, ctx }) { ... }
}
```

然后跑 `node scripts/check-mcp-coverage.mjs` —— 它会断言"声明的工具真的注册且级别一致"。

## 十二、前端

### 12.1 一条页面的生命周期

```
App.tsx 路由  →  Layout 菜单  →  pages/*.tsx  →  DataPage（列表骨架）  →  api/client.ts
```

- **列表页 90% 用 `DataPage`**：传 `fields`（列 + 表单）和 `path`，增删改查/分页/导出全有了；
- **下拉选项从 `/api/meta/*` 取**（`hooks/opts.ts`），**页面里不写死枚举**；
- **所有请求走 `src/api/client.ts`**（统一带 token、拆 `{code,data}`、把业务错误转成 Error）。

### 12.2 加一个页面（四步，缺一不可）

1. `src/pages/<域>/<Page>.tsx` 新建文件（**文件头写「文件标识」块**）；
2. `src/App.tsx` 加 `<Route>`；
3. `src/components/Layout.tsx` 加菜单项（`roles: rolesOf(...)`）；
4. 若需要新接口：`server/routes/*` + `server/openapi.js` + `npm run gen:api`。

## 十三、测试与守卫（改完必须跑）

### 13.1 一条命令

```bash
GML_DATA_DIR=/tmp/reg node scripts/regress-all.mjs        # 默认 3 轮
ROUNDS=1 GML_DATA_DIR=/tmp/reg node scripts/regress-all.mjs
```

它按顺序跑：56 套 `test-*.mjs` × 3 行业 → `verify-*` → 10 道 `check-*` → `smoke-api` → `tsc` → `vite build`，
最后输出「通过 N / 失败 M」与断言累计。

### 13.2 十道静态守卫

| 守卫 | 守什么 |
|---|---|
| `check-api-contract` | 前端调用的接口都在 OpenAPI 里；类型文件与契约一致 |
| `check-contract-routes` | 契约里的路径后端真有（反向也查） |
| `check-route-order` | 字面段路由排在参数段之前（`/x/explain` 不被 `/x/:id` 吃掉） |
| `check-doc-events-edges` | 留痕里的边与内核 `doc_actions` 一致 |
| `check-inv-txn-dict` | 库存流水类型都在字典里 |
| `check-bizcode-shape` | 业务码格式统一 |
| `check-env-pinning` | 脚本自己钉 `GML_DATA_DIR`，不会误写仓库库 |
| `check-test-helper-shape` | 测试脚本的断言形状正确（防止 `ok(msg, cond)` 参数错位导致恒真） |
| `check-mcp-coverage` | 声明的 MCP 工具真的注册；无归属列的单据只限已知 7 个 |
| `check-file-header` | 381 个源文件都有「文件标识」块（棘轮 100%） |

### 13.3 反例纪律（这条比断言数更重要）

**"断言绿"不等于"功能对"**。凡是修缺陷，必须做一次**先红后绿**：

1. 在 `/tmp` 影子副本里把被测代码改坏（**不改仓库文件**）；
2. 跑测试 → 必须**红**，且失败项**可读**（不是崩栈）；
3. 还原（逐字节写回 + sha256 比对）→ 必须**绿**。

如果改坏了还是绿，说明这条断言没覆盖到，或者断言本身写错了对象。

## 十四、演示数据（seed vs demo-seed）

| 文件 | 负责 | 为什么分开 |
|---|---|---|
| `db/seed.js` | 主数据 + 全量业务单据 | 它的 `rnd()` 序列是**全库可复现的锚点** |
| `db/demo-seed.js` | 连续 22 天零售日报 + 部分流转 | 单独模块，**不动主序列**，插进去不会让整库数据漂移 |

演示数据的三条要求：

1. **可复现**：两次 `npm run reseed` 逐表 0 差异（随机只用 `rnd/R/RI/RF/PICK`，禁 `ORDER BY RANDOM()`）；
2. **中间态必须有**：部分发货 / 部分开票 / 部分收款 / 部分入库 / 待检，靠随机是造不出来的；
3. **幂等**：重复执行不叠加（用"本模块才会产生的日期/备注"当哨兵）。

## 十六、代码规范（不是风格问题，是防事故）

| 规则 | 为什么 |
|---|---|
| **每个源文件头有「文件标识」块** | 接手的人第一屏就知道这文件干什么、改它注意什么；`check-file-header` 守 100% |
| **判据只有一处** | 状态机在内核、配置在 `SETTING_RULES`、颜色在 `tailwind.config.js`、产品名在 `brand.ts` |
| **日期只用 `lib/dates.js`** | `toISOString().slice(0,10)` 在 UTC+8 会差一天 |
| **随机只用 seed 的 `rnd/R/RI/RF/PICK`** | 保证重建可复现 |
| **金额 `round2`、数量 `round4`** | 混用会出现 0.0001 的残差，对账时找不到 |
| **错误码要具体** | `throw bad('...', 'PO_OVER_RECEIVE', 409)`，前端与测试都靠它 |
| **catch 里按错误码分支必须 fail-closed** | `if (e?.code === X)` 会把未知异常静默降级 |
| **改被 `require` 的模块先 `node --check`** | 语法错在启动时才炸，演示现场最难看 |

## 十七、故障排查速查

| 现象 | 最可能的原因 | 怎么查 |
|---|---|---|
| 登录 401 / 一直跳登录页 | token 过期 / `JWT_SECRET` 变了 | 看 `localStorage.gml_token`，重新登录 |
| 接口 403 | 角色或权限点没配 | `SELECT * FROM role_permissions WHERE role_code=?`，注意 `byModule()` 是**批量授予**，grep 会假阴 |
| 接口 404 但路由写了 | 路由顺序被参数段吃掉 | `check-route-order` |
| 状态推进 409 `TRANSITION_NOT_ALLOWED` | 当前状态不在该动作的 `from_state` | 查 `doc_actions` |
| 页面数据是空的 | 数据范围（data_scope）过滤了 | 换 admin 看；或查 `resolveOrgScope` |
| 库存对不上 | 有人绕过 `lib/stock.js` 直接改表 | 查 `inventory_transactions` 有没有对应流水 |
| 重灌后测试红一片 | 用了裸 `cp` 复制库（丢 `-wal`） | 改用 `db.backup()` |
| 前端改了没生效 | 看的是旧 `dist/` | `npm run build` 或强刷 |

## 十八、已知边界与技术债（不藏）

1. **边权限跨域不一致**：`assertEdgePermitted` 只被 5 个通用入口调用，部分领域专属流转端点没调 ——
   补一半会让同一单据两套规则，**刻意保持现状**，等统一收口。
2. **7 种单据没有归属列**（AR / CA / OCS / OM / RCP / RFD / VOUCHER）⇒ 受限令牌看不到它们；
   已在「AI 与 MCP 控制台」打标并钉死清单。
3. **盘盈成本三条路分叉**：总部按结存均价 / MCP 传 `unitCost:null` 被吃成 0 / 门店 `lib/pos2.js` 仍是 0。
4. **契约 ②方向历史欠账**：前端调用→契约的检查不计入退出码（`--strict` 才红）。
5. **服装版只做"前端不展示、后台保留"**，业务差异（颜色×尺码矩阵）未补。
6. **钉钉/飞书**只做了映射与冲突检测，**真实租户 HTTP 未实现**（刻意不写假实现）。
7. **没有自动化 UI 测试**：断言管"有没有"不管"对不对"，关键页面仍需人眼看。
